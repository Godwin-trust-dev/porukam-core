## 0. Три «Claude» и где что происходит

Чтобы не путаться в процессе, держим в голове разделение:

- **Облачный ассистент (чат)** — здесь ведём документы, исследования, юрматериалы, концепцию. Прямого доступа к рабочему коду нет.
- **Claude Code в PyCharm** — CLI-плагин на твоей машине, внутри git-репозитория. Здесь пишется и тестируется код. Основной инструмент разработки.
- **GitHub Actions** — облачный CI. Проверяет то, что ушло в репозиторий: линтеры, типы, границы модулей, тесты, миграции.

Правило: **замысел и спеки — в документах проекта; реализация — в PyCharm через Claude Code; проверка — в CI.**

### Ключевые решения по раскладке

**Один Django-проект, приложения из §4 спецификации — буквально.** Не «модули», а Django apps со слоями внутри. Периферийные сервисы (`evidence_ingest`, `notification_dispatcher`, `audit_vault`) — это **отдельные процессы поверх того же кодбейза** (shared apps), а не отдельные проекты. Так их можно масштабировать независимо, не переписывая (как и требует §2.1).

**Audit Vault — исключение: своя БД.** Он подключается к отдельной PostgreSQL-базе и имеет односторонний API (запись + верификация цепочки). В монорепо код лежит рядом, но в рантайме это изолированный процесс со своим коннектом — иначе компрометация основного приложения даёт редактировать лог (ADR-038).

**Слои внутри каждого приложения — по §2.4 спецификации (паттерн HackSoftware):**

```
apps/contracts/
├── models.py        # модели, CHECK/EXCLUDE-ограничения БД, «якорные» методы без сайд-эффектов
├── services.py      # use cases: транзакции, инварианты FSM, публикация событий
├── selectors.py     # read-слой для API и дашбордов
├── events.py        # типы доменных событий контекста
├── api/             # DRF: сериализаторы, вьюсеты, permissions (тонкие)
├── providers/       # интерфейсы внешних провайдеров (где есть)
├── tasks.py         # Celery-задачи (тонкие обёртки над services)
├── fsm.py           # декларация переходов машины состояний
├── migrations/
└── tests/
    ├── test_services.py
    ├── test_fsm.py
    ├── test_selectors.py
    └── test_api.py
```

Тесты живут **рядом с кодом** приложения (`apps/<name>/tests/`), а не в одной общей папке. В `backend/tests/` — только e2e и кросс-контекстные сценарии.

## 2. Локальный запуск (Docker Compose)

Вся инфраструктура поднимается одной командой. Ты пишешь и отлаживаешь код на хост-машине (PyCharm видит интерпретатор), а зависимости — postgres/redis/minio — крутятся в контейнерах.

### Состав `infra/compose/docker-compose.local.yml`

| Сервис | Образ / роль | Порт | Заметка |
|---|---|---|---|
| `postgres` | postgres:16 | 5432 | основная БД |
| `postgres_audit` | postgres:16 | 5433 | отдельная БД Audit Vault (ADR-038) |
| `redis_cache` | redis:7 | 6379 | кеш, rate-limit, блокировки |
| `redis_broker` | redis:7 | 6380 | брокер Celery (разделены по §3.1) |
| `minio` | S3-совместимое | 9000/9001 | замена Yandex/VK Object Storage в dev; бакеты с версионированием под WORM |
| `mailhog` | перехват SMTP | 8025 | опциональный email-дубль уведомлений |
| `core` | Django (runserver/uvicorn) | 8000 | основное API |
| `evidence_ingest` | ASGI-инстанс | 8001 | приём доказательных пакетов |
| `audit_vault` | сервис append-only | 8002 | коннект к `postgres_audit` |
| `celery_worker` | Celery worker | — | очереди: payments / timers / notifications / registry / media |
| `celery_beat` | Celery beat | — | sweep дедлайнов (1 мин), сверки, НПД-проверки |
| `prometheus` | Prometheus | 9090 | скрейпит `core`/`celery_worker` через `host.docker.internal` — оба процессы хоста (docs/tasks/fundament-2.md ЭФ.6) |
| `alertmanager` | Alertmanager | 9093 | алёрты из `infra/compose/monitoring/alert_rules.yml`; email через `mailhog`, webhook — заглушка |
| `grafana` | Grafana | 3000 | анонимный доступ в dev; борд `infra/compose/monitoring/grafana/dashboards/porukam-overview.json` |

Метрики Celery worker'а — отдельный порт `:9808` (не порт compose-сервиса, worker всё ещё
процесс хоста): `common/celery_metrics.py` поднимает его сам при старте (`celery.signals.
worker_init`), никаких дополнительных флагов запуска не требуется.

Внешние провайдеры (ЕСИА, ЕГРЮЛ, платёжки, ФНС НПД, TSA) в dev — **фейки/песочницы**: реализации интерфейсов из §9.1, отдающие детерминированные ответы. Это же основа контрактных тестов (§3).

### Как это выглядит в PyCharm

Запуск двумя способами, оба удобны:

1. **Инфраструктура в Compose, приложение из PyCharm.** Поднимаешь `docker compose up postgres postgres_audit redis_cache redis_broker minio`, а `core`, `celery_worker`, `evidence_ingest` запускаешь как Run/Debug конфигурации PyCharm — тогда работают брейкпоинты прямо в IDE. Это основной режим для отладки.
2. **Всё в Compose.** `docker compose up` целиком — для проверки «как в проде» и e2e.

Заведи в PyCharm готовые Run-конфигурации (они версионируются в `.idea/runConfigurations/` и их можно закоммитить):

- **core** — `manage.py runserver 0.0.0.0:8000` с `DJANGO_SETTINGS_MODULE=config.settings.local`
- **celery worker** — `celery -A config worker -Q payments,timers,notifications,registry,media -l info`
- **celery beat** — `celery -A config beat -l info`
- **evidence-ingest** — `uvicorn services.evidence_ingest.asgi:app --port 8001`
- **pytest (all)** и **pytest (current file)** — конфигурации pytest
- **migrate** и **makemigrations** — django-конфигурации

### Быстрый старт (Makefile в `backend/`)

Обёртки, чтобы не помнить длинные команды (и чтобы Claude Code их звал):

```
make up        # поднять инфраструктуру в compose
make migrate   # применить миграции (обе БД)
make seed      # наполнить dev-справочники (catalog, jurisdictions РФ)
make run       # core + celery локально
make test      # весь pytest
make lint      # ruff + mypy + import-linter
make fmt       # ruff format
make openapi   # сгенерировать docs/openapi/schema.yml
```

## 3. Тестирование

Стратегия прямо из §11 НФТ спецификации. Инструмент — **pytest + pytest-django**; фабрики — **factory_boy**; property-based — **Hypothesis**.

### Слои тестов (снизу вверх)

**1. Юнит-тесты сервис-слоя — ядро покрытия.** Каждый переход FSM и каждый запрет проверяются явно. Это обязательное требование спеки, а не пожелание:

- машина согласования (`draft → under_review → pending_signature → awaiting_signatures → signed`) и все откаты (правка после `pending_signature` возвращает в `under_review` и аннулирует подписи);
- машина этапа (`pending → in_progress ⇄ suspended → under_acceptance → accepted/disputed → paid`);
- `compute_segment()` — **покрытие каждого правила §6.6** и запрета `excluded` (создание `excluded`-типа → `403`);
- транзакционность подписания: `signed` + снепшоты полномочий + начисление/оплата `contract_fee` — в одной транзакции; провал платежа комиссии не даёт договору вступить в силу.

**2. Property-based (Hypothesis)** — там, где спека прямо это требует:

- **деньги**: `Money` не складывает разные валюты, округление, отсутствие валюты по умолчанию;
- **дерево этапов**: сумма листьев = сумма договора при любой структуре; запрет `amount` у ветки; глубина ≤ 6;
- **маржинальная шкала комиссии**: монотонность (договор на рубль дороже никогда не платит меньше), отсутствие скачков на границах диапазонов, корректность Σ по диапазонам.

**3. Контрактные тесты провайдеров.** Каждый интерфейс из §9.1 (`IdentityVerificationProvider`, `PaymentProvider`, `EntityRegistryProvider`, `NpdComplianceProvider`, `TimestampAuthority`, …) имеет:

- фейковую реализацию для локали и e2e;
- **записанные кассеты** (VCR.py / responses) реальных ответов песочниц — чтобы поймать расхождение схемы, когда реальный провайдер изменится;
- тест идемпотентности вебхуков (`UNIQUE (provider, provider_operation_id)`).

**4. Тесты БД-инвариантов.** CHECK/EXCLUDE-ограничения — часть модели, значит их надо проверять на живой БД: пересечение эпох владения (`EXCLUDE USING gist`), «ровно один customer и один contractor», `source=customer OR unit_price>0` у материала, уникальность подписи на версию. Гоняются на реальном PostgreSQL 16 (не sqlite — иначе EXCLUDE не проверится).

**5. e2e основных путей** — обязательный критерий готовности Р1: полный прогон «договор → этапы → сдача → спор → скидка-допник → оплата → гарантия → экспорт пакета» **для двух сегментов**: `free_c2c` (комиссии нет) и `paid_business` (комиссия по шкале). Гоняются через API поверх реального стека (`docker compose up` целиком).

### Гейты покрытия

Не «общий процент», а точечные обязательства (через маркеры/проверку в CI):

- `apps/*/fsm.py` и `services.py` с переходами — покрытие переходов **100%** (каждый переход и каждый запрет);
- `compute_segment` и `compute_contract_fee` — 100% ветвей;
- остальное — разумный порог (напр. 85%), чтобы не превращать в формальность.

### Скорость (важно для соло + Claude Code)

Claude Code гоняет тесты сам и чинит по результатам — чем быстрее петля, тем лучше. Поэтому:

- `pytest -n auto` (pytest-xdist) — параллельно;
- `--reuse-db` — не пересоздавать тестовую БД каждый раз;
- быстрые юнит-тесты сервисов отделены маркером от медленных БД/e2e (`pytest -m "not e2e"` в обычной петле, полный прогон — в CI).

## 4. Git-флоу и GitHub Actions

### Соло-флоу: trunk-based, короткие ветки

Для соло + Claude Code не нужен GitFlow с release/develop — это оверхед. Правило:

- `main` всегда зелёный и деплоится;
- каждая задача — короткая ветка `feat/contracts-signing`, `fix/segment-calc`, живёт часы-день, не неделю;
- merge в `main` только через PR (даже соло — чтобы прогонялся CI и оставался diff-след);
- **Conventional Commits** (`feat:`, `fix:`, `test:`, `refactor:`) — Claude Code хорошо их генерирует, а тебе это даёт авто-changelog;
- ADR-журнал продолжается в `docs/adr/` — каждое новое архитектурное решение отдельным файлом в том же PR, что и код.

Ветка = единица работы, которую отдаёшь Claude Code: «сделай приложение `billing` с маржинальной шкалой» → ветка → PR → зелёный CI → merge.

### GitHub Actions: пайплайн из §3.1 спецификации

Один workflow `ci.yml`, срабатывает на PR и push в `main`. Джобы (параллельно, где можно):

```
lint:
  - ruff check + ruff format --check
  - mypy --strict (на services.py и models.py — как требует спека)
  - import-linter  # КОНТРАКТ ГРАНИЦ МОДУЛЕЙ (см. ниже)

migrations-gate:
  - manage.py makemigrations --check --dry-run   # нет незакоммиченных миграций
  - применить миграции на чистую БД (обе: основная + audit)

test:
  - поднять postgres:16 + redis (services в GH Actions)
  - pytest -n auto --reuse-db (юнит + БД-инварианты + property-based)
  - отдельный шаг: e2e (free_c2c + paid_business)
  - проверка гейтов покрытия FSM/compute_segment

security:
  - pip-audit          # уязвимости зависимостей
  - секрет-скан (gitleaks/trufflehog)

openapi:
  - manage.py spectacular --file docs/openapi/schema.yml
  - проверить, что схема не разошлась с коммитом (--check)

frontend:   # только если менялись web/ или mobile/ (paths-filter)
  - линт/тесты соответствующего клиента
```

**import-linter — это тот самый гейт границ модулей из §2.3.** Контракт слоёв в `pyproject.toml`:

```
[tool.importlinter]
root_package = "apps"

# catalog и jurisdictions — нижний слой, ни от кого не зависят
# contracts НЕ импортирует payments/disputes (они подписаны на его события)
# social зависит только от accounts
# dashboards — только selectors поверх остальных
```

Именно эта проверка не даёт монолиту деградировать в «большой ком грязи»: если Claude Code (или ты) случайно импортирует чужую модель в обход сервисного фасада — CI краснеет.

### Деплой в РФ-облако

На старте — образы собираются в CI и пушатся в реестр РФ-облака (Yandex/VK), деплой — вручную или простым workflow на self-hosted раннере/через SSH. Kubernetes не нужен, пока не появится нагрузка (§3.2: «Docker Compose на старте, K8s при росте»). Отдельные деплой-юниты закладываем сразу: `core`, `evidence-ingest`, `audit-vault`, `celery-worker/beat` — чтобы потом масштабировать раздельно без переписывания.

### 4.1. Санкционная устойчивость CI — не «план Б», а конструктив с первого дня

> **Пересмотр 30.10.2026 (ADR-197, ADR-198; внутренние ADR, не публикуются).** Раздел писался
> под схему «раннер и реестр в том же РФ-облаке, где прод». С переездом прода на зарубежный
> хостинг эта посылка не верна: образ и так идёт через публичный интернет. Что ИЗМЕНИЛОСЬ:
> реестр образов переехал в `ghcr.io` (организация проекта); служебная ВМ с раннером вынесена
> от прежнего облачного провайдера на отдельный VPS, метки раннера те же. Что ОСТАЛОСЬ в силе:
> прод никогда не тянет образы из чужого реестра (п. 2 — меняется только адрес нашего),
> lock-файлы обязательны (п. 3), экшены пинятся (п. 4), план эскалации на Gitea/Forgejo (п. 5)
> остаётся планом. **П. 1 отменён:** раннер больше не в РФ-облаке, причина не санкционная, а
> эксплуатационная (упавшая ВМ блокирует всю выкатку). **П. 3 и п. 4 — «план с триггером»:**
> кеши зависимостей (devpi, Verdaccio) были подняты, но ни к одной сборке не подключены
> (в репозитории нет ни `PIP_INDEX_URL`, ни `index-url`, ни `.npmrc`; Dockerfile тянет `uv`
> и зависимости прямо с pypi.org, `npm ci` идёт из публичного реестра). Lock-файлы и
> пиннинг экшенов остаются обязательными. Gitea-зеркало теряет смысл вместе с переездом
> раннера; включать кеши имеет смысл только вместе с правкой Dockerfile.


Статус на лето 2026 (проверено по открытым источникам): это уже не гипотетический риск. С мая 2026 доступ к GitHub из РФ деградирует через ТСПУ (доля неудачных соединений выросла с ~4% до ~16%, тяжёлые clone/push отваливаются по таймауту); с 1 июня pypi.org недоступен с российских IP (TLS/SNI-фильтрация, побочный эффект блокировок CDN Fastly); в марте 2026 ужесточились ограничения на публичный Docker Hub; git.kernel.org недоступен с февраля. РКН предлагает «ГосVPN для разработчиков» — на него закладываться нельзя (единая точка отказа + риск гео-блокировки государственных IP самими зарубежными платформами).

Вывод: **изоляция от внешних реестров закладывается в архитектуру CI с первого коммита**, а не добавляется при первом инциденте. Схема из пяти правил:

**1. Раннер — self-hosted в РФ-облаке с первого дня.** ВМ в том же Yandex/VK Cloud, где будет прод. Это решает сразу три проблемы: оплату Actions-минут из РФ (self-hosted раннеры на приватных репозиториях бесплатны), сетевой путь деплоя (раннер внутри РФ-контура пушит в РФ-реестр и деплоит по внутренней сети — никаких вопросов «дойдёт ли внешний раннер до РФ-облака»), и доступ к зависимостям (раннер тянет их через РФ-кеши, см. п. 3). Нюанс: self-hosted раннер сам ходит на github.com за задачами (long-poll), поэтому деградация GitHub его тоже касается — но эти запросы лёгкие и retry-устойчивые, в отличие от тяжёлых clone в hosted-раннерах.

**2. Никакого `FROM docker.io` в Dockerfile'ах.** Все базовые образы (python:3.12-slim, postgres:16, redis:7, nginx…) один раз затягиваются в собственный реестр РФ-облака (Yandex Container Registry / VK Cloud Registry) и пинятся по digest; Dockerfile'ы ссылаются только на свой реестр. Синхронизация базовых образов — отдельная ручная/полуавтоматическая операция через pull-through-кеш или зеркала (dockerhub.timeweb.cloud, Yandex Mirror, huecker.io). Кешированные слои переживают блокировки с вероятностью 90–99%; некешированное — лотерея. Прод **никогда** не тянет образы из внешних реестров.

**3. Кеш зависимостей в РФ-контуре.** Python: lock-файл (uv/pip-tools) обязателен + прокси-кеш devpi или Nexus на той же ВМ, что раннер (fallback-зеркало — pypi.depkit.ru и аналоги); собранные wheels для прод-образа хранятся в своём реестре как слой. npm (web/): Verdaccio-прокси там же. Логика одна: внешний индекс нужен только чтобы **однажды** затянуть пакет в кеш; сборка ходит в кеш.

**4. Git-зеркало + вендоринг экшенов.** Репозиторий зеркалится в РФ (pull-mirror на своём Gitea/Forgejo на той же ВМ, либо GitFlic/GitVerse) — не ради бэкапа (git распределённый, полная история и так на твоей машине), а ради непрерывности CI при отказе GitHub. Сторонние GitHub Actions пинить по SHA и **вендорить критичные в репозиторий** (`uses: ./.github/actions/...`) — это защищает от недоступности marketplace и делает миграцию почти бесплатной, потому что…

**5. …план эскалации — Gitea/Forgejo Actions, совместимые с синтаксисом GitHub Actions.** Если деградация GitHub сделает PR/CI неработоспособными, origin переключается на своё Gitea/Forgejo в РФ-облаке, а workflow-файлы переезжают почти без правок (Gitea Actions исполняет тот же YAML-формат). Именно поэтому workflows держим простыми и без экзотических marketplace-зависимостей. Триггер перехода — не «однажды», а измеримый: Uptime Kuma на РФ-ВМ мониторит github.com, pypi.org и зеркала; если доля неудачных CI-прогонов по сетевым причинам превышает порог (напр. 20% за неделю) — переключаемся.

Секреты деплоя — канонически в Yandex Lockbox/Vault в РФ-контуре; GitHub Secrets — лишь точка инъекции, а не единственное хранилище.

Стоимость всей обвязки — одна небольшая ВМ в РФ-облаке (раннер + devpi + Verdaccio + Gitea-зеркало + Uptime Kuma умещаются на одной машине на старте) плюс реестр образов, который и так нужен для прода.

## 5. Порядок первых шагов (bootstrap)

Порядок разработки внутри Р1 — по зависимостям приложений из §13 спецификации. Это же порядок, в котором ты будешь ставить задачи Claude Code:

1. **Каркас**: `config/`, settings-профили, Docker Compose, `common/` (Money, FSM-механизм, envelope-crypto **сразу** — crypto-shredding ретроспективно не добавляется, ADR-035), CI-скелет, import-linter.
2. **Нижний слой**: `jurisdictions`, `catalog` — справочники (формы, налоговые режимы, **каталог типов договоров** для `compute_segment`). Наполнение РФ — в `make seed`.
3. **Субъекты**: `accounts` (User + TrustID), `identity`, `social` (@handle, контакты), `entities` (claim), `authority` (SigningAuthority).
4. **Ядро договора**: `contracts` (+ FSM согласования, `compute_segment`), `milestones` (дерево этапов).
5. **Деньги**: `payments` (0% комиссии платформы), `billing` (маржинальная шкала комиссии за заключение).
6. **Доказательства**: `evidence` + сервис `evidence_ingest` + `DeviceKey`.
7. **Споры и гарантия**: `disputes`, `warranty`.
8. **Надстройки**: `reputation`, `profiles`, `links`, `dashboards`, `marketplace`.
9. **Сквозное**: `notifications` + `deadlines` (sweep), `compliance` (НПД, счётчик самозанятости), `audit` (Audit Vault, outbox).

Интеграционные треки с длинным внешним lead time (доступ к ЕСИА, договоры с платёжными партнёрами, API ФНС) — стартуют **параллельно с первого дня**, потому что зависят не от кода, а от внешних сроков.

Каждый шаг = ветка + PR + зелёный CI. К концу каждого — работающий вертикальный срез, а не «полработы во всех приложениях сразу».

## 6. Рабочая петля с Claude Code в PyCharm

### CLAUDE.md — главный файл настройки

Claude Code читает `CLAUDE.md` в корне репозитория как постоянный контекст. Сюда выносим правила, которые он обязан соблюдать всегда — тогда не придётся повторять их в каждом запросе. Скелет под этот проект:

```markdown
# Trust Platform — правила для Claude Code

## Архитектура
- Модульный монолит на Django. Приложения — bounded contexts из тех-спецификации §4.
- Слои: api/ (тонкие) → services.py (use cases, транзакции, события) →
  selectors.py (чтение) → models.py. Бизнес-логику НЕ писать в сериализаторах и вьюхах.
- Приложения общаются через services.py-фасады и доменные события (outbox), НЕ через
  прямой импорт чужих моделей. Django-сигналы для бизнес-логики ЗАПРЕЩЕНЫ.
- Границы проверяет import-linter. Перед коммитом гонять `make lint`.

## Обязательные инварианты (см. доменную модель)
- Подпись — всегда на integrity_hash замороженной версии.
- Подписанный договор неизменяем; изменения — только через Amendment.
- Деньги — всегда пара (amount, currency); валюты по умолчанию нет.
- compute_segment покрывает §6.6; создать excluded-тип нельзя.
- Дедлайны — строки в БД + sweep, НЕ отложенные Celery-задачи.

## Тесты
- Каждый переход FSM и каждый запрет — отдельным тестом.
- Деньги/дерево этапов/маржинальную шкалу — Hypothesis.
- Перед PR: `make test` зелёный, `make lint` чистый.

## Стиль
- Conventional Commits. Русские комментарии там, где термины домена.
- Термины домена — из доменной модели (Contract, Milestone, SigningAuthority…).
- Терминологическая красная линия: никакой лексики трудовых отношений в API
  (projects/orders/contractors — можно; лексика трудовых отношений — нельзя).
```

Дополнительно можно класть `CLAUDE.md` внутрь отдельных приложений (напр. `apps/payments/CLAUDE.md`) с локальными правилами — Claude Code подхватывает вложенные.

### Что делегировать Claude Code, а что держать на себе

- **Делегировать смело**: реализация приложения по готовой спеке модели данных, написание тестов на FSM, миграции, сериализаторы/вьюсеты, фейки провайдеров, рутинный рефакторинг, генерация фабрик.
- **Держать на себе / ревьюить внимательно**: изменения архитектурных инвариантов (это ADR, а не код), формулировки, влияющие на юридическую позицию (снепшоты, юрканал уведомлений), маржинальная шкала и налоговые правила, всё вокруг crypto-shredding и Audit Vault.

Claude Code показывает правки нативными diff-виджетами PyCharm — принимай/отклоняй по частям, не глотай целиком.

### Выбор модели (из прошлого разговора)

- **Sonnet** — база для повседневной реализации приложений и тестов.
- **Opus** (или `opusplan`: план на Opus, код на Sonnet) — проектирование модуля договоров/этапов, распутывание сложных инвариантов FSM, разбор багов в транзакционной логике подписания.
- **Haiku** — сабагентам на рутину (форматирование, простые правки), чтобы не жечь дорогие токены.

### Типовой цикл одной задачи

1. В документах проекта уже есть спека модуля (модель данных, FSM, API — всё в тех-спецификации).
2. В PyCharm: новая ветка → Claude Code: «реализуй приложение `billing` по §5.2.6 и §6.6: модель `ContractFee`/`FeeScheduleTier`, `compute_contract_fee` по маржинальной шкале, тесты Hypothesis на монотонность и границы».
3. Claude Code пишет код + тесты, гоняет `make test` и `make lint`, чинит по результатам.
4. Ты ревьюишь diff, правишь спорное.
5. PR → зелёный CI → merge. При новом архитектурном решении — файл ADR в том же PR.

## 7. Расхождения между документами — к синхронизации до старта кода

Выявлено при сверке спецификации 2.0, концепции v9.0, доменной модели v9 и этого документа (23.07.2026). Правило приоритета спеки действует: ADR-журнал > спецификация > доменная модель (псевдокод). Но расхождения стоит закрыть явно, иначе они всплывут в коде.

> **Статус на 23.07.2026: Р-1…Р-6 — ИСПРАВЛЕНЫ.** Доменная модель обновлена в проекте (Р-1: семантика `has_business_status`; Р-2: `PLATFORM_SPLIT` упразднён; Р-3: комментарий про Sphere-справочник; Р-4: `PROCESSING`/`FAILED`; Р-5: класс `Amendment`). Спецификация переиздана как **2.0.1**: пример §8.4 исправлен (1 020 ₽), [Т-решения] зафиксированы в §14 пп. 15–16. Открытым остаётся только **Р-7** — пометка «Заменено» в ADR-009 при следующей редакции ADR-журнала. Описания ниже сохранены как обоснование правок.

**Р-1 (важно, деньги). `User.has_business_status()` в доменной модели семантически неверен.** Метод возвращает `any(self.available_entities())`, а `available_entities()` — это юрлица, где пользователь **активный Representative**. То есть наёмный менеджер чужого ООО получил бы «бизнес-статус», и его личные возмездные услуги ушли бы в `paid_business` вместо `free_c2c` — сломано правило §6.6 п. 2 («плавный вход»). Правильная семантика (как в спеке: хранимый `has_business_status bool`): статус есть, только если у человека **собственный** бизнес-профиль (СМЗ/ИП, где субъект — он сам). Исправить в доменной модели и покрыть тестом отдельно: «представитель чужого юрлица + личная услуга → free_c2c».

**Р-2 (важно, enum'ы). `PLATFORM_SPLIT` есть в концепции (§15.1, шесть способов расчёта) и доменной модели, но отсутствует в CHECK спеки** (§5.2.4: `direct_platform|hold|prepayment|cash|external` — пять). По смыслу split слился с `direct_platform` (СБП-сплит и есть рельс прямого платежа). Нужно [Т-решение]: либо официально упразднить `PLATFORM_SPLIT` в доменной модели и концепции, либо вернуть в CHECK. Иначе генерация кода по доменной модели даст enum на шесть значений против ограничения БД на пять.

**Р-3. `Sphere`: enum в доменной модели, таблица-справочник в спеке** (§5.2.5 прямо: «справочник, не enum»). Реализуем таблицей (спека права — сферы должны расти без миграций кода); enum в псевдокоде — упрощение. В `make seed` сферы уже учтены.

**Р-4. `PaymentStatus`: в спеке есть `processing` и `failed`, в доменной модели их нет.** Спека первична (ретраи и ошибки провайдера нужны). При реализации — состав статусов из §5.2.6.

**Р-5. Нейминг: `Amendment` (спека, API, термины §1.5) vs `AdditionalAgreement` (класс в доменной модели).** В коде — `Amendment`, единообразно с публичным API.

**Р-6 (косметика). Арифметика примера в §8.4 спеки:** договор 120 000 ₽ → комиссия 900 ₽ (0,75%). По шкале концепции (1% до 50 тыс + 0,8% следующие 50 тыс + 0,6% далее) выходит 500+400+120 = 1020 ₽; 900 ₽ соответствует договору на 100 000 ₽. Пример поправить при финализации шкалы (открытый вопрос №6 спеки).

**Р-7 (уже зафиксировано).** ADR-009 (один терминальный статус `NOT_CONCLUDED`) vs концепция v9/доменная модель (два: `rejected_by_counterparty`/`withdrawn_by_initiator`) — спека сама отметила в §14 п. 14; при следующей редакции ADR-журнала пометить часть ADR-009 «Заменено».

**Стек — проверен, валиден на 2026:** Python 3.12 + Django 5.2 LTS (поддержка до апреля 2028) + DRF 3.16 + drf-spectacular + PostgreSQL 16 (поддержка до ноября 2028) + Redis 7 + Celery 5 — взаимосовместимы; django-fsm-2 — живой поддерживаемый форк заброшенного django-fsm (либо свой лёгкий FSM, как допускает [Т-решение] спеки). Дерево Django-приложений в §1 сверено с §4 спецификации — совпадает полностью (25 приложений).

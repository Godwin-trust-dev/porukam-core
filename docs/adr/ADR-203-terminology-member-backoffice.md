# ADR-203. Терминология перед публикацией кода: роль member, приложение backoffice

**Статус:** принято
**Контекст:** публикация кода (публичное зеркало), аудит содержимого, терминологическая красная линия (CLAUDE.md)
**Номер:** 203 (зарезервирован владельцем).

## Контекст

Перед публикацией кода аудит нашёл два места, где в коде и публичном контракте остаётся лексика
трудовых отношений: роль представителя юрлица `employee` («Сотрудник») и имя приложения
`apps.staff`. Первое попадает в API (`role: "employee"`) и в БД, второе — в структуру репозитория
и import-linter.

## Решение

1. `Representative.Role.EMPLOYEE = "employee", "Сотрудник"` заменена на
   `MEMBER = "member", "Участник"`. Новая миграция `authority/0002` — `AlterField` choices плюс
   `RunPython` employee -> member (с обратной функцией). В CHECK-констрейнтах значение не зашито
   (0001 хранит только choices), пересоздавать их не нужно. Пресет прав роли не менялся.
2. Приложение `apps.staff` (пустая заготовка) переименовано в `apps.backoffice`: каталог,
   контракты import-linter, комментарии, упоминания в tech-spec, dev-setup. Смысл прежний —
   служебный доступ операторов платформы.
3. Поле Django `is_staff` и `/admin/` остаются: это системное имя фреймворка, а не доменная
   лексика.

## Совместимость

Внешних клиентов API, кроме нашего фронта, нет, а фронт значение роли не использует (проверено
поиском по `web/`, `packages/`, `l10n/`), поэтому значение меняется без переходного периода.

## Последствия

Линтер терминов проходит по публикуемым путям без исключений для этих двух имён. Отклонено:
оставить исключение в CONTRIBUTING — оно закрепляло бы запретное слово в публичном API.

# ADR-132. Отмена аванса запрещена

- Статус: принято
- Дата: 2026-08-26
- Ветка: `feat/payments-advance-cancel`
- Связано с: ADR-130 (платёжный контур Э5, FSM платежа, `UNIQUE (milestone,
  kind)`), tech-spec.md §6.3 (финансовое условие гейта), ADR-048 (допник —
  единственный путь изменить подписанные условия)

## Контекст

ADR-130 разрешил `cancel` из `pending` для любого платежа и зафиксировал схемой
`UNIQUE (milestone, kind)`: у листа ровно один аванс и одна постоплата. Вместе
эти два решения дают тупик для `kind=advance` (найдено агентами 25.08, волна 4):

- отменённый аванс остаётся единственной строкой `(milestone, advance)` —
  `ensure_contract_payments`/`create_payment` второй не создадут;
- гейт §6.3 считает `financial_condition_met` от ПОДТВЕРЖДЁННОГО аванса, а
  такого больше никогда не будет — этап навсегда `advance_not_confirmed`;
- фронт (`RealPaymentsPanel`) временно прячет «Отменить» у авансов, но API
  дыру не закрывал: любой клиент мог загнать договор в тупик одним вызовом.

Постоплаты это не касается: она выставляется по событию приёмки и после
отмены ничего не блокирует (лист уже `accepted`, платить можно по любому
рельсу договора; read-repair `ensure_contract_payments` её тоже не пересоздаёт —
отдельный хвост, здесь не решается).

## Решение

**`cancel` для `kind=advance` запрещён на уровне `services.cancel_payment`.**

- `AdvanceNotCancellableError` → `409 payment_advance_not_cancellable`. Свой
  код, не `invalid_payment_transition`: FSM-переход `pending → cancelled`
  формально существует, запрет — по ВИДУ платежа. Фронт различает «не тот
  статус» и «так нельзя вообще» без разбора текста.
- Проверка идёт ПОСЛЕ проверки стороны (`403 permission_denied` чужаку —
  прежде всего) и ДО FSM: чужак по коду не узнаёт вид платежа.
- Схема не меняется, миграций нет. FSM платежа (ADR-130 §3) не меняется:
  `cancel` остаётся переходом из `pending` для постоплаты.
- EN-текст — во встроенном реестре `common/api/error_texts.py`
  (`ERROR_TITLES_EN`), как у остальных кодов платёжного контура: в пакеты
  `l10n/packs` они осознанно не выносятся до платёжного партнёра (комментарий
  там же).

Ошибочный аванс (не тот способ расчёта, не та сумма) лечится не отменой, а
допником (ADR-048): смена `payment_method`/суммы листа — изменение подписанных
условий, у него уже есть подписной контур.

## Альтернатива: повторное выставление — отклонена

Снять `UNIQUE (milestone, kind)` (или заменить на partial unique по
не-отменённым) и пересоздавать аванс после отмены. Отклонено до появления
платёжного провайдера:

- отменённый + новый аванс на один лист — два денежных факта в ленте и в
  зеркале `Milestone.advance_*_at` (ADR-130 §1: отметки на этапе — проекция
  ОДНОГО платежа), зеркало пришлось бы учить «какой из авансов настоящий»;
- у провайдера отмена — это `void`/`refund` с собственной идемпотентностью и
  вебхуками (ADR-130 §8); проектировать «повторный аванс» без него значит
  переделывать при подключении;
- реальной потребности нет: аванс выставляется автоматически по подписи
  договора ровно с теми условиями, что подписаны — «ошибочным» он бывает только
  когда ошибочны условия, а это допник.

Когда появится провайдер и возвраты (Р2), вопрос возвращается вместе с
`refund` — тогда «аванс отозван» станет денежным фактом, а не удалением строки.

## Последствия

- `POST /payments/{id}/cancel` для аванса — `409 payment_advance_not_cancellable`;
  существующие сценарии отмены постоплаты не меняются.
- Фронт может убрать временное скрытие кнопки и показывать честную ошибку —
  либо оставить скрытие, теперь оно подкреплено бэком.
- Запрет — отдельными тестами (сервис и API), как каждый запрет FSM (CLAUDE.md).

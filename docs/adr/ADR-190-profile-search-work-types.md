# ADR-190. Виды работ («подсферы») в профиле и в каталожном поиске

**Статус:** принято (12.09, разбор `docs/backlog.md` «12.09 вечер — ПОДСФЕРЫ (виды работ) в
профиле и в поиске»)
**Номер:** 190 — сверено по репозиторию и всем ворктри (`ls docs/adr ~/porukam-worktrees/*/docs/adr
| grep -o 'ADR-[0-9]*' | sort -u | tail`, максимум занятый — 189).

## Постановка владельца (дословно, 12.09)

> давай ещё дадим возможность в профиле и поиске указывать подсферы

Затем, после первой (неверной) оценки агента, что нужен отдельный справочник/пикер:

> подожди… не надо так. пусть через поиск сферу находят. а ниже к сфере выдаётся перечень видов
> работ. как у нас в договоре. не усложняй

И отдельным решением по найденному по ходу разбора факту — 4 кода без человекочитаемой подписи:

> не показывать их как виды работ

## Контекст

«Вид работ» — НЕ отдельная модель. Это `ChecklistTemplateItem.category`: тот же справочник,
которым уже пользуется мастер договора (`GET /v1/catalog/work-types?sphere=`, ADR-091) — под
выбранной сферой разворачивается список её видов работ, ровно как просил владелец («как у нас в
договоре»). Разведка перед этой веткой (см. backlog) установила три факта:

1. Человекочитаемые подписи для 101 из 105 видов работ уже существуют и переведены на все 29
   локалей: ключи `catalog.categories.<сфера>.<код>` в языковых пакетах (ADR-097). Поиск сфер
   (`GET /v1/spheres?q=`, ADR-100) этими подписями уже пользуется
   (`_category_labels_by_sphere`/`_rank_work_types`, `apps/catalog/api/views.py`).
2. `WorkTypeSerializer`/`WorkTypeListView` при этом честно возвращали `name == code` — подписи из
   пакета не читали вовсе (докстринг сериализатора прямо это признавал).
3. Ровно 4 кода не подписаны НИ В ОДНОЙ из 29 локалей: `other.loan`, `other.rent_home`,
   `other.rent_items`, `other.sale_vehicle` — это не услуги, а строки чек-листов социальных
   архетипов (займ между людьми, наём жилья, аренда вещей, купля-продажа ТС — `docs/content/
   checklists/CL-other_GLOBAL.md` §2), которые парсер `import_checklists` (ADR-081) кладёт в сферу
   `other` вместе с обычными видами работ этой сферы (`other.other`, подпись «Прочее» — есть).

## Решения

### 1. `/v1/work-types` отдаёт подпись, а не код

`WorkTypeListView` теперь строит `name` из языкового пакета той же логикой фолбэка
`locale → en → ru`, что уже использует поиск сфер (`_localized_category_names`, новый общий
хелпер в `apps/catalog/api/views.py`, вынесенный из `_category_labels_by_sphere`/
`_rank_work_types`). Код БЕЗ подписи ни в одной из локалей — из выдачи **исключается**, а не
подставляет сырой код вместо имени: показывать `other.loan` под именем `loan` было бы честнее,
чем врать, но решение владельца прямее — эти 4 кода вообще не виды работ для конечного
пользователя, это социальные/имущественные договоры с собственными архетипами и собственной
формой (не чек-лист услуги). `WorkTypeSerializer`/докстринг обновлены — прежнее «name == code
честно, не притворный перевод» отменено этим ADR.

`apps.catalog.selectors.is_selectable_work_type(sphere_code, code)` — тот же критерий
(есть текущие пункты чек-листа И подпись хотя бы в ru или en — канонические языки, локаль зрителя
роли не играет) вынесен в read-слой отдельно от HTTP: он же валидирует выбор в профиле (см. ниже).
Использование именно ru/en, а не полного перебора 29 локалей — сознательное упрощение: владелец
проверил, что 4 «социальных» кода не подписаны нигде, поэтому ru∪en как индикатор «подписан хоть
где-то» эквивалентен полному перебору для всех существующих кодов на сегодня и не платит 27
лишними обращениями к `LocalePack` на каждую проверку.

### 2. Профиль: `Profile.work_type_codes` — тот же приём, что `sphere_codes` (ADR-122)

Новое JSON-поле `Profile.work_type_codes` (миграция `apps/profiles/migrations/
0010_work_type_codes.py`), по аналогии с `Profile.sphere_codes` (ADR-122), а НЕ по аналогии с
`WorkArea` (ADR-182): `WorkArea` — отдельная таблица со своим справочником геоиерархии и
BД-инвариантами масштаба (ссылка ровно на свой уровень), это оправдано, когда сама структура
данных многоуровневая. Вид работ такой структуры не имеет — это плоский список кодов
каталога, ИМЕННО как заявленные сферы. Заводить отдельную таблицу под плоский список ради
единообразия с ADR-182 было бы усложнением без причины (владелец прямым текстом: «не усложняй»).

**Формат элемента — составной код `<сфера>.<категория>`** (`renovation.turnkey`), НЕ голый код
категории. Причина: `category` не уникальна глобально — `other` есть почти в каждой сфере
(докстринг `apps.catalog.selectors._by_sphere`), поэтому голый `"other"` в списке профиля был бы
неоднозначен (вид работ какой сферы?). Составной код — тот же формат, которым уже пользуется
внутреннее ранжирование поиска типов работ (`_rank_work_types`, ключ `f"{sphere_code}.
{category_code}"`) — не новая конвенция, а переиспользование существующей.

**Лимит — `PROFILE_MAX_WORK_TYPES = 30`.** Обоснование: 3× лимита сфер (10) — по несколько видов
работ на каждую заявленную сферу, а не «один вид работ = одна сфера» и не «без ограничения».
Как и `PROFILE_MAX_SPHERES`, лимит — на уровне сервиса (`apps.profiles.services.
_normalize_work_type_codes`), не БД: продуктовое решение, которое может понадобиться поменять
без миграции.

**Инвариант согласованности со сферами — обязателен, решение НЕ альтернативное.** «Нельзя
выбрать вид работ из сферы, которую человек не заявил»: `_normalize_work_type_codes` проверяет
сферу каждого составного кода против ИТОГОВЫХ `sphere_codes` профиля (тех, что получаются ПОСЛЕ
применения этого же PATCH — если `sphere_codes` и `work_type_codes` переданы вместе, действует
НОВЫЙ список сфер, не старый). Нарушение — `ProfileWorkTypeSphereNotDeclaredError`, 422
`work_type_sphere_not_declared`. Обоснование выбора (не альтернативы): вид работ без своей сферы
в профиле бессмысленен для человека, читающего карточку («Плитка» без «Ремонт и строительство»
рядом — вырванный из контекста ярлык), и бессмысленен для поиска (см. §3) — фильтровать по виду
работ, у которого профиль не заявил родительскую сферу, значило бы либо молча учитывать
незаявленную сферу, либо давать несогласованную карточку.

**Сужение sphere_codes без указания work_type_codes в том же PATCH** — осиротевшие виды работ
(чья сфера выпала из нового списка) молча обрезаются `update_profile`, а не остаются в
противоречивом состоянии до следующего явного вызова. Если `work_type_codes` передан в ТОМ ЖЕ
PATCH, что сужает сферы — обрезка не участвует, работает обычная валидация (несогласованный код
422-ит явно, а не выпадает молча) — тихая подстройка допустима только когда клиент вообще не
трогал `work_type_codes` в этом вызове.

**Валидность кода** — `catalog_selectors.is_selectable_work_type` (см. §1): неизвестный код или
код без подписи (в т.ч. все 4 «социальных» кода `other.*`) — `ProfileWorkTypesInvalidError`, 422
`invalid_work_type`. Согласованно с тем, что `/work-types` их не показывает: то, что нельзя
увидеть в списке видов работ сферы, нельзя и записать в профиль.

**API** — тот же эндпоинт, что `sphere_codes`: `PATCH`/`GET /v1/profiles/{id}` (не отдельный
роут, не «соседний» — здесь честнее ровно повторить форму сфер, которая уже там живёт).
`ProfileSerializer` отдаёт `work_type_codes` публично (та же публичность, что `sphere_codes`
ADR-122 §2: владелец вносит виды работ именно чтобы его находили точнее).

**Crypto-shredding** (CLAUDE.md): `work_type_codes` очищается в `apps.profiles.services` тем же
путём, что `sphere_codes`, при удалении аккаунта пользователя.

**Не сделано этой веткой:** `work_type_codes` НЕ добавлен в карточку репутации
(`GET /reputation/profiles/{id}/card`, `apps/reputation/api/views.py`) — та карточка сегодня сама
читает `profile.sphere_codes` напрямую (кросс-модельное чтение, не через `apps.profiles`-фасад).
Расширять этот путь новым полем — отдельное решение, не заказанное постановкой («в профиле и в
поиске», не «в карточке репутации»).

### 3. Каталожный поиск: `work_type=` — независимый фильтр, И с остальными

Расширение ADR-184 (`GET /v1/dashboard/search`, ветка `catalog`): новый повторяемый параметр
`work_type=` — составные коды `<сфера>.<категория>`, тот же формат хранения, что в профиле, без
разбора на части при фильтрации (`apps.profiles.selectors.declared_work_type_q`, прямое сравнение
через JSONB `contains`, тот же приём, что `declared_sphere_q`). Между несколькими значениями —
ИЛИ (владелец не разделял разные виды работ одной потребности); с остальными фильтрами
(гео/`sphere`/опыт) — И. Присутствие параметра — тоже флаг «включить `catalog`»
(`_catalog_requested`), тот же keyset `(created_at, id)` без изменений в форме курсора.

**`sphere` и `work_type` — независимые условия, не связанные проверкой.** Передать оба
одновременно НЕ обязывает их ссылаться на одну и ту же сферу (`sphere=cleaning&work_type=
repair.tiling` — валидный, хоть и вряд ли осмысленный запрос, вернёт профили, удовлетворяющие
ОБОИМ условиям по отдельности). Как и с гео/сферой в ADR-184 — коды не проверяются на
существование, несуществующий/опечатанный код просто не находит совпадений, не ошибка.

**Только заявленное — НЕ подтверждённое сделкой, и это осознанный пробел, не недосмотр.** Сферы в
каталожном поиске матчатся ИЛИ по заявке в профиле, ИЛИ по факту завершённой сделки
(`contractor_sphere_deal_q`, ADR-184) — у видов работ второй путь отсутствует технически:
`apps.reputation.DealFact` несёт `sphere_codes` ДЕРЕВА ЭТАПОВ ЦЕЛИКОМ, но не категорию чек-листа
отдельного листа/этапа — такой гранулярности в модели репутации сегодня нет. Заводить новое поле
на `DealFact` (какой ценой — придётся тянуть категорию через `Milestone`/`ChecklistItem` до
`apps.reputation`, у которого сейчас нет такой зависимости) ради этой задачи — явное усложнение,
которое владелец просил не делать. Поэтому: **виды работ в поиске — только `Profile.
work_type_codes`**, фактическая подтверждённость сделкой для них не считается вовсе, до отдельного
решения, если/когда понадобится.

## Пределы задачи (сознательно не сделано)

- **Только `GET /v1/work-types` и `Profile.work_type_codes`/`GET /v1/dashboard/search`** — фронт
  (единый компонент «сфера → виды работ» и в профиле, и в поиске, повторяющий мастер договора) —
  отдельная ветка, не эта.
- **Подтверждение вида работ завершённой сделкой** — не реализовано (см. §3); при появлении
  такой потребности нужно сначала решить, откуда берётся категория на уровне `DealFact`/
  `Milestone`, это отдельная задача с собственным ADR.
- **Карточка репутации** (`GET /reputation/profiles/{id}/card`) не получает `work_type_codes` —
  см. §2 «Не сделано».
- **4 кода `other.*` без подписи** не получают подписей и не становятся видимыми ни в
  `/work-types`, ни в профиле, ни в поиске — прямое решение владельца, не временная заглушка.
- **Локализация новых кодов ошибок API** (`profile_work_types_limit`, `invalid_work_type`,
  `work_type_sphere_not_declared`) не добавлена в языковые пакеты — тот же (существующий, не
  новый) пробел, что у соседних кодов той же природы (`profile_spheres_limit`, `invalid_sphere`,
  `work_area_limit` и другие ADR-122/ADR-182): ни для одного из них нет записи ни в
  `common/api/error_texts.py`, ни в `l10n/packs/*.json` — заголовок всегда отдаётся на RU через
  фолбэк `common/api/exceptions.py`. Заводить локализацию только для новых трёх кодов, оставляя
  соседние непереведёнными, было бы несогласованной половинчатой правкой; если/когда владелец
  решит закрыть этот пробел — разумно закрывать его для всей группы кодов сразу, отдельной
  задачей.

## Последствия

- Новая read-функция без миграции: `apps.catalog.selectors.is_selectable_work_type`.
- `apps.catalog.selectors` получил новую (разрешённую) прямую зависимость на `apps.l10n.
  selectors` — оба нижний слой одного import-linter контракта.
- Новая колонка `profile.work_type_codes` (миграция 0010, только схема — данных не переносит,
  список пуст у существующих профилей до явного PATCH).
- `apps.profiles.selectors` получил `declared_work_type_q` — фасад для `apps.dashboards`, тот же
  приём, что `declared_sphere_q`.
- `apps.dashboards.api` — новый параметр `work_type=` у `GET /dashboard/search`; старое поведение
  (`q`/`zone`/`sphere`/гео/опыт) не изменилось.
- Фронт (не в этой ветке): переиспользовать `GET /v1/work-types?sphere=` для разворачивания
  списка под выбранной сферой — ОДИН компонент для профиля (`PATCH .../work_type_codes`) и поиска
  (`?work_type=`), как в мастере договора.

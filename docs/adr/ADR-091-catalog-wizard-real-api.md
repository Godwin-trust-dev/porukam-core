# ADR-091. `apps.catalog`: справочники мастера договора — сферы/виды работ/материалы/единицы/рекомендации чек-листа из существующих моделей, «вид работ» = категория импортированного чек-листа

**Статус:** принято
**Дата:** 2026-08-17
**Контекст этапа:** `docs/tasks/Задача_feat_catalog-real-api.md` — `apps.catalog` не имел
`api/urls.py` вообще (0 роутов, подтверждено
`docs/tasks/audit-web-api-contract-sweep-report.md` §2 «Каталог»), хотя модели
(`Sphere`/`MaterialCatalogItem`/`ChecklistTemplateItem`, ADR-081) — есть и
наполнены реальным контентом (17 сфер, `docs/content/checklists/CL-*_GLOBAL.md`).
Фронт мастера (`features/contractNew/api.ts`) бьёт в 5 несуществующих путей —
создание договора не стартует без первого шага (выбор сферы).

## Контекст: чего реально нет, а что есть

Проверка моделей и content-пайплайна (`apps.catalog.services.import_checklists`,
ADR-081) перед проектированием дала находку, изменившую план мастера «вид работ»:

- **`WorkType` как отдельная модель НЕ СУЩЕСТВУЕТ и никогда не упоминается**
  ни в `docs/tech-spec.md`, ни в `docs/domain-model.md`, ни в `docs/catalog-v2.md`
  — только в мок-типе фронта. Строить новую модель ради мастера значило бы
  плодить справочник без домена под ним.
- **Реальный аналог «вида работ» уже существует как импортированный контент:**
  `ChecklistTemplateItem.category` (ADR-081) — «категория» из markdown-таблицы
  каждого `CL-*_GLOBAL.md` (`docs/content/checklists/`, 17 файлов, все
  отревьюены и лежат в репо). Докстринг `import_checklists`/сам CL-файл
  (`CL-renovation_GLOBAL.md` §0) описывает категорию как ровно ту вещь, что
  фронтовый `WorkType` и делает: «сужает рекомендации чек-листа»
  (`is_default=True` пункты — «предзаполняется при выборе типа работ»,
  дословно). Строить новую модель НЕ нужно — нужно только прочитать то, что
  контент-пайплайн уже кладёт в `category`.
- **Загвоздка: `import_checklists` — не миграция, а деплой-шаг**
  (`.github/workflows/deploy-staging.yml`, ПОСЛЕ `manage.py migrate`,
  докстринг management-команды). На чистой тестовой БД `category` пусто у
  ВСЕХ строк (сид миграции 0006 — «минимальный набор для тестов Э4.3» — тоже
  не заполняет `category`). Тесты этой задачи явно вызывают
  `apps.catalog.services.import_checklists(docs/content/checklists)` перед
  проверкой `work-types`/`checklist-recommendations` — тот же приём, что уже
  использует `apps/catalog/tests/test_checklist_import.py`, не новый.
- **У категории нет человекочитаемого имени нигде в модели.** `category` —
  сырой слаг из таблицы (`turnkey`, `tiling`, …), `check_method`-подобного
  словаря для категорий нет; заголовок раздела в markdown («### 1.1.
  `renovation.turnkey` — Комплексный ремонт под ключ») парсер
  (`checklist_markdown.parse_file`) вообще не сохраняет — используется
  только как документация файла, не структурные данные (`services.
  _import_sphere_file` берёт из парсинга только `category`/`code`/
  `description`/…, не заголовок секции).

## Решения

1. **Read-only `apps/catalog/api/`, пять GET-путей, из существующих моделей,
   без миграций:**
   - `GET /spheres?q=` — `Sphere` (активные), `q` — префикс по
     ЛОКАЛИЗОВАННОМУ имени (регистронезависимо, Python-фильтр — сфер ~17-18,
     гонять через JSONField-запрос ради этого объёма избыточно).
   - `GET /work-types?sphere=` — DISTINCT `ChecklistTemplateItem.category`
     (`is_current=True`, непустая) по сфере (`sphere` FK ИЛИ
     `catalog_item__sphere` FK — тот же союз условий, что нужен признать оба
     пути импорта: ручной сид 0006 кладёт `catalog_item` без `sphere`,
     `import_checklists` кладёт `sphere` всегда).
   - `GET /material-catalog[?sphere=]` — `MaterialCatalogItem` (активные);
     `sphere` — новый опциональный параметр (дёшево, задел на будущее), но
     ЕДИНСТВЕННЫЙ текущий вызов фронта (`useMaterialCatalog()`,
     `StagesStepPage.tsx`) его не передаёт — сознательно НЕ трогается (см.
     §3 «Не делать»).
   - `GET /units` — DISTINCT непустых `MaterialCatalogItem.suggested_unit`
     (сами единицы измерения отдельной моделью НЕ заведены — производная
     выборка тоже реальные данные, не выдумка).
   - `GET /checklist-recommendations?sphere=&workType=` — НОВЫЙ путь на
     уровне каталога (не `GET /milestones/{id}/checklist-recommendations` —
     тот требует существующий milestone, здесь договора ещё нет вообще,
     разная применимость, аудит §«Каталог» это и зафиксировал).
     `ChecklistTemplateItem` по (`sphere` ИЛИ `catalog_item__sphere`) +
     `category=workType` + `is_current=True` + `is_default=True` —
     `is_default` дословно по докстрингу «предзаполняется при выборе типа
     работ», расширенный набор (`is_default=False`) сюда не попадает.
     **`sphere` — ОБЯЗАТЕЛЬНЫЙ параметр** (400 без него), не опциональный:
     `category` — НЕ уникальна глобально, «other» (тип работ «Прочее»)
     встречается практически в каждом из 17 файлов — без `sphere` в фильтре
     `workType=other` смешал бы рекомендации из случайной сферы с той, что
     реально выбрана. Фронт (`useChecklistRecommendations`) обновлён передавать
     оба параметра — единственная правка мастера в этой задаче (см. §3).

2. **Локализация — `common.i18n.resolve_request_locale(request)` (уже
   существующий общий резолвер, ГВ.5/Л.2, не новый механизм), фолбэк
   `name_i18n.get(locale) or name_i18n.get("ru") or <первое, что есть>`** —
   тот же порядок, что уже задокументирован `apps.l10n.selectors` докстринг
   («name_i18n/body_i18n `.get(locale, "ru")`, common/i18n.py»). Применяется
   к `Sphere.name_i18n`/`MaterialCatalogItem.name_i18n`. **НЕ применяется к
   `work-types`** — у `category` нет `_i18n`-поля (см. «Контекст» выше):
   `name` пункта работ = сам `category`-слаг (`code === name`), честно, без
   притворного перевода. Аналогично **рекомендации чек-листа локализуются**
   (`description_i18n.get(locale) or description`, то же поле, что уже
   существует и заполнено ГВ.5 для минимального сида — для полного контента
   `import_checklists` кладёт EN автоматически, `_content_tuple`/парсер).

3. **`popular` в ответе `/spheres` — всегда `[]`, поле `Sphere.popular` не
   выставляется ни у одного элемента `results`.** Нет ни модели, ни поля,
   ни продуктового сигнала «эта сфера популярнее той» — строить рейтинг из
   воздуха значило бы выдумывать данные. `SpherePicker.tsx` уже переживает
   пустой `popular` штатно (`popular ?? []`, README компонента: «показывает
   кнопку "Все сферы"» при пустой секции популярных) — UI не ломается,
   просто ведёт сразу к полному списку. Задел на будущее (не в этом PR):
   `Sphere.sort_order`/`is_popular` поле, если продукту понадобится курировать
   витрину.

4. **`GET /spheres` без `q` — отдаёт ВСЕ активные сферы, не пусто.**
   `SpherePicker` при `q=''` и `showAll=true` использует ТОТ ЖЕ `results` от
   последнего запроса (`web/src/pages/contract-new/SphereStep.tsx`,
   `results={showAll ? undefined : data?.results}` → компонент падает
   обратно на `results` без фильтра) — если бы пустой `q` отдавал `[]`,
   кнопка «Все сферы» показывала бы пустоту. Раз популярных нет (см. п.3),
   это ЕДИНСТВЕННЫЙ путь увидеть сферы без набора текста в поиск.

5. **`AllowAny`, не `IsAuthenticated`.** Справочные данные, не персональные —
   тот же уровень, что `apps.l10n.api.views` (`GET /locales`). Мастер
   договора и так живёт за `RequireAuth` на фронте, но сам каталог не
   обязан требовать токен.

## Не делать (в этом PR)

- **Изменять форму `POST /v1/contracts`, чтобы она принимала
  `sphere`/`work_type`.** Реальный `ContractCreateSerializer`
  (`apps/contracts/api/serializers.py`) принимает `client_option`/
  `contract_type_code` — НЕ `sphere`/`work_type` вообще. Выбор сферы/вида
  работ в мастере СЕЙЧАС уходит в `api.patch('', {...})` через
  `useContractApi` (`features/contracts/api.ts`) — старый мок-агрегатный
  контур (`ContractDetail`), НЕ вызовы, которые чинит эта задача. Это зона
  `redesign/contracts-execution-flow-*` — явно не трогается (постановка
  задачи, §«НЕ делать»). **Следствие: этот PR разблокирует справочники
  мастера (нет больше 404 на `/spheres`/`/work-types`/…), но САМО создание
  договора (`POST /v1/contracts`) остаётся на мок-контуре — не разблокировано
  целиком, см. отчёт задачи.**
- **`?sphere=` в единственном текущем вызове `useMaterialCatalog()`** —
  бэкенд поддерживает параметр (дёшево), но `StagesStepPage.tsx` его не
  передаёт: без сферы список материалов при реальных данных покажет позиции
  ВСЕХ 17 сфер вперемешку (включая 18 одноимённых «Прочее», по одной на
  сферу) — известный, зафиксированный в отчёте продуктовый пробел мастера,
  НЕ каталожная неточность (это wizard UX, не форма API) — не в объёме этой
  задачи («приведи путь к тому, что реально читает фронт», не «перепроектируй
  экран»).
- **Заголовки секций CL-файлов как имена «видов работ».** Реальные, живые
  тексты («Комплексный ремонт под ключ») лежат в markdown, но парсер их не
  сохраняет — добавить это значило бы трогать `checklist_markdown.py`/
  `services.import_checklists`/завести новую миграцию поля — контентный
  пайплайн, не read-only каталожный API. Отдельная задача, если продукту
  нужны красивые названия видов работ раньше, чем полная i18n-локализация
  каталога.
- **Новая модель `Unit`/справочник единиц измерения.** Производной выборки
  `suggested_unit` достаточно для непустого MVP-списка; отдельная модель —
  когда появится реальная потребность в метаданных (пример-подсказка,
  перевод), не сейчас.

## Тесты

- `apps/catalog/tests/test_api.py` — HTTP-слой, по всем 5 путям, включая:
  `q=''` отдаёт непустой список, `q=`префикс сужает по локализованному
  имени, `Accept-Language: en` меняет `name`, `work-types` пуст на чистой БД
  (сид 0006 не заполняет `category`) и непуст после `import_checklists`,
  `checklist-recommendations` без `sphere` — 400, с `sphere`+`workType=other`
  не путает сферы.
- `apps/catalog/tests/test_selectors.py` — новые селекторы напрямую, тот же
  приём, что `test_material_catalog.py` (сравнение с сидом 0006 +
  `import_checklists` фикстура, как `test_checklist_import.py`).
- `makemigrations --check` — без миграций (read-only, ничего в моделях не
  меняется).

# ADR-179. Справочник географии (страна → регион → город) на бэкенде

**Статус:** принято (план 11.09, часть 2 из 5 — «делаем справочник городов на бэкенде.
Для нас немного работы, для пользователя удобнее. Ещё давай страна, регион, город. Причём
поиск возможен на любом уровне. И вообще без этого фильтра»)
**Контекст:** новое приложение `apps.geo` (нижний слой, как `apps.catalog`/`apps.jurisdictions`/
`apps.l10n`); `backend/apps/profiles/models.py` (`Profile.city_name` — свободная строка,
источник проблемы), `backend/apps/dashboards/selectors.py` (`get_search` — зоны `world|
country|city` по гео зрителя, сравнение городов строками)
**Номер:** 179 — следующий свободный на момент создания, сверено по всем ворктри
(`ls ~/porukam-worktrees/*/docs/adr ~/porukam/docs/adr`, максимум был 178 — занят в другой,
ещё не смёрженной ветке; следующий свободный — 179). Строка добавлена в индекс README.

## Контекст

Сейчас география человека в продукте — свободная строка `Profile.city_name` плюс
`User.country_code`. У этого два самостоятельных недостатка:

1. **Опечатки и разнобой написания.** «Алматы» ≠ «алматы» ≠ «Almaty» ≠ «г. Алматы» —
   поиск по городу (`apps.dashboards.selectors.get_search`, зона `city`) сравнивает эти
   строки буквально и промахивается мимо очевидных совпадений.
2. **Нет уровня «регион».** Между «вся страна» и «конкретный город» ничего нет, хотя для
   стран с несколькими часовыми поясами/языками/рынками (Россия, Казахстан, США, Германия…)
   это разумная и ожидаемая от пользователя гранулярность фильтра.

Решение владельца дословно: справочник на бэкенде — валидированные страна/регион/город,
поиск по любому уровню (можно искать сразу город, не выбирая сначала страну), и фильтр
по географии остаётся НЕобязательным («и вообще без этого фильтра» — свободный поиск без
гео тоже должен работать).

Эта задача — ТОЛЬКО справочник и его read-only API. Привязка `Profile` к City/Region и сам
фильтр `get_search` — части 4 и 5 того же плана, отдельные ветки/ADR.

## Решение

### Справочник, а не свободная строка

`apps.geo.models.Country/Region/City` — три таблицы, ссылки друг на друга по FK, поиск
делает БД (индексы), а не полнотекстовое совпадение случайно введённой строки. Это тот
редкий случай, когда владелец явно выбрал «немного работы нам — вместо полагаться на то,
что пользователь наберёт то же самое, что и другие пользователи».

### Источник данных — GeoNames, порог 15 000 жителей

[GeoNames](https://www.geonames.org/) (`https://download.geonames.org/export/dump/`) —
открытая, регулярно обновляемая база географических объектов, лицензия
**CC BY 4.0**. Это ТРЕБУЕТ указания авторства при использовании данных — размещаем на
странице «О проекте»/в юридических документах платформы (страница ещё не существует в
этой задаче — только сам текст-обязательство здесь, в ADR; добавление ссылки на GeoNames
в `l10n/packs/*.json` namespace `legal` — отдельная маленькая задача до продакшена этой
фичи, не блокирует API/справочник как таковые).

Города берутся из `cities15000.txt` — уже отфильтрованного самим GeoNames среза
(`feature class = P`, население ≥ 15 000). Причины порога:
- на весь мир это ≈26 тысяч городов — заведомо достаточно для фильтра исполнителей (никто
  не ищет подрядчика в посёлке на 400 жителек через глобальный каталог) и не требует
  особой инфраструктуры (одна Postgres-таблица с индексами, без Elasticsearch);
- полный дамп GeoNames (`allCountries.zip`) — миллионы строк, большинство из которых
  никогда не понадобятся продукту, а раздувание таблицы усложняет и поиск (крупные
  админ-индексы), и последующие миграции/бэкапы;
- порог совпадает с общепринятой практикой (это ЖЕ пороговый файл, который GeoNames сам
  публикует как «города» — `cities500`/`cities1000`/`cities5000`/`cities15000`; 15000 —
  самый крупный/компактный из готовых срезов, разумный старт, который можно понизить
  позже без смены источника, если понадобится).

Регионы — `admin1CodesASCII.txt` (первый уровень административного деления). Страны —
`countryInfo.txt`.

### Region.code — НЕ настоящий ISO 3166-2, и это осознанно

Задание просило код региона в духе ISO 3166-2. На практике GeoNames для многих стран НЕ
публикует официальные ISO 3166-2 коды в `admin1CodesASCII.txt` — это внутренние коды
самого GeoNames (иногда унаследованные от FIPS, иногда просто порядковые числа). Проверено
на реальном дампе при разработке: Казахстан — `KZ.02` (Алматинская область), `KZ.1537272`
(Шымкent, недавно выделенный город республиканского значения получил числовой, не
буквенный код) — ни то, ни другое не похоже на официальный `KZ-75`/`KZ-ALA`.

Решение: `Region.code` хранит код ИЗ ИСТОЧНИКА как есть, уникальность — только в паре со
страной (`UniqueConstraint(country, code)`, что и просил владелец буквально: «уникален в
паре со страной»), без притворства, что это официальный ISO. Наружу (API, `selectors.
format_region_code`) отдаётся составной идентификатор `<страна>-<код>` (например `KZ-02`) —
он глобально самодостаточен для фильтра `/v1/geo/cities?region=`, не требует передавать
`country` отдельно. Настоящий ISO 3166-2 — отдельная задача с другим источником данных
(например платным или ручным сопоставлением), если/когда понадобится.

### Без координат

`City`/`Region` не хранят широту/долготу. GeoNames их даёт, но в объёме этой задачи
(текстовый фильтр поиска по стране/региону/городу) координаты не на что употребить — карты,
расчёт расстояний и подобное вне плана 11.09. Хранить их «про запас» — лишняя поверхность
ПД-примыкающего риска (геокоординаты в связке с профилем человека — чувствительные данные
даже когда сам город публичен) без сегодняшней пользы; понадобятся — добавить миграцией
вместе с конкретной задачей, которая их использует.

### Названия — `name`/`name_latin` из источника + `name_i18n` на будущее

`Country` вообще не хранит названия — фронт уже умеет локализовывать код страны через
`Intl.DisplayNames` (`web/src/features/groups/groupLabels.ts::countryName`), и делает это
лучше, чем ручной перевод 200+ названий на 29 языков в БД: браузер знает больше локалей,
чем есть пакетов в `apps.l10n`, и не требует поддержки.

`Region`/`City` названий на 29 языков в GeoNames НЕТ — `admin1CodesASCII.txt`/
`cities15000.txt` дают только исходное написание (часто уже английскую/официальную
транслитерацию, а не письменность страны — например для России и Казахстана `name` в
`cities15000.txt` УЖЕ латиница: `Udomlya`, не `Удомля`) и отдельно ASCII-транслитерацию
(`name_latin`), различающуюся от `name` там, где в оригинале есть диакритика (немецкие
умляуты, албанские `ë`, `ç` и т.п.). Оба поля — что дал источник, без домыслов.

`name_i18n` (JSONField, код локали → название) заведён НА БУДУЩЕЕ — если появится
источник с настоящими переводами (например отфильтрованный `alternateNamesV2.txt` по
`isPreferredName` + языку, что уже осознанно НЕ делается в этой задаче — слишком сложная
схема для объёма плана 11.09). Импорт `import_geo` этот словарь пока не заполняет —
пустой словарь = фолбэк на `name` на стороне читателя (фронт следующей части плана; сам
API просто отдаёт все три поля как есть).

### Коллация и регистронезависимость поиска

Поля, участвующие в поиске (`name`, `name_latin`, `Region.code`), объявлены с явной
коллацией `"C"` (встроенная, детерминированная) — НЕ дефолтная локаль кластера и НЕ своя
именованная ICU-коллация (как `case_insensitive` у `apps.accounts`/`apps.social`):

- `apps.geo` — нижний слой и не должен зависеть от `apps.accounts` даже на уровне порядка
  миграций (создание общей ICU-коллации живёт в `accounts/migrations/0001_...`);
- регистронезависимое РАВЕНСТВО (ради чего заводят именованную нон-детерминированную
  коллацию) здесь не нужно — нужен только префиксный поиск;
- `"C"` не зависит от того, какие ICU/glibc-локали установлены в конкретном окружении
  (dev/CI/прод на разных базовых образах могут расходиться), и допускает обычный
  btree-индекс для `LIKE 'x%'` без `text_pattern_ops`.

Регистронезависимость поиска реализована через Postgres-функцию `lower()` (НЕ через
Django `istartswith`/`icontains`, которые компилируются в `ILIKE`, чей регистр-фолдинг
зависит от КОЛЛАЦИИ колонки, а не от локали БД — под `"C"` он не свернул бы, например,
кириллицу или умляуты к одному регистру). `lower()` в Postgres берёт правила из
`LC_CTYPE` СЕССИИ/БД (Unicode-осведомлённый на образе `postgres:16`, `initdb` по
умолчанию генерирует `en_US.utf8`), а не из коллации колонки — поэтому корректно
сворачивает регистр и для нелатинских/акцентированных символов, хотя сами колонки лежат
под `"C"`. Индексы под поиск поэтому — ФУНКЦИОНАЛЬНЫЕ, по `Lower(name)`/`Lower(name_latin)`
(`apps.geo.models`, `apps.geo.selectors` фильтрует именно по ним) — обычный индекс по
сырому полю не покрыл бы `WHERE lower(name) LIKE ...`.

### Дамп не в git

`countryInfo.txt`/`admin1CodesASCII.txt` — десятки/сотни КБ, `cities15000.zip` — несколько
МБ, распакованный — ≈8 МБ на 34 тысячи строк. Хранить это в репозитории — раздувать git
без пользы (данные меняются импортом, не код-ревью построчно) и без необходимости (файл
качается с открытого источника командой). В git — только маленькая фикстура для тестов
(`apps/geo/tests/data/*_sample.txt`, по 7–28 строк на файл — не архив, plain-текст, чтобы
diff был читаем) с реальными строками источника (та же лицензия CC BY 4.0 распространяется
и на неё).

### Импорт — идемпотентный, потоковый, батчами

`manage.py import_geo` (тонкая CLI-обёртка) → `apps.geo.services.import_geo_dataset`
(вся логика, CLAUDE.md — бизнес-логика не в командах). Идемпотентность —
`bulk_create(..., update_conflicts=True)` (Django 5.2 / Postgres `INSERT ... ON CONFLICT
DO UPDATE`) по естественному ключу источника (`geonames_id` у City/Region,
`code` у Country) — повторный запуск ОБНОВЛЯЕТ существующие строки, а не плодит дубли.
Файлы читаются построчно (`apps.geo.geonames` — генераторы, включая чтение члена
`cities15000.zip` через `ZipFile.open()`, а не `.read()`) — ни один файл целиком не
загружается в память (боевая ВМ с ограниченным объёмом ОЗУ, см. CLAUDE.md/README
инфраструктуры). Битая строка (не разбирается по формату, портит числовое поле, ссылается
на страну, которой нет в справочнике) — пропускается со счётчиком и предупреждением в
лог, не валит весь импорт.

Список стран по умолчанию — 68 кодов из фронтового `COUNTRY_CODES`
(`web/src/features/groups/groupLabels.ts`), продублированных в `apps.geo.constants.
DEFAULT_COUNTRY_CODES` (backend не может импортировать TS-модуль — при изменении
фронтового списка нужно поправить оба места вручную). Это ТОЛЬКО дефолт: `--countries=all`
или явный список кодов тянут любые страны источника без правки кода — справочник обязан
расширяться (владелец: «Ещё давай страна, регион, город» — явно не ограничивая набор
навсегда этими 68).

## Последствия

- Новая нижнеуровневая зависимость: `apps.geo` в `INSTALLED_APPS` и в import-linter
  (`нижний слой`, запрет для `apps.analytics`) — по образцу `catalog`/`jurisdictions`/`l10n`.
  Приложениям выше по стеку (в первую очередь `apps.profiles`, `apps.dashboards` — части 4/5
  плана) разрешено импортировать `apps.geo.selectors`.
- Перед продакшеном фичи — добавить упоминание источника (GeoNames, CC BY 4.0) в юр-текст
  «О проекте»/аналог, иначе лицензия нарушена молча.
- Реальный размер таблиц на дефолтных 68 странах: страны — 68, регионы — низкие сотни,
  города — низкие десятки тысяч (полный `cities15000.txt` на весь мир — 34 135 строк;
  на 68 стран — заметно меньше, точная цифра зависит от набора стран и появится при первом
  проде-импорте).
- Настоящая локализация названий регионов/городов (`name_i18n`) откладывается до появления
  подходящего источника — сейчас поле существует, но remains пустым для всех строк.

# ADR-093. Репутационная карточка фронта на реальном API: взаимная развязка «хендл ↔ profile_id», что скрыто

**Статус:** принято
**Дата:** 2026-08-18
**Контекст задачи:** feat/reputation-card — карточка репутации против
боевого бэка (отчёт — `docs/tasks/reputation-card-real-api-report.md`) (финал §E-смоука: после приёмки этапа репутация стороны обновляется реально).
Продолжает ADR-076 (read-модель ГВ.4) и закрывает разрыв, который ADR-076 сам за собой
записал: «Реальная карточка фронтенда (`web/src/pages/ReputationCardPage.tsx`) — уже
существующий UI-мокап на другом контракте данных… ГВ.4 не переписывает и не подключает его
— отдельная задача». Аудит подтвердил разрыв как 🟠 B
(`docs/tasks/audit-web-api-contract-sweep-report.md`, раздел «Репутационная карточка»).

## Контекст

Фронт звал `GET /v1/handles/{handle}` и ждал `{profile, portfolio, memberships}` — форму,
которой ни один сериализатор не отдаёт. Реальные ресурсы:

- `GET /v1/reputation/profiles/{profile_id}/card` (`ReputationCardSerializer`, `AllowAny`) —
  возраст профиля, число сделок, число контрагентов, список завершённых сделок
  (тип/сегмент/сферы/период/исход/контрагент/счётчики этапов и споров);
- `GET /v1/handles/{handle}` (`HandlePublicSerializer`, `AllowAny`) — `{handle, kind, verified}`.

Разрыв не только в форме ответа, но и в КЛЮЧЕ: карточка ключуется `profile_id`, публичная
ссылка продукта — хендлом (`/@handle`, `GET /users/me/reputation-link` строит URL из хендла),
а сторона договора известна как `profile_id` (`ContractPartySerializer.profile_id`). Ни один
из двух идентификаторов не выводился из другого.

## Решения

1. **Два аддитивных поля вместо одного «удобного» эндпоинта — взаимная развязка.**
   `GET /handles/{handle}` отдаёт `profile_id` (person-профиль владельца хендла), а карточка
   отдаёт `handle`. Иначе пришлось бы либо заводить дублирующий
   `GET /reputation/handles/{handle}/card` (второй роут на тот же ресурс), либо оставить
   маршрут `/@handle` вообще нерабочим. Оба поля — `null`-безопасные: хендл объединения
   (`kind: "group"`) в person-профиль не разрешается, бизнес-профиль юрлица хендла не имеет.
2. **`apps.social` → `apps.profiles` — только `import_string`, `apps.reputation` →
   `apps.social` — прямой импорт.** Первое запрещено import-linter-контрактом «social зависит
   только от accounts», поэтому `settings.HANDLE_PUBLIC_PROFILE_SELECTOR` — тот же приём, что
   уже применён для `GET /users/me` (`USER_ME_PROFILES_SELECTOR`/`USER_ME_HANDLE_SELECTOR`,
   ADR-086). Второе НЕ запрещено ничем (запрещено обратное направление), а вьюха карточки уже
   композирует `apps.profiles`/`apps.accounts` селекторами — заводить ради симметрии третью
   настройку было бы карго-культом.
3. **Тяжёлого бэка не строим: чего read-модель не считает — того на карточке нет.**
   Мок-контракт DEV-01 рисовал рейтинги по сферам («в срок 141/156»), денежный объём сделок,
   портфолио «подтверждено/заявлено», объединения и переключатель ролей исполнитель/заказчик.
   Ничего из этого `DealFact` не хранит и ГВ.4 не считает («зеркало, а не гарант», док 31 §3).
   Эти блоки УДАЛЕНЫ, а не заглушены «пока пусто»: пустое состояние обещает данные, которых
   не появится без отдельной задачи. Компоненты `RoleSwitch`/`SphereRow`/`TrustNumber`/
   `PortfolioTile`/`CommunityPill` остаются в `@porukam/ui` (дизайн-система, свои тесты) —
   удалён только их вызов с выдуманными данными.
4. **Стартовая карточка (`restricted: true`) показывает, что скрыто, а не притворяется
   пустой.** `deals_count`/`counterparties_count` приходят `null` — рисуем «скрыто» и
   объяснение «владелец показывает историю сторонам завершённых сделок», а не «0 сделок»:
   ноль — утверждение о факте, `null` — отказ его раскрывать. Возраст профиля виден всегда
   (ADR-076 §2).
5. **Статус верификации — только когда он реально известен.** `verified` живёт в
   `apps.social` и достаётся по хендлу; у карточки без хендла его нет. `PassportHeader.
   verification` стал optional: отсутствие плашки честнее, чем «Не подтверждён» вместо
   «неизвестно».
6. **Имена сфер — из публичного `GET /v1/spheres`, с фолбэком на код.** `DealFact.sphere_codes`
   хранит коды; отдельного словаря на фронте не заводим и локализовать коды в i18n не начинаем
   (каталог уже отдаёт локализованные имена, ADR-091). Не разрешился код — показываем код.

## Не рассматривалось

Агрегаты «в срок / гарантия / объём», рейтинги и графики (нет источника данных: события-исходы
ГВ.4 не несут ни сроков-план-факта, ни денег). Карточка репутации объединений
(`AddressableGroup.reputation_mode`) — ГВ.4 их не считает вовсе. Публикация портфолио
FROM_CONTRACT — отдельный шаг, ADR-076 §3. Дедублирование `contract_type_code` в
человекочитаемое имя — на карточке показываем код ровно так же, как это уже делает
`ContractDetailPage` (единый приём, а не локальная выдумка).

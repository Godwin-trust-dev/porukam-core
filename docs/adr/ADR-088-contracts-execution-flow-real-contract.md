# ADR-088. Сделка/этапы/подписание против реального REST: композиция на клиенте, фазовый план, не одноразовый rewrite

**Статус:** принято
**Дата:** 2026-08-17
**Контекст этапа:** `docs/tasks/Задача_redesign_contracts-execution-flow-real-api.md`, продолжение
`docs/tasks/audit-web-api-contract-sweep-report.md` §2 «Договор целиком». Design-first по образцу
ADR-086/087, но на порядок больше по площади — это не «переименовать путь/поле», это открытие, что
бо́льшая часть заявленного продуктового контракта фронта на бэке пока не существует.

## Контекст

Фронт держит договор одним аггрегатным объектом `ContractDetail` (~35 полей верхнего уровня + вложенные
`MilestoneNode`/`RevisionProposal`/`ContractVersion`/`SignatureRecord`/`TimelineEvent`, ещё под сотню
полей суммарно) и обновляет его универсальным `.post/.patch/.del('/contracts/{id}{path}', body)`,
ожидая `ContractDetail` от ЛЮБОГО вызова. Реальный бэк (`apps.contracts` 32 пути + `apps.milestones`
17 путей + `apps.social`/`apps.evidence` для подписания/доказательств) — раздельный REST по узким
ресурсам.

Второй проход (агент по моделям `apps/contracts`, `apps/milestones`, `apps/billing`, `apps/
jurisdictions` — не только сериализаторам) дал более точную картину, чем первичный аудит: часть полей
`ContractDetail` — ДЕШЁВО вычислимые величины, которых просто нет в `Meta.fields` сериализатора
(«Фаза 0» ниже); часть — данные, для которых на бэке есть смежные модели/поля, но нужен новый
selector (написать по образцу уже существующих); часть — продуктовые концепции (AI-резюме версии
договора, N вариантов правки в одной записи, денежная политика по юрисдикции, полный денежный расчёт
расторжения), которых на бэке НЕТ ВООБЩЕ и которые либо уже сознательно отложены командой (документально,
до этой задачи — `payment_policy` → «Ф6», `settlement_amount` → «этап 7», ADR-028), либо не существуют
даже как план.

## Решения

### 1. Композиция на клиенте, НЕ рефакторинг потребляющих компонентов
`ContractDetailPage.tsx`(826 строк)/`ContractReviewPage.tsx`(536)/`SigningPage.tsx`(322)/мастер создания
(6 файлов, ~880 строк) читают `ContractDetail` как единый объект очень широко. Переписать все эти
компоненты на россыпь отдельных хуков-по-ресурсам (как сделано для `features/profile/api.ts` после
ADR-086/087) — на порядок больше кода под риском, чем сама задача приведения контракта к реальности.

**Решение:** держать `ContractDetail`-подобную форму как VIEW MODEL на клиенте, собираемую композицией
из нескольких реальных вызовов (`GET /contracts/{id}` + `GET .../milestones` + `GET .../revisions` +
`GET .../amendments` + `GET .../signature-requests` + `GET .../timeline`, где каждый реально нужен) —
не единым запросом, а параллельным `Promise.all`/react-query-композицией на фронте. Поля без реальной
опоры — либо derive на клиенте, где дёшево (`is_cross_language = Object.keys(renders).length > 1`),
либо честно `undefined`/скрыты в UI (тот же принцип Tier B, что ADR-087), НЕ подделываются нулями/
заглушками, выдающими себя за факт.

### 2. Фазовый план, не один PR
Разбито по естественным границам жизненного цикла сделки — каждая фаза отдельной задачей
(docs/tasks/Задача_*), со своим Tier A/B внутри (по образцу ADR-087), а не одним PR на всё:

| Фаза | Контур | Приоритет |
|---|---|---|
| 0 (эта задача, backend, done) | `total`/`initiator_role` в `ContractSerializer` | — |
| 1 | Чтение: список + деталь договора (`GET`, без мутаций) | 🔴 |
| 2 | Создание черновика + мастер (согласовать с `feat/catalog-real-api` — сфера/вид работ) | 🔴 |
| 3 | Переговоры: отправка/отзыв/отклонение + ревизии/предодобренные | 🔴 |
| 4 | Заморозка + ДВУХШАГОВОЕ подписание (создать заявку → подписать) | 🔴 |
| 5 | Этапы исполнения: чек-листы/материалы/старт/сдача + evidence (реальный multipart) | 🔴 |
| 6 | Приёмка (`accept`/`reject`, реальные тела) | 🔴 |
| 7 | Допники, расторжение (settlement_amount — заглушка на бэке, ADR-028 «этап 7» — не разрешать в этой ветке задач) | 🟠 |

Порядок фаз — зависимостный (2 нужен для 3, 3 для 4, 4 для 5/6), не приоритетный внутри 🔴 — все
фазы 1–6 в сумме составляют «основной смоук», ни одна не менее приоритетна.

### 3. «Фаза 0» — сделано в этом PR: дешёвые довычисления без миграций
- `apps.contracts.selectors.initiator_role(contract)` — новый селектор (роль стороны, создавшей
  договор — `user_owned_profile_ids(contract.created_by)`, тот же приём, что `resolve_counterparty`).
- `ContractSerializer.total` — `SerializerMethodField`, вызывает уже существующий
  `apps.milestones.services.total_leaf_amount(contract)` (отложенный импорт — тот же приём, что
  `services.freeze`, разрыв цикла `apps.milestones` ⇄ `apps.contracts`). `None` на черновике без
  этапов — не ошибка.
- `ContractSerializer.initiator_role` — тот же приём, что выше.
- Оба поля — `{amount, currency}`-строкой (CLAUDE.md), по образцу `SigningAuthoritySerializer.max_amount`.

**`tax_note` НЕ добавлен**, хотя технически дёшев (`ContractTypeCatalogItem.tax_note_i18n`, уже
существует) — резолюция локали требует `self.context['request']` (`common.i18n.resolve_request_locale`),
а НИ ОДИН из 11 call-site `ContractSerializer(contract)` в `apps/contracts/api/views.py` сейчас не
передаёт `context={'request': request}`. Правка 11 сайтов ради одного информационного поля — уже не
«минимально» (границы задачи, docs/tasks/…: «чинить только тривиальное»). Отнесено в Фазу 1 (фронт
всё равно собирает деталь композицией — заодно и context-плумбинг, если понадобится).

**`updated_at` НЕ добавлен** — `Contract` не имеет этого поля вообще, добавление требует новой
миграции (`AddField` с `auto_now=True`, бэкофилл существующих строк) — не «минимальное поле в
сериализатор», реальная схемная правка. Отнесено к Фазе 1/аналитике по факту необходимости (нужна ли
вообще фронту дата последнего изменения, если есть `timeline`).

### `MilestoneNode` vs `MilestoneSerializer`
`id/parent_id/title/amount` ✅; `status` ✅ (сверить enum один-в-один при реализации); `checklist_items`/
`materials` — A (отдельные `GET`); `kind` (branch/leaf) — B, ДЕРЕВО backend не хранит явный тип узла,
видимо derive по наличию children + `amount is None`; `depth` — derive на клиенте (проход по дереву);
`meta` — B (фронтовый текстовый хинт, собрать из deadline/duration на клиенте); `duration_days` — B,
частично derive из `deadline`; `payment.{advance,advance_percent}` — B, реальные поля
(`advance_confirmed_by_*_at`) — только булевы отметки подтверждения, не сумма/процент аванса; `terms_override`
— B (упирается в отсутствующий `ContractTerms` целиком).

### `RevisionProposal.variants` — архитектурное расхождение, не баг
Бэк хранит один `old_value`/`new_value` на запись; встречное предложение — НОВАЯ запись с
`old_value = new_value` предыдущей (цепочка через `item_ref`, не список в одной записи). Фронтовый
«1..N вариантов сразу» либо агрегируется на клиенте по цепочке `item_ref`, либо UI признаёт линейную
модель бэка (продуктовое решение — не мой вызов здесь, для Фазы 3).

### `ContractVersion` — AI-резюме нет, `renders` структурно близко
`ai_summary`/`ai_summary_items` — НЕТ вообще, ни модели, ни сервиса (B, отдельная крупная фича, не
блокер подписания — можно скрыть в UI как Tier B). `renders` (`{lang: {language, hash, document}}`) —
структурно близко к фронтовому `ContractRender[]`; `is_cross_language` тривиально derive
(`Object.keys(renders).length > 1`) — Фаза 4 может это подключить без бэкенд-работы.

## Не рассматривалось
- **Полный rewrite потребляющих компонентов на отдельные хуки-по-ресурсам сейчас.** Отклонено — см.
  решение 1; композиция даёт тот же результат для потребителей (форма объекта не меняется на входе UI)
  при на порядок меньшем риске правки 1700+ строк вьюх за один заход.
- **Достраивать `settlement_amount`/AI-резюме/денежную политику в рамках этой ветки задач.** Оба уже
  либо явно отложены командой (Ф6/этап 7), либо не входят в «основной смоук» (сделка проходит и без
  AI-резюме — это украшение экрана подписания, не блокер).

## Последствия
- Фаза 0 (это PR) — только бэкенд: 2 новых поля, 1 новый селектор, 0 миграций, 2 новых теста. Фронт НЕ
  тронут (потребители текущего мок-контракта не сломаны — поля аддитивны).
- Заготовки задач для фаз 1–7 — `docs/tasks/Задача_redesign_contracts-execution-flow-real-api-phase-{1..7}-*.md`.
- До прохождения всех фаз 1–6 «основной смоук» (договор→подпись→этап→приёмка→репутация) физически не
  проходит против боевого бэка ни в одной своей части (создание, подписание и т.д.) — статус, уже
  зафиксированный в исходном аудите, этим PR не меняется, только на 2 поля приближается.

## Дополнение — Фаза 2 (создание, мастер): рез объёма и найденные ограничения (2026-08-18)

Найдено при реализации фазы (не было видно из сериализаторов при написании этого ADR):

- **`forms.validate_form_data` строгая**: неизвестный ключ → 422 `unknown_field`; отсутствующее
  обязательное видимое поле → 422 `required`; `PATCH form_data` — ПОЛНАЯ ЗАМЕНА (валидируется
  целиком); пустой `form_data` валиден. Следствие: «частичную» форму сохранить нельзя — мастер
  собирает и шлёт форму целиком (`web/src/features/contractNew/serviceFormData.ts`), а шаг «Условия»
  оказался секциями ТОЙ ЖЕ сервисной схемы (warranty/acceptance/modules), не отдельным ресурсом.
- **`POST /contracts` требует контрагента при создании** — черновик создаётся при выходе с шага
  «Стороны», а не «Типа»; до этого выбор живёт в zustand-сторе. `my_role` фиксируется созданием.
- **Резолв типа асимметричен** — «Услуга» по `client_option`, остальным нужен явный код: закрыто
  эндпоинтом `GET /v1/contract-types` (ADR-094).

Рез объёма PR фазы (решение владельца: «В без отправки пустых»):

- **Услуга — полностью**: существо по серверной схеме, этапы плоскими `POST /contracts/{id}/milestones`
  (+ чек-пункты), условия, превью, отправка. Ровно контур §E-смоука.
- **Продажа/Аренда/Займ — создаются реально** (код из ADR-094, стороны, название), но форма существа
  не подключена: шаг «Суть» честно говорит об этом, а «Превью» БЛОКИРУЕТ отправку на согласование
  (`validationIssues`) — сервер `send_for_review` предусловий не имеет, и без блокировки договор без
  существа дошёл бы до подписания (юрриск). Полные формы остальных типов (~69 полей, 3 списочных
  редактора, ~200 ключей × 29 языков) — отдельные задачи.
- Скрыто как отсутствующее на бэке: длительность этапа, материалы (создание требует
  `catalog_item_code`-подключения), аванс/разбивка оплат, разделы-ветки в мастере, удаление этапа
  (DELETE нет), удаление черновика (DELETE нет), инвайт несуществующего контрагента, `party_details`,
  валюта на уровне договора (валюта — у сумм этапов).

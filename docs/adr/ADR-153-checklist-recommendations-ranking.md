# ADR-153. Ранжирование подсказок критериев приёмки по востребованности

**Статус:** принято (решение владельца 2026-09-03)
**Контекст:** apps.catalog (нижний слой), apps.milestones

## Контекст

Мастер договора подсказывает формулировки критериев приёмки: `GET
/checklist-recommendations?sphere=&workType=` (ADR-091 §1) отдаёт плоский `{results:
string[]}`, фронт (`feat/web-stage-criteria-typeahead`) показывает первые 5 при пустом вводе
и фильтрует по подстроке при наборе. Выдача формировалась так: только `is_default=True`,
порядок — каталожный `order` автора CL-файла (ADR-081). То есть «первые 5» — это всегда
первые пять строк markdown-таблицы, а не то, что стороны реально пишут в чек-листы.

Владелец 03.09: подсказки должны быть «самые релевантные». Принятая трактовка
релевантности — **востребованность**: сколько раз пункт шаблона реально попадал в чек-листы
этапов настоящих договоров. Это единственный сигнал, который у платформы уже есть и который
не требует ни разметки контента, ни оценок пользователей.

Главная сложность — границы слоёв (CLAUDE.md, import-linter): `apps.catalog` — нижний слой,
он не имеет права читать `apps.milestones.ChecklistItem`, где эта востребованность
фактически накапливается. Вторая — версионирование пунктов (ADR-081): правка формулировки в
markdown заводит НОВУЮ строку `ChecklistTemplateItem` с тем же `slug` и `version + 1`, у
старой `is_current=False`; счётчик, живущий на строке, обнулялся бы на каждой правке текста.

## Решение

1. **Счётчик денормализован в каталоге, отдельной таблицей по `slug`.**
   `ChecklistTemplatePickStat(slug UNIQUE, pick_count, last_picked_at)`, `db_table =
   checklist_template_pick_stat`. Ключ — `slug`, а не FK на строку пункта: у новой редакции
   пункта тот же `slug`, значит востребованность копится по ПУНКТУ, а не по его редакции и
   переживает переимпорт `import_checklists`. CHECK-инвариант `slug <> ''`: пункты ручного
   сида 0006 стабильного идентификатора не имеют — их пики не учитываются (в ранжируемую
   выдачу они и так не попадают: `category` у них пустая, а `workType` в запросе обязателен).
   Отдельная таблица ещё и разводит горячую на запись величину и холодный справочник под
   кешем `_cached_payload`.

2. **Счётчик двигает фасад `apps.catalog.services.record_checklist_pick(description,
   sphere_id)`**, который зовёт `apps.milestones.services.create_checklist_item` при
   создании пункта чек-листа. Направление milestones → catalog разрешено import-linter'ом,
   обратное — нет: знание едет в каталог, каталог за ним не ходит. Инкремент — одним
   UPDATE с `F()`; первая вставка строки статистики защищена уникальным индексом `slug`
   (проигравший гонку просто инкрементирует, вложенный `atomic` не даёт `IntegrityError`
   сломать транзакцию вызывающей стороны).

3. **Сопоставление — по точному тексту формулировки**, не по id
   (`selectors.find_checklist_template_by_description`). Причина не в удобстве: id пункта у
   вызывающей стороны нет физически — `GET /checklist-recommendations` отдаёт плоский
   `string[]`, и `POST /milestones/{id}/checklist-items` приносит обратно только текст.
   Менять контракт ответа ради этого не стали (фронт уже сделан; форма ответа осталась
   ровно `{results: string[]}`). Один текст может встречаться в разных сферах (категория
   `other` есть почти в каждом CL-файле) — сначала пробуем сферу этапа
   (`effective_sphere_id`), потом глобально, остаточная неоднозначность разрешается
   наименьшим `slug` (детерминированно). Текст, написанный руками, ни с чем не совпадёт —
   счётчик не двинется.

4. **`ChecklistItem.source_template`** — nullable FK на редакцию шаблонного пункта,
   заполняется тем же сопоставлением в момент создания (`related_name="+"` — обратного
   аксессора у каталога нет намеренно). Фиксирует ПРОИСХОЖДЕНИЕ пункта; PATCH связь не
   пересчитывает и счётчик не двигает. Даёт прямую связь для будущих агрегатов, чтобы не
   сопоставлять тексты каждый раз заново.

5. **Порядок выдачи:** `is_default` ↓, `pick_count` ↓, `order` ↑, `slug` ↑.
   Расширенный необязательный набор (`is_default=False`) теперь ВХОДИТ в выдачу («пусть
   читают и умнеют»), но строго после дефолтных при любом счётчике: дефолт — редакторское
   решение автора CL-файла, востребованность его не отменяет. Замер на реальном контенте
   (18 CL-файлов, 105 пар сфера×вид работ): дефолтных медианно 9 на пару (максимум 19),
   необязательных — 2 (максимум 6), суммарно медиана 13, потолок 23. Список не раздувается —
   включён целиком, урезать не стали.

6. **Бэкфилл — data-миграцией `milestones.0008`**, по совпадению текста (единственный след
   происхождения у пунктов, созданных до этой ветки); тем же проходом заполняется и
   `source_template`. Миграция живёт в `apps.milestones`, а не в каталоге, по той же
   причине, что и фасад: каталог не может читать `checklist_item` даже миграцией.

7. **Пересчёта Celery-задачей нет.** Счётчик инкрементальный, точность «плюс-минус пик»
   для порядка подсказок несущественна. Периодическая агрегация добавила бы beat-задачу
   (с ловушкой `timedelta`-расписания, не переживающего пересоздание контейнера, —
   `fix/audit-vault-checkpoint-cron`) ради величины, которая никуда не спешит. Если
   когда-нибудь понадобится точный пересчёт (например после массовой чистки договоров),
   он делается разово по `source_template__slug` тем же способом, что и бэкфилл.

## Последствия

- Идемпотентности «на запрос» у фасада нет и быть не может: `POST
  /milestones/{id}/checklist-items` не денежный и не подписной, `Idempotency-Key` на нём
  не требуется (CLAUDE.md — только денежные/подписные POST). Единица счёта — СОЗДАННАЯ
  строка `ChecklistItem`: повторный POST создаёт второй пункт чек-листа, и это честно
  второй пик. Зато пик атомарен и откатывается вместе с транзакцией создания.
- Удаление пункта чек-листа счётчик не уменьшает: величина — «сколько раз пункт выбирали»,
  а не «сколько таких пунктов живо сейчас». Для порядка подсказок это ровно то, что нужно.
- Холодный старт: на свежей БД все `pick_count = 0`, порядок вырождается в прежний
  каталожный — регрессии выдачи нет, ранжирование «прорастает» по мере использования.
- Выдача перестала быть одинаковой для всех: две площадки с разной историей увидят разный
  порядок подсказок. Это и есть цель, но это же означает, что скриншоты мастера в
  документации нестабильны.
- `GET /milestones/{id}/checklist-recommendations` (ADR-047, путь по материалам этапа)
  РАНЖИРУЕТСЯ ТАК ЖЕ — решение владельца 03.09, реализовано в ADR-155: общий хелпер
  `apps.catalog.selectors.rank_checklist_templates` (`is_default ↓, pick_count ↓, order ↑,
  slug ↑`) используют оба селектора, форма ответа (объекты) не изменилась. Один и тот же
  список в двух местах интерфейса не может ранжироваться по-разному.
- Прод: миграции `catalog 0019` (новая таблица), `milestones 0007` (NULL-колонка,
  без блокировки), `milestones 0008` (бэкфилл, один проход по `checklist_item`).

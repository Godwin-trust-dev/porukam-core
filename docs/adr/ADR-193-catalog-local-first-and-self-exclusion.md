# ADR-193. Каталог исполнителей: свой профиль исключён, местные — первыми

**Статус:** принято (решения владельца 18.09, продолжение ADR-184 «Каталожный поиск исполнителей
с фильтрами»)
**Номер:** 193 — сверено `ls docs/adr ~/porukam-worktrees/*/docs/adr | grep -o 'ADR-[0-9]*' | sort -u
| tail`, максимум занятый — 192.

## Постановка владельца (дословно, 18.09)

> выбрала например Армению, страну, где нет ни одного пользователя сейчас, он выдал всех из моей
> записной книги и плюс сам мой аккаунт

Разбор бага — две независимые причины:

1. **Зритель не исключён из выдачи вовсе.** `apps.dashboards.selectors.get_search_catalog` не
   знал, кто смотрит — свой же профиль проходил все фильтры каталога наравне с чужими.
2. **Профили с `WorkArea(scope=world)` покрывают любой гео-запрос — by design (ADR-184).** Старая
   галочка «работаю удалённо» превратилась в `scope=world` командой `migrate_profile_geo_to_work_areas`
   (часть 11.09/4, ADR-182) — и при фильтре «Армения» (где реально никого нет) в выдаче оказались
   ВСЕ, кто когда-то поставил эту галочку, без разбора: они физически не в Армении, но формально
   «покрывают» любой гео-запрос. Ответ владельца: показывать таких при гео-фильтре можно (сам факт
   видимости — не баг, ADR-184 решил это осознанно), но ОТДЕЛЬНЫМ блоком снизу, а не вперемешку с
   местными — иначе местный исполнитель тонет на третьей странице за чужими «мировыми» флагами.

## Решение

### 1. Самоисключение зрителя

`get_search_catalog` получил обязательный параметр `viewer: User` (тем же способом, каким зритель
уже прокидывается в соседние read-функции модуля — `get_stages(user, request)`,
`get_payments(user, request)`, `get_search(user, ...)`) и исключает `owner_user=viewer` БЕЗ
дополнительного условия `kind=PERSON`. Не потому что бизнес-профиль того же владельца тоже нужно
исключать особым правилом, а потому что `owner_user` СТРУКТУРНО бывает только у person-профиля —
`CheckConstraint profile_owner_matches_kind` (`apps.profiles.models.Profile.Meta`) требует
`kind=business → owner_user IS NULL, owner_entity IS NOT NULL`. Прямой фильтр по `owner_user`
проще, чем повторять `kind=PERSON` рядом, и не потребует правки, даже если модель когда-нибудь
разрешит `owner_user` у business (сейчас не разрешает).

Бизнес-профиль, которым зритель управляет через `owner_entity.claimed_by` (не `owner_user`,
`apps.contracts.selectors.user_owned_profile_ids` — другая функция, других use case) — ДРУГАЯ
сущность и этим исключением не убирается: жалоба владельца была про «сам мой аккаунт», не про
«бизнесы под моим управлением», а искать чужой (даже управляемый) бизнес в каталоге исполнителей —
легитимный сценарий (найти конкурента/партнёра), не баг.

Место в коде — `apps.dashboards.api.views.SearchView.get` (`request.user` уже читается там на
уровень выше, строка ~230) передаёт `viewer=cast(User, request.user)` в `get_search_catalog`.

### 2. Местные первыми, «работающие удалённо» — отдельным блоком, с признаком от бэка

Группировку и порядок отдаёт БЭК, а не фронт: если бы сортировку/группировку строил фронт по
`work_areas` элемента, ему пришлось бы повторять то же правило покрытия, что уже в
`geo_filter_coverage_q` (страна покрывает регион/город внутри и т.д., ADR-184) — второе определение
тех же правил в другом слое, ровно то, чего CLAUDE.md просит избегать.

- **`apps.profiles.selectors.geo_filter_local_coverage_q(country=, region=, city=)`** — НОВАЯ
  функция рядом с `geo_filter_coverage_q`: тот же Q, но БЕЗ ветки `scope=world`. Общая часть (разбор
  гео-параметров запроса в цель подзапроса `WorkArea`) вынесена в приватный
  `_resolve_geo_coverage_target`, общее тело веток `country`/`region`/`city` — в
  `_geo_local_coverage_q`; `geo_filter_coverage_q` теперь просто добавляет к нему
  `Q(scope=WORLD)`. Второго определения правил покрытия в проекте нет — обе публичные функции
  собраны из одних и тех же двух кирпичей.
- **`apps.dashboards.selectors.get_search_catalog`**: когда гео-фильтр задан (`geo_q is not None`),
  профили аннотируются `geo_rank` (`1`, если покрыты `_geo_local_coverage_q` — «местный», иначе
  `0` — покрыт только `scope=world`) и сортируются `(-geo_rank, -created_at, -id)`: местные первой
  группой, «мировые» — второй, порядок ВНУТРИ группы не меняется (тот же `-created_at, -id`, что
  был). `geo_rank` аннотируется БЕЗУСЛОВНО (даже без гео-фильтра, тогда — константа `0`) — приём
  нужен, чтобы django-stubs/mypy не теряли аннотацию, добавленную только в одной ветке `if`, тот же
  паттерн уже используется для `completed_deals_count` (`annotate()` вне условия).
- **Каждый элемент выдачи несёт `geo_match`**: `"local"` (есть `WorkArea` уровня страна/регион/
  город, покрывающая запрос), `"remote"` (покрыт ТОЛЬКО через `scope=world`), `null` (гео-фильтр не
  задан вовсе — группировать нечего, фронт показывает один список). `CatalogItemSerializer.geo_match`
  — `ChoiceField(["local", "remote"], allow_null=True)`.

### Курсор keyset-пагинации несёт группу

Страница 2 обязана знать, с какой стороны границы local/remote она продолжает — иначе при
`limit=1`/маленьких страницах она либо повторит последний local, либо перепрыгнет часть remote (тот
же класс бага, который ADR-184 уже решал для `created_at/id`, только теперь для третьего измерения
сортировки). Формат курсора расширен третьим полем: `base64(group|created_at.isoformat()|id)`, где
`group ∈ {"local", "remote", "none"}` (`"none"` — гео-фильтр не был задан, группы нет, тот же смысл,
что старое поведение). Курсор без группы (старый двухчастный формат, курсоры, выданные ДО этой
ветки) и курсор, чья группа не совпадает с активной группировкой текущего вызова (рассинхронизация
параметров между страницами) — оба явно 400-ятся (`InvalidCatalogCursorError` → `ValidationError` в
`api/views.py`, путь ошибки не новый). Обратная совместимость СТАРОГО курсора сознательно НЕ
сохранена — выбран второй вариант из двух, которые предлагала постановка задачи («сохрани
совместимость ИЛИ явно 400-ь»): формат пагинации этой ветки моложе месяца (ADR-184, 11.09), в проде
нет долгоживущих сохранённых курсоров, а код без ветки обратного разбора проще и не тянет два
формата вперёд.

## Пределы задачи

- **Группировка — только когда задан хотя бы один уровень гео-фильтра.** Без него (`catalog=1`,
  «весь мир, без фильтра») `geo_match=null` у всех, порядок — прежний `-created_at, -id`: группировать
  действительно нечего, «местнее» самого широкого запроса не бывает.
- **`region_name` у города (`apps.geo.api.serializers.CitySerializer`, ветка `feat/geo-city-region`,
  ещё не в `main` на момент этой записи)** — того же происхождения решение владельца 18.09, но другая
  задача: фронту нужно готовое имя региона, чтобы подставлять его по введённому городу в каскадном
  гео-пикере (не трогает ни самоисключение, ни `geo_match` — упомянуто здесь только чтобы не потерять
  связь между двумя решениями одной сессии).
- **Бизнес-профили без `owner_user` (`owner_entity`, представитель чужого юрлица) исключением
  зрителя не затронуты** — уже описанное ограничение каталога (ADR-184 «Пределы задачи»), не новое.
- **Фронт (группировка «В выбранном месте» / «Работают удалённо» как отдельные заголовки списка) —
  не в этой ветке.** API отдаёт готовый порядок и `geo_match` на элементе — фронт кладёт разделитель
  ровно там, где `geo_match` переходит с `"local"` на `"remote"`, не пересчитывая покрытие сам.

## Прогон

Окружение сессии: Docker/PostgreSQL/Redis не подняты — `pytest` падает на фикстурах ДО первого
теста (`redis.exceptions.ConnectionError: ... connecting to localhost:6379`), а не на самих
тестах. `ruff check`, `ruff format --check`, `mypy --strict`, `lint-imports` — прогнаны и чисты.
Тесты требуют прогона на следующей сессии с поднятым стендом (`backend/apps/dashboards
apps/profiles`, флок `/tmp/porukam-pytest.lock` — общая тестовая БД).

## Последствия

- `apps.profiles.selectors`: новая `geo_filter_local_coverage_q`; `geo_filter_coverage_q` и её
  докстринг перефразированы под общий кирпич `_geo_local_coverage_q`/`_resolve_geo_coverage_target`
  без изменения внешнего поведения (тот же результат на тех же входах).
- `apps.dashboards.selectors.get_search_catalog` — новый ОБЯЗАТЕЛЬНЫЙ параметр `viewer`: любой
  внешний вызывающий этой функции (сейчас только `apps.dashboards.api.views.SearchView`) обязан его
  передать — сознательно без default, чтобы забыть было нельзя.
- `apps.dashboards.api`: `CatalogItemSerializer` получил `geo_match`; формат `catalog.next_cursor`
  сменился с двухчастного на трёхчастный — старые сохранённые курсоры (если у кого-то остались
  открытые вкладки с момента до этой ветки) 400-ятся, что для пагинации каталога, живущего секунды
  просмотра, не проблема.

# ADR-079. Локализация фронта: JSON-пакеты, EN-канон, RTL-фундамент, переключатель языка

**Статус:** принято
**Дата:** 2026-08-10
**Контекст этапа:** DEV-16 (`docs/tasks/DEV-16_локализация-фронта.md`) + DEV-16a
(`docs/tasks/DEV-16a_переключатель-языка_1.md`), ветка `feat/web-l10n`.

## Контекст

До этой ветки `packages/i18n` хранил два плоских TS-файла (`ru.ts` ~1400 строк,
`en.ts` ~350 строк) с `fallbackLng: 'ru'`; `ru.ts` фактически был единственным
полным словарём (наследие RU-первого MVP), `en.ts` покрывал только GLOBAL-вход/
онбординг/DEV-10/DEV-14/DEV-15 (более поздние EN-first срезы). Переключателя
языка не было вовсе — `useForceLocale('en')` жёстко держал экраны Google-входа
на английском, весь остальной рантайм был неявно RU.

DEV-16 требует: канонический язык — EN, формат словарей — JSON-пакеты по
неймспейсам (совместимо с внешним конвейером, который поставляет готовые
переводы файлами), RTL-фундамент без включения RTL-языков, локаль-осознанный
`Intl`, лint «нет строк вне i18n». DEV-16a поверх этого — компонент
`LanguageSwitcher` с тремя вариантами триггера и авто/ручным выбором языка
для гостя и залогиненного пользователя.

## Решения

### 1. JSON-пакеты по неймспейсам, EN — канонический фолбэк

`packages/i18n/src/locales/<code>/<namespace>.json` — 21 неймспейс на язык
(`common`, `auth`, `nav`, `contract`, `contractNew`, … + новый `locale`
для самого переключателя). `locales/<code>/index.ts` статически импортирует
все JSON-файлы неймспейса и собирает объект — **не** `import.meta.glob`
(Vite-специфика, недоступна в `tsc --noEmit` типчеке пакета `i18n`, который
гоняется без Vite). `createI18n()` — `fallbackLng: 'en'` (было `'ru'`);
рантайм-язык по умолчанию остаётся `ru` (`createI18n('ru')` в
`web/src/app/providers.tsx`) — это **независимая** настройка от того, что
является фолбэком для недостающих ключей.

EN-пакет доведён до 100% паритета ключей с RU (переведены `contract`,
`contractNew`, `contracts`, `dashboard`, `acceptance`, `archive`, `stage`,
`reputation`, `signing`, `payment`, остаток `profile`/`nav`/`actor`/`shell`/
`segment`/`emptySection`) — единственное осознанное исключение: `onboarding`
(GLOBAL-вход/онбординг, `useForceLocale('en')`, экраны ПОСЛЕ Google-логина) —
англо-only по дизайну ГВ.2/ADR-071, у него никогда не было RU-аналога, и он
вне скоупа DEV-16a (не входит в 3 точки монтирования переключателя).

Побочно найден и исправлен реальный разрыв: `auth`-неймспейс GLOBAL-flow
(`welcomeTitle`, `googleButton`, `inviteBanner*`, `cookieBanner*`, `callback*`,
`mock*` — 31 ключ) тоже существовал только в EN — эти экраны раньше были
принудительно на `en`, RU-перевод никому не был нужен. С добавлением
переключателя (§4 ниже) на `WelcomePage` это стало бы тихо сломанной фичей
(выбор «Русский» ничего не менял бы — фолбэк молча отдавал бы EN-текст).
Добавлен полный RU-перевод — паритет ru↔en 100% подтверждён скриптом.

### 2. RTL-фундамент без включения RTL-языков

Логические CSS-свойства везде, где раньше были физические (`margin/padding/
border-left/right` → `*-inline-start/end`, `left/right` → `inset-inline-*`,
`text-align: left/right` → `start/end`) — 45 файлов, ~78 деклараций.
`useHtmlLangDir()` (`@porukam/i18n`) держит `<html lang>`/`<html dir>` в
синхроне с `i18n.language`, смонтирован один раз в `AppProviders`. Список
RTL-языков (`ar`, `fa`, `he`, `ur`, `dv`) — статический (`dir.ts`), не зависит
от `/v1/locales` (гостю нужен `dir` до первой загрузки каталога). `Icon`
получил `directional`-проп + CSS auto-mirror (`[dir='rtl'] .directional`) —
применено ко всем текущим употреблениям иконки `back`/шеврона. `LtrText` —
`dir="ltr"` + `unicode-bidi: isolate` для хешей/кодов/хендлов (применено
к `integrity_hash` на карточке договора и `handle` в `PassportHeader` как
образец паттерна — не разнесено по всем местам, где мог бы пригодиться).

Сами RTL-языки **не включены**: в моке `/v1/locales` у `ar`/`fa`/`he`/`ur`
стоит `enabled: false` — видны в списке (тест «отключённая локаль» заодно
покрывает и этот сценарий), выбор недоступен. Включение — отдельный
маленький PR волны B3 (как и предписано DEV-16 §6).

### 3. `useFormatters()` — единственная точка Intl-форматирования

`packages/core/src/format.ts` уже принимал `locale` параметром (с дефолтом
`ru-RU`) — не хватало реального прокидывания активного языка. `formatFileSize`/
`formatCountdown` переписаны на `Intl.NumberFormat({style:'unit'})` вместо
хардкоженных строк-единиц (`Б/КБ/МБ/ГБ`, `дн/ч/мин`) — локализуются через
`Intl`, не через новый набор i18n-ключей (меньше площадь охвата, надёжнее).
`web/src/shared/formatters.ts` — `useFormatters()`, хук-обёртка, привязывающая
все форматтеры `@porukam/core` к `i18n.language`; 12 страниц, звавших
форматтеры напрямую из `@porukam/core`, переведены на хук (список — в истории
коммитов).

### 4. Переключатель языка: 1 компонент, 3 варианта, JS-ветвление mobile/desktop

`LanguageSwitcher` (`chip`/`globe`/`row`) открывает `LocaleList` (поиск +
секции + строки). **Важное отклонение от паттерна `Sheet`/`ActionMenu`**
(«тот же DOM, разница только в CSS-брейкпоинте»): для `Sheet` это работает,
потому что там ОДИН элемент, стилизуемый по-разному. Для переключателя
mobile (`Sheet`-модалка с оверлеем) и desktop (небольшой anchored dropdown
без оверлея) — структурно разные деревья; рендерить оба одновременно и
прятать один через CSS означало бы **дублирование** `role="option"` в DOM
при открытой панели — ломает `getByRole` в тестах и создаёт две
фокус-ловушки разом. Решение: `useIsDesktop()` — `matchMedia('(min-width:
640px)')` (тот же брейкпоинт, что у `Sheet`) — рендерится **только** нужный
вариант, JS решает, не CSS. Прецедент для JS-ветвления по `matchMedia` в
проекте уже был (`web/src/features/pwa/useInstall.ts`, `display-mode:
standalone`) — не новый приём для кодовой базы, просто впервые применён
внутри `packages/ui`.

`row`-вариант переиспользует `SettingRow control="link"` (не новая вёрстка).
Данные — `GET /v1/locales` (мок, 29 языков, `es`/`de`/… `quality:'machine'`
для демонстрации beta-бейджа, `bn`/`ar`/`fa`/`he`/`ur` — `enabled:false`).

### 5. Разрешение языка: разово у корня, не в каждой точке монтирования

`useLocaleResolution()` смонтирован один раз в `AppProviders` (не в каждом
`LanguageSwitcher`) — фолбэк отключённой локали должен сработать даже на
экране, где самого переключателя не видно. Приоритет: залогинен → `me.locale`;
гость → `useGuestLocaleStore` (sessionStorage, не localStorage — выбор гостя
на сессию, не навсегда); ни то ни другое → `detectGuestLocale(navigator.
language, enabledCodes)` (чистая функция, юнит-тестируема отдельно от React).
Отключённый/неизвестный код → откат на `en` + `Toast` («{Язык} временно
недоступен») на 4 секунды. `usePickLocale()` — гость → сессия, залогинен →
`PATCH /users/me { locale }` (тот же паттерн, что остальной профиль).

**Известное ограничение (не регрессия, честно задокументировано):** выбор
гостя, сделанный ДО Google-логина (на `WelcomePage`), не переносится
автоматически в `me.locale` после завершения GLOBAL-онбординга — тот
проходит с принудительным `en` (`useForceLocale`, ConsentsPage/
ProfileStepPage, вне скоупа DEV-16a), и `useLocaleResolution` для свежего
профиля без `locale` заново запускает автоопределение по `navigator.
language`. Перенос гостевого выбора в профиль при регистрации — отдельная
доработка онбординг-флоу, не часть DEV-16a.

### 6. `WelcomePage`: `useForceLocale('en')` снят

DEV-16a §6 явно ставит chip-переключатель на `WelcomePage` («над кнопкой
Google») — жёсткий форс на `en` для всего экрана прямо противоречил бы
самой возможности переключить язык там же. Убран для этого экрана;
`useLocaleResolution` (см. §5) берёт на себя разрешение языка для гостя
единообразно. `ConsentsPage`/`ProfileStepPage` (после Google-логина) этот
хук сохранили — не входят в 3 явные точки монтирования DEV-16a, трогать не
стали (см. ограничение в §5).

### 7. `manifest.webmanifest`: `lang` НЕ тронут (осознанно, задокументировано)

DEV-16 §7 — «если просто, иначе `en`, не блокер». Манифест — один статический
файл, собираемый `vite-plugin-pwa` на этапе `build`; настоящий per-пользователь
`lang` потребовал бы нескольких файлов манифеста, переключаемых JS до
`beforeinstallprompt`, либо серверной генерации — не «просто». `name`/
`short_name`/`description` в том же манифесте тоже статические и на русском —
менять один `lang` на `en` без перевода остального сделало бы несоответствие
только хуже. Оставлено как есть, решение — в комментарии рядом с кодом
(`web/vite.config.ts`).

## Последствия

- Реальная переводческая волна на 20+ языков (кроме EN/RU + частично ES для
  демонстрации beta) — НЕ в этой ветке: список в `/v1/locales` содержит
  метаданные языков для UI переключателя (поиск/сортировка/бейджи), но у
  большинства из них нет JSON-пакета в `packages/i18n` — выбор такого языка
  корректно упадёт в EN-фолбэк по каждому ключу (ровно то поведение, которое
  и тестируется на примере `es`). Наполнение реальных переводов — конвейер
  внешний конвейер, отдельная волна.
- `LtrText`/`Icon.directional` — механизм есть, применён точечно (по одному
  образцу каждый); систематическое применение по всем хешам/кодам/шевронам
  приложения — при включении RTL (волна B3), не сейчас.
- `packages/ui` впервые получил встроенную (не в `web/src`) зависимость от
  `window.matchMedia` внутри компонента (`LanguageSwitcher`) — прецедент для
  будущих responsive-by-JS компонентов дизайн-системы.

# ADR-116: Запрос на сотрудничество — вход в переговоры через минимальный черновик

Дата: 2026-08-24. Статус: принято (решение продукта, обсуждение 2026-08-24).

## Контекст

Пользователь хочет «начать чат» с человеком (по контактам или @хендлу) — но переписка
платформы намеренно привязана к договору (ADR-112: доказательная база сделки; свободный
мессенджер — не наш продукт, вариант отвергнут владельцем продукта: «это не чат, это
переговоры по сделке»). При этом реальное общение начинается не с заполненного договора,
а с вопроса — нужен лёгкий вход «предложить сотрудничество», как отклик.

ADR-112 в «Последствиях» предвидел ровно этот стык: «открытие чата из карточки контрагента
без общего договора — пока нечего открывать; UX-вход появится после первого черновика».

## Решение

«Запрос на сотрудничество» — UX-обёртка над существующей моделью, БЕЗ новых сущностей:

1. Кнопка «Начать переговоры» на `/chat` → страница `/chat/new`: мини-форма
   «кому (контакты/@хендл) + моя роль + тип работы (клиентское дерево ADR-094) +
   сообщение по предзаготовленному шаблону».
2. Под капотом: `POST /v1/contracts` с минимальным телом (`my_role`, `client_option` |
   `contract_type_code`, `counterparty_handle`, `title` = имя выбранного типа) — черновик
   без суммы/этапов валиден по построению (суммы требует только send, этапы — freeze);
   затем `POST /contracts/{id}/messages` с текстом запроса; переход в тред.
3. Контрагент — полноценная сторона черновика с момента создания (ADR-088): видит договор
   в списке, тред в `/messages/threads` (после первого сообщения) и получает уведомление
   `message.received` (анти-шторм ADR-112). Инициатору контрагент попадает в контакты
   (ADR-106, `contract.drafted`).
4. Сложилось → тот же черновик дорабатывается в мастере (`?draft=<id>`, ADR-104) и
   подписывается — переговоры «с вопроса» бесшовно перетекают в договор, переписка с
   первого сообщения в доказательной базе. Не сложилось → черновик удаляется/остаётся
   висеть без последствий (юр-значимости у черновика нет).

Тип работы в форме ОБЯЗАТЕЛЕН: инвариант создания черновика (create требует тип) не
ослабляем; выбранный тип даёт и название черновика (иначе тред в списке диалогов был бы
безымянным), и шаблон текста в будущем.

## Альтернативы

- Прямые диалоги без договора (новая модель треда) — отвергнуто: пересмотр ADR-112,
  неясный юрстатус переписки вне сделки, дрейф продукта в мессенджер.
- Новая сущность CollaborationRequest с конверсией в черновик при акцепте — отложено:
  дублирует черновик; вернуться, если понадобятся отклонение с причиной/квоты анти-спама.

## Последствия

- Бэкенд не меняется вообще (проверено: чат работает на черновиках и покрыт тестами,
  статусных гейтов в messaging нет).
- Отдельный тип уведомления «запрос на сотрудничество» (вместо message.received) —
  осознанно отложен: 5 точек регистрации + bump pack_version во всех 29 паках; сделать
  при первой жалобе на непонятность уведомления.
- Тот же механизм станет «откликом» для объединений и портфолио (задача «Объединения v2»).
- Анти-спам (лимиты запросов незнакомым людям) — отслеживать после запуска; сейчас
  косвенно ограничен идемпотентностью create и тем, что запрос создаёт видимый черновик.

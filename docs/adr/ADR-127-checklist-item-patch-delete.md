# ADR-127. `PATCH`/`DELETE /checklist-items/{id}` — правка и удаление пункта чек-листа до подписания

Дата: 2026-08-25. Статус: принято.
Ветки: `feat/milestones-checklist-item-delete` (бэкенд, этот ADR),
`feat/web-wizard-checklist-edit` (мастер создания договора).

## Контекст

Отсмотр 2026-08-25, дословно: «создаю договор аренды: после создания одного
критерия, другие уже не пропускает. не сохраняет. Мы не ограничиваем
количество критериев».

Разбор показал, что лимита на бэкенде нет и не было: `ChecklistItem`
(`apps/milestones/models.py`) не имеет ни уникальности по
`(milestone, order)`/`(milestone, description)`, ни CHECK-констрейнтов, ни
счётчика; `create_checklist_item` проверяет только сторону договора,
редактируемость (`_assert_editable`: `draft`/`under_review`) и «этап —
лист». Несколько POST подряд, в том числе с одинаковым `order` (мастер шлёт
`default=0`), создают все пункты.

Отвергал второй критерий мастер. В `web/src/pages/contract-new/
StagesStepPage.tsx` шаг «Этапы» сохраняется одной точкой по «Далее»:

- пункты чек-листа отправляются ТОЛЬКО в ветке `isLocalId(s.id)`, то есть
  для этапа, которого ещё нет на сервере; для уже созданного этапа
  выполняется лишь `PATCH /milestones/{id}` (название/сумма/order), а
  чек-лист не досылается — добавленный критерий молча теряется;
- поэтому редактор чек-листа для созданного этапа и прятался:
  `isStageChecklistEditable={(s) => isLocalId(s.id)}` с комментарием
  «PATCH/DELETE пунктов нет» (ADR-088 Фаза 2).

Сценарий пользователя: критерий, добавленный до первого сохранения этапа,
уезжает на сервер; всё, что добавляется после возврата на шаг, — нет.
Без правки и удаления пункта по его id мастер не может ни досылать
изменения, ни убирать ошибочный критерий (сейчас единственный способ —
удалить весь этап, ADR-101).

## Решение

Пункт чек-листа получает собственные endpoint'ы по плоскому пути — как
`/milestones/{id}` (ADR-101), пункт адресуется своим id, а не парой
milestone+индекс:

- `PATCH /checklist-items/{id}` → `200 ChecklistItem`, сервис
  `apps.milestones.services.patch_checklist_item`. Все поля опциональны,
  отсутствующее (`None`) — «не менять» (приём `patch_milestone`).
  Правка `order` — то, чем фронт перенумеровывает оставшиеся пункты после
  удаления.
- `DELETE /checklist-items/{id}` → `204`, сервис `delete_checklist_item`.

Общее для обоих (симметрично `create_checklist_item` и `delete_milestone`):

- зона редактируемости — `_assert_editable` (`draft`/`under_review`), после
  заморозки версии `409 contract_immutable`; изменения подписанного договора
  — только через Amendment;
- любая сторона договора, чужой — `403`, несуществующий id — `404`;
- мягкого удаления нет: до подписания пункт не юрзначим, снепшотов
  `ContractVersion` на него ещё нет (CLAUDE.md);
- события в outbox — `milestone.checklist_item_updated` (с перечнем
  изменённых полей) и `milestone.checklist_item_removed`, симметрично
  существующему `milestone.checklist_item_added`; PATCH без фактических
  изменений события не публикует.

Лимит на количество пунктов не вводится (прямое требование отсмотра);
миграция не нужна — снимать нечего.

## Последствия

- tech-spec.md §8.5: к строке чек-листа добавляются `PATCH`/`DELETE
  /checklist-items/{id}` — уточнение таблицы этим ADR.
- Фронту (`feat/web-wizard-checklist-edit`) снимается ограничение
  `isStageChecklistEditable`: чек-лист правится и у созданного этапа,
  диффом «добавленные → POST, изменённые → PATCH, убранные → DELETE».
- Тесты: сервис (правка полей и событие, PATCH без изменений — без
  события, контрагент при `under_review`, чужой, после подписания — для
  PATCH и DELETE) и API (пять пунктов подряд, удаление, правка; репродукция
  отсмотра на договоре аренды: три пункта с одинаковым `order`; удаление с
  последующей перенумерацией; `409` после подписания; `403`/`404`).

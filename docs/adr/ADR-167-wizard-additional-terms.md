# ADR-167: «Дополнительные условия» — ручной ввод в мастере, тот же список `additional_terms`

**Статус:** Accepted
**Дата:** 2026-09-05
**Решение принято:** владелец продукта (05.09): в мастере создания договора нет ни одного
свободного текстового поля — «добавить поле „Дополнительные условия“ в мастер».
**Связанные:** репо-ADR-123 (правки v2: `item_ref = "other"` → `Contract.additional_terms`),
репо-ADR-157 (структурные `item_ref` протокола разногласий), репо-ADR-088 (реальный контур
сделки, фазы мастера), репо-ADR-139 (доказательный пакет: `index.html` для человека)
**Область:** `apps.contracts` (черновик, snapshot заморозки), `apps.archive` (`index.html`),
фронтенд (мастер договора, экран подписания, карточка)

---

## Контекст

Типы договоров в мастере — это структурные формы (`apps.contracts.forms`): каждое поле
описано схемой, произвольного текста в них нет по замыслу. До сих пор единственные два
места, где стороны могли написать своё условие своими словами:

1. **протокол разногласий** — правка с `item_ref = "other"` (ADR-123); принятая правка
   дописывает текст в `Contract.additional_terms`. Доступна только на `under_review`, то
   есть уже ПОСЛЕ отправки договора контрагенту;
2. **допсоглашение** (`Amendment.custom_terms`) — уже после подписания.

Инициатор, составляющий договор, не мог записать очевидное условие («ключи передаются под
расписку») до отправки: сначала отправь, потом предложи правку себе же самому — и жди, пока
вторая сторона её примет. Владелец 05.09 потребовал закрыть эту дыру в мастере.

## Решение

### 1. Тот же список `Contract.additional_terms`, а не второе поле

Ручной ввод пишет в **уже существующий** `Contract.additional_terms` (JSONField, список
строк, ADR-123, миграция `0008`). Второе поле («условия от инициатора» отдельно от «условий
из протокола») означало бы склейку двух списков при заморозке, в canonical snapshot, в
архиве и в тексте договора — с вопросом «в каком порядке», на который нет содержательного
ответа: для читателя договора это один и тот же раздел. Миграции нет.

### 2. Ручная правка — только на черновике, полной заменой списка

`services.patch_draft(..., additional_terms=[...])` под тем же гейтом, что и `form_data`:
`negotiation_status = draft`, иначе `DraftNotEditableError` → `409 draft_not_editable`.
Мастер шлёт список **целиком** (как `form_data`), а не дописывает — иначе удалить пункт из
мастера было бы нечем. `create_draft` тоже принимает список (симметрия с `form_data`).

Два пути записи в один список пересечься не могут и потому не конфликтуют:

| Состояние договора | Ручной PATCH | Принятая правка «Другое» |
|---|---|---|
| `draft` | заменяет список целиком | недоступна (нет протокола разногласий) |
| `under_review` | `409` | **дописывает в конец** (`_apply_revision_value`) |
| подписан | `409` | недоступна — только допсоглашение |

Пункты, введённые вручную, остаются на месте: `accept_revision` делает
`[*contract.additional_terms, значение]`.

### 3. Валидация — в `services.clean_additional_terms`, ошибки по полям

Список строк; каждый пункт непуст после `strip`, не длиннее `ADDITIONAL_TERM_MAX_LENGTH`
(2000 символов), пунктов не больше `ADDITIONAL_TERMS_MAX_ITEMS` (20).
`AdditionalTermsInvalidError` несёт список `{field, code, message}` — тот же формат, что у
`forms.FormValidationError` и `RevisionValueInvalidError`; `field` указывает на конкретный
пункт (`additional_terms.3`), чтобы форма мастера подсветила нужное поле. HTTP —
`400 additional_terms_invalid` (`context.errors`).

Пределы **не** применяются к правке «Другое»: принятая сторонами правка — согласованное
условие договора, отказать в её применении из-за счётчика пунктов нельзя, это сломало бы
FSM протокола разногласий уже после `accept`. Практический потолок ручного ввода (20)
существует ради формы, а не ради права.

### 4. Текст договора и архив

`additional_terms` уже входили в canonical snapshot заморозки (`_build_snapshot`, под
`integrity_hash`) и в запись доказательного пакета (`apps.archive.selectors`,
`manifest.json`) — ручной ввод не меняет ни того, ни другого. Пробел был в `index.html`
пакета — «оглавлении для человека»: секции «Дополнительные условия» там не было, то есть в
человекочитаемом слое пункты не показывались вовсе. Добавлена (только если список непуст).

## Последствия

- Инициатор может записать своё условие до отправки; протокол разногласий остаётся
  инструментом ВТОРОЙ стороны, а не обходным путём для первой.
- Условия под подписью: они в snapshot, значит в `integrity_hash` — после подписания
  меняются только допсоглашением. Подсказка в мастере говорит об этом прямо.
- Свободный текст в юридически значимом документе пишет пользователь; платформа его не
  проверяет по существу (как и `Amendment.custom_terms`). Экранирование при выводе — на
  всех рендерах (`escape` в `index.html`, React — по умолчанию).
- Ограничение «20 пунктов» — только для ручного ввода. Договор, где протокол разногласий
  добавил больше, остаётся валидным; мастер такой список показать не сможет, но он и не
  открывается после отправки.

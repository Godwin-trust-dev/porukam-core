# ADR-066. CD: один образ приложения, core/celery как имена в реестре

**Статус:** принято
**Дата:** 2026-08-01
**Контекст этапа:** ЭФ.5 (опционально, `docs/tasks/fundament.md`) — сквозной фундамент,
завершающая (опциональная) часть цепочки ЭФ.1–ЭФ.5; готовим рельс сборки/публикации образов,
деплоя ещё нет.

## Контекст

`docs/tasks/fundament.md` ЭФ.5 требует: GitHub Actions workflow на merge в `main`
(self-hosted раннер, `служебная ВМ/`), сборка образов **core/celery**, тег по короткому sha
+ `latest`, push в Yandex Container Registry по ключу сервисного аккаунта. Реального
Container Registry в РФ-облаке ещё нет (`docs/plan.md` описывает его как будущий шаг), как и
prod-сервера — этим займётся ЭФ.7 (`docs/tasks/fundament-2.md`).

`core` (Django/DRF API) и `celery` (worker/beat) в деве запускаются как два процесса
(`make run` / `celery -A config worker ...`, `infra/compose/docker-compose.local.yml`) из
ОДНОГО и того же кода `backend/` — общий `pyproject.toml`/`uv.lock`, общие Django-приложения,
разница только в команде запуска.

## Решение

- **Один Dockerfile (`infra/docker/app/Dockerfile`), один собранный образ**, а не два
  отдельных `core/Dockerfile` + `celery/Dockerfile`. Роль выбирается командой контейнера
  (`CMD`/`command:` у оркестратора), не образом — дублировать сборочные стадии (multi-stage
  `uv sync`) ради идентичного набора зависимостей было бы избыточной абстракцией без причины
  (CLAUDE.md: не проектировать под гипотетические различия, которых нет).
- **CI пушит этот образ под ДВУМЯ именами репозитория в реестре** — `.../core:<tag>` и
  `.../celery:<tag>` — сохраняя формулировку fundament.md ЭФ.5 буквально («образы core/celery»)
  и оставляя их отдельными деплой-юнитами на уровне реестра/версионирования
  (dev-setup.md §4.1: «core, evidence-ingest, audit-vault, celery-worker/beat — чтобы потом
  масштабировать раздельно без переписывания») — раздельность нужна на уровне деплоя
  (масштабирование, откат), не на уровне содержимого образа.
- **Тег — короткий sha (12 символов) + `latest`**, оба на каждое имя (4 тега на push).
- **Триггер — `push` на `main`** с `paths` фильтром (`backend/**`,
  `infra/docker/app/Dockerfile`, сам workflow) — не пересобирать образ на PR в чисто
  фронтенд/докс ветках, которые тоже мержатся в `main`.
- **Раннер — `[self-hosted, Linux, X64, <метка служебной ВМ>]`**, метки в точности как у
  `служебная ВМ`. Обычный `actions/checkout@v4` — без вендоринга: раннер
  и так ходит на github.com за задачами (dev-setup.md §4.1 п.1), вендоринг экшенов — эскалация
  по измеримому триггеру (§4.1 п.5), не дефолт с первого коммита.
- **`docker build`/`docker push` напрямую, БЕЗ buildx/`docker/build-push-action`.**
  `служебная ВМ` ставит только пакет `docker.io` + `docker-compose-v2` —
  плагин `docker-buildx` отдельно не устанавливается, полагаться на него в workflow означало
  бы скрытую зависимость от состояния раннера, которую этот PR не проверяет вживую (раннер
  ещё не поднят на реальной ВМ на момент подготовки рельса). Классический билдер поддерживает
  multi-stage Dockerfile без buildx.
- **`FROM ${BASE_IMAGE}` с ARG по умолчанию `cr.yandex/REPLACE_WITH_REGISTRY_ID/python:3.12-slim`**
  — буквально следует правилу CLAUDE.md «FROM только из собственного реестра», хотя реестр
  ещё не создан и плейсхолдер `REPLACE_WITH_REGISTRY_ID` нерабочий: `dev-setup.md` §4.1 п.2
  сам описывает синхронизацию базовых образов как отдельную ручную операцию, не блокирующую
  подготовку Dockerfile. До неё сборка — только явным `--build-arg
  BASE_IMAGE=python:3.12-slim` (задокументировано в `infra/docker/README.md`), тот же приём
  bootstrap-исключения, что уже применён в `служебная ВМ/Dockerfile` (тоже
  `FROM python:3.12-slim` напрямую, до появления реестра/кеша).
- **CMD образа — `manage.py runserver`** (роль core по умолчанию), не gunicorn/uvicorn:
  прод-сервер — зависимость и решение ЭФ.7 (`docs/tasks/fundament-2.md`, «core
  (gunicorn/uvicorn)»), добавлять её здесь означало бы тянуть чужую задачу в опциональный
  ЭФ.5. `DJANGO_SETTINGS_MODULE` в образе явно `config.settings.production` (не дефолт
  `manage.py` → `local`, который включает `DEBUG=True`).

## Альтернативы

- **Два отдельных Dockerfile (`core/`, `celery/`).** Отклонено — идентичные стадии сборки
  зависимостей, различался бы только последний `CMD`; дублирование без содержательной причины.
- **`docker/build-push-action` + `setup-buildx-action`.** Отклонено на этом шаге — добавляет
  зависимость от `docker-buildx` на раннере, которую негде проверить вживую в рамках этого PR
  (служебная ВМ разворачивается по `служебная ВМ` отдельно от кода). Если
  позже понадобится multi-arch/кеш слоёв — переход на buildx стоит одной правки workflow,
  ничего в Dockerfile под это не заточено специально против.
- **Дождаться реального Container Registry перед тем, как писать workflow.** Отклонено — ЭФ.5
  прямо просит «готовим рельс», секреты (`YC_REGISTRY_ID`, `YC_SA_KEY_JSON`) — точка
  инъекции, workflow бездействует (падает на логине) до их появления, что нормально для
  незадеплоенного рельса.

## Последствия

- ЭФ.7 (`docs/tasks/fundament-2.md`) подключает `docker-compose.prod.yml`, который тянет
  `cr.yandex/.../core` и `cr.yandex/.../celery` (тот же образ, разные `command:`) — правка
  локализована в новом compose-файле, `infra/docker/app/Dockerfile` не меняется под это.
- Реальный `BASE_IMAGE` и секреты (`YC_REGISTRY_ID`, `YC_SA_KEY_JSON`) — ручной шаг владельца
  после создания Container Registry и сервисного аккаунта (`docs/plan.md`), задокументирован
  в `infra/docker/README.md` и в комментариях самого workflow.
- Если понадобится multi-arch (arm64) сборка — потребуется buildx на раннере; на этот случай
  Dockerfile уже совместим (multi-stage без специфики классического билдера), правка —
  только в workflow.

## Дополнение 30.10.2026: адрес реестра изменён (ADR-197 (внутренний ADR, не публикуется))

Реестр переехал с `cr.yandex/<registry-id>` в `ghcr.io/godwin-trust-dev` — разбор и цифры
в ADR-197 (внутренний ADR, не публикуется), порядок действий в
`docs/ops/registry-migration-ghcr.md`. Всё остальное в этом ADR остаётся в силе: один
Dockerfile и один образ под двумя именами (`core`/`celery`), теги `<sha12>` + `build-N` +
`latest`, триггер и `paths`-фильтры, сборка классическим `docker build` без buildx.

Техническая разница: адрес реестра больше не вшит в workflow, а читается из переменной
репозитория `vars.IMAGE_REGISTRY` (не задана → прежнее поведение с `cr.yandex`), а способ
логина выбирается по адресу — `ghcr.io` встроенным `GITHUB_TOKEN`, `cr.yandex` ключом
сервисного аккаунта. Это сделано ради отката: переезд и возврат — изменение одной переменной.

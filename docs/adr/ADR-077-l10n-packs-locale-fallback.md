# ADR-077. Инфраструктура языковых пакетов: Locale, LocalePack, фолбэк locale→en

**Статус:** принято
**Дата:** 2026-08-09
**Контекст этапа:** Л.2 (`feat/l10n-packs`, docs/tasks/l10n-wave.md)

## Контекст

Доку 32 (язык договора: EN-канон + два рендера) и решение владельца 08.08
(«локализация — сейчас, не по спросу») требуют механизма, которым внешний конвейер
может поставлять статические переводы для ~30 языков без единого runtime-
вызова внешнего переводческого API. ГВ.5 (ADR-075, `common/i18n.py`) уже
даёт фолбэк-цепочку, но жёстко зашитую на пару `ru`/`en`
(`SUPPORTED_LOCALES`) — третий язык добавить было некуда: ни справочника
языков, ни хранилища переведённого контента.

К моменту начала Л.2 контент для волн A/B1/B2 (`docs/tasks/l10n-wave.md`
§«Конвейер контент-пакетов») уже сгенерирован и лежит в `l10n/packs/*.json`
(24 языка + `en`) — код опережает план на ~3 недели (постановка,
«Контекст»). Формат этих файлов — по факту, а не по иллюстративному JSON из
самой постановки: реальные пакеты несут `catalog.client_tree` вместо
`checklists`/`materials`, namespace `ui` (строки фронта, тот же конвейер,
один файл на язык) и не несут `clauses` вообще (переводы `ClauseTemplate` —
Л.1, отдельная ветка, ещё не начата). Схема ниже и `l10n/README.md`
зафиксированы под этот реальный формат, не под черновой пример постановки.

## Решение

- **`apps.l10n`** — новое приложение, нижний слой import-linter (рядом с
  `apps.catalog`/`apps.jurisdictions` в контракте «ни от кого не зависят»):
  ноль импортов из других `apps.*`, чтобы быть безопасной универсальной
  зависимостью для `common/i18n.py` и, по мере подключения, любого другого
  приложения — тем же приёмом, что `apps.jurisdictions` для резолвера
  контура.
- **`Locale`** (code BCP-47 PK, name, rtl, enabled, quality:
  canonical|reviewed|machine) — справочник языков. Сид (миграция 0002):
  `en` (canonical), `ru` (reviewed) — остальные языки создаёт/обновляет
  `services.import_pack` из шапки файла. `enabled` — ручной рубильник:
  импорт пакета выставляет `True` только при ПЕРВОМ создании строки,
  повторный импорт его не трогает — включение/выключение языка (например,
  задержка волны B3 до готовности RTL-вёрстки фронта) не должно откатываться
  случайным реимпортом контента.
- **`LocalePack`** — одна строка на `Locale`: `pack_version` + sha256
  `checksum` содержимого (без `pack_version` — версия сверяется отдельно) +
  сырой `content` (JSONField, всё дерево пакета целиком). Хранение целиком,
  а не разложенным по строкам «namespace/key/value»: пакет читается по
  locale целиком (`selectors.get_pack_text` и типизированные обёртки), а
  частичность/фолбэк — забота селектора, не схемы таблицы. История версий
  не хранится — версионирование живёт в `pack_version` файла, не в БД
  (осознанное упрощение: откат на старую версию — новый пакет со следующим
  номером и старым содержимым, не операция над БД).
- **`services.import_pack`** — идемпотентный (тот же `pack_version` + тот
  же `checksum` → no-op), версионированный (`pack_version` меньше текущего
  → `StalePackError`; тот же `pack_version`, другой `checksum` →
  `PackVersionConflictError` — версия не может значить два разных
  содержимых), частичный пакет валиден (validator требует только шапку;
  любой namespace может отсутствовать целиком). Валидация — ДО записи в БД,
  одной транзакцией на файл. Неизвестный top-level ключ (не namespace из
  фиксированного набора и не `_`-комментарий) — пакет отклоняется целиком:
  это дешёвая защита от опечатки в названии namespace, которая иначе тихо
  потерялась бы (значение просто никогда бы не читалось никаким селектором).
- **Валидация без `jsonschema`** (пакета нет в зависимостях проекта) —
  ручные проверки в `services._validate_pack_shape`, тот же уровень
  строгости, что уже был у `_parse_accept_language` («упрощённый разбор»,
  ADR-075): проверяем форму (dict/строка/bool/int), не полный JSON Schema.
- **Фолбэк-цепочка `запрошенный → en`** (`selectors._fallback_chain`) — НЕ
  до `ru`: RU-контур остаётся на своём отдельном, не тронутом этой веткой
  механизме (`name_i18n`/`body_i18n` `.get(locale, "ru")` в
  `apps.catalog`/`apps.notifications` — расширение ГВ.5 на них самих —
  следующая волна, инфраструктура готова, полный рольаут — по контент-
  пакетам). Единственное готовое в Л.2 подключение —
  `common/api/exceptions.py`: заголовок ошибки на языке запроса читает
  `apps.l10n.selectors.get_error_title` первым, при `None` — встроенный
  `ERROR_TITLES_EN`, при снова `None` — исходный (RU) `title` вызова.
- **`common/i18n.py`: `_parse_accept_language` расширен** — код языка из
  `Accept-Language` признаётся, если это встроенная `ru`/`en` ИЛИ есть
  включённый `Locale` с этим кодом (`apps.l10n.selectors.is_locale_enabled`).
  `apps.l10n` добавлен вторым (после `apps.jurisdictions`) разрешённым
  исключением из правила «`common/` не импортирует `apps.*`» — тем же
  обоснованием: нижний слой, специально спроектированный безопасной
  универсальной зависимостью.
- **`Consent.locale`** (`apps.social`, CharField по значению, НЕ FK на
  `apps.l10n.Locale`) — язык ПОКАЗАННОГО текста согласия. Не FK, потому что
  `apps.social` по контракту import-linter зависит только от
  `apps.accounts` — тот же приём, что `JurisdictionConfig.primary_locale`/
  `ClauseTemplate.country_code` (по значению, не импортом модели).
  `record_consent` теперь пишет `locale` на саму строку (раньше он только
  выбирал версию текста через `settings.CONSENT_TEXT_VERSIONS`, не
  сохраняя, каким языком фактически воспользовался). Бэкфилл исторических
  строк — `text_version="v1-en-draft"` → `locale="en"` (единственное
  EN-значение `CONSENT_TEXT_VERSIONS` на момент миграции, задублировано в
  ней как данные, не settings — тот же приём, что `jurisdictions/
  0004_seed_ru_and_global`); остальные строки остаются на дефолте `"ru"`,
  это и есть их фактический язык показа (RU-регистрация — единственный
  флоу без явного locale до этой ветки).
- **`GET /v1/locales`** (`apps.l10n.api`, `AllowAny`) — активные языки с
  `quality`, для бейджа beta на фронте ДО входа пользователя (экран выбора
  языка при регистрации).
- **Реимпорт `ru` — diff + подтверждение по каждому реальному конфликту**
  (`import_l10n_pack`, `services.diff_pack_texts`/`apply_text_overrides`).
  `ru` — единственная locale с уже ревьюленным вручную контентом; остальные
  языки — `machine`/пакет как единственный источник, там перезапись без
  вопросов ожидаема и безопасна. Диф — только по текстовым namespace'ам
  (`_TEXT_NAMESPACES`), не по шапке; вопрос задаётся только там, где текст
  был по обе стороны сравнения и отличается — для добавленного/снятого
  ключа оставить «старым» нечего, это просто строка в выводе diff. `--yes`
  — пропустить вопросы (новое побеждает), для неинтерактивных прогонов.

## Альтернативы

- **Писать переводы напрямую в существующие i18n-поля** (`NotificationTemplate.
  body_i18n`, `*.name_i18n`, будущий `ClauseTemplate`) вместо отдельного
  generic-хранилища `apps.l10n`. Отклонено: это заставило бы
  `import_l10n_pack` импортировать модели `apps.notifications`/
  `apps.catalog` напрямую — нарушение «приложения общаются через
  services.py-фасады» (CLAUDE.md) и import-linter (нижний слой не должен
  писать в верхние приложения). Generic-хранилище с типизированными
  read-обёртками в `selectors.py` даёт то же самое потребителям без этой
  связанности; цена — сериализация через JSON вместо нормальных колонок,
  приемлемая для read-редкого, write-редкого справочника.
- **Схема пакета строго по иллюстративному примеру постановки**
  (`catalog.checklists`/`catalog.materials`, `legal.tos`/`consents`/
  `disclaimer` без `translation_disclaimer`/`custom_terms_notice`/
  `no_legal_force_disclaimer`). Отклонено в пользу формата уже
  сгенerированных 24 пакетов (см. «Контекст») — фиксировать инфраструктуру
  под черновик, который реальный контент уже не использует, означало бы
  либо перегенерировать 24 файла заново, либо держать validator, который
  реальные пакеты не проходят. `catalog`/`legal` спроектированы как
  вложенные на один уровень словари БЕЗ фиксированного набора подключей —
  будущие `checklists`/`materials`/другие `legal.*` добавятся тем же
  способом, без миграции схемы.
- **`jsonschema`-валидация** вместо ручной. Отклонено: пакета нет в
  зависимостях backend/pyproject.toml, а форма пакета — плоская и
  небольшая (5 namespaces, каждый — словарь строк максимум с одним уровнем
  вложенности) — не оправдывает новую зависимость ради этого объёма правил.
- **Хранить фолбэк на `ru` вместо `en` для новых языков** (симметрично
  существующему `body_i18n.get(locale, "ru")`). Отклонено прямым текстом
  постановки (Л.2 п.4: «фолбэк-цепочка запрошенный язык → en») — EN, не RU,
  канон по доку 32; RU — язык одного конкретного контура, не канон
  платформы.

## Последствия

- `apps.notifications.selectors.render_body`/каталожные `*_i18n`-геттеры
  (их пока нет как отдельной функции — поля читаются напрямую там, где
  нужны) НЕ подключены к `apps.l10n.selectors` в этой ветке — только
  `common/api/exceptions.py`. Тексты уведомлений/каталога на языках сверх
  `ru`/`en` пока не рендерятся нигде, хотя пакеты волн A/B1/B2 уже несут
  `notifications`/`catalog` — это следующая волна работы (инфраструктура
  готова, интеграция — по потребителям), не регресс: до этой ветки таких
  текстов не было вообще ни для одного языка кроме ru/en.
- Реальный импорт волн A/B1/B2 (`l10n/packs/*.json`, кроме `en`) — не часть
  этого PR (только инфраструктура + тестовый импорт `es` в тестах). Кто и
  когда прогоняет `import_l10n_pack` по всем 24 файлам — операционный шаг
  после мёржа, по очерёдности `docs/tasks/l10n-wave.md`.
- `ur` (волна B2) несёт `rtl: true` по факту письменности, при этом не
  входит в волну B3 (`ar`/`fa`/`he`) — задача, которую постановка
  ограничивает RTL-вёрсткой фронта. Это не блокируется схемой/импортом:
  `Locale.rtl` — честное поле, фронт обязан проверять именно его, а не
  полагаться на «волна B3 = все RTL-языки» (см. `l10n/README.md` §RTL).

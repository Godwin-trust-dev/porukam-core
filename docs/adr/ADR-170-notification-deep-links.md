# ADR-170. Уведомление открывает раздел, а не «общую вкладку сделки»

**Статус:** принято (решение владельца 2026-09-07)
**Контекст:** apps.notifications (`selectors.feed_href_for`/`feed_anchor_for`,
`providers.WebPushProvider`, `providers._deal_url`), фронт `web/src/pages/ContractDetailPage.tsx`
(разбор хеша -> вкладка)
**Номер:** 170 — следующий за 169 по всем веткам. Строка добавлена в индекс README.

## Контекст

Владелец, 07.09: «у нас уведомление открывает общую вкладку сделки. и потом допустим в правку
надо искать. Сильно сложно, чтобы открывался сразу раздел, по которому пришло уведомление?»

`_feed_href` строил `/contracts/{id}` для ВСЕХ шаблонов, кроме одного:
`contract.materials_changed` получал якорь `#milestone-<id>` (ADR-156 §3). Карточка договора —
восемь вкладок (`overview | terms | stages | payments | chat | negoSign | amendments |
timeline`), и человек, пришедший по уведомлению «контрагент предложил правку», попадал на обзор
и дальше искал вкладку сам. То же и в дублирующих каналах: пуш строил `url` своей строкой в
`WebPushProvider.send`, кнопка письма — своей в `_deal_url`; три места, где «куда ведёт
уведомление» решалось независимо.

Фронт при этом уже умел два якоря — `#milestone-*` и `#amendments` (ADR-161 §1), — но бэк
второй из них не отдавал НИКОГДА: код был написан под ссылку, которой не существовало.

## Решение

### 1. Одна карта «шаблон -> цель» на все каналы

`apps/notifications/selectors.py`:

- `feed_anchor_for(template, payload) -> str` — чистая функция, якорь раздела карточки договора
  или пустая строка;
- `feed_href_for(template, contract_id, payload) -> str` — полный путь; её зовут пункт ленты
  (`_feed_item`), пуш (`WebPushProvider.send`) и кнопка письма (`_deal_url`).

Карта живёт рядом с `_FEED_TEMPLATE_TYPES` и `_FEED_TYPE_GROUP`: это одна и та же
презентационная развёртка кода шаблона (ADR-159), и расходиться им нельзя — иначе пункт ленты и
пуш об одном и том же поводе уведут в разные места.

Устройство карты — точные коды плюс префиксы семейств:

| Шаблоны | Куда |
| --- | --- |
| `negotiation.*`, `signature_requested`, `contract.signed` | `#negoSign` |
| `amendment.*`, `contract.amended` | `#amendments` |
| `milestone.*` (кроме платёжных), `milestone_*`, `evidence_received`, `contract.materials_changed` | `#milestone-<id>`, без `milestone_id` — `#stages` |
| `payment.*`, `milestone.paid`, `milestone.payment_confirmed*`, `milestone.advance_confirmed*` | `#payments` |
| `dispute.*`, `warranty*` | `/disputes/<dispute_id>`, без id — карточка |
| `message.received` | `/chat/<contract_id>` |
| `archive.ready` | `/contracts/<id>/archive` |
| `contract.completed/closed/terminated/idle_*/auto_closed`, `evidence.*`, всё остальное | карточка без якоря |

Точные коды нужны там, где семейство НЕ совпадает с разделом: подтверждения оплаты названы
`milestone.*`, а живут в «Платежах» (тот же разрыв уже зашит в `_FEED_TEMPLATE_TYPES` — у них
тип `payment`). Префиксы нужны, чтобы новый код шаблона попадал в свой раздел без правки карты.

### 2. Незнакомый шаблон — без якоря

Шаблона нет в карте -> якоря нет -> карточка целиком, как было до этой ветки. Промахнуться
разделом хуже, чем не угадать его вовсе: пункт ленты — юрканал (ADR-057), он обязан вести к
договору всегда, а «в нужное место» — по возможности.

### 3. Разногласия, чат и архив — свои страницы, а не вкладки

Вкладки «Споры» у карточки нет вовсе (`/disputes/{id}` — отдельная страница), а вкладка «Чат» —
каллаут с кнопкой «Открыть чат»: вести через неё в переписку значит просить лишний клик.
Поэтому для этих трёх семейств цель — не якорь, а путь. `dispute_id` есть в payload и споров
(`disputes.services._event_payload`), и гарантийных претензий (`warranty.services._payload`);
легаси-записи без него ведут на карточку.

### 4. Фронт: карта хеш -> вкладка

`ContractDetailPage.tsx` вместо цепочки `if` разбирает хеш общей таблицей. Вкладка, которой у
этого договора нет (`chat` без второй стороны, `amendments` до подписания), даёт обзор, а не
пустой экран; неизвестный хеш игнорируется.

## Последствия

- Якорь безвреден для клиента, который его не разбирает (старый PWA из кэша, почтовый клиент):
  браузер не найдёт цель и оставит верх страницы.
- Ссылки в УЖЕ размещённых уведомлениях меняются задним числом — `action.href` считается на
  чтении, в строке `Notification` его нет. `content_hash` и payload не трогаются, юрзначимость
  не затронута.
- Добавляя шаблон, надо дописать строку в карту якорей рядом со строкой в `_FEED_TEMPLATE_TYPES`
  — иначе новый повод молча уведёт на обзор.

## Альтернативы

- **Отдавать раздел отдельным полем пункта (`section`), а не якорем.** Честнее по слоям, но
  пуш и письмо ведут по URL, а не по полю: пришлось бы всё равно склеивать якорь, только в трёх
  местах. Якорь и есть общий язык всех трёх каналов.
- **Вести `signature_requested` на `/contracts/{id}/sign`.** Самый короткий путь к действию, но
  страница подписания — не «раздел, о котором уведомление»: она откроется и когда подписывать
  уже нечего. Оставлено на решение владельца.

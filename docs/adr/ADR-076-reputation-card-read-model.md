# ADR-076. Репутационная карточка (ГВ.4): read-модель поверх outbox, видимость гостю, портфолио «факт vs заявление»

**Статус:** принято
**Дата:** 2026-08-08
**Контекст этапа:** ГВ.4 (`docs/tasks/global-wave.md`) — минимальная репутационная карточка,
часть октябрьского GLOBAL-релиза, поднятая раньше этапа 8 (док 31 §4). Зависимость — Э4.6
(события-исходы уже публикуются с докстринг-пометкой «для будущей ГВ.4»).

## Контекст

ГВ.4 просит карточку (возраст профиля, число сделок, число контрагентов, список завершённых
сделок — тип/сфера/период/исход/контрагент), построенную ИСКЛЮЧИТЕЛЬНО из событий outbox
(`milestone.accepted`/`auto_accepted`/`rejected`, `dispute.opened`/`resolved`,
`contract.completed`), плюс границу «факт vs заявление» портфолио (ADR-045) и видимость
ADR-059 с явной оговоркой «гостю — стартовая карточка». Постановка не фиксирует три вещи
буквально — решения ниже.

## Решения

1. **Сфера сделки добавлена в event-payload, а не читается напрямую из `apps.milestones`.**
   `Contract` не хранит сферу (только `Milestone.sphere`, «мультисферность» дерева этапов), и
   ни один существующий payload её не нёс. Чтобы карточка осталась ИСКЛЮЧИТЕЛЬНО
   event-sourced (докстринг `_event_payload`/`_self_sufficient_payload`: «не записанное сейчас
   не восстановится»), `milestone_sphere_code` добавлен аддитивным полем в
   `apps.milestones.services._event_payload` и `apps.disputes.services._self_sufficient_payload`
   — тот же приём, что уже применяли ГВ.1/ГВ.2/ГВ.5 (одна ветка волны трогает несколько
   приложений, а не буквально одно "своё"). `DealFact.sphere_codes` — список, не одно значение
   (мультисферность одной сделки).
2. **«Гостю — стартовая карточка» — интерпретируется по факту аутентификации, не по значению
   заголовка.** `public`-профиль — полная карточка всем; `link_and_deals` — владельцу и
   подтверждённым контрагентам хотя бы одной ЗАВЕРШЁННОЙ сделки (проверка — свой же
   `DealFact`, без обращения к `apps.contracts`); всем остальным, включая анонимного гостя, —
   стартовая карточка (профиль/возраст видны честно, `deals`/`deals_count`/
   `counterparties_count` — нет, иначе частичная утечка через число). Отдельно — реальная
   дыра защиты: `ReputationCardView` обязан быть `AllowAny` (гость должен видеть публичные и
   стартовые карточки без токена), но `ActingProfileMiddleware` проверяет владение
   `X-Acting-Profile` ТОЛЬКО если запрос нёс валидный JWT (её собственный докстринг:
   «отсутствие аутентификации отклонит `IsAuthenticated` самого view» — у ЭТОГО view его нет).
   Поэтому view доверяет `request.acting_profile_id` только когда `request.user.is_authenticated`
   — иначе анонимный запрос с чужим `X-Acting-Profile` получил бы полную карточку
   `link_and_deals`-профиля без всякой проверки владения.
3. **Портфолио FROM_CONTRACT создаётся, но НЕопубликованным.** `apps.profiles` уже несёт весь
   инвариант ADR-045 (`is_verified` только у `FROM_CONTRACT`, `publish_project` гейтит
   `FROM_CONTRACT` согласием контрагента, `PortfolioConsentRequiredError`) — но до сих пор не
   было писателя `FROM_CONTRACT` вообще (`services.py` докстринг: «недостижимо сейчас»).
   `apps.reputation.subscriber` на `contract.completed` вызывает новый facade
   `apps.profiles.services.record_from_contract_project` — создаёт запись для ОБЕИХ сторон,
   `is_verified=True`, но `is_published=False`, `counterparty_consent=False`: сам факт
   завершения сделки — не согласие на публикацию фото (которых на этом шаге ещё и нет,
   `media=[]` — реальный evidence-пайплайн с EXIF-очисткой это ГВ.3, вне ГВ.4). Публикация —
   отдельный шаг, вне ГВ.4 (существующий `POST /portfolio/projects/{id}/publish` уже умеет
   требовать `counterparty_consent`; откуда конкретно оно возьмётся для FROM_CONTRACT —
   решение будущей задачи, не изобретается здесь).
4. **Список завершённых сделок не включает расторжение.** Задача перечисляет буквально
   `milestone.*`/`dispute.*`/`contract.completed` — НЕ `contract.terminated`. `DealFact.Outcome`
   поэтому содержит только `completed`; расторгнутые сделки в ГВ.4 на карточке не появляются
   (расширение на будущее, не молчаливое расхождение — см. докстринг `DealFact`).
5. **Идемпотентность — двумя независимыми линиями.** `ProcessedEvent(event_id)` (тот же приём,
   что `AuditEntry.source_event_id`, ADR-065) отбивает ПОВТОРНУЮ ДОСТАВКУ события целиком ДО
   того, как подписчик тронет `DealFact`/`PortfolioProject`; `get_or_create` внутри — вторая
   линия (тот же приём, что дедуп открытого спора в
   `apps.disputes.handlers.handle_milestone_rejected`), не единственная защита.

## Не рассматривалось

Публикация read-модели через отдельную БД/шину (масштаб ГВ.4 — один Django-app с обычным
outbox-подписчиком, как `apps.profiles`/`apps.audit`, не отдельный сервис). Реальная карточка
фронтенда (`web/src/pages/ReputationCardPage.tsx`, `docs/tasks/DEV-01_reputation-card.md`) — уже
существующий UI-мокап на другом контракте данных (агрегаты по сферам, `GET /handles/:handle`);
ГВ.4 не переписывает и не подключает его — только backend read-модель и её собственный API
(`GET /v1/reputation/profiles/{id}/card`). Свести оба контракта воедино — отдельная задача.

# ADR-063. `entities`: сокращённый claim Р1, фейк-реестр, эпохи владения

**Статус:** принято
**Дата:** 2026-07-30
**Контекст этапа:** 3.4 (`entities`)

## Контекст

tech-spec.md §7.10 п.3 (открытый вопрос №3, строка 1197) отмечает, что
механизм claim из domain-model.md §3.2.2 избыточен (7 способов подтверждения
контроля) и просит пересмотреть его до реализации `entities`, вплоть до
гипотезы «claim = выдача первого `SigningAuthority`». Решение по этому
вопросу зафиксировано в постановке `docs/tasks/etap-3.md` (3.4, согласовано
с заказчиком) и реализуется здесь.

Дополнительно: `apps.jurisdictions` пока не содержит справочника
`LocalEntityForm`/`LocalTaxRegime` (`apps/jurisdictions/models.py` явно
откладывает это до отдельного этапа) — `entities` не может опираться на
такой каталог для определения типа юрлица (ИП/СМЗ/ООО). Реестр ЕГРЮЛ/ЕГРИП
— внешний провайдер вне периметра Р1 (CLAUDE.md: «внешние провайдеры —
только интерфейсы + фейки»).

## Решение

- **Гипотеза «claim = первый `SigningAuthority`» отклонена** — модель
  `BusinessEntity`/`ClaimMethod` НЕ меняется относительно domain-model.md
  §3.2.2: claim остаётся самостоятельной сущностью с собственным статусом
  (`unclaimed|pending|claimed|disputed`), а не производной от факта выдачи
  первого права подписи (которое появится только в `apps.authority`, 3.5, и
  концептуально отвечает на другой вопрос — «кто может подписывать», а не
  «кто подтвердил контроль над карточкой»).
- **Модель `ClaimMethod` остаётся полной** (все 7 значений enum из
  domain-model.md §3.2.2), но флоу реализованы только для трёх
  (`BusinessEntity.IMPLEMENTED_CLAIM_METHODS`, `apps/entities/models.py`):
  - `DIRECTOR_IDENTITY_MATCH` и `OWNER_IDENTITY_MATCH` — автоматически,
    внутри `services.try_auto_claim()` (при онбординге и повторно через
    `POST /claim`, если верификация пользователя случилась позже
    онбординга);
  - `MANUAL_REVIEW` — переводит карточку в `pending`; очередь для backoffice и
    экран оператора не реализуются (только статус, без API согласования) —
    заявлено явно в постановке 3.4.
  - Остальные четыре (`organization_esignature`, `notarized_poa`,
    `bank_account_proof`, `postal_to_legal_address`) существуют как
    значения enum; `GET .../claim-methods` показывает их с
    `available: false`; `POST .../claim` с этими методами отвечает
    `422 claim_method_not_available`.
- **`local_form_code` — фиксированный текстовый код, не FK.** Пока в
  `apps.jurisdictions` нет каталога форм собственности, `entities` сама не
  вводит такой каталог (не её ответственность и не задача 3.4) — вместо
  этого `BusinessEntity.OWNER_CLAIMABLE_FORMS` — простой frozenset кодов
  (`ru_ip`, `ru_self_employed`), которых достаточно, чтобы отличить
  ИП/самозанятого (может подтвердить контроль по своему ИНН) от ООО (только
  по совпадению ФИО директора). Когда каталог появится, `entities` перейдёт
  на FK без изменения бизнес-логики `try_auto_claim`.
- **`FakeEntityRegistryProvider`** (`apps.entities.providers`) — 4
  канонических детерминированных ИНН (ООО с директором, ИП, самозанятый,
  ликвидированная), плюс параметр `records` для тестовых сценариев с
  произвольными ФИО/ИНН — тот же принцип, что и `FakeEsiaProvider` (ADR-062):
  тесты управляют результатом, не полагаясь на внешний реестр.
- **`OwnershipEpoch` — EXCLUDE-констрейнт GiST** (`entity WITH =,
  tstzrange(started_at, ended_at) WITH &&`), первое использование
  `ExclusionConstraint`/`BtreeGistExtension` в кодовой базе — требует
  расширения `btree_gist` (включено миграцией `apps.entities.0001_initial`
  перед созданием таблицы). Проверено на живом PostgreSQL (CLAUDE.md), не на
  sqlite.
- **Фоновая сверка директора — Celery beat, не sweep-каждую-минуту.** Это
  НЕ доменный дедлайн (те по CLAUDE.md — строки в БД + sweep раз в минуту) —
  `apps.entities.tasks.reconcile_ownership_epochs` зарегистрирована в
  `CELERY_BEAT_SCHEDULE` с интервалом раз в час: смена директора в реестре —
  редкое и не время-критичное событие, в отличие от истечения дедлайна
  сделки.
- **Гейт `assert_entity_operable()` (ADR-042) — закрытый список из ОДНОЙ
  операции на 3.4:** `update_business_entity()` (PATCH ручных полей —
  налоговый режим, банковские реквизиты). Остальные операции из
  domain-model.md §3.2.2 («договоры, выдача полномочий, портфолио,
  репутация, показ в поиске») появятся в следующих этапах и будут вызывать
  тот же гейт из своих сервисов — список расширяется, но не сейчас.
- **`director_full_name` — без envelope-шифрования**, в отличие от ПД
  физлица: это данные ПУБЛИЧНОГО реестра (ЕГРЮЛ), tech-spec.md §5.2.2 явно
  не помечает поле суффиксом `_encrypted`. `bank_details_encrypted` —
  единственное ПД-поле `BusinessEntity`, шифруется с первой миграции.

## Отклонённые варианты

- **Полная реализация всех 7 способов claim** — отклонено: 4 из них
  (ЭП организации, нотариальная доверенность, контрольный платёж, письмо на
  юр. адрес) требуют интеграций/криптографии за пределами Р1 и не
  тестируются «обязательным тестом (деньги)» этой под-задачи; реализация
  «для галочки» без реального провайдера увеличила бы поверхность без
  ценности.
- **`local_form_code` как FK на новый каталог `LocalEntityForm` прямо в
  `apps.entities`** — отклонено: строить каталог форм собственности —
  ответственность `apps.jurisdictions` (domain-model.md §15), выходит за
  рамки 3.4; фиксированный frozenset — временное, дёшево заменяемое решение.
- **Реальная очередь модерации для `MANUAL_REVIEW`** (таблица заявок,
  API оператора) — отклонено постановкой 3.4 явно: «без UI оператора —
  просто статус pending».
- **`assert_entity_operable(entity, user)` с проверкой владельца внутри
  общего гейта** — отклонено: домен-модель фиксирует `assert_entity_
  operable(entity)` с единственным параметром (только статус claim);
  проверка «редактирует именно claimant» — отдельная, самостоятельная
  проверка (`EntityPermissionDeniedError`) в `update_business_entity()`, не
  часть гейта ADR-042 — иначе гейт terял бы точное соответствие спеке и
  смешивал бы два разных вопроса («карточка вообще операбельна» и «этот
  конкретный пользователь имеет право её редактировать»).

## Последствия

- Новые таблицы `business_entity`, `tax_identifier`, `ownership_epoch`
  (миграция `apps.entities.0001_initial`) + расширение PostgreSQL
  `btree_gist`.
- `apps.entities` зависит от `apps.accounts` (facade `set_business_status`)
  и `apps.identity` (`selectors.get_latest_verification`/
  `get_verified_full_name` — чтение подтверждённого ФИО для director/owner
  match) — не запрещено текущим import-linter контрактом.
- Outbox-топики `entity.claimed`, `entity.claim_disputed`,
  `entity.epoch_changed` (реестр — tech-spec.md §6.4) — использованы
  ровно по назначению; для «заявка на manual review» и «онбординг
  unclaimed-карточки» отдельных топиков в реестре нет — событие не
  публикуется (не выдумываем топик вне реестра).
- `require_verification`, `IMPLEMENTED_CLAIM_METHODS`, `assert_entity_
  operable` будут переиспользоваться/расширяться в 3.5 (`authority`):
  `SigningAuthority` появится как отдельная сущность, использующая
  `has_separated_ownership`-подобную классификацию формы собственности —
  на momento это не блокирует 3.4.

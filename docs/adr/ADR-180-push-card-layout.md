# ADR-180: Карточка push-уведомления — название договора + фото контрагента, один логотип

**Статус:** Принято
**Дата:** 2026-09-11
**Решение принято:** владелец продукта (снимок
`docs/tasks/screenshots_bugs/Screenshot_20260911_094629_One UI Home.jpg`, дословно: «Текста много и
2 наших логотипа. Надо 1 логотип, название договора + фото контрагента»; по приватности — «фото да,
имя не надо»)
**Связанные:** ADR-110 (Web Push, первый реальный канал), ADR-141 (приватные ключи payload — экран
блокировки), ADR-170 (карта якорей клика), ADR-173 (фото контрагента — поле агрегатов разделов),
ADR-176 (нативный push-канал, RuStore Universal Push), ADR-103 (фото профиля, видимость и подпись
ссылки), ADR-059 (видимость карточки контрагента, «завершённая сделка»)
**Область:** notifications (бэкенд), web (service worker)

---

## Контекст

На шторке Android push-уведомление «По рукам» показывало:

- заголовок = subject шаблона и тело = body шаблона — оба варианта одного и того же события
  («Этап сдан на приёмку» / «Откройте личный кабинет, чтобы посмотреть детали») и оба обрезаются на
  узком экране;
- крупную цветную иконку приложения (`icon-192.png`) РЯДОМ с монохромным силуэтом самого приложения,
  который Android рисует в строке заголовка уведомления — на экране получались два одинаковых по
  смыслу логотипа «По рукам».

Владелец 11.09 (по снимку карточки): «Текста много и 2 наших логотипа. Надо 1 логотип, название
договора + фото контрагента». На уточнение про приватность — «фото да, имя не надо».

## Решение

### 1. Заголовок и тело меняются местами (без новых строк локализации)

Заводить новые локализованные строки под 29 локалей ради этой карточки — отдельная дорогая работа,
которую эта задача не тянет. Вместо этого **переиспользуются уже существующие тексты**:

- `title` = `payload["contract_title"]` — название договора, если оно у уведомления есть (то самое
  поле, которое `apps.notifications.services._enrich_payload` кладёт в payload при размещении,
  ADR-098);
- `body` = subject шаблона (после подстановок и вырезания приватных ключей, ADR-141) — он короткий
  по конструкции: «Предложена правка», «Этап принят», «Этап сдан на приёмку». Длинное тело письма
  (`payload["body"]`) в push больше не идёт вовсе — это и было источником «текста много».
- Если названия договора нет (уведомления объединений, claim юрлица и т.п. — они не проходят через
  контрактную ветку `_enrich_payload`) — поведение прежнее: `title` = subject, `body` = тело.
  Проверено тестом (`test_webpush_falls_back_to_subject_and_body_without_contract_title`): пустого
  заголовка не возникает — `payload.get("contract_title")` не заведён ключом ни разу.

Реализовано в одной точке — `apps.notifications.providers.push_payload` — общей для Web Push и
нативного канала (см. п.4).

### 2. Фото контрагента — новый ключ `icon`, имя контрагента текстом не добавляется

`push_payload` считает `icon` — абсолютный URL фото КОНТРАГЕНТА (не своей стороны), тем же способом,
что и остальные разделы (ADR-173):

- контрагент — `apps.contracts.selectors.resolve_counterparty(contract, recipient)`, тот же вызов,
  что уже используется в `apps.notifications.services._enrich_payload`;
- видимость — `apps.profiles.selectors.viewer_may_see_avatar(profile, viewer=recipient,
  viewer_profile_id=…)`, где `viewer_profile_id` — сторона получателя в ЭТОМ ЖЕ договоре
  (`contract_selectors.own_party`). Правило видимости (`public` — всем, `deals_only` — владельцу/
  представителю и контрагенту ХОТЯ БЫ ОДНОЙ ЗАВЕРШЁННОЙ сделки, `apps.reputation.selectors.
  is_counterparty`) не меняется и не обходится: push для мидл-переговорного уведомления («Предложена
  правка») по незавершённому договору с `deals_only`-профилем фото не покажет, если у сторон раньше
  не было завершённой сделки — это тот же контур, что уже действует для ленты/карточки профиля, и
  трогать его ради одной этой карточки — вне рамок задачи;
- URL — `apps.profiles.selectors.avatar_url(profile, allowed=…)`, приведённый к абсолютному
  (`PUBLIC_WEB_BASE_URL` + путь) — service worker тянет картинку отдельным запросом, без Referer
  текущей вкладки и без куки сессии, поэтому относительный путь не сработал бы;
- фото нет или зрителю нельзя — ключа `icon` в ответе `push_payload` просто нет (не пустая строка,
  не битая ссылка) — service worker показывает свою цветную иконку как и раньше.
- **Имя контрагента текстом в push не добавляется** — решение владельца («фото да, имя не надо»).
  `counterparty_name` остаётся в `PUSH_PRIVATE_KEYS` (ADR-141) и продолжает вырезаться из
  подстановок; ничего в этой задаче в противоположную сторону не менялось.

### 3. Срок жизни подписи аватара — существующего TTL достаточно

Ссылка `deals_only`-аватара подписана (`profiles.selectors.make_avatar_token`,
`django.core.signing.TimestampSigner`) со сроком `PROFILE_AVATAR_URL_TTL_SECONDS` (по умолчанию
**7 дней**). ADR-173 явно отверг вариант «класть `avatar_url` в payload уведомления при размещении»
именно из-за этого TTL — ссылка «мертва к моменту прочтения» ленты, которая может открываться
месяцами позже. Для push риск похожей природы: пуш может быть открыт (протух не открытым, а сама
картинка запрашивается сервис-воркером В МОМЕНТ ПОКАЗА уведомления, а не в момент тапа) позже
отправки, и служба доставки может задержать сообщение, если устройство было офлайн.

Проверка по факту:

- Web Push: `WEBPUSH_TTL_SECONDS` (по умолчанию **1 сутки**) — push-сервис сам роняет недоставленное
  сообщение раньше, чем истечёт 7-дневная подпись. Показ уведомления (и, значит, запрос иконки)
  происходит не позже этого TTL — 7 дней comfortably покрывают 1 сутки.
- Нативный канал (ADR-176): явного TTL сообщения RuStore/FCM/HMS сейчас НЕ выставляют (только
  таймаут HTTP-запроса на отправку, `_native_timeout()`), у провайдеров действует их дефолт (у FCM,
  например, до 4 недель). В теории устройство, офлайн дольше 7 дней, получит уведомление с уже
  протухшей подписью и увидит фолбэк-иконку вместо фото — деградация не ломающая (фолбэк уже
  предусмотрен), но не идеальная.

Решение: **не менять общий TTL аватаров и не заводить отдельный более долгий срок специально под
push** — 7 дней уже больше, чем у любого из каналов доставки push на практике, риск с нативным
каналом при отсутствии явного TTL сообщения — теоретический граничный случай (устройство неделями
офлайн), деградация graceful. Если после включения нативного канала (после 22.09, см. ADR-176)
метрики покажут заметную долю пуш-показов без фото у давно офлайн-устройств — годный первый шаг:
выставить явный `ttl`/`android.ttl` в RuStore/FCM/HMS-сендерах не больше `PROFILE_AVATAR_URL_TTL_
SECONDS`, а не удлинять сам аватарный токен (он используется много где ещё, не только в push).

### 4. Нативный канал (ADR-176) — общая сборка сохранена, проброс фото не сделан

`NativePushProvider.send` и `WebPushProvider.send` уже вызывают ОДНУ И ТУ ЖЕ `push_payload(message,
recipient=recipient)` — отдельной сборки полезной нагрузки у нативного канала не было и не появилось,
так что после будущего перехода на RuStore Universal Push раскладка title/body останется той же (два
логотипа там и не грозили — заголовок/иконку уведомления в нативном канале рисует сама ОС из ресурсов
приложения, а не из payload).

**Что осталось**: `icon` в payload `push_payload` есть, но `RuStorePushSender`/`FcmSender`/
`HmsSender` его никуда не передают — шлют только `{title, body, url}` (`notification`/`data` блоки
внешних API). У каждого провайдера свой формат под картинку (`notification.image` у FCM,
аналогичное поле у RuStore/HMS по их документации) — сверка и правка трёх интеграций без реальных
кредов под рукой (`RUSTORE_PUSH_SERVICE_TOKEN`, `FCM_PROJECT_ID`, `HMS_APP_ID` не заведены в
dev/тестах) — отдельная задача, а не часть этой правки. Практического эффекта пока нет: нативный
канал сам по себе включается «после подачи на production», ориентир 22.09 (ADR-176).

## Альтернативы

- **Держать заголовок/тело как есть, обрезать текст короче.** Не убирает дублирование смысла и два
  логотипа — не решает жалобу.
- **Класть `avatar_url` в основной payload уведомления при размещении** (как в ADR-173
  «Альтернативы» — уже отвергнуто там же по той же причине протухания подписи; для push решение то
  же самое: считать `icon` отдельно, на отправке, а не хранить в БД).
- **Отдельный, более долгий TTL специально для push-ссылки аватара.** Отклонено п.3 — 7 суток уже с
  запасом покрывают оба канала доставки; отдельный срок добавил бы вторую точку конфигурации ради
  теоретического края.
- **Показывать имя контрагента текстом рядом с фото.** Отклонено явным решением владельца («фото да,
  имя не надо») — `counterparty_name` остаётся приватным ключом (ADR-141).

## Последствия

- Карточка push: один логотип (фолбэк-иконка ИЛИ фото контрагента — не оба одновременно), заголовок
  — название договора, тело — короткая фраза действия.
- `push_payload` меняет сигнатуру: `recipient: User | None = None` — опциональный именованный
  параметр, обратная совместимость с местами, где `recipient` взять неоткуда, сохранена (`icon`
  просто не считается).
- Миграций нет — читаются существующие поля (`Profile.avatar_key`, `Profile.avatar_visibility`).
- Тесты `apps/notifications`: заголовок/тело поменялись местами (обновлён
  `test_webpush_payload_substitutes_without_private_keys` и аналог в `test_native_push.py`), плюс
  новые — фолбэк без договора, фото подставляется при `public`, не подставляется при `deals_only` до
  завершения сделки, без `recipient` — без `icon`.
- `web/public/push-sw.js`: `icon: data.icon || '/icons/icon-192.png'`; `badge` (монохромная «вспышка»
  в статус-баре, ADR предыдущей правки 10.09) не тронут.

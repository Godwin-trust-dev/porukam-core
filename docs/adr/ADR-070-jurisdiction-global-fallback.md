# ADR-070. Контур GLOBAL и fallback-резолвер юрисдикции

**Статус:** принято
**Дата:** 2026-08-06
**Контекст этапа:** ГВ.1 (`feat/jurisdictions-global`, docs/tasks/global-wave.md)

## Контекст

Постановка ГВ.1 ссылается на «ADR-060 §2/§8/§9, приложение „изменения в
техспецификации“» как на основание. В этом репозитории номер ADR-060 уже
занят (`ADR-060-outbox-common.md`, транзакционный outbox, принят раньше) —
внешний документ с профилем GLOBAL и таблицей §2 в `docs/adr/` не попал.
Этот ADR фиксирует решение по факту реализации ГВ.1 под следующим свободным
номером (070); ссылки постановки на «ADR-060» в контексте GLOBAL-волны
следует читать как ссылки на этот файл. Расхождение номеров стоит поправить
в исходнике постановки отдельно — это не блокирует код ГВ.1: содержательный
минимум (профиль GLOBAL, приёмка) описан в самом docs/tasks/global-wave.md
и был реализован по нему напрямую.

`apps.jurisdictions` до ГВ.1 содержал только валютный блок
(`default_currency_code`/`allowed_currency_codes`, ADR-041); ни одной строки
`JurisdictionConfig` не существовало как данные миграции — RU заводился ad
hoc в тестах. Волне GLOBAL (док 31, GLOBAL-first) нужен контур для
пользователя без страны или со страной без своего плагина, при этом
RU-контур должен продолжать работать без изменений.

## Решение

- **`JurisdictionConfig.is_global_default`** (bool, default False) — признак
  контура-fallback. Констрейнт БД (`UniqueConstraint(condition=Q(is_global_default=True))`,
  живой PostgreSQL) не даёт завести вторую такую строку — не полагаемся на
  дисциплину сид-миграций.
- **`country_code` расширен до `max_length=8`.** Это не ISO 3166-1 alpha-2
  везде: единственное отклонение — литерал `"GLOBAL"` (константа
  `GLOBAL_COUNTRY_CODE` в `models.py`) для контура-по-умолчанию. Остальные
  страны — по-прежнему двухбуквенный код.
- **`selectors.resolve_jurisdiction(country_code: str | None)`** — резолвер:
  явный код страны → плагин, если он есть; иначе → `GLOBAL_COUNTRY_CODE`.
  Отсутствие страны (`None`/пустая строка) — тоже в GLOBAL. У функции нет
  параметра геолокации/IP: гео-детекция — подсказка при выборе страны выше
  по стеку (UI/API уровень, вне этой задачи), в резолвер она не попадает
  вообще, поэтому не может подменить явный выбор пользователя.
- **Профиль контура** — четыре булевых поля, читаемые приложениями выше по
  стеку по мере реализации соответствующих флоу (не поведение самого
  `apps.jurisdictions`, который не знает про SMS/платежи/налоги):
  - `legal_force_available` — контур утверждает юридическую силу подписанного
    договора по местному праву. RU — `True` (63-ФЗ). GLOBAL — `False`:
    платформа фиксирует факты, юридическую судьбу определяет юрисдикция
    пользователя (общее требование волны — этой формулировкой, без
    «пригодно для суда», нигде в текстах).
  - `tax_guidance_available` — контур считает/подсказывает налоговый режим.
    RU — `True` (даже до реализации tax_regimes, стадия 2). GLOBAL — `False`.
  - `platform_mediates_payment` — платёж идёт через контур платформы (RU)
    vs GLOBAL, где платежи сторон — вне платформы, только reference-код
    (сама реализация off-platform-tracking — не в этой задаче, `apps.payments`
    ещё каркас).
  - `sms_channel_enabled` — SMS как канал допустим в контуре. RU — `True`.
    GLOBAL — `False` (ГВ.5: web-push + email вместо SMS-фоллбека).
  Дефолт полей — `True` (обычный страновой плагин ничего не выключает по
  умолчанию); GLOBAL — единственная строка, которая явно выключает все
  четыре.
- **Валюты — данные миграции, не код.** `apps.catalog.Currency.is_active`
  активируется для USD/EUR отдельной миграцией `catalog/0007_seed_usd_eur`
  (RUB уже активна, `0002_seed_rub`). `JurisdictionConfig.allowed_currency_codes`
  — per-контур список: RU остаётся `["RUB"]` без изменений, GLOBAL —
  `["USD", "EUR", "RUB"]`. Код валюты в обеих таблицах не связан импортом
  (`apps.jurisdictions` и `apps.catalog` — оба нижний слой, друг от друга не
  зависят по духу правила CLAUDE.md, хотя формальный контракт import-linter
  прямо этого не запрещает) — совпадение кодов поддерживается дисциплиной
  сид-миграций и комментариями, а не FK/импортом.
- **Сид RU** (`jurisdictions/0004_seed_ru_and_global`) — первые данные для
  RU в миграциях; ad hoc `JurisdictionConfig.objects.create(country_code="RU", …)`
  в тестах заменены на чтение сид-строки (`.get(country_code="RU")`), чтобы
  тесты проверяли реальный контур, а не его копию, и не конфликтовали по PK
  с сид-миграцией.

## Альтернативы

- **Хранить признак GLOBAL только строковым сравнением `country_code == "GLOBAL"`,
  без `is_global_default`.** Отклонено: резолвер и любой код выше по стеку
  тогда обязаны знать магическую строку и её написание; отдельный bool +
  констрейнт БД делает «ровно один fallback-контур» инвариантом уровня
  данных, а не соглашением по коду.
- **Разрешить `resolve_jurisdiction` принимать IP/заголовки для гео-fallback
  внутри себя.** Отклонено прямым требованием постановки (страна — только
  явный выбор пользователя, гео — подсказка вне резолвера) — сохраняет
  инвариант «резолвер детерминирован от одного явного входа».
- **Профиль контура одним JSON-полем вместо четырёх bool.** Отклонено:
  остальной `JurisdictionConfig` (и его будущее продолжение из
  domain-model.md §15) — типизированные поля с говорящими именами
  (`registry_director_lookup_available` и т. п.); JSON-профиль ломает этот
  стиль и мешает CHECK-констрейнтам/индексам на конкретный флаг в будущем.

## Последствия

- `apps.jurisdictions` внутри себя не читает и не пишет ничего в
  notifications/accounts/payments — профиль контура становится действующим
  для конкретного флоу только когда соответствующее приложение (ГВ.2 —
  OTP+SMS не предлагается GLOBAL, ГВ.3 — платежи вне платформы, ГВ.5 — SMS
  выключен конфигурацией контура) начинает читать это поле. До этого момента
  поле — просто данные, приёмка ГВ.1 проверяет его значение, не эффект в
  чужом флоу.
- Любая новая страна добавляется той же формой (сид-миграция + запись с
  `is_global_default=False`), GLOBAL — не специальный код, а обычная строка
  с одним отличающимся флагом.

# ADR-072. Реестр доменных дедлайнов: sweep, конфигурация длительностей, компенсация простоя

**Статус:** принято
**Дата:** 2026-07-31
**Контекст этапа:** ЭФ.2 (`docs/tasks/fundament.md`) — сквозной фундамент, юр-независимая
работа на паузу этапов 4–5.

## Контекст

`docs/tasks/fundament.md` ЭФ.2 требует единый реестр доменных тайм-аутов (`DomainDeadline`,
tech-spec.md §5.2.10) со sweep каждую минуту (Celery beat), сервис-слой (создание, якорение,
пауза, массовая компенсация простоя — ADR-039) и явное требование: «значения длительностей —
из конфигурации (JurisdictionConfig/категории), НЕ константы в коде».

Схема `domain_deadline` из tech-spec.md §5.2.10 не имеет измерения по юрисдикции —
`kind text` свободный, `country_code` в таблице нет. `apps.jurisdictions.JurisdictionConfig`
(ADR-041) на сегодня хранит только валютный блок; расширение на длительности по стране
подразумевало бы добавление `country_code` в `domain_deadline`, чего спека не описывает и
что не нужно ни одному из требуемых сценариев ЭФ.2.

## Решение

- **Длительности — отдельная таблица категорий `apps.deadlines.DeadlineKindConfig(kind PK,
  duration)`**, не расширение `JurisdictionConfig`. Обоснование — прямая цитата tech-spec.md
  §11 п.4: «значения тайм-аутов по категориям (приёмка, окно выгрузки, окна оспаривания) —
  таблица категорий договоров с юристом; в системе — конфигурация, не код». Это ровно
  «категории» из формулировки fundament.md («JurisdictionConfig/категории») — юрисдикционного
  измерения схема не просит. `apps.deadlines` не зависит от `apps.jurisdictions` — обе
  остаются в нижнем слое (import-linter, CLAUDE.md), интеграция не потребовалась.
- **Сид данных — миграция `0002_seed_kind_durations.py`** (тот же приём, что
  `apps.catalog.migrations.0002_seed_rub`): `milestone_acceptance` = 48 ч, `evidence_upload_window`
  = 72 ч, `dispute_cap` = 30 дней — значения, уже зафиксированные в tech-spec.md §2.5/§7/§6.3
  текстом, не придуманные. Финальные цифры — предмет согласования с юристом (§11 п.4);
  когда он их скорректирует, это ОБНОВЛЕНИЕ СТРОКИ, не правка кода. Окна оспаривания
  (ADR-019) и истечение хранения доказательств в спеке даны без числа — не сидируются здесь,
  добавятся отдельной миграцией, когда появится значение.
- **`kind` в `DomainDeadline` — свободный текст, не FK на `DeadlineKindConfig`** (схема §5.2.10
  прямо так и определяет). Разрешает создать `DomainDeadline` с `kind`, для которого
  конфигурации ещё нет, — ошибка (`DeadlineKindNotConfiguredError`) возникает только в момент
  вычисления `deadline_at` (создание с явным `anchor_at` или `anchor_deadline()`), не раньше.
- **`anchor_at` НЕ обязателен при создании.** `starts_from=cabinet_placement` создаёт дедлайн
  с `deadline_at IS NULL` («не тикает» — требование fundament.md); анкор проставляет
  `anchor_deadline()`, которая по контракту ЭФ.4 (`place_notification`) вызывается РОВНО ОДИН
  РАЗ — повторный вызов бросает `DeadlineAlreadyAnchoredError`, а не молча перезаписывает
  дедлайн (юридически значимый момент отсчёта не должен плавать).
- **Sweep — простой цикл по `DomainDeadline.objects.filter(...)`, БЕЗ `select_for_update`**,
  по аналогии с `common.relay.deliver_due_events()` (ADR-064): на этом этапе воркер
  Celery beat один, блокировка избыточна; если появится горизонтальное масштабирование sweep'а,
  добавляется отдельным PR. Каждое срабатывание — своя `transaction.atomic()` (fired_at +
  outbox-событие в одной транзакции, CLAUDE.md), а не одна транзакция на весь батч — падение
  на середине батча не откатывает уже обработанные дедлайны.
- **Sweep публикует generic `outcome="timed_out"`, не бизнес-специфичный исход.** Обработчики
  конкретных `kind` (авто-приёмка, авто-закрытие спора) — этап 4; до них generic-значения
  достаточно, спека это прямо разрешает («обработчики появятся в этапе 4 — сейчас тестовый
  обработчик»). Топик `domain_deadline.fired` подписан на `apps.deadlines.handlers.
  log_fired_deadline` — логирующая заглушка (dev-приёмка: «в логах sweep — событие
  срабатывания»).
- **`compensate_downtime()` сдвигает ВСЕ незавершённые заякоренные дедлайны
  (`fired_at IS NULL AND deadline_at IS NOT NULL`) одним `UPDATE ... SET deadline_at =
  deadline_at + downtime`, включая уже поставленные на паузу.** Пауза (одиночная,
  доменная — `apps.milestones` в этапе 4 будет ставить её при `in_progress ⇄ suspended`) и
  компенсация простоя (массовая, инфраструктурная — ADR-039) — независимые механизмы:
  сдвигать `deadline_at` паузнутого дедлайна безопасно (sweep всё равно его не тронет, пока
  `paused=true`), а не сдвигать значило бы разъехаться с реальным временем на момент
  резюмирования.

## Альтернативы

- **Расширить `JurisdictionConfig` полем длительностей по стране.** Отклонено: без
  `country_code` на `domain_deadline` это добавляло бы аргумент, который негде использовать
  до появления реальной юрисдикционной дифференциации сроков (её в спеке нет).
- **`select_for_update(skip_locked=True)` в sweep для будущей горизонтальной масштабируемости
  воркера.** Отклонено сейчас как преждевременная оптимизация — `common.relay` тем же путём
  не защищается; если появится нагрузка, требующая нескольких воркеров sweep'а, добавляется
  отдельным PR вместе с бенчмарком.

## Последствия

- `apps.deadlines` не добавляет новых контрактов import-linter — он уже значится целью в
  списке `forbidden_modules` контракта «catalog и jurisdictions — нижний слой» (эти два не
  вправе импортировать `apps.deadlines`), а сам `apps.deadlines` ничего из бизнес-приложений
  не импортирует (`lint-imports` подтверждает: 3 kept, 0 broken).
- ЭФ.4 (уведомления) обязана вызывать `apps.deadlines.services.anchor_deadline()` из
  `place_notification` РОВНО ОДИН РАЗ на дедлайн; повторное размещение того же юридически
  значимого уведомления (если оно вообще возможно) не должно повторно анкорить дедлайн.
- Этап 4 (обработчики) подписывается на `domain_deadline.fired` в `OUTBOX_SUBSCRIBERS` рядом
  с `apps.deadlines.handlers.log_fired_deadline` (или вместо неё) и переопределяет `outcome`
  по бизнес-логике конкретного `kind`.

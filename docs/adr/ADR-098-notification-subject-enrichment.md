# ADR-098. Субъект уведомления и центральное обогащение payload

Дата: 2026-08-19. Статус: принято.
Ветки: `feat/notifications-feed-subjects` (бэкенд, этот ADR), `feat/web-review-aug19` (UI).

## Контекст

Отсмотр прода 2026-08-19, лента `/notifications`:

1. Уведомления некликабельны. Фронт (DEV-14 §3) умеет переходить по
   `action.href`, но реальный `NotificationFeedItemSerializer` отдавал
   только `id/type/title/severity/created_at/read/group` — ни `action`,
   ни `contract`, ни `counterparty` (мок всё это отдаёт — «мок — зеркало
   бэкенда» здесь было нарушено в обратную сторону).
2. В заголовках печатался буквальный `{contract_title}`: тексты пакетов
   ссылаются на него, но события контрактного контура публикуются с пустым
   payload (`negotiation.*`, `contract.*` — `payload={}`), а
   `_SafeFormatDict` оставляет неизвестный плейсхолдер как есть.
3. `subject_type`/`subject_id` события доезжали до `place_notification`,
   использовались для якоря дедлайна — и выбрасывались: у `Notification`
   не было колонок субъекта, навигацию «к месту события» строить не из чего.

## Решение

### 1. Субъект персистится

`Notification.subject_type/subject_id` (по значению, без FK — субъект может
жить в любом приложении) + денормализованный `contract_id`: из
`subject.contract_id` события (его уже публикуют milestone/dispute-события)
либо из `subject.id` при `type="contract"`. Миграция 0009.

### 2. Обогащение payload — центральное, в `place_notification`

Одна точка вместо правки каждого publish-сайта: при наличии `contract_id`
в payload дозаписываются (`setdefault` — издатель главнее):

- `contract_number` — последние 6 hex UUID, верхний регистр (uuid7: хвост
  случайный, начало — таймштамп, у соседних договоров почти одинаковое).
  Доменного номера у Contract нет (tech-spec §5.2) — это презентационная
  производная, стабильная для id;
- `contract_title` — `contract.title`, фолбэк `№ <номер>` (пустой title —
  валидное состояние), закрывает баг №2 разом для всех шаблонов;
- `counterparty_profile_id` / `counterparty_name` — противоположная
  получателю сторона (`resolve_counterparty` ОТНОСИТЕЛЬНО recipient);
  имя — `profiles.selectors.public_display_name` (уважает `show_name`;
  вынесен из `ProfileSerializer`, там теперь переиспользование). Без имени
  ключ отсутствует, пустых строк не пишем.

Импорты contracts/profiles — локальные в функции: `apps.contracts.services`
сам импортирует `apps.notifications.services`, модульного цикла не заводим.
Границам import-linter не противоречит (notifications не в forbidden-списках).

### 3. Лента отдаёт навигацию и мету

`_feed_item` при `contract_id`: `action = {label: "", href: "/contracts/<id>"}`
(метка пуста — фронт не рисует чип, но весь пункт кликабелен, как в моке),
`contract = {id, number?, title?}`, `counterparty = {name, profile_id}?`.
Все поля опциональны: события без договора (`entity_claimed`) и уведомления,
размещённые до этой миграции, отдаются как раньше — фронт пропускает пустое.

## Отвергнутые варианты

- **Заполнять payload в каждом publish-сайте** (contracts/milestones/
  disputes): ~15 точек, дублирование, и контрагента там не вычислить —
  он зависит от получателя, который известен только подписчику.
- **Доменный номер договора** (поле/секвенция на Contract): продуктовое
  решение с юр-последствиями (номер в договоре печатается из других
  механизмов); для меты ленты достаточно производной от UUID.
- **Резолв контрагента на чтении ленты** (в `_feed_item`): N+1 по
  договорам/сторонам на каждый GET и расхождение с юрзначимым
  content_hash — payload фиксируется в момент размещения.

## Последствия

- `content_hash` считается по обогащённому payload — содержимое юрканала
  самодостаточно (как `party_identity_snapshot` для outbox, тот же принцип).
- Старые уведомления без `contract_id` остаются инертными — обратной
  дозаписи нет (append-only контур, честная история).
- Фронт: клик ведёт по `action.href` с фолбэком на `contract.id`; мета —
  «контрагент · № договора», пустые поля пропускаются (ветка UI).

## Дополнение 2026-08-20 (отсмотр прода: лента читаема и кликабельна целиком)

1. **Сумма в мете пункта.** `_enrich_payload` дописывает `amount` (строка
   Decimal) + `currency` — «сумма листьев = сумма договора»
   (`apps.milestones.services.total_leaf_amount`, тот же источник, что у
   карточки). Черновик без этапов / разные валюты листьев → ключей нет;
   `_feed_item` отдаёт `amount: {amount, currency}` только парой.
2. **Договор — не только из subject.** «Прямые» шаблоны
   (`signature_requested`, `milestone_submitted_for_acceptance`,
   `milestone_material_notice`) subject не передавали или передавали
   milestone без contract_id — самое важное уведомление контрагенту
   («подпишите») оставалось без ссылки и обогащения. `_subject_contract_uuid`
   теперь падает на `payload.contract_id`, затем на договор этапа
   (`payload.milestone_id` / subject=milestone). Туда же — `milestone_title`
   по этапу для текстов прямых шаблонов.
3. **Старые записи (до ADR-098).** Дозаписи payload по-прежнему нет
   (append-only, content_hash). Вместо сломанной фразы с буквальным
   `{contract_title}` лента показывает тему шаблона («Договор подписан»):
   `_feed_title` — если после подстановки остался `{…}`, берём `subject`.
4. **Тексты ru/en** в `l10n/packs` переписаны единообразно (этап, а не
   «работа»; всегда «Договор «…»»); четыре прямых шаблона получили
   subject/body в паках (раньше — только `body_i18n` ru/en в БД, без темы;
   остальные 27 локалей падают на en по цепочке l10n).

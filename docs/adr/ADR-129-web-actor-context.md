# ADR-129. Контекст актёра на фронте: объединение — актёр оболочки

Дата: 2026-08-25. Статус: принято.
Ветка: `feat/web-actor-context` (только фронтенд; бэкенд не трогаем).

## Контекст

Замечание 2026-08-25, дословно: «При переключении в правом верхнем углу
компанию/человека, интерфейс должен тоже меняться. Пока оставляем такой же
функционал как и у обычного аккаунта + то что мы уже сделали. Смену логотипа и
хендла отправляем в настройки. Оставляем только пригласить».

До этого ADR переключатель в шапке (`ActorSwitcher`) работал с двумя разными
сущностями по-разному:

- **личный профиль и организации** — настоящие актёры: их id уходит в
  `X-Acting-Profile` (`packages/core/src/api/client.ts`), при выборе
  инвалидировался один ключ `['contracts']` и происходил переход на
  `/contracts`;
- **объединения** (ADR-118) — НЕ актёры: строка меню просто открывала карточку
  `/groups/{id}`, контекст оболочки не менялся вовсе.

Одновременно управление объединением (витрина, логотип, смена хендла) жило
панелью прямо в публичной карточке `/groups/{id}` — вперемешку с тем, что видит
любой читатель.

### Что умеет бэкенд (проверено по коду, 2026-08-25)

Это ограничивает решение сильнее всего, поэтому фиксируем факты:

1. `X-Acting-Profile` читает ОДНО место — `apps/accounts/middleware.py`
   (`ActingProfileMiddleware`). Принимается только UUID **профиля**
   (`apps.profiles.Profile`), право проверяет
   `apps.profiles.selectors.can_act_as` (владение или активное
   представительство). Id объединения этой проверки не проходит → **403
   `acting_profile_not_allowed`**. ADR-118 §5 говорит то же прямо:
   объединение не может быть `X-Acting-Profile`.
2. Ни одна выборка на бэкенде не сужается по acting-профилю. `contracts`,
   `dashboards`, `notifications`, `messaging`, `social`, поиск — все скоупятся
   по `request.user` (в contracts/dashboards — через
   `contracts.selectors.user_owned_profile_ids(user)`, объединение ВСЕХ
   профилей пользователя). Заголовок сегодня — сигнал личности зрителя ровно
   для двух приватных гейтов (карточка репутации, аватар `deals_only`) и метка
   аудита в `account.logged_in`.
3. Объединение не может быть стороной договора: `ContractParty.profile` — FK на
   `profiles.Profile`, а `contracts.services` держит отдельную ошибку
   `CounterpartyIsGroupError`. Группового дашборда, ленты, чатов и уведомлений
   не существует; `/users/me` объединения не отдаёт вовсе.

Отсюда прямое следствие: «функционал как у обычного аккаунта» в контексте
объединения сегодня — это ровно функционал личного аккаунта. Иначе и быть не
может, пока бэкенд не научится группам (см. §4).

## Решение

### 1. Объединение — полноценная строка актёра в шапке

`ActorSwitcherProps` получает `onSelectGroup`. Строка объединения теперь
`aria-selected`, с галочкой активного, с логотипом вместо инициала, а `current`
может быть id объединения. Повторный клик по уже активному объединению
открывает его карточку (`onOpenGroup`) — тот же приём, что `onOpenCurrent` у
профиля. Без `onSelectGroup` поведение прежнее (ADR-118), обратная
совместимость компонента сохранена.

### 2. Объединение надстраивается над person-профилем, а не заменяет его

`actorStore` хранит `activeGroupId` рядом с `activeProfileId` (оба переживают
F5). Правила:

- `setActiveGroup(id)` ставит объединение И переводит `activeProfileId` на
  person-профиль. Объединение не сторона договора и бизнес-статуса не даёт
  (§6.6) — доменные запросы обязаны идти от физлица, а не от организации,
  которая была активна до переключения;
- `setActive(profileId)` снимает `activeGroupId`: два контекста сразу — это две
  разные «шапки» на одном экране;
- `setGroups(...)` снимает активное объединение, которого больше нет в списке
  управляемых, — тем же приёмом, каким `setProfiles` чистит мёртвый
  `activeProfileId`.

**`X-Acting-Profile` при активном объединении несёт person-профиль владельца.**
Id объединения туда не уходит: бэкенд ответил бы 403 (§Контекст п.1).

### 3. `actorKey` — одна величина смены контекста

`actorKeyOf(activeProfileId, activeGroupId)` → `group:<id>` либо id профиля.
Ключ входит в `queryKey` доменных выборок оболочки: `['dashboard', actorKey]`,
`['real-contracts', actorKey, params]`, `['notifications', actorKey, filter]`,
`['chat','threads', actorKey]`. Смена актёра меняет ключ — данные прежнего
актёра не показываются под именем нового ни на кадр.

Сама смена — единственной точкой `useSwitchActor()`: переставить актёра →
`queryClient.removeQueries()` → уйти на `/contracts`.

Именно `removeQueries`, а НЕ `invalidateQueries`: инвалидация перезапрашивает
ещё живой запрос ПРЕЖНЕГО актёра (стор обновлён, React перерисоваться не успел)
— на каждое переключение уходил лишний запрос со старым `X-Acting-Profile`
(воспроизведено тестом: три запроса вместо двух). Удаление кэша такого запроса
не порождает — подписчик перезапрашивает уже на следующем рендере, с новым
ключом.

### 4. Настройки объединения — раздел АКТИВНОГО актёра

`/me/settings/group` (`GroupSettingsPage`): логотип, смена хендла, витрина.
Пункт «Объединение» появляется в `SettingsLayout` первым и только когда
объединение активно; при выходе из контекста, стоя в этом разделе, — редирект
на `/me/settings/profile`.

Из карточки `/groups/{id}` витрина, логотип и хендл УБРАНЫ. У владельца там
остаются «Пригласить» и очередь заявок (это не настройка, а операционная
очередь рядом со списком участников), плюс текстовый указатель со ссылкой в
настройки — без него лидер, стоящий в личном контексте, не нашёл бы переехавшее.

## Альтернативы

**Слать id объединения в `X-Acting-Profile`.** Отвергнуто: middleware ответит
403, а «починить» это на бэке значит сделать объединение профилем — против
tech-spec §5.2.1b и модели `apps.social` (членство ключуется по `User`, не по
`Profile`).

**Второй заголовок `X-Acting-Group` уже сейчас.** Отвергнуто: бэкенд его не
читает — это был бы непроверяемый мёртвый код. Точка добавления одна
(`actorStore` + `ApiClient`), когда контракт появится.

**Оставить объединения ярлыком перехода в карточку (как в ADR-118).** Отвергнуто
замечанием: пользователь ожидает от переключателя смену контекста, а не переход.

## Последствия

- Контекст объединения сегодня **презентационный**: те же данные, что у личного
  аккаунта, плюс поверхности объединения (карточка, участники, приглашения,
  настройки). Это ровно то, что просило замечание («пока оставляем такой же
  функционал»), но об этом надо помнить, планируя групповые сделки.
- Новому доменному запросу оболочки нужен `actorKey` в ключе; entity-scoped
  запросы (по id договора/этапа) в нём не нуждаются — от них уводит навигация,
  а кэш чистит `removeQueries`.
- `removeQueries()` при переключении сбрасывает и `['me']`/`['groups']` — оба
  активны в оболочке и перезапрашиваются сразу; имя в шапке кратко берётся из
  фолбэка `actorStore.profiles`.

## Чего для полноценного контекста объединения не хватает на бэкенде

Не реализуем в этой ветке; перечень — задача бэкенд-веток:

1. `X-Acting-Group` (или расширение `X-Acting-Profile` до групп) —
   `apps/accounts/middleware.py`: разбор, проверка через
   `social.selectors.can_manage_group`/активное членство, `request.acting_group_id`.
2. `GET /v1/users/me` — отдавать объединения пользователя (или добавить
   `GET /v1/groups/mine`): сейчас `list_public_groups()` фильтрует
   `is_public=True`, и ЗАКРЫТОЕ объединение лидер в списке не видит вовсе —
   в переключателе его нет.
3. `GET /v1/contracts`, `GET /v1/dashboard`, `/dashboard/stages`,
   `/dashboard/payments` — сужение по группе (сейчас
   `user_owned_profile_ids(user)` без учёта контекста).
4. `GET /v1/notifications`, `GET /v1/messages/threads` — групповой инбокс
   (`Notification.recipient` и членство сейчас ключуются по `User`).
5. Договоры от лица объединения (если это вообще станет продуктовой целью) —
   изменение `ContractParty` и снятие `CounterpartyIsGroupError`; это
   пересмотр tech-spec §5.2.1b, отдельным решением, не техническим PR.

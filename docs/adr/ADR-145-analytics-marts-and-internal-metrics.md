# ADR-145. Аналитика: витрины и внутренние метрики отдельным приложением-читателем

**Статус:** принято (docs/tasks/marketing-metrics.md v2.0 от 27.08, §8.3 и §9)
**Контекст:** новое приложение `apps/analytics`, каталог `analytics/` в корне репозитория,
`CELERY_BEAT_SCHEDULE`, контракт import-linter

## Контекст

Продукт бесплатный и глобальный: ни выручки, ни РФ-контура, GMV принципиально неизмерим
(марк-метрики §0). Мерить надо людей и географию, и мерить нечем — цифры до сих пор
доставались разовыми запросами руками. Документ метрик уже спроектировал ответ целиком:
единственный источник истины — `outbox_events`, три витрины (§8.3), внутренние read-only
эндпоинты за статическим токеном (§9.1), каталог `analytics/` со снимками в git (§9.2),
мост на psycopg до появления эндпоинтов (§9.3) и ежедневный монитор из 12 строк (§10).

Решать надо было четыре вопроса, на которые документ ответа не давал.

## Решение

### 1. Аналитика — читатель, а не участник: ноль импортов из `apps.*`

`apps.analytics` не импортирует **ничего** из других приложений — ни моделей, ни
`services`, ни `selectors`. Витрины считаются SQL-запросами (`apps/analytics/sql/*.sql`)
по `outbox_event` и доменным таблицам. Контракт import-linter это проверяет.

Почему жёстче, чем у `apps.dashboards` (тот ходит через чужие `selectors`): дашборд —
часть продукта и обязан видеть ту же модель, что пользователь. Аналитика — сторонний
наблюдатель: если она импортирует чужой фасад, она попадает в граф зависимостей продукта
и становится причиной падений в приложениях, которые о ней не знают. Читателя выносить
из графа дешевле, чем потом объяснять, почему `apps.contracts` не собирается из-за метрики.

Цена решения названа прямо: SQL-запросы витрин знают имена таблиц и колонок чужих
приложений. Это связь по схеме БД вместо связи по коду; ломается она на миграции
переименования и ловится тестами витрин (`backend/tests/test_analytics_marts.py`).

### 2. Витрины — обычные таблицы, а не `MATERIALIZED VIEW`

`mart_daily_pulse` (+ разрезы), `mart_contract_lifecycle`, `mart_user_cohorts` — обычные
Django-модели, полностью пересчитываемые `INSERT ... ON CONFLICT DO UPDATE` раз в час.

Против `MATERIALIZED VIEW`: витрине нужны миграции, тесты через ORM, mypy и, главное,
наблюдаемость пересчёта. `MartRefreshRun` пишется на каждый прогон, а возраст последнего
успешного отдаётся в `/internal/v1/metrics/health` — **витрина, которая молча перестала
пересчитываться, хуже отсутствующей: по ней принимают решения, считая её свежей.**
`REFRESH MATERIALIZED VIEW` такого следа не оставляет.

Порядок пересчёта — часть контракта: дневная витрина считается ПОВЕРХ двух других (§8.3),
поэтому базовые идут первыми и дневной ряд не может разойтись с жизненным циклом договора.

### 3. Две грани, а не одна: договор и пользователь

У договора две стороны и, в кросс-страновой сделке, две разные страны — «подписанные
договоры по странам» без оговорок складывались бы дважды. Поэтому:

* `mart_contract_lifecycle` — договорная грань (путь, этапы, споры, обе страны);
* `mart_daily_pulse_slice` — пользовательская, ровно воронка по странам из §4.2
  (регистрация → первый подписанный договор → первый принятый этап);
* `mart_daily_pulse` — день целиком, включая НЕаддитивные величины (уникальные пары,
  медиана числа листьев), которые из разрезов не складываются в принципе.

### 4. Мост и API отдают ОДНУ форму ответа, и это проверяется командой

Каждый SQL-файл моста собирает готовый JSON (`json_build_object`) — ровно тот, что отдаёт
эндпоинт. Перевод клиента на API меняет только `analytics/client.py` (§9.3), а расхождение
двух источников ловится `python -m analytics.pull --compare`: это не удобство, а
единственный способ убедиться, что витрина не разошлась с базой.

Доступ к эндпоинтам — статический токен из окружения плюс список адресов, наружу не
выведены (тот же принцип, что у `/metrics` Prometheus). Пустой `ANALYTICS_METRICS_TOKEN`
закрывает контур полностью: то, что «работает из коробки без настройки», в проде
оказывается открытым.

### 5. Язык — такой же первоклассный разрез, как страна

`country` и `locale` в витринах и ответах СИММЕТРИЧНЫ: одинаковый набор полей, одинаковая
динамика по дням, одинаковое правило «живой» (есть хотя бы один подписанный договор за окно).
Так сделано потому, что §4.3 называет три решения, и два из них задаются об одном и том же
договоре: «какую страну поднимать до собственного плагина» и «какой язык вычитывать носителем
следующим». Разрез, который есть только у одной из осей, отвечает ровно на половину вопросов.

Отсюда же `is_cross_language` рядом с `is_cross_country`: кросс-страновой договор — про
юрисдикцию, кросс-языковой — про понимание. Растущая доля вторых означает, что вычитывать
переводы важнее, чем добавлять новые языки.

**`GLOBAL` в `User.country_code` — не страна.** `apps.accounts` проставляет его автоматически
при входе через Google как стартовое значение, то есть он означает ровно «страна не выбрана».
Витрина кладёт такие аккаунты в ту же корзину, что и пустые, но помнит причину в
`country_source`. Проверка на живом проде 31.08 показала, почему это не педантизм: из девяти
аккаунтов пять имели `country_code = 'GLOBAL'`, три пустой и лишь один настоящий код. Считай
мы `GLOBAL` страной — карта продукта показывала бы вторую по величине «страну», которой не
существует, и решение §4.3 «какую страну поднимать до собственного плагина» принималось бы
по фантому.

Коды стран нормализуются к ISO-3166 alpha-2 в верхнем регистре ещё в витрине. «Страна не
выбрана» и «язык не сохранён» вынесены ОТДЕЛЬНЫМИ полями (`country_not_chosen`,
`locale_not_set`), а не спрятаны в корзину `??` среди прочих кодов: это не география, а
онбординг, и пока доля высока, любые выводы по разрезам считаются по меньшинству
пользователей — молчать об этом нельзя.

### 6. Виральности нет — есть воронка по статусам договора

Блок K-фактора из §5.3 не реализован и не будет реализован «как-нибудь приблизительно».
Сущности приглашения в домене НЕТ: `create_draft` требует уже существующий профиль
контрагента (`profile_id` либо `@handle`), договор с незарегистрированным не создаётся в
принципе. Телефонная книга атрибуции тоже не даёт, и это осознанно: `reconcile_phonebook`
удаляет несовпавшие хеши в той же транзакции, следа «у меня есть контакт вне платформы» в
базе не остаётся. Контур приглашений спроектирован и ждёт решения владельца
(`docs/tasks/invites-design-proposal-2026-08-28.md`, вариант C — `ContractInvite`).

Вместо гадания меряем то, чем продукт устроен на самом деле — **договор и его статус**:

* `negotiation.by_status` — распределение договоров, созданных за окно, по статусам FSM
  согласования, вместе с обоими отвалами (`rejected_by_counterparty`, `withdrawn_by_initiator`);
* `negotiation.counterparty_response` — ответ приглашённой стороны: отправили на согласование →
  подписал / отклонил / молчит. Это и есть «самая узкая и самая важная воронка продукта» из
  §5.2, просто в терминах, которые в домене существуют;
* `negotiation.step_hours` — сколько времени договор проводит на каждом шаге: где именно
  застревает, а не только сколько дошло.

Отдельно — `acquisition.arrival`: человек зарегистрировался и в течение N часов стал стороной
договора, который создал НЕ он. Это ответ на вопрос §5.1 «пришёл в конкретную сделку»
(документ называет его основным сценарием входа) — и это ФАКТ, две метки времени, а не прокси
(§1 п.1). Атрибуции «кто привёл» здесь нет и не подразумевается: метрика отвечает на «за чем
пришли», а не «кто позвал», и подменять одно другим было бы ровно тем самым самообманом,
который §0 запрещает применительно к GMV.

### 7. Ровно один поведенческий слой — шаги конструктора

`ConstructorStepEvent` (§8.1) заведён потому, что брошенный черновик иначе неизмерим:
доменного события «бросил на шаге 3» не существует и не должно существовать. Условия, на
которых слой существует, — часть решения, а не пожелание: только экран конструктора, без
персональных данных (ни пользователя, ни IP, ни значений полей), хранение 90 дней
отдельной периодической задачей. Юридические факты остаются только в outbox: событие
конструктора ничего не утверждает о договоре — оно утверждает о форме.

Приёмник требует аутентификации. Это не про персональные данные, а про защиту от мусора:
анонимная запись без лимита позволила бы кому угодно залить витрину выдуманными шагами, а
мастер договора и так живёт за логином — для продукта ограничение бесплатное. Личность
аутентифицированного пользователя в событие НЕ ПОПАДАЕТ: она нужна только на входе.

## Последствия

* Появляется четвёртая точка правды о схеме БД (SQL витрин) — переименование колонки в
  чужом приложении ломает пересчёт. Ловится тестами витрин, чинится правкой одного файла.
* Метрики отстают на час. Для «здоровья» (§7) это неприемлемо — недоставленное юрзначимое
  уведомление нельзя увидеть с часовой задержкой, — поэтому `/health` считается по живым
  таблицам, а не по витринам.
* Снимки метрик лежат в git (§9.2): витрины пересчитываются и переписывают прошлое, снимок
  фиксирует, что мы видели в тот день.

## Чего измерить сегодня нельзя и почему это отдано наружу как `null`, а не как `0`

Ноль в этих полях читался бы как измеренный факт, то есть как неправда. Ответ содержит
`available: false` и причину.

| Метрика (§) | Причина | Что разблокирует |
|---|---|---|
| K-фактор, время жизни приглашения, обратная виральность (§5.3) | сущности приглашения в домене нет — см. §6 выше | решение владельца по `invites-design-proposal-2026-08-28.md` (вариант C) |
| Разрыв «страна по IP vs выбранная страна» (§4.1) | код страны по IP при регистрации нигде не сохраняется | колонка кода страны ISO-3166 на регистрации; сырой IP не хранить никогда |
| Шаг отвала черновика (§5.2, §10 строка 12) | нет данных, пока фронт не шлёт события конструктора | приёмник готов (`POST /v1/analytics/constructor-step`), отправка — ветка `feat/web-analytics-steps` |
| Доступность API 99,9 (§7) | считается по Prometheus, не по БД | `docs/performance-capacity.md` |

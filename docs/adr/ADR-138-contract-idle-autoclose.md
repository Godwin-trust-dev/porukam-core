# ADR-138. Автозакрытие сделки без движения: учёт движения, дедлайн `contract_idle`, предупреждение за две недели

- Статус: принято
- Дата: 2026-08-26
- Ветка: `feat/contracts-idle-autoclose`
- Связано с: ADR-137 (сроки хранения — требование 8 и «Ранее открытые
  вопросы» п.2, решение владельца 26.08), ADR-057 (ЛК как юрканал и якорь
  дедлайнов), ADR-064 (outbox-реле, at-least-once), ADR-065 (глобальные
  подписчики «*»), ADR-072 (свип доменных дедлайнов), ADR-098
  (самодостаточный payload), ADR-126 (матрица «действие → событие →
  уведомление»), ADR-130 (зеркало платежей в этапе), ADR-131 (потолок спора
  30 дней, `cap_reached` оставляет этап `disputed`)

## Контекст

ADR-137 зафиксировал: сроки хранения считаются «от окончания договора», а
у сделок, которые стороны просто бросили, окончания нет. Решение владельца:
**3 месяца без движения → сделка считается завершённой**, далее обычный
цикл хранения; **движение — любая активность по сделке, включая переписку
в чате**; сторонам — **предупреждение за две недели**.

В коде до этой ветки не было ни понятия «движение по договору», ни
состояния, в которое можно перевести брошенный `in_progress`-договор:
`EXECUTION_FSM` знала только `in_progress → completed → warranty → closed`
(все листья оплачены) и расторжения.

## Решение

### 1. Движение = действие стороны, метка на договоре

`Contract.last_activity_at` (миграция contracts/0009, `default=timezone.now`;
бэкфилл — max(дата последнего outbox-события по договору, `created_at`)).

Метку двигает **подписчик на ключе «*»** реестра `OUTBOX_SUBSCRIBERS` —
`apps.contracts.handlers.handle_contract_activity`, а не список из ~50
топиков: новый топик семейства (следующий `dispute.*`, `payment.*`)
считается движением сам собой. Критерии:

- топик из семейств договорного контура (`contract.`, `negotiation.`,
  `amendment.`, `milestone.`, `payment.`, `dispute.`, `evidence.`,
  `message.`, `warranty.`);
- у события есть **`actor.user_id`** — движение это действие СТОРОНЫ.
  Системные события (свип дедлайнов, `milestone.auto_accepted`,
  `payment.overdue`, `dispute.cap_reached`, само `contract.auto_closed`)
  актора не имеют и метку не двигают: иначе автоприёмка по тайм-ауту
  «оживляла» бы договор, по которому никто ничего не делает, и цикл никогда
  не сходился бы;
- договор — из `subject.id` (type=contract) / `subject.contract_id` /
  `payload.contract_id` — тот же резолв, что у `apps.notifications.subscriber`.
  Чужие модели apps.contracts не импортирует.

Момент движения — `occurred_at` события, не время доставки.
`record_contract_activity` **монотонна и идемпотентна**: более ранняя или та
же метка — NOOP (реле at-least-once и не гарантирует порядок между темами).

Единственный прямой вызов — из `start_execution`: старт исполнения и есть
первое движение, от которого тикает срок; событие `contract.started` без
актора и через подписчик не прошло бы.

### 2. Дедлайн `contract_idle` — одна строка, перенос, а не новая строка

`DeadlineKindConfig(kind="contract_idle")` = 90 суток (deadlines/0008),
`starts_from=event`, `anchor_at = last_activity_at`. Ведётся **только в
`in_progress`**:

- `pending_start` (подписан, гейт первого листа не пройден) — не тикает;
  стороны, возможно, ждут материалов или аванса, а закрытие договора, по
  которому не начиналось исполнение, — отдельный вопрос владельцу (см. ниже);
- согласование/подписание — свои тайм-ауты (`signature_request_expiry`);
- `warranty` — свой срок (`contract_warranty`), движение по гарантийному
  договору (претензия) метку двигает, но дедлайн idle не заводит.

При каждом движении — `apps.deadlines.services.reschedule_deadline`: новый
`anchor_at`, пересчёт `deadline_at` по актуальной длительности. **Одна
строка на договор**, не строка на каждое сообщение чата. `anchor_deadline`
для этого не годится — он «ровно один раз» (юридическая доставка, ADR-057),
поэтому перенос — отдельный сервис. Досрочное закрытие
(`close_deadline`, без события `domain_deadline.fired`) — когда договор уходит
из `in_progress` (`complete_execution`, `terminate_by_*`): иначе серия
напоминаний продолжила бы слать «договор будет закрыт» по завершённому
договору.

### 3. Предупреждение за две недели — серия напоминаний обеим сторонам

`ReminderPointConfig(kind="contract_idle", template="contract.idle_warning",
points=[1 − 14/90])` (notifications/0023) — тот же механизм, что
`milestone_acceptance_reminder`: строки `ReminderSchedule`, свип каждую
минуту, размещение в ЛК (юрканал), финальная точка — с fallback-SMS. Точка
задана **долей интервала**: при смене срока в `DeadlineKindConfig` её нужно
пересчитать, чтобы предупреждение осталось за 14 суток (задокументировано в
обеих миграциях). В payload напоминания добавлен `days_left` — целых суток до
`deadline_at` на момент отправки (общий для всех серий, тексты
`{days_left}`).

Два изменения в apps.notifications ради двух получателей:

- уникальность `ReminderSchedule` стала (deadline, recipient, point) вместо
  (deadline, point) (notifications/0022) — у `milestone_acceptance`
  получатель один, здесь — обе стороны;
- `replan_reminder_series(deadline, recipients)` — после переноса дедлайна
  план строится **заново**: все прежние точки удаляются, включая уже
  отправленные (они считались от прежнего `anchor_at`; отправленное
  предупреждение относилось к дате, которой больше нет). Размещённые
  `Notification` остаются — удаляется только план.

### 4. Срабатывание: `auto_close_idle_contract`

Свип публикует `domain_deadline.fired` (kind=`contract_idle` либо
`contract_idle_retry`) → `apps.contracts.handlers.handle_deadline_fired` →
use case. Actor — система (пустой, как у `finalize_acceptance(auto=True)`).
Порядок проверок:

1. договор не `in_progress` — NOOP (повторная доставка события, ADR-064;
   либо договор завершился/расторгнут между свипом и доставкой);
2. `last_activity_at > deadline.anchor_at` — **гонка**: свип выстрелил, а
   движение случилось до доставки. NOOP, исход дедлайна `stale`; новую
   строку `contract_idle` уже завёл `record_contract_activity`;
3. **есть незавершённые действия сторон** — отсрочка (ниже);
4. иначе `in_progress → closed` переходом `auto_close_idle` + событие
   `contract.auto_closed` (`reason=idle`, `idle_days`, `last_activity_at`,
   `parties`) → уведомление обеим сторонам.

**Почему сразу `closed`, а не `complete_execution` → `warranty`.** Работы не
приняты и не оплачены (иначе `complete_execution` уже сработал бы на
последнем оплаченном листе). «Завершённым» такой договор не был:
`contract.completed` считает репутация (ГВ.4) как исход, гарантия — на
принятый результат, а `warranty` добавил бы ещё 180 дней до `closed` и
отодвинул бы цикл хранения ADR-137 («3 месяца → завершён → год архива»).
`contract.closed` тоже НЕ публикуется: этот топик означает «гарантийный
срок истёк» (текст уведомления), второе уведомление о том же моменте было
бы дублем (ADR-126 §4). Самостоятельный исход — тем же приёмом, что
`dispute.cap_reached` рядом с `dispute.resolved` (ADR-131 §5).

**Следствие для потребителей «договор окончен».** Э6 (хранение, ADR-137,
`feat/evidence`) и любой другой потребитель, слушающий
`contract.completed/closed/terminated`, обязан добавить
`contract.auto_closed` в свой список. Репутация его сознательно НЕ считает.

### 5. Что блокирует автозакрытие — и что с этим делать

Блокируют **этапы в статусах `under_acceptance` и `accepted`**:

- `under_acceptance` — окно приёмки тикает, исход впереди (действие
  заказчика либо автоприёмка);
- `accepted` — принят, но не оплачен (ADR-130: `accepted → paid` только по
  двусторонней отметке). Закрыть договор с долгом за принятую работу —
  ущемить исполнителя.

НЕ блокируют: `pending`, `in_progress`, `suspended` (ждать материалов 90 дней
без единого действия — это и есть «без движения»), `disputed`. Последнее —
осознанно: открытый спор живёт не дольше 30 дней (ADR-020) и порождает
события с актором; к 90-му дню без движения спор либо закрыт диалогом, либо
`cap_reached` — а тот оставляет этап `disputed` навсегда (ADR-131 §5).
Считать это блокером значило бы никогда не закрывать договоры, ушедшие в
суд, и вечно слать по ним уведомления.

Отсрочка: `DomainDeadline(kind="contract_idle_retry")` = 14 суток от
«сейчас» (deadlines/0008), исход сработавшего дедлайна `postponed`, событие
`contract.idle_blocked` (`idle_days`, `retry_days`, `pending` —
{статус: число этапов}) → уведомление обеим сторонам «есть незавершённые
действия, через 14 дней проверка повторится». Оно же — предупреждение за
две недели для следующей попытки. По истечении — тот же use case: препятствия
сняты → закрытие; остались → новая отсрочка и новое уведомление. Движение
во время отсрочки закрывает её (исход `activity`) и заводит `contract_idle`
заново — стороны ведут именно то действие, ради которого её давали.

Определение блокеров — по статусам этапов (`contract.milestones`, обратная
связь FK, значения по строке), без импорта apps.payments/apps.disputes:
платежи зеркалятся в статус этапа (ADR-130), споров дольше потолка не бывает.

### 6. API

`ContractSerializer`: `last_activity_at` (поле), `idle_deadline_at`
(`deadline_at` активного `contract_idle`/`contract_idle_retry`; `null` вне
`in_progress`) — фронту есть что показать под предупреждением.

## Уведомления (реестры ADR-126)

`contract.idle_blocked`, `contract.auto_closed` — системные события без
актора → `NOTIFICATION_TOPIC_COUNTERPARTY_TEMPLATES`, обеим сторонам.
`contract.idle_warning` — не топик, а шаблон серии напоминаний (в реестрах
его нет, как и `milestone_acceptance_reminder`). Все три юрзначимы. Лента:
`deadline`/«Дедлайны» (`idle_warning`, `idle_blocked` — `due`; `auto_closed`
— `normal`). Тексты — во все 29 пакетов
(`l10n/patches/adr-138-idle-autoclose.json`, `pack_version` +1 каждого,
`packs.lock.json` обновлён); строки `NotificationTemplate` —
notifications/0023 с пустым `body_i18n`.

## Последствия и осознанные хвосты

- Глобальный подписчик — одна дополнительная выборка договора + UPDATE на
  каждое событие с актором. Для in_progress-договоров ещё UPDATE дедлайна и
  пересборка 2 строк серии; на объёмах ближайших этапов незаметно.
- `pending_start` без движения не закрывается никогда — вопрос владельцу.
- Вечная отсрочка: договор с принятым, но неоплаченным этапом будет получать
  `contract.idle_blocked` каждые 14 суток без предела. Ограничить число
  повторов (и закрывать принудительно) — вопрос владельцу; технически —
  одна проверка в `auto_close_idle_contract`.
- Точка серии — доля интервала, а не «за N суток»: смена срока требует
  синхронной правки `ReminderPointConfig.points`. Заводить в конфиге
  «отступ от конца» — отдельное расширение серии, если сроки начнут менять
  часто.
- `idle_deadline_at` в списке договоров — запрос на каждый
  `in_progress`-договор страницы (N+1). Если станет заметно —
  prefetch активных дедлайнов селектором списка.
- Топики — строками; при мерже с `feat/contracts-timeline` (реестр
  `apps.contracts.events.Topic`) перевести на `Topic.*`.

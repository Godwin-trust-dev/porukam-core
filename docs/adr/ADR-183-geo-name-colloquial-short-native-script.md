# ADR-183. Разговорные/короткие имена и латинская транслитерация под чужой локалью в geo-справочнике

**Статус:** принято (продолжение ADR-179/ADR-181 — импорт названий городов/регионов из GeoNames)
**Контекст:** 11.09 сделан справочник `apps.geo` (ADR-179), 11.09 (часть 2b) — имена на языке
зрителя из подушевых файлов GeoNames alternatenames (ADR-181). 12.09 импорт прогнали на проде
(68 стран, 28 605 городов, 146 012 имён городов, 38 861 имя регионов), и владелец нашла на живых
данных России ДВА дефекта: регион «Ставропольский край» показывался разговорным «Ставрополье»;
город «Ставрополь» показывался латиницей «Stavropol’» (с типографским апострофом). Главный
(системный) дефект — регионы: «Пятигорск как город есть, проблема была со Ставропольский край»
(владелец, 12.09) — города по России в целом на месте и на русском.
**Номер:** 183 — сверено по всем ворктри (`ls ~/porukam-worktrees/*/docs/adr ~/porukam/docs/adr
| grep -o 'ADR-[0-9]*' | sort -u`, максимум был 182; 184 занят параллельной задачей, не берём).

## Факты (шаг 0 — прогон импорта по RU на реальном дампе, до каких-либо правок)

Локально поднята dev-БД (Postgres в Docker, `compose-postgres-1`), прогнан
`import_geo --download --countries=RU` (в коде ДО этой ветки — только `is_preferred`/`is_historic`
читались из подушевого файла, колонки 5/6 источника — `isShort`/`isColloquial` — не читались вовсе).
Результат: страны=1, регионы=83, города=1108, имена городов=7969, имена регионов=2406.

### Дефект 1 (регионы) — реальная причина НЕ `isColloquial`, а `isShort`

`RegionName` для Ставропольского края (geonameid 487839), локаль `ru`:

| alternateNameId | name                 | isPreferred | isShort | isColloquial | isHistoric |
|-----------------:|----------------------|:-----------:|:-------:|:-------------:|:-----------:|
| 2298599          | Ставрополье          | 1           | **1**   | 0             | 0           |
| 8656359          | Ставропольский Край  | 0           | 0       | 0             | 0           |

Прежний код выбирал `ORDER BY -is_preferred, id` среди `is_historic=False` — «Ставрополье» с
`isPreferred=1` побеждало безоговорочно. Задание при постановке предполагало, что причина —
непрочитанный флаг `isColloquial`; **факт опровергает это**: `isColloquial` у «Ставрополье» равен
`0`, разговорность здесь помечена ИСКЛЮЧИТЕЛЬНО `isShort=1`. Проверка на всех 83 регионах RU
(скрипт по сырому `RU.txt`, до правки кода) показала — это НЕ единичный случай: **26 из 83
регионов (31%)** показывались бы коротким именем вместо официального (Татарстан→«Татарстан»
вместо «Республика Татарстан», Карелия, Коми, Дагестан, Чечня, ХМАО, ЯНАО, Кузбасс и т.д.) —
системный дефект, не разовая аномалия источника.

### Дефект 2 (город Ставрополь) — реальная причина НЕ «имени `ru` нет», а тай-брейк между двумя `ru`-строками

`CityName` для Ставрополя (geonameid 487846), локаль `ru` — их ДВЕ, обе `isPreferred=0`:

| alternateNameId | name         | isPreferred | isShort | isColloquial | isHistoric |
|-----------------:|--------------|:-----------:|:-------:|:-------------:|:-----------:|
| 3738190          | Stavropol’   | 0           | 0       | 0             | 0           |
| 5961934          | Ставрополь   | 0           | 0       | 0             | 0           |

Имя `ru` в источнике ЕСТЬ и корректно («Ставрополь») — задание допускало версию «имени `ru` нет
вовсе», это не так. Ни один флаг не отличает эти две строки; `alternateNameId 3738190` (латинская
BGN/PCGN-транслитерация — апостроф U+2019 передаёт мягкий знак) просто МЕНЬШЕ, а прежний тай-брейк
`ORDER BY ..., id` брал первую по возрастанию `id` — то есть латинскую. Проверка по всем 1108
городам RU (сгруппировано по `city_id` для `locale='ru', is_preferred=0, is_historic=0`, счётчик
кандидатов > 1) нашла **47 городов** с такой неоднозначностью, но только **2 из 1108 (≈0,2%)**
показывали БЫ латиницу — geonameid 487846 (Ставрополь) и geonameid 504250 (Пугачёв: аналогично,
`3738190`-подобная пара «Pugachëv»/«Пугачёв»). В остальных 45 случаях латинская строка случайно
получила БОЛЬШИЙ `id`, и старый код угадывал верно. **Вывод: единичная особенность конкретных
записей источника (не системная дыра импорта)** — но раз дефект детерминирован (не рандомен) и
проверяемо воспроизводится, чинится общим правилом, а не патчем под два geonameid.

## Решение

### Хранить `isColloquial`/`isShort` из источника — обе колонки, не одна

`CityName`/`RegionName` получают поля `is_colloquial`/`is_short` (колонки 6/5 подушевого файла —
`0 alternateNameId, 1 geonameid, 2 isolanguage, 3 name, 4 isPreferred, 5 isShort, 6 isColloquial,
7 isHistoric, 8 from, 9 to`), заполняются на импорте (`services.import_alternate_names`).
Разговорное имя может быть помечено ЛЮБЫМ из двух флагов по отдельности (факт «Дефекта 1» выше) —
хранить нужно оба, фильтровать по обоим.

### Правило выбора отображаемого имени: полная форма → фолбэк на короткую/разговорную → НИКОГДА историческая

Как и `is_historic` (ADR-181), `is_colloquial`/`is_short` участвуют в ПОИСКЕ наравне с текущими
именами (`apps.geo.selectors` не фильтрует ни один из этих флагов — «Ставрополье» обязано находить
Ставропольский край, «Алма-Ата» — Алматы), но НЕ в отображении по умолчанию.

Отличие от `is_historic` — НЕ абсолютное правило, а фолбэк-иерархия
(`services._names_by_locale_with_fallback`):

1. Кандидаты БЕЗ `is_historic`, БЕЗ `is_colloquial`, БЕЗ `is_short` («полная форма») —
   `-is_preferred`, затем тай-брейк по родной письменности (ниже), затем `id`;
2. если для локали у объекта НЕТ НИ ОДНОГО такого кандидата — фолбэк на `is_historic=False`
   (короткие/разговорные РАЗРЕШЕНЫ), тот же порядок внутри;
3. `is_historic=True` не участвует НИКОГДА, даже как последний фолбэк.

Абсолютное исключение (без фолбэка) сначала казалось правильным и для `is_short`/`is_colloquial` —
но проверка на ПОЛНОМ RU-датасете после первой версии правки вскрыла регрессию: у города Мурманск
(geonameid другой, `ru`) источник помечает САМО действующее имя «Мурманск» одновременно
`isPreferred=1, isShort=1, isColloquial=1` — полной формы для этого места в источнике нет вообще,
только исторические («Романов-на-Мурмане», «Романов», «Семёновский») и явные прозвища («столица
Заполярья», «рыбная столица», «столица Арктики»). Абсолютное исключение оставило бы Мурманск без
`ru`-имени вовсе (откат на `City.name` = латиница) — хуже, чем показать «Мурманск», которое и так
единственное реальное имя места на этом языке, просто ошибочно помечено источником. Отсюда —
фолбэк-иерархия, а не жёсткий запрет. На полном RU-прогоне после правки таких случаев (объект,
показываемый коротким/разговорным именем, при отсутствии полной формы) — 2: Мурманск и Свиблово
(район Москвы); ни один регион в эту категорию не попал (у всех 26 «сломанных» регионов полная
форма в источнике ЕСТЬ, просто раньше проигрывала `isPreferred`-конкуренту).

### Тай-брейк «латинская транслитерация под чужой локалью» — по диапазону СКРИПТА, не по ASCII

Первая версия правила для Дефекта 2 была «предпочесть кандидата с хотя бы одним НЕ-ASCII
символом» — оказалась НЕДОСТАТОЧНОЙ, проверено фактом: апостроф U+2019 в «Stavropol’» САМ ПО СЕБЕ
уже не ASCII, поэтому проверка «есть непустой не-ASCII символ» не отличала «Stavropol’» от
настоящей «Ставрополь» — обе проходили. Рабочее правило — проверка по ДИАПАЗОНУ СКРИПТА локали
(`apps.geo.constants.LOCALE_SCRIPT_RANGES`: кириллица для `ru`/`kk`/`uk`, арабское письмо для
`ar`/`fa`/`ur`, иврит, армянское, грузинское, деванагари, бенгальское, тайское, хань+кана
(`ja`/`zh-Hans`), хангыль (`ko`)) — среди кандидатов с ОДИНАКОВЫМ `is_preferred` внутри одного
уровня фолбэк-иерархии побеждает тот, что содержит хотя бы один символ родной письменности локали.
Локали с латинским письмом (`az, de, en, es, fr, id, it, pl, pt-BR, ro, sw, tr, uz, vi`) в словарь
сознательно не входят — тай-брейк для них не применяется, поведение не меняется (то же самое, что
`id` было единственным правилом до ADR-183).

Индексы `geo_city_name_refresh_idx`/`geo_region_name_refresh_idx` расширены новыми колонками
фильтра (`is_colloquial`, `is_short`) — новая миграция `geo/0003` (см. «Деплой»).

### Команда аудита — `manage.py geo_name_audit`, только чтение

Владелец просит регулярную проверку прода на такие случаи. `apps.geo.selectors.
audit_region_name_coverage`/`audit_city_name_coverage` (селектор — только чтение, никакой записи)
+ тонкая CLI-обёртка `geo_name_audit` (`--locale=ru --countries=RU,KZ,BY --limit=50`, оба
параметра необязательны): по каждой стране — сколько объектов показываются латиницей (имени
локали нет вовсе) и сколько — разговорным/коротким именем (фолбэк-уровень 2 выше), плюс примеры.
**Регионы печатаются первыми** (владелец, 12.09 — главный дефект был там). Реальный вывод на
RU-датасете после исправления:

```
--- РЕГИОНЫ ---
Всего: 83; латиницей: 0 (0.0%); разговорным/коротким: 0 (0.0%)
Проблем по странам нет — все показываются полной формой.

--- ГОРОДА ---
Всего: 1108; латиницей: 7 (0.6%); разговорным/коротким: 2 (0.2%)
По странам (только с проблемами):
  RU: всего=1108 латиница=7 (0.6%) разг/кор=2 (0.2%)
Примеры «латиница, имени 'ru' нет»: Kisilevsk, Kurortnyy, Narian-Mar, Obruchevo,
  Petrodvorets, Roshal', gorod Solnetchnogorsk (источник не даёт `ru`-альтернативу вовсе —
  не дефект импорта, а пробел в самих данных GeoNames для этих 7 объектов).
Примеры «разговорное/короткое имя (полной формы нет)»: Murmansk → 'Мурманск', Sviblovo → 'Свиблово'.
```

## Дополнение 12.09 — регистр родовых слов в названиях регионов

После первого прохода владелец проверила фикс на живых данных: регион 70 → «Ставропольский Край»
вместо «Ставрополье» (дефект исправлен), НО вылез хвост — GeoNames отдаёт русские альтернативные
имена регионов **в Title Case** («Ставропольский Край», «Амурская Область», «Чукотский
Автономный Округ»), а официальная орфография (и постановка владельца — «Ставрополья**к**рай»)
требует родовое слово со строчной буквы. Проверено на всех 83 регионах RU-датасета: **54 из 83**
показывались бы с заглавной в родовом слове (владелец насчитала 72 на промежуточном срезе —
расхождение из-за момента подсчёта, не в сути дефекта).

### Решение — список родовых слов по локали, не «lower() всего подряд»

`apps.geo.constants.GENERIC_TERM_LOWERCASE: dict[str, frozenset[str]]` — для `ru`:
`{"край", "область", "округ", "автономный", "автономная", "автономное"}` (три рода
прилагательного «автономный», т.к. согласуется с родом существительного — «Автономный округ»,
«Автономная область»). `normalize_generic_terms(name, locale)` — регекс со словом-границей
(`\b...\b`, `re.IGNORECASE`), приводит найденное слово к строчным, **ЕСЛИ ОНО НЕ ПЕРВОЕ В
СТРОКЕ** (`match.start() != 0`) — первое слово названия остаётся как дал источник (в реальном
RU-датасете родовое слово первым не встретилось, но правило универсально, не привязано к
конкретным значениям).

**«Республика» сознательно НЕ входит в список** (владелец: «не трогать») — официальная
орфография капитализирует это слово в ЛЮБОЙ позиции: и «Республика Адыгея» (первое слово), и
«Чеченская Республика» (второе слово) равно правильны с заглавной — это не родовое слово вроде
«край»/«область», которое лишь классифицирует объект, а часть официального наименования формы
правления субъекта. Отдельно от него есть исходно-строчные варианты источника («Ингушская
республика», «Хакасская республика», «Карельская республика») — их регистр тоже НЕ трогаем
(они не в списке, значит вообще не проходят через `normalize_generic_terms`).

Применяется **только в точке выбора отображаемого имени** — единственный вызов внутри
`services._select_best_names` (общая для `refresh_city_name_i18n`/`refresh_region_name_i18n`,
обеих ветвей фолбэк-иерархии выше). Сырые `CityName.name`/`RegionName.name` в БД НЕ меняются —
поиск (`apps.geo.selectors`) по-прежнему видит и находит написание источника один в один, включая
Title Case («ставропольский край» находит регион и по строчному, и Title Case запросу — префиксный
поиск через `Lower()` регистронезависим в любом случае, ADR-181).

Побочный эффект: `selectors._audit_name_coverage` (аудит) сравнивает текст `name_i18n[locale]`
с сырыми `CityName.name`/`RegionName.name`, чтобы понять, разговорное/короткое ли сейчас имя
показано — раз `name_i18n` теперь хранит НОРМАЛИЗОВАННЫЙ текст, сравнение нормализует и сырую
строку той же функцией перед сверкой (иначе разговорное/короткое имя, случайно содержащее родовое
слово в Title Case, не совпало бы само с собой).

### Другие локали с нелатинским письмом — проверены, той же болезни нет

Владелец предложила проверить `uk, kk, be, bg, sr, mk`. Из них в `LOCALE_TO_GEONAMES_LANGS`
реально есть только `uk` и `kk` (`be`/`bg`/`sr`/`mk` в проекте нет вовсе — 29 локалей `l10n/
packs/*.json`, не выдумываем несуществующие). Проверено на живом RU-дампе (все 83 региона,
locale=`uk`/`kk`, `is_historic=is_colloquial=is_short=False`):

- `uk` — родовые слова УЖЕ строчные в источнике («Ставропольський край», «Амурська область»,
  «Ненецький автономний округ») — дефекта нет, добавлять правило не нужно;
- `kk` — вообще не использует отдельное родовое слово: постпозитивный суффикс, слитный с
  топонимом («Ставрополь өлкесі», «Ярославль облысы», «Ненец округі») — категория «родовое
  слово Title Case» к этой языковой конструкции неприменима.

**Не выдумываем правило для `be`/`bg`/`sr`/`mk`** — их нет в справочнике вовсе; если появятся
(новый языковой пакет), проверка на реальных данных ЭТОЙ локали обязательна ПЕРЕД добавлением
записи в `GENERIC_TERM_LOWERCASE` — см. «Пределы» ниже.

### Проверено на всех 83 регионах RU (до/после)

54 региона изменились, 29 — без изменений (уже без родового слова в Title Case, либо это

## Деплой

1. Миграция `geo/0003` (новая; `0001`/`0002` уже применены на проде — НЕ трогать): добавляет
   `is_colloquial`/`is_short` в `CityName`/`RegionName`, пересоздаёт оба `*_refresh_idx` под новый
   набор фильтров. Безопасна и быстра (только DDL — `ADD COLUMN ... DEFAULT false` + переиндексация
   двух таблиц, не миллионы строк).

2. **Флаги заполняются ТОЛЬКО на импорте** — существующие на проде строки `CityName`/`RegionName`
   после миграции получат `is_colloquial=False, is_short=False` по умолчанию, что для строк,
   реально являющихся короткими/разговорными в источнике (например «Ставрополье»), — НЕВЕРНО,
   пока их не перечитать из подушевого файла. Простой пересчёт `name_i18n` из УЖЕ имеющихся в БД
   строк `CityName`/`RegionName` (без повторного скачивания источника) дефект НЕ исправит — сами
   значения флагов в БД будут пустыми до повторного импорта строк из `alternatenames/<CC>.zip`.

3. **Регистр родовых слов (доп. 12.09) — без НОВОЙ миграции**: `GENERIC_TERM_LOWERCASE`/
   `normalize_generic_terms` — чистый код (константа + функция), не схема; применяется в той же
   точке (`services._select_best_names`), что и остальной выбор `name_i18n` — тот же
   `import_geo --names-only` (шаг 4 ниже) пересчитывает `name_i18n` уже с учётом нормализации,
   отдельного деплой-шага не нужно.

4. **Полный повторный импорт (страны+регионы+города+имена) НЕ требуется** — `countryInfo.txt`/
   `admin1CodesASCII.txt`/`cities15000.zip` этой веткой не затронуты, City/Region не меняются.
   Нужно только доимпортировать `alternatenames/<CC>.zip` (заполнить новые флаги в уже
   существующих строках `CityName`/`RegionName` по натуральному ключу `geonames_alt_name_id` —
   `bulk_create(update_conflicts=True)`, идемпотентно) и пересчитать `name_i18n`. Для этого —
   явный ключ команды **`import_geo --names-only`** (новый в этой ветке): не скачивает и не
   разбирает три базовых файла вообще, качает/читает только `alternatenames/<CC>.zip` по странам,
   которые УЖЕ есть в справочнике (`selectors.list_countries()`, а не `DEFAULT_COUNTRY_CODES`), и
   пересчитывает `name_i18n`. Порядок деплоя на проде:
   ```
   python manage.py migrate geo
   python manage.py import_geo --names-only --download   # без --countries — все страны справочника
   python manage.py geo_name_audit --locale=ru --limit=50
   ```
   Второй шаг качает *все* подушевые файлы alternatenames заново (по одному ZIP на страну — то же
   сетевое время, что и обычный `import_geo --download`, ADR-181 «Импорт», просто БЕЗ трёх базовых
   файлов) — ощутимо дешевле по данным, чем полный прогон, но НЕ дешевле по числу HTTP-запросов;
   учитывать в окне деплоя так же, как обычный повторный `import_geo`.

## Последствия

- Новая миграция `geo/0003` (2 булевых поля × 2 таблицы + 2 пересозданных индекса).
- `manage.py import_geo --names-only` — новый режим, для деплоя ADR-183 и для будущих аналогичных
  ситуаций (правка только логики разбора/выбора имён без изменения набора City/Region).
- Новая read-only команда `manage.py geo_name_audit` — постоянный инструмент владельца, не
  разовый скрипт.
- Фолбэк-иерархия (полная форма → короткая/разговорная → НИКОГДА историческая) — общее правило
  для `refresh_city_name_i18n`/`refresh_region_name_i18n`; проверять на реальных данных при
  добавлении новых стран стоит через `geo_name_audit`, а не читать код.
- `LOCALE_SCRIPT_RANGES` покрывает 15 из 29 локалей (нелатинописьменные) — при добавлении новой
  локали с нелатинским письмом в `LOCALE_TO_GEONAMES_LANGS` стоит проверить, нужен ли ей диапазон
  здесь (иначе для неё тай-брейк «Дефекта 2» просто не будет применяться, поведение — старое,
  тай-брейк по `id`).
- `GENERIC_TERM_LOWERCASE` (доп. 12.09) сейчас — только `ru`. **Пределы**: `uk`/`kk` проверены на
  реальном RU-дампе и не нуждаются в записи (см. «Дополнение 12.09» выше); для любой другой
  локали (в т.ч. `be`/`bg`/`sr`/`mk`, которых пока нет в `LOCALE_TO_GEONAMES_LANGS` вовсе) запись
  добавлять ТОЛЬКО после проверки на реальных данных ЭТОЙ локали (нужно знать: (1) есть ли у неё
  вообще отдельное родовое слово, а не постпозитивный суффикс, как у `kk`; (2) в каком регистре
  его реально отдаёт GeoNames) — придумывать список слов по аналогии с русским нельзя.

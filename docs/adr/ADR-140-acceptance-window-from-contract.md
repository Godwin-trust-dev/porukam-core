# ADR-140. Окно приёмки этапа — из условий договора, а не только из категории дедлайна

**Статус:** принято (решение владельца 2026-08-27)
**Контекст:** apps.milestones, apps.deadlines, apps.contracts (формы)

## Контекст

Форма договора услуг (`apps/contracts/forms.py`, секция `acceptance`, блок K7) содержит
поле `acceptance_window_hours` (default 72, min 1) — стороны видят и подписывают его как
условие договора. Но системный дедлайн `milestone_acceptance` создавался с длительностью
категории из `DeadlineKindConfig` (48 ч, `deadlines 0002`, tech-spec §7), и значение из
договора не читалось нигде: договор обещал одно, автоприёмка наступала по другому.
Найдено 27.08 при написании описательной документации (`docs/platform-capabilities.md`).

Варианты: (а) убрать поле из формы, оставить 48 ч для всех; (б) читать срок из договора.
Владелец выбрал (б): «читать из договора» — условие, которое стороны подписали, обязано
исполняться системой буквально.

## Решение

1. `DomainDeadline.duration_override` (`DurationField`, NULL) — длительность **конкретного**
   дедлайна; `NULL` — длительность категории. Хранится в строке, а не вычисляется при
   анкоринге: `anchor_deadline()` вызывается из `apps.notifications` в момент размещения
   уведомления в ЛК (ADR-057) и знает только дедлайн, не договор.
2. `create_deadline(..., duration=timedelta | None)`; `anchor_deadline` и
   `reschedule_deadline` считают `deadline_at` по `_effective_duration()` = override или
   категория. Override не заменяет конфигурацию категории: строка в `DeadlineKindConfig`
   обязана существовать, как и раньше (иначе `DeadlineKindNotConfiguredError`). Нулевая
   и отрицательная длительность — `ValueError`.
3. `apps.milestones.services`: при `submit`/`resubmit_fix` окно берётся из
   `contract.form_data["acceptance_window_hours"]` (целое ≥ 1, иначе — как отсутствует).
   `form_data` после подписания не меняется (входит в `snapshot` замороженной версии,
   ADR-073), поэтому читаем с договора без обращения к версии.
4. Серия напоминаний по окну приёмки (`ReminderPointConfig`, точки 0.5/0.75/0.9/0.99)
   считается от `deadline_at − anchor_at` и автоматически следует за фактическим окном.

## Последствия

- Типы без поля (продажа, аренда, заём) и старые договоры — прежние 48 ч. Никакой
  миграции данных: override пишется только новым дедлайнам.
- tech-spec §2.5/§7 «приёмка 48 ч» читать как «48 ч по умолчанию, если договор не задал
  своё окно»; правка спеки — отдельным chore.
- Тот же механизм пригоден для других договорных сроков (гарантийное окно, окно осмотра
  при продаже), если владелец решит выносить их в форму.
- Прод: миграция `deadlines 0010` (добавление NULL-колонки, без блокировки).

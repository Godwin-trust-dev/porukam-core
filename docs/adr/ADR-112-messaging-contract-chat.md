# ADR-112. Чат по договору — bounded context `messaging`

Дата: 2026-08-23. Статус: принято.

## Контекст

Отсмотр 2026-08-22: «что с чатом? сейчас не открывается при переходе из
карточки контрагента» — /chat был заглушкой, кнопки «Написать» вели в пустой
раздел. Решение пользователя: чат делать. Переписка в контексте платформы —
не мессенджер общего назначения, а канал по СДЕЛКЕ: договорённости в чате —
потенциальное доказательство в споре (docs/domain-model.md: доказательная
база).

## Решение

1. **Новый bounded context `apps.messaging`** (tech-spec §4 дополнен):
   модель `Message` (contract FK, sender_profile FK, body ≤ 4000, created_at,
   read_at). Переписка привязана к ДОГОВОРУ, не к паре пользователей: у пары
   может быть много сделок, а доказательная ценность — в контексте конкретной.
2. **Append-only**: правок и удалений сообщений нет — как у юрзначимых
   сущностей, хотя само сообщение юрзначимым не является (юрканал — ЛК,
   ADR-057). `evidence`-экспорт переписки в пакет спора — следующая волна.
3. **Read-состояние** — один `read_at`: сторон ровно две, «прочитано» =
   контрагент открыл тред (POST /messages/read, идемпотентно).
4. **API**: `GET/POST /v1/contracts/{id}/messages`,
   `POST /v1/contracts/{id}/messages/read`, `GET /v1/messages/threads`
   (диалоги: последнее сообщение + непрочитанное). Не сторона договора — 404
   (существование не раскрываем).
5. **Уведомление контрагенту** — прямой `place_notification`
   (`message.received`, группа deals) по паттерну `signature_requested`, НЕ
   через outbox-подписчика (тот адресует actor = отправителя). Событие
   `message.created` в outbox публикуется для будущих подписчиков
   (audit/reputation). **Анти-шторм**: пока у получателя висят непрочитанные
   от этого отправителя, новые уведомления не создаются — «звонок в дверь»
   один на серию сообщений; тексты — в l10n-паках (29 языков,
   pack_version +1, lock пересобран).
6. **Доставка в реальном времени** — ПОЛЛИНГ (5–10 с, TanStack Query
   refetchInterval), НЕ WebSocket/SSE: на текущем объёме пользователей это
   на порядок дешевле в инфраструктуре (gunicorn sync-воркеры, без ASGI),
   а UX-разница на переписке по сделке незначима. WebSocket — отдельный ADR,
   когда появится метрика, что поллинг мешает.
7. **Фронт**: раздел /chat (список диалогов) + /chat/{contractId} (тред);
   фич-флаг `chat` включён по умолчанию (навигация показывает «Чат»).

## Отклонено

- Переписка в `social` (контакты) — чат общего назначения без привязки к
  сделке размывает доказательную ценность и юрпозицию платформы.
- WebSocket/Channels сейчас — инфраструктурная цена (ASGI, sticky
  sessions за Cloudflare) без подтверждённой пользы.
- Редактирование/удаление сообщений — конфликтует с ролью переписки как
  доказательной базы.

## Последствия

- tech-spec §4: +1 приложение (`messaging`); import-linter: contracts не
  импортирует messaging; нижний слой не зависит от messaging.
- Кнопки «Написать» получают рабочую цель; открытие чата из карточки
  контрагента без общего договора — пока нечего открывать (чат по сделке);
  UX-вход появится после первого черновика с этим контрагентом.

# ADR-064. Transactional outbox: relay (доставка подписчикам)

**Статус:** принято
**Дата:** 2026-07-30
**Контекст этапа:** ЭФ.1 (`docs/tasks/fundament.md`) — сквозной фундамент, юр-независимая
работа на паузу этапов 4–5.

## Контекст

ADR-060 завёл `common.models.OutboxEvent` и `common.outbox.publish()` — запись события той
же транзакцией, что и доменное изменение, но явно оставил доставку подписчикам («реле»)
нереализованной. `docs/tasks/fundament.md` ЭФ.1 требует ровно эту доставку: выборку
неопубликованных строк, вызов подписчиков по реестру `topic -> задачи`, простановку
`published_at`, ретраи с джиттером и идемпотентность подписчиков по `event_id`.

## Решение

- **Схема.** К `OutboxEvent` добавлены `published_at` (NULL — не доставлено),
  `delivery_attempts`, `next_attempt_at` (служебные поля реле, НЕ часть конверта события
  из tech-spec.md §6.4 — потребители видят только `event_id/topic/occurred_at/actor/
  subject/payload/schema_version`). Частичный индекс на `created_at WHERE published_at
  IS NULL` — под выборку релея.
- **Реестр подписок — данные, не код.** `settings.OUTBOX_SUBSCRIBERS: dict[topic,
  list[dotted.path]]`. Пока пуст в `config/settings/base.py` — реальных подписчиков ещё
  нет (Audit Vault и уведомления — ЭФ.3/ЭФ.4); тестовые сценарии подключают обработчики
  через `override_settings` на время теста. `common.relay` резолвит путь через
  `django.utils.module_loading.import_string` в момент вызова — `common` не получает
  статической зависимости на `apps.*` (остаётся вне графа import-linter, ADR-060).
- **Гранулярность доставки — на уровне СОБЫТИЯ, не пары (событие, подписчик).**
  `published_at` — одно поле на строку. Если хоть один подписчик темы падает, событие
  остаётся неопубликованным целиком и на следующем sweep'е вызываются ЗАНОВО ВСЕ
  подписчики темы, включая уже отработавшие. Отдельная таблица `outbox_delivery`
  (по подписчику) в спеке не описана и здесь не заводится — минимальный вариант,
  достаточный для требований ЭФ.1.
- **Следствие: идемпотентность — обязанность подписчика.** Ровно то, что требует
  fundament.md («event_id — ключ дедупликации»): каждый обработчик должен уметь
  безопасно обработать один и тот же `event_id` повторно. Это не деталь реализации
  релея, а контракт для будущих подписчиков (Audit Vault, уведомления).
- **Ретраи с джиттером — экспоненциальный backoff по `delivery_attempts`,
  `base * 2^(attempts-1)` до `OUTBOX_RELAY_RETRY_MAX_SECONDS`, плюс случайная добавка до
  `OUTBOX_RELAY_RETRY_JITTER_SECONDS`; результат — `next_attempt_at`.** Параметры —
  настройки (`OUTBOX_RELAY_RETRY_*`, `OUTBOX_RELAY_BATCH_SIZE`), не константы в коде.
- **Воркер — периодическая Celery-задача `common.tasks.relay_sweep`, Celery beat каждые
  5 секунд** (`CELERY_BEAT_SCHEDULE["outbox-relay-sweep"]`). Это НЕ sweep доменных
  дедлайнов (CLAUDE.md требует для них отдельный BD-driven sweep раз в минуту, ЭФ.2) —
  разная природа: релей — инфраструктурная доставка, дедлайны — доменные тайм-ауты.
  `django-celery-beat` не добавлен — расписание статическое (как уже было для
  `entities-reconcile-ownership-epochs`), динамическая регистрация подписчикам ЭФ.1 не
  нужна.

## Альтернативы

- **Таблица `outbox_delivery` (событие × подписчик).** Точнее (ретраит только упавших
  подписчиков), но не требуется спекой и добавляет сущность без нынешней необходимости
  — при реальной нагрузке нескольких требовательных подписчиков можно ввести отдельным
  PR.
- **Доставка через `transaction.on_commit()` + немедленный `apply_async()` вместо
  периодического sweep.** Ниже латентность, но теряет надёжность при падении процесса
  между коммитом и постановкой в очередь — sweep остаётся источником истины
  (at-least-once), `on_commit`-путь можно добавить позже как оптимизацию задержки поверх
  того же релея.

## Последствия

- `entity.claimed`/`entity.claim_disputed`/`entity.epoch_changed` (уже публиковавшиеся
  через `common.outbox.publish`, ADR-060/ADR-063) ничего переключать не потребовалось —
  они уже шли через outbox; релей добавляет им доставку.
- `apps.social` пуст (заглушка каркаса) — переключать `social.*` не на что, будет сделано
  в своём этапе.
- Реальные подписчики (Audit Vault — ЭФ.3, уведомления — ЭФ.4) регистрируются в
  `OUTBOX_SUBSCRIBERS` в своих PR; каждый обязан быть идемпотентным по `event_id`.

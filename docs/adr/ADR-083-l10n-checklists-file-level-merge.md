# ADR-083. Переводы чек-листов вливаются в языковые пакеты на уровне файлов, не через второй `import_l10n_pack`

**Статус:** принято
**Дата:** 2026-08-12
**Контекст этапа:** chore/l10n-checklists-merge (продолжение П-03/ADR-081 —
переводческий конвейер чек-листов; заменяет умершую наработку
chore/l10n-checklists-image — та не коммитилась, реверты не нужны)

## Контекст

Первоначальный план (chore/l10n-checklists-image) — второй независимый
деплой-цикл по `l10n/checklists/*.checklists.json` рядом с существующим
циклом по `l10n/packs/*.json` (`.github/workflows/deploy-staging.yml`),
оба гоняют `import_l10n_pack`. Умер на реальном смоуке — собранный образ,
живой Postgres, ручной прогон обоих циклов подряд:

```
CommandError: az: pack_version=1 меньше уже импортированного (2)
```

Причина структурная, не флюк окружения или порядка прогонов:

- `LocalePack` (`backend/apps/l10n/models.py`) — одна строка на `Locale`.
  `pack_version` и `checksum` считаются на пакет **целиком** — так
  спроектировано в ADR-077 («версия ЭТОГО файла целиком (шапка + все
  namespaces)»), не по отдельному namespace.
- `apps.l10n.services.import_pack` на обновлении делает `existing.content
  = data` — полную замену JSONField, не merge по ключам.
- `l10n/packs/<code>.json` и `l10n/checklists/<code>.checklists.json`
  пересекаются по всем 26 локалям, для которых существуют переводы
  чек-листов.

Значит, второй `import_l10n_pack` на ту же locale в одном деплое либо
падает по версии (как выше — безопасный отказ: `|| exit 1` стоит ДО
`docker compose up -d`, старые контейнеры продолжают отвечать трафику),
либо, если версию поднять искусственно, «успешно» **молча стирает**
`errors`/`notifications`/`ui`/`legal` целевой локали — в БД остаётся
только то, что принёс последний прогон.

## Решение

**Вариант B.** `import_pack`, модель `LocalePack`, деплой-цикл
`deploy-staging.yml` — не трогаем; они и дальше видят ровно один файл на
locale, один `pack_version`, одну запись.

Переводы чек-листов вливаются в `l10n/packs/<code>.json` как namespace
`catalog.checklists` **на этапе подготовки контента**, скриптом
`l10n/merge_checklists.py` (запускается вручную/CI content-джобой, не
деплоем):

- Вход — строго маска `l10n/checklists/*.checklists.json`.
  `_source.ru.json` (исходник для переводчиков, регенерируется
  `export_checklists_i18n`, ADR-081) под неё не попадает по имени и в
  merge не участвует.
- Валидация ДО любой записи, по каждому файлу независимо: `locale` шапки
  = коду в имени файла; `rtl` шапки = `rtl` целевого `l10n/packs/<code>.json`;
  набор ключей `catalog.checklists` побайтово (по множеству ключей)
  совпадает с `_source.ru.json`; ни одно значение не содержит маркер
  `[Л]`/`[L]` (ADR-081, дополнение 12.08); ни одного пустого значения.
  Отказ по одному файлу не пишет на диск и не блокирует обработку
  остальных.
- Слияние — только подключ `catalog.checklists` целевого пакета; остальные
  namespace и остальные подключи `catalog` (`spheres`/`contract_types`/
  `client_tree`) не трогаются. `pack_version` читается из текущего файла
  пакета и увеличивается на 1 — не хардкодится, порядок повторных прогонов
  не ломает счётчик.
- Идемпотентность: если `catalog.checklists` пакета уже равен вливаемому —
  no-op, `pack_version` не растёт. Прод по-прежнему получает переводы
  чек-листов ОБЫЧНЫМ циклом `import_l10n_pack` по `l10n/packs/*.json` —
  для него это просто ещё один namespace внутри уже знакомого файла.
- `l10n/checklists/` остаётся staging-каталогом переводчиков — ни
  деплой, ни Dockerfile его не видят (проверено: `git grep -n
  "l10n/checklists" -- .github Dockerfile .dockerignore` пуст).

## Альтернативы

- **Вариант A — merge по namespace внутри `apps.l10n.services.import_pack`**
  (принимать несколько файлов на одну locale, мержить, а не заменять
  `content`). Отклонено: рассыпается сама семантика идемпотентности
  ADR-077 — один `checksum` от содержимого целиком и один `pack_version`
  на locale не переживают два независимых файла с независимой историей
  правок один и тот же контракт «тот же `pack_version` ⇒ тот же
  checksum» перестаёт быть проверкой на неизменность, а не просто разными
  описаниями одного и того же среза. Честная версия A требует
  версионирования по namespace — отдельного поля/таблицы на пакет,
  миграции схемы `LocalePack` и пересмотра контракта `import_l10n_pack`
  (`l10n/README.md` «Импорт») — несоразмерно задаче «добавить один
  namespace одному существующему конвейеру».
- **Оставить второй независимый деплой-цикл (chore/l10n-checklists-image)**
  и просто починить маску/COPY-путь. Отклонено смоуком выше — маска и
  COPY были верным диагнозом для ДРУГОЙ, более мелкой ловушки (та
  починка сохранена ниже в «Последствия» как полезный побочный результат
  расследования), но не устраняют структурную несовместимость двух
  независимых источников на одну версионируемую целиком запись.

## Последствия

- `l10n/README.md` — строка «checklists/materials… подхватываются тем же
  `import_l10n_pack`» была неточна (описывала путь, который не пережил
  смоук); заменена на актуальный путь: патч-проход (снятие `[Л]`/`[L]`,
  сверка с `_source.ru.json`) → `merge_checklists.py` → `l10n/packs/` →
  обычный деплой-цикл.
- Фактический прогон `merge_checklists.py` по всем 26 локалям — **не в
  этой ветке**. На 12.08.2026 все `l10n/checklists/*.checklists.json`
  сознательно НЕ проходят валидацию скрипта (23 маркера `[Л]`/`[L]` и 1
  лишний ключ `sales.other.inspection.3` — подтверждено на `az` в этой же
  сессии) — это ожидаемое состояние, ждёт отдельного патч-прохода по всем
  файлам (аналог патча en/ru в `chore/l10n-patch-v2`, PR #67). После
  патча — прогон скрипта, затем `l10n/packs/*.json` едут обычным
  деплой-циклом; для `ru` уже применяется отдельная логика diff/подтверждения
  реимпорта (`l10n/README.md` «Реимпорт ru»), добавленные merge'ем ключи
  вопросов не задают (ADR-077: добавленный ключ — не конфликт).
- Диагностика умершего варианта (маска строго `*.checklists.json`, не
  `*.json` — чтобы `_source.ru.json` не попал в цикл; COPY в Dockerfile по
  тому же абсолютному пути, что и `l10n/packs`) больше не нужна как код —
  `l10n/checklists/**` не входит ни в один деплой-путь. Само расследование
  задокументировано здесь как причина, почему вариант с отдельным циклом
  отклонён, чтобы не возвращаться к нему без перечитывания этого ADR.

## Проверено

- `l10n/merge_checklists.py` + 13 pytest-тестов (`l10n/test_merge_checklists.py`,
  синтетические фикстуры: happy-path, идемпотентность, отказ по лишнему/
  недостающему ключу, `[Л]`/`[L]`, пустому значению, расхождению
  `locale`/`rtl`, отсутствующему целевому пакету, сквозной прогон по
  каталогу) — зелёные, `ruff check`/`ruff format --check` чисты.
- Смоук на копии (не в реальных файлах ветки): `az.checklists.json`
  вручную приведён к `_source.ru.json` (23 маркера сняты, 1 лишний ключ
  убран) → `merge_checklists.py` → получившийся `l10n/packs/az.json`
  (`pack_version` 2→3) прогнан через реальный `import_l10n_pack --yes` на
  живом Postgres — импорт прошёл, `catalog.checklists` (1378 ключей) и все
  прежние namespaces (`errors`/`notifications`/`ui`/`legal`/остальной
  `catalog`) подтверждены в БД одним запросом.

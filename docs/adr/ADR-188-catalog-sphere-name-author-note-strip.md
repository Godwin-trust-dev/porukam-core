# ADR-188. Имя сферы каталога: пометка автора в скобках не часть имени, `name_i18n` — только фолбэк RU-контура

**Статус:** принято
**Номер:** 188 — сверено по репозиторию и всем ворктри (`ls docs/adr ~/porukam-worktrees/*/docs/adr
| grep -o 'ADR-[0-9]*' | sort -t- -k2 -n | uniq | tail`, максимум занятый на момент написания — 187).

## Контекст

Владелец, дословно (12.09): «опять в названии вылезло сфера "Продажи (архетип сделки sale, док
24)", нужно просто Продажи, мы ранее убирали. сейчас опять есть». Тот же класс дефекта уже чинили
для сферы `renovation` миграцией `0018_rename_renovation_sphere.py` («Ремонт» → «Ремонт и
строительство») — и он вернулся, потому что причина была устранена только в данных, а не в
источнике.

Три места, где живёт имя сферы, и как они на самом деле связаны:

1. **Шапка `docs/content/checklists/CL-<code>_GLOBAL.md`** — строка вида «Сфера N: `<code>` —
   <имя>.». Формат задан `00_индекс.md` §2, но НЕ оговаривает, что после имени в этой же фразе
   может идти авторская пометка для ревью в скобках — а она регулярно там оказывается: «Продажи
   (архетип сделки sale, док 24)» (CL-sales), «Прочее (единственная категория `other.other`) +
   блок …» (CL-other), «Ремонт и строительство (стартовая вертикаль)» (CL-renovation). Пометка —
   это заметка ДЛЯ АВТОРОВ файла, не для конечного пользователя каталога.
2. **`Sphere.name_i18n`** (`apps/catalog/models.py`) — заполняется `_import_sphere_file`
   (`apps/catalog/services.py`) регэкспом `_SPHERE_NAME_RE`
   (`apps/catalog/checklist_markdown.py`), который до этого ADR брал ВСЁ до точки в конце строки —
   вместе со скобкой. Причём пишется он ТОЛЬКО при создании строки
   (`Sphere.objects.get_or_create(defaults={...})`) — обычный переимпорт чек-листов при деплое уже
   существующее кривое имя не трогает, править нужно отдельной миграцией данных (как 0018).
3. **Пакет `catalog.spheres.<code>`** во всех 29 `l10n/packs/*.json` — независимый ручной перевод,
   ADR-097 закрепил его источником показа имени сферы для всех локалей, КРОМЕ `ru`
   (`SphereSerializer.get_name`, `apps/catalog/api/serializers.py`): для `ru` контекст пакета в
   сериализаторе не передаётся, RU-контур остаётся на `name_i18n`. Поэтому скобка из шапки была
   видна ИМЕННО по-русски — на английском и остальных 28 языках сфера уже показывалась по своему
   (независимому) переводу из пакета.

Дефект прошёл дважды по одной и той же причине: парсер не знал, что скобка — не часть имени, и
никто не потребовал от парсера этого явно.

## Решение

### Пометка в скобках вычищается парсером, а не руками из данных

`checklist_markdown._strip_author_note` обрезает `sphere_name` по первой открывающей скобке —
всё, что после (включая саму скобку), однозначно пометка автора, не имя. Проверено на всех 18
файлах `CL-*_GLOBAL.md`: скобка встречается ровно в трёх (`sales`, `other`, `renovation`), во всех
трёх правило «обрезать по первой `(`» даёт короткое имя без искажений (`other` — с двумя вложенными
скобочными пометками и «+ блок …» после первой, «Прочее» — корректный результат уже после первой
скобки). У пятнадцати файлов без скобки поведение не меняется.

Это решает проблему НА БУДУЩЕЕ: любой новый файл сфер с такой пометкой при первом импорте (сид или
`import_checklists`) получит уже чистое имя, без отдельной миграции данных.

### Существующие кривые данные — только миграция, импорт их не чинит

`_import_sphere_file` пишет `name_i18n` лишь в `defaults=` для `get_or_create` — по конструкции
(идемпотентность повторного импорта не должна перетирать РУЧНЫЕ правки `name_i18n`, если их
когда-нибудь сделают через админку). Значит для уже испорченной строки `sales` фикс парсера
сам по себе ничего не поменяет — нужна миграция данных, аналогичная 0018:
`0020_fix_sales_sphere_name.py`, `{"ru": "Продажи", "en": "Sales"}`, с обратной миграцией на
старое значение. Проверены все 18 сфер в БД на момент миграции — со скобкой была только `sales`.

**Правило на будущее**: если парсер меняет то, как ИЗ MARKDOWN получается `sphere_name`, это
чинит только новые/пересозданные сферы. Для уже существующих в БД строк — отдельная миграция
данных с явной сверкой, у кого из сфер значение действительно разошлось с ожидаемым.

### `name_i18n` — фолбэк RU-контура, не источник показа

Закрепляем явно (ADR-097 это подразумевала, здесь — прямая формулировка): единственный источник
имени сферы для показа — пакет `catalog.spheres.<code>` (все локали, включая `ru`, КОГДА он
доступен в контексте сериализатора); `name_i18n` — фолбэк на случай, если пакет недоступен или
код вызывается вне API-контекста с пакетами (RU-контур, `SphereSerializer.get_name`). Практическое
следствие: пометка в скобках, случайно попавшая в `name_i18n`, никогда не должна быть ЕДИНСТВЕННЫМ
местом, где хранится имя сферы — расхождение между `name_i18n` и пакетом обнаруживается сравнением
(см. «Пределы» ниже), а не рендерится напрямую без сверки.

### Заодно поймана и исправлена сама сфера `sales` в пакетах

Помимо кривого текста, `catalog.spheres.sales` во всех 29 пакетах называл сферу услугой:
«Помощь с продажами» (ru) / «Sales assistance» (en) и аналогично на остальных 27 языках. Это НЕ
та сфера: `sales` — архетип сделки `sale` (продажа ТОВАРОВ, док 24), а не услуга по продажам.
Исправлено на прямой перевод слова «Продажи» (значение «продажа товаров» там, где в языке есть
разница со «услугами продаж») — отдельные коммиты по языковым группам, `pack_version` поднят в
каждом паке (иначе деплой падает на `PackVersionConflictError`, см. `l10n/lock_packs.py`).

## Пределы (сознательно не в этой ветке)

- **Обрезка по первой `(` — эвристика, не парсер естественного языка.** Она верна для всех
  СЕГОДНЯШНИХ 18 файлов (скобка после имени — всегда пометка), но если когда-нибудь понадобится
  сфера, чьё НАСТОЯЩЕЕ имя содержит скобку (например, аббревиатура), правило придётся уточнять —
  сейчас такого случая нет, специально не усложняем.
- **Другие расхождения имени сферы между тремя источниками (markdown / `name_i18n` / пакет),
  не связанные со скобкой, этой веткой НЕ правятся** — они разные по природе (не пометка автора, а
  независимо разошедшийся текст/смысл, местами возможно исторический — см. `education`
  после `0014_dedupe_tutoring_into_education`). Полный список расхождений, найденных сверкой всех
  18 сфер по трём источникам, — в отчёте по этой ветке; самое похожее на `sales` по духу (смысловой
  сдвиг, не просто длина текста) — `care` (пакет «Уход и помощь» вместо «Уход и присмотр»,
  «присмотр» ýже и точнее «помощи») и `household` (пакет «Домашние работы и мелкий ремонт» вместо
  «Уборка и бытовые услуги» — рискует пересекаться по смыслу со сферами `appliance`/`renovation`).
  Переименовывать их не наш вызов — решение владельца.
- **`SphereSerializer.get_name` не тронут** — контракт «пакет, иначе `name_i18n`» и так уже
  соответствовал этому ADR (ADR-097), правка только документирует и закрепляет его явно.

## Тесты

`apps/catalog/tests/test_checklist_import.py` — `test_parse_file_strips_author_note_in_parens_from_sphere_name`
на трёх видах пометки, встречающихся в реальных файлах (архетип сделки, оговорка про единственную
категорию с «+» продолжением, стартовая вертикаль), плюс
`test_parse_file_sphere_name_without_parens_is_unchanged` — имя без скобки не меняется. Миграция
`0020_fix_sales_sphere_name.py` проверена вручную (`migrate catalog` вперёд/назад/вперёд ещё раз) —
отдельного теста на неё нет, как и у 0018 (прецедент). `apps/l10n/tests/test_packs_lock.py` и
`test_packs_coverage.py` проходят на обновлённых 29 пакетах (checksum/pack_version синхронизированы
через `python l10n/lock_packs.py`).

## Дополнение 12.09

Владелец, дословно: «у нас верный вариант сейчас отражается в сферах в приложении» — про то, что
РЕАЛЬНО показывается по-русски в приложении сегодня. Это дало прямой ответ на вопрос из «Пределы»
выше (кто из двух источников — пакет или `name_i18n` — прав, когда они расходятся по смыслу, а не
только по длине формулировки): эталон — то, что уже в БД каталога (`Sphere.name_i18n['ru']`,
единственный контур, где `name_i18n`, а не пакет, служит источником показа, см. «Решение» выше);
пакеты `catalog.spheres.<code>` приводятся к нему, а не наоборот.

Сверка всех 18 сфер по трём источникам (БД `name_i18n.ru`, пакет `ru`, пакет `en`) нашла
расхождение по СМЫСЛУ, а не только по длине формулировки, у четырёх сфер — во всех 29 пакетах
пакет называл сферу уже, шире или иначе, чем каталог:

| Сфера | БД `name_i18n.ru` (эталон) | Было в пакете `ru` | Стало в пакете `ru` |
| --- | --- | --- | --- |
| `care` | Уход и присмотр | Уход и помощь | Уход и присмотр |
| `household` | Бытовые услуги | Домашние работы и мелкий ремонт | Бытовые услуги |
| `beauty` | Красота и здоровье | Бьюти-услуги | Красота и здоровье |
| `media` | Фото, видео и аудио | Медиа и контент | Фото, видео и аудио |

Для `household` расхождение было содержательным риском, не только словесным: «домашние работы и
мелкий ремонт» пересекается по смыслу со сферами `appliance` (ремонт техники) и `renovation`
(ремонт и строительство) — пользователь мог не понять, в какую из трёх сфер попадёт его заявка.

Остальные 14 сфер на момент этой сверки расходились между пакетом и БД только длиной/полнотой
формулировки при том же смысле (например `marketing`: БД «Маркетинг, реклама и тексты» / пакет
«Маркетинг») — тогда их не трогали, это казалось не тем классом дефекта. Позже в тот же день
владелец пересмотрела это решение для части из них (см. ниже, «`it` и ещё семь сфер») — короткие
варианты в пакете заменены на полные, как в БД.

Отдельно: `education` — пакеты и `name_i18n` УЖЕ совпадают друг с другом («Обучение и
репетиторство») и с этим и есть правильный вариант по прямому подтверждению владельца. Разошлась
третья сторона — шапка `docs/content/checklists/CL-education_GLOBAL.md` («Обучение и тренировки»,
устаревшее со времён `0014_dedupe_tutoring_into_education`). Поправлена только шапка (источник,
из которого `name_i18n` может быть перезаписан при пересоздании сферы, см. «Решение» выше) — сама
БД и пакеты не тронуты, чтобы не создавать риск конфликта с уже согласованным значением.

Перевод по остальным 28 языкам в четырёх исправленных пакетах делался ОТ СМЫСЛА нового русского
названия (не подстрочником со старого текста пакета) — там, где старый перевод в конкретном языке
случайно давал более точный термин, тот термин утерян осознанно ради единообразия смысла со всеми
локалями и с каталогом.

**`it` и ещё семь сфер, отдельно (12.09, позже в тот же день).** Владелец посмотрела список сфер
и сначала решила про одну, дословно: «IT и разработка мне нравится больше, если честно» — про то,
каким должно быть имя сферы `it`, а не про то, какой источник сейчас прав. Это не общий случай
«пакет расходится с каталогом по смыслу» (как `care`/`household`/`beauty`/`media` выше) и не
общий случай «длина формулировки» (как оставленные ранее 14 сфер) — это прямое решение владельца
о содержании имени, которое отменяет для `it` правило «эталон — БД, пакет приводится к ней»:
здесь эталоном стало новое решение, и приводить нужно ОБА источника к нему.

В тот же день владелец распространила это решение на весь класс дефекта, сформулировав ПРИНЦИП
(дословно): «везде более полный вариант, потому что автоуслуги могут включать перевозки, а это
логистика. Более полные названия делают навигацию проще и понятнее». То есть там, где пакет и БД
расходятся только длиной/полнотой формулировки при одном смысле (тот самый класс, который в
первой сверке решили не трогать), выбор больше не «эталон — БД» по умолчанию, а «эталон — более
полный вариант из двух», потому что он лучше ведёт человека по навигации между похожими сферами.
Короткие варианты остаются только там, где полного варианта нет ни в одном из источников (нечего
удлинять по смыслу) — таких на 12.09 три: `design`, `pets`, `other`.

Сверка по этому принципу нашла ещё семь сфер, где пакет короче БД:

| Сфера | БД `name_i18n.ru` (полный, эталон) | Было в пакете `ru` | Стало в пакете `ru` |
| --- | --- | --- | --- |
| `it` | IT (до этой правки) | IT и software (ПО) | IT и разработка |
| `appliance` | Ремонт и установка техники | Ремонт техники | Ремонт и установка техники |
| `auto` | Транспорт: ремонт и обслуживание | Автоуслуги | Транспорт: ремонт и обслуживание |
| `business` | Деловые и профессиональные услуги | Бизнес-услуги | Деловые и профессиональные услуги |
| `events` | Праздники и мероприятия | Мероприятия | Праздники и мероприятия |
| `garden` | Сад и благоустройство участка | Сад и участок | Сад и благоустройство участка |
| `marketing` | Маркетинг, реклама и тексты | Маркетинг | Маркетинг, реклама и тексты |
| `delivery` | Доставка (короче пакета — особый случай) | Доставка и логистика | Перевозки и доставка |

`delivery` — не просто «пакет короче БД», а отдельный случай трёх разных названий одновременно:
БД «Доставка» (короче всех), пакет «Доставка и логистика», шапка чек-листа
`CL-delivery_GLOBAL.md` — «Перевозки и доставка». Владелец прямо выбрала «Перевозки и доставка»:
слово «перевозки» должно читаться именно в сфере `delivery`, а не в `auto` — иначе, по её примеру,
пользователь с задачей перевезти груз мог принять это за «автоуслуги» (ремонт/обслуживание
транспорта, не имеет отношения к логистике). Поэтому `auto` сузили до «Транспорт: ремонт и
обслуживание» (без слова «перевозки») одновременно с расширением `delivery` — это не два
независимых решения, а одна правка ради разделения смысла между двумя сферами; то же учтено в
переводах на все 29 языков (специально подобраны разные корни для «транспорт/техника» в `auto` и
«перевозки/грузоперевозки» в `delivery`, где в языке есть оба).

Правились оба источника (БД и пакет) для `it` и `delivery` — единственных двух из восьми, где БД
была короче выбранного варианта; для остальных шести (`appliance`, `auto`, `business`, `events`,
`garden`, `marketing`) БД уже содержала полный вариант, поэтому там правился только пакет.
Миграции данных: `0021_fix_it_sphere_name.py` (`ru` → «IT и разработка», `en` → «IT &
development») и `0022_fix_delivery_sphere_name.py` (`ru` → «Перевозки и доставка», `en` →
«Transport & delivery»), обе по образцу `0020_fix_sales_sphere_name.py`, с обратной миграцией.
`catalog.spheres.<code>` поправлен во всех 29 пакетов для всех восьми кодов, переводы — по смыслу
нового русского названия, не подстрочником со старого текста пакета.

Причина, почему для `it`/`delivery` нужны оба источника для одного сдвига смысла: РУ-контур в
приложении читает имя сферы напрямую из `Sphere.name_i18n['ru']` (см. «Решение» выше, единственный
контур с этим исключением), а остальные 28 языков — из пакета; правка только одного источника
снова развела бы RU и остальные локали по смыслу, как и произошло с исходной группой из четырёх
сфер.

**Предложение на будущее (не реализовано в этой ветке).** Пока `catalog.spheres.<code>` —
независимый ручной перевод (ADR-097), два источника имени сферы обязаны расходиться по мере того,
как каждый меняется своим чередом (ровно так и произошло: `sales`/`renovation` чинили в БД, четыре
сферы выше разошлись через пакет). Правильный долгосрочный фикс — сделать так, чтобы источник
имени сферы был ровно один: генерировать `catalog.spheres.<code>` (как минимум для `ru`, в идеале
как каноническую RU-строку, от которой переводчик отталкивается для остальных 28 языков) из
`Sphere.name_i18n` при экспорте/сборке пакетов, а не хранить его отдельной ручной записью. Это
отдельная задача (нужно решить, как в неё встраивается ручной перевод остальных языков и `quality`
пакета) — здесь только фиксируем направление, чтобы третий заход на тот же класс дефекта не
понадобился.

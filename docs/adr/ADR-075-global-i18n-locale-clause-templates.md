# ADR-075. Механизм выбора языка по контуру, EN-данные, ClauseTemplate GLOBAL

**Статус:** принято
**Дата:** 2026-08-06
**Контекст этапа:** ГВ.5 (`feat/global-i18n`, docs/tasks/global-wave.md)

## Контекст

Этот ADR изначально создавался под номером 072 (следующий свободный на
момент создания ветки `feat/global-i18n`, ответвлённой от main до PR #34).
К моменту слияния обратно в main номер 072 оказался занят ДВАЖДЫ независимо
другими ветками (`chore/adr-journal` — «Реестр доменных дедлайнов», и
`feat/authority-profiles`), обе уже разрешены отдельным PR (`chore/adr-journal-v2`,
см. `docs/adr/README.md`, раздел «Исторический контекст», случаи 2–3).
Этот файл — четвёртая по счёту такая коллизия за тот же день, обнаруженная
и исправлена прямо здесь: 072 занят «Реестром доменных дедлайнов»
(смёржен раньше), этот ADR перенесён на следующий свободный номер по
состоянию main на момент слияния этой ветки — **075**. Содержание решения
не менялось, только номер и имя файла (тот же принцип, что все предыдущие
исправления в `docs/tasks/chore-adr-journal.md`).

Постановка ГВ.5 ссылается на «приложение ADR-060 п. 3» для структуры
`ClauseTemplate`/`legal_anchors` — внешний документ, недоступный в этом
репозитории (тот же паттерн, что уже зафиксирован в ADR-070/071: локальный
`ADR-060-outbox-common.md` — другой документ, про outbox). `ClauseTemplate`
реализован здесь по фактической структуре К/V-блоков, уже существующей в
`apps/contracts/forms.py` (`FormField.kv_block`), а не по недоступному
внешнему тексту — см. решение ниже.

## Решение

### Механизм выбора языка по контуру/Accept-Language

- **`JurisdictionConfig.primary_locale`** (`apps.jurisdictions`, миграция
  0005/0006) — язык контура: RU → `"ru"` (дефолт поля), GLOBAL → `"en"`
  (сид). Канонический источник «страна → язык» — `apps.jurisdictions.
  selectors.resolve_locale(country_code)`, тонкая обёртка над
  `resolve_jurisdiction()` (ГВ.1). Никакое другое место (`common/i18n.py`,
  `apps.accounts.selectors.get_user_locale`, `apps.notifications.services`)
  не хранит своего сопоставления — все читают отсюда.
- **`User.country_code`** (`apps.accounts`, миграция 0005) — недостающее
  звено: до ГВ.5 у `User` не было поля, куда мог бы попасть явный выбор
  страны (ГВ.1 требует «страна — по явному выбору пользователя», но
  хранить его было негде). Self-service — через `PATCH /users/me`
  (`services.update_profile`, как email/full_name), НЕ отдельный
  «единственный санкционированный мутатор»: этим полем не владеет чужое
  приложение, в отличие от `has_business_status`/`discoverable_by_phone`.
- **Регистрация проставляет стартовый контур детерминированно**, а не
  полагается на пустое поле + Accept-Language: `verify_otp` (телефон+SMS —
  RU-канал по построению, ГВ.2) ставит `country_code="RU"`;
  `complete_google_login` (Google-вход — GLOBAL по построению, ГВ.2) ставит
  `country_code="GLOBAL"`. Без этого КАЖДЫЙ пользователь без явного выбора
  (то есть все, кто не трогал PATCH /users/me) резолвился бы в GLOBAL по
  голому правилу ГВ.1 «нет страны → GLOBAL» — для RU-пользователей,
  входящих по телефону, это была бы неожиданная и неверная смена языка
  ошибок/уведомлений сразу у всех. Явная простановка на регистрации —
  единственный способ сделать «RU-пользователь получает на русском»
  истинным без побочных эффектов для уже работающего RU-потока.
- **`common/i18n.py::resolve_request_locale(request)`** — контур
  аутентифицированного пользователя приоритетно (страна — явный выбор);
  Accept-Language — ТОЛЬКО подсказка для запросов без известного контура
  (анонимных, либо пользователя без сохранённой страны) — тот же принцип,
  что «гео — подсказка» из ГВ.1/ADR-070, применённый к языку браузера
  вместо геолокации. `common/` не импортирует `apps.accounts` (осталось бы
  common → apps, обратное задуманному направлению) — читает `request.user`
  дак-тайпингом (`getattr(user, "country_code", None)`), `apps.
  jurisdictions` — ЕДИНСТВЕННОЕ исключение (спроектирован нижним слоем
  специально ради такой безопасной универсальной зависимости, ADR-070).

### application/problem+json — EN title

- **`common/api/error_texts.ERROR_TITLES_EN`** — реестр `code → EN title`
  (не по вызову: один `code` может нести разные RU `title` в разных местах
  — осознанное упрощение, `detail` не переводится). Наполнен для ВСЕХ 40
  кодов `DomainAPIError`, поднимаемых по всему проекту на момент этого PR
  (не стаб на пару кодов) — код без записи в реестре просто остаётся RU
  (безопасный fallback).
- **`problem_json_exception_handler`** — единственная точка правки: читает
  `resolve_request_locale(request)`, при `"en"` подменяет `title` из
  реестра. Ни один из 50+ call sites `DomainAPIError(...)` не тронут.
- **`code` не локализуется никогда** (уже было в `common/api/problem.py` —
  подтверждено, не изменено).

### Уведомления — EN-данные + SMS конфигурацией контура

- **`NotificationTemplate.body_stub` → `body_i18n`** (миграция 0003,
  данные перенесены, не потеряны) — `{"ru": ..., "en": ...}`, тот же приём,
  что `name_i18n` в `apps.catalog`. `body_stub` был мёртвым полем (нигде не
  читался за пределами модели/сида) — конвертация безопасна, звонков
  `body_stub` вне `models.py`/сида не было.
- **`apps.notifications.selectors.render_body(code, locale=...)`** —
  `body_i18n[locale]`, иначе `body_i18n["ru"]`, иначе `""`.
  `place_notification` резолвит `jurisdiction = resolve_jurisdiction(
  recipient.country_code)` ОДИН раз, использует `.primary_locale` для
  `render_body` и передаёт `locale`/`body` в payload push/email/SMS-
  провайдеров (реального рендер-пайплайна нет ни для RU — `body_stub`
  никогда не рендерился, «тексты придут отдельным контентным пакетом»,
  fundament.md ЭФ.4 — этот PR не меняет этот факт, только делает данные
  per-локальными и доводит `locale` до провайдера).
- **SMS-фоллбек** — дополнительное условие `jurisdiction.
  sms_channel_enabled` (ГВ.1 профиль, RU=True/GLOBAL=False) поверх
  существующих (`force_sms`, `not push_delivered`, `settings_row.
  sms_enabled`). Ветка кода одна и та же для всех контуров — SMS «выключен
  конфигурацией контура, не удалением кода» буквально: код не разветвляется
  по контуру, просто условие не выполняется для GLOBAL.
- **`apps.accounts.services.request_otp` НЕ проверяет контур** — не
  пробел: вход по телефону анонимный (контура физически неоткуда взять до
  входа), а сам этот канал — RU-канал по построению (ГВ.2: «в GLOBAL не
  предлагается»). Контур-зависимая развилка живёт там, где получатель уже
  известен — `place_notification`.

### `name_i18n`/`description_i18n` EN — каталоги

- **`ContractTypeCatalogItem`** — EN добавлен ТОЛЬКО для 7 кодов
  клиентского дерева Р1 (`docs/catalog-v2.md` §2) — не для всех 15 строк
  сида 0004: остальные (excluded/special/Р2 hidden) не показываются
  пользователю ни в одном контуре, переводить нечего.
- **`Sphere`** — EN для всех 7 ТЕКУЩИХ кодов (не «17 сфер» из
  формулировки постановки — те 10 дополнительных сфер сами ещё не
  заведены как данные ни в одной миграции, докстринг модели прямо называет
  их отдельным контентным треком П-03/Б9; ГВ.5 добавляет EN к тому, что
  реально есть).
- **`ChecklistTemplateItem.description_i18n`** — НОВОЕ поле РЯДОМ с
  `description`, не взамен: `description` — часть естественного ключа
  выборки в сид-миграции 0006 (`update_or_create` по
  catalog_item/sphere/description) и читается напрямую
  `apps.milestones.services` — менять его смысл означало бы трогать чужой
  домен с этой ветки. `description_i18n` — тот же механизм, что `name_i18n`
  остальных каталогов, но добавочный, а не замещающий.

### `ClauseTemplate` — GLOBAL-профиль конструктора

- **Модель — в `apps.catalog`**, не в `apps.contracts`: `ClauseTemplate` —
  справочник (текст пункта договора по контуру и блоку), тот же класс
  сущностей, что `Currency`/`ContractTypeCatalogItem`/`Sphere`/
  `ChecklistTemplateItem` — все живут в `apps.catalog` (нижний слой,
  безопасная универсальная зависимость), не там, где их когда-нибудь
  будет читать бизнес-логика. `apps.contracts` (когда дойдёт до реальной
  генерации юртекста — «отдельный трек», `apps/contracts/forms.py`
  docstring) будет ЧИТАТЬ эту таблицу через `apps.catalog.selectors.
  assemble_clauses`, не наоборот.
- **`block_code` — те же коды, что `FormField.kv_block`** в
  `apps/contracts/forms.py` (K1, K2, K3, K4, K7, K8, V-ACCESS, V-GOODS,
  V-HANDOVER, V-INV, V-LOAN, V-PORT, V-RENT, V-SUB, tax_note) — реально
  используемое подмножество, не полный список К1–К15 из доктрины
  (`docs/contract-forms.md`). `apps.catalog` НЕ импортирует
  `apps.contracts` (запрещено контрактом import-linter «contracts не
  импортирует payments/disputes» здесь ни при чём, но направление
  зависимости и так неверное — catalog нижний слой) — коды
  синхронизированы вручную, тот же приём, что коды валют между
  `apps.catalog.Currency`/`apps.jurisdictions.JurisdictionConfig`
  (0007_seed_usd_eur).
- **`country_code` — по значению**, не FK на `JurisdictionConfig`:
  `apps.catalog` и `apps.jurisdictions` — сиблинги нижнего слоя, ни один
  их сид не зависит от миграций другого (тот же принцип, зафиксированный в
  ADR-070 для валют).
- **RU-строки НЕ заводятся.** Постановка просит только `country_code=
  'GLOBAL'`; генерация юридического текста для RU — отдельный, ещё не
  начатый трек (тот же `forms.py` docstring). Модель спроектирована так,
  чтобы этот будущий трек просто добавил недостающие строки той же формы,
  не переопределяя структуру.
- **`selectors.assemble_clauses(country_code, block_codes)`** —
  демонстрирует «черновик договора в GLOBAL собирается из GLOBAL-блоков
  без правовых анкоров» на уровне справочника: чистая выборка по
  (country_code, block_code IN ...), без побочных эффектов. Полная
  интеграция со сборкой реального черновика договора — предмет будущего
  контракт-трека (не этого PR: `apps.contracts` не тронут).

## Отклонённые варианты

- **`resolve_request_locale` резолвит «нет страны» прямо в GLOBAL/en для
  АУТЕНТИФИЦИРОВАННЫХ пользователей** (буквальное применение резолвера
  ГВ.1). Отклонено — см. решение выше: сломало бы язык ошибок для всех
  существующих RU-пользователей без сохранённой страны. Explicit
  простановка контура на регистрации — решение этого конфликта, не
  ослабление резолвера ГВ.1 (он остаётся верным для `resolve_jurisdiction`/
  валют/профиля — там «нет страны → GLOBAL» корректно и ожидаемо).
- **`common/i18n.py` импортирует `apps.accounts` для резолва
  локали пользователя.** Отклонено — обратило бы направление зависимости
  common → apps; дак-тайпинг `request.user.country_code` этого не требует.
- **Единый `title` per `code` заменить точным переводом каждого вызова
  `DomainAPIError`.** Отклонено для этого PR — 50+ call sites, полная
  точность потребовала бы либо параметра `title_key` на каждом вызове,
  либо реестра по (code, title) — оставлено как известное, документированное
  упрощение (`common/api/error_texts.py` docstring), не блокирует
  приёмку ГВ.5.
- **`ChecklistTemplateItem.description` → `description_i18n` тем же
  приёмом, что `NotificationTemplate.body_stub` (конвертация, не
  добавление).** Отклонено — `description` активно используется как ключ
  сида и читается `apps.milestones.services` напрямую; конвертация задела
  бы чужой домен с этой ветки без необходимости.
- **`ClauseTemplate.country_code` — FK на `JurisdictionConfig`.** Отклонено
  — та же причина, что валютные коды в ГВ.1: `apps.catalog`/`apps.
  jurisdictions` — независимые сиблинги, миграции одного не должны
  требовать состояния другого.

## Последствия

- `apps.jurisdictions.JurisdictionConfig` — третий профильный флаг с ГВ.1
  (`sms_channel_enabled`) получил реального потребителя (`apps.
  notifications`), как и предсказывал ADR-070 («действующим для
  конкретного флоу только когда соответствующее приложение начинает читать
  это поле») — ГВ.5 стал этим приложением для SMS и языка.
- Любое новое доменное исключение с `code`, которому нужен EN title,
  добавляется одной строкой в `common/api/error_texts.ERROR_TITLES_EN` —
  без правки call site.
- `ClauseTemplate`/`assemble_clauses` — готовая точка расширения для
  будущего RU-трека генерации юртекста и для реальной интеграции в сборку
  черновика договора (`apps.contracts`), без изменений схемы.

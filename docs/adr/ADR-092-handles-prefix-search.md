# ADR-092. `GET /v1/handles?q=` — префикс-поиск хендлов для выбора контрагента: узкий лукап, а не поиск людей

**Статус:** принято
**Дата:** 2026-08-18
**Контекст этапа:** `docs/tasks/audit-web-api-contract-sweep-report.md`
«Handle-поиск контрагента — 🔴 B»: фронт мастера создания договора
(`web/src/features/contracts/api.ts::useHandleSearch`,
`web/src/pages/contract-new/PartiesStepPage.tsx`) бьёт в `GET /v1/handles?q=`,
которого нет — есть только точный `GET /v1/handles/{handle}` (без query).
Шаг «Стороны» мастера без него не проходится.

## Решение

`GET /v1/handles?q=<префикс>&limit=` в `apps.social` (`HandleSearchView` →
`selectors.search_handles`). Только чтение, никаких новых моделей и миграций —
поиск идёт по существующей `Handle` (`is_active=True`).

## Почему именно префикс, и почему не «поиск людей»

Задача узкая — **адресный лукап**: пользователь уже знает, с кем заключает
договор, и набирает известный ему хендл. Это НЕ дискавери-поиск исполнителей
(за него отвечает `apps.marketplace`) и НЕ соц-граф.

- **`startswith`, не `icontains` и не полнотекст.** Подстрочный поиск по
  справочнику хендлов — это перечисление пользователей платформы по любому
  фрагменту; префикс отвечает ровно на «я знаю начало хендла».
- **Порог `HANDLE_SEARCH_MIN_PREFIX = 2`.** Короче (и пустой `q`) → `200` с
  пустым `results`, НЕ `400`: строка ввода растёт по символу, и первый
  набранный символ — нормальное состояние поля, а не ошибка клиента. Тот же
  выбор уже сделан в `GET /v1/spheres?q=` (ADR-091).
- **Потолок выдачи `HANDLE_SEARCH_MAX_LIMIT = 50`** (по умолчанию 20) —
  клиент не может одним запросом выкачать справочник.

## Что НЕ попадает в выдачу (каждая граница — доменная)

| Исключены | Почему |
| --- | --- |
| Хендлы `AddressableGroup` | Объединение — витрина, **не сторона договора** (`tech-spec.md` §5.2.1b). Выбор группы контрагентом всё равно отвергает `apps.contracts.services` (`CounterpartyIsGroupError`) — не показываем то, что заведомо не выбрать. |
| `discoverable_by_handle=False` | Единственный флаг находимости по хендлу (`apps.accounts.models.User`, etap-3 3.3). Согласия 152-ФЗ его не покрывают — «хендл публичен по своей природе», поэтому отдельного согласия под поиск НЕ вводим. |
| `is_banned` / `is_active=False` | С ними договор не заключить. |
| Сам себя | Контрагент — это ДРУГАЯ сторона. |
| Освобождённые хендлы (`is_active=False`) | История смен хранится (антифрод), но адресует всегда только активный. |

**Аутентификация обязательна** — в отличие от точного `GET /handles/{handle}`
(`AllowAny`). Точный лукап отвечает на «существует ли @ivan», перебор
префиксов анониму — уже перечисление справочника.

## Форма ответа

```json
{"results": [{"user_id": "…", "handle": "@ivan_master",
              "display_name": "Иван Мастеров", "kind": "person",
              "verification_level": "guest"}]}
```

- Совпадает с `HandleEntry` фронта (`packages/core/src/api/contract-types.ts`)
  плюс `user_id` — существующий контракт мастера не меняется, добавляется
  только стабильный идентификатор.
- `user_id`, а не `id`: id пользователя в `apps.social` уже так называется
  (`PhonebookMatchSerializer`). Хендл сменить можно, пользователя — нет;
  но **резолвится контрагент при создании договора по `@handle`**
  (`apps.contracts.services._resolve_counterparty_profile`,
  `counterparty_handle`) — `user_id` нужен как ключ строки/дедуп, не как
  ключ создания.
- `handle` — **с «@»**, как `GET /v1/users/me.handle` (ADR-086) и мок-справочник
  фронта; резолвер «@» всё равно срезает.
- `kind` — `person`/`business` по `has_business_status` (= `ProfileKind` фронта).
  Это НЕ тот `kind`, что у `HandlePublicSerializer` (`user`/`group`): групп в
  этой выдаче нет по построению, различать нечего.
- `display_name` — пустая строка, если ФИО не заполнено или ключ субъекта
  уничтожен (crypto-shredding): «имени нет» — одно состояние, фронт показывает
  хендл, тип `HandleEntry.display_name: string` остаётся честным.
- Ни телефона, ни e-mail, ни `trust_id` (`tech-spec.md` §5.1 — не отдаётся
  нигде и никогда). Закреплено тестом
  `test_handle_search_never_exposes_private_fields`.

## Техническая заметка: `Collate(..., "C")` обязателен

`Handle.value` лежит под НЕдетерминированной ICU-коллацией `case_insensitive`
(`social/migrations/0001_initial`), а PostgreSQL запрещает по такой `LIKE`
(«nondeterministic collations are not supported for LIKE») — и `istartswith`,
и `startswith` падают на живой БД (на sqlite прошли бы: см. CLAUDE.md —
БД-инварианты проверяем на PostgreSQL). Поэтому фильтр идёт по
`Collate("value", "C")`. Регистронезависимость от этого не теряется: хендл
нормализуется в нижний регистр при выдаче
(`apps.social.services._normalize_handle`), префикс — в `search_handles`.

## Последствия

- Фаза СОЗДАНИЯ договора получает готовый контракт: выбрать контрагента →
  `PATCH` черновика с `counterparty.handle` → `apps.contracts` резолвит по
  `@handle`. Ничего в мастере менять не требуется (кроме отключения мока).
- Дискавери-поиск исполнителей (`apps.marketplace`) этот роут не решает и
  решать не должен — при его появлении это будет отдельный ресурс.

# ADR-080. Язык договора на подписании: реальный Accept-Language, языковой слой без «канона»

**Статус:** принято
**Дата:** 2026-08-10
**Контекст этапа:** DEV-16b (`docs/tasks/DEV-16b_подписание-язык-договора.md`), ветка
`feat/web-signing-l10n`, поверх DEV-16/16a (ADR-079, уже в `main`).

## Контекст

DEV-16 §3 (языковой слой на подписании) был сознательно вырезан и пересмотрен —
ревизия 3 ло-фая явно требует: канон (официальный язык договора) **не выпячивать**,
аудитория — простые люди. DEV-16b пиннит финальное поведение: одноязычная сделка —
чистый экран без единого языкового элемента; разноязычная — бейдж «автоперевод» +
тихая строка «Официальный текст — English · показать»; слово «канон» — вообще не в UI.

Данные (`is_cross_language`, `viewer_render`, `official_render`) заявлены как «готовые»
со стороны Л.1 (бэкенд-ADR-078, уже в `main`), но фронт до этой ветки работал на
MSW-моках — потребовалось и расширить мок под новую форму ответа, и — что оказалось
важнее — обнаружить и закрыть реальный пробел в DEV-16: `ApiClient` слал
`Accept-Language: ru` **статичной строкой**, никогда не менявшейся с выбором языка
интерфейса (DEV-16a). Для UI-текста это было незаметно (i18next живёт своей жизнью,
не через HTTP), но для DEV-16b — критично: `viewer_render` подбирается ИМЕННО по
Accept-Language, статичный заголовок сделал бы весь языковой слой нерабочим для
любого языка, кроме жёстко зашитого «ru».

## Решения

### 1. `ApiClient.getLocale` — геттер вместо статичной строки

`packages/core/src/api/client.ts`: `ApiClientConfig.getLocale?: () => string`
(приоритетнее устаревшего `locale?: string`, оставленного для обратной совместимости) —
читается на КАЖДЫЙ запрос, тот же приём, что уже был у `getAccessToken`/
`getActingProfileId`. `web/src/shared/activeLocale.ts` — plain-модуль (`current: string`
+ get/set), **без** импорта `app/providers.tsx` напрямую: `providers.tsx` → (транзитивно,
через хуки вроде `useLocaleResolution`) → `shared/api.ts` уже существующий цикл, если бы
`shared/api.ts` импортировал `i18n` из `providers.tsx` напрямую, получился бы реальный
циклический импорт. `providers.tsx` вместо этого зовёт `setActiveLocale(i18n.language)`
один раз при инициализации и подписывается на `i18n.on('languageChanged', ...)`.

### 2. Мок: `is_cross_language`/`viewer_render` считаются НА ЗАПРОС, не хранятся

`web/src/mocks/contractsDb.ts`: `versionRenders` (`Map<versionId, Record<lang,
ContractRender>>`) хранит все доступные рендеры версии (`en` официальный + `ru`
автоперевод — только эти два языка реально «переведены» в моке; любой другой язык
интерфейса — честный фолбэк «перевод недоступен», ровно то же поведение, что и у
непереведённого UI-ключа, DEV-16 §1). `resolveViewerFields()` пересчитывает
`is_cross_language`/`viewer_render` из `Accept-Language` заголовка КАЖДОГО ответа
(`contractHandlers.ts`, `withViewerRender()`, duck-typing по `.version`) — зеркалит,
как это сделал бы реальный бэк (viewer-контекст запроса, не статика на объекте версии).
Мок официально проговаривает язык как `en` для всех сидов (§0.1 — мастер не спрашивает
язык договора вообще).

### 3. Языковой слой — только при `is_cross_language`, слово «канон» запрещено линтом

`SigningPage.tsx`: весь новый UI (`AutoTranslateBadge`, `OfficialTextLine`,
`OfficialTextView`, `CustomTermsBlock` — кроме своей независимой видимости по
`custom_terms`) рендерится строго под `version.is_cross_language` — одноязычная сделка
не получает ни одного нового узла в DOM (не просто «скрыт CSS», а не рендерится вовсе —
проверено e2e/unit на отсутствие текста). `scripts/lint-terms.mjs` получил новое правило
(канон/canon(ical) запрещены в `packages/i18n/src`/`web/src`, вне комментариев) — сразу
нашло и исправило собственный текст DEV-16a (`locale.settingsCanonExplain` →
`settingsLanguageExplain`, без слова «канон»), подтверждая, что проверка не бутафорская.

### 4. `OfficialTextView`: mobile Sheet vs desktop `CompareColumns` — тот же приём, что `LanguageSwitcher`

`useIsDesktop()` вынесен из `packages/ui/src/components/LanguageSwitcher.tsx`
(DEV-16a) в переиспользуемый `packages/ui/src/useIsDesktop.ts` — `OfficialTextView`
использует его для того же структурного решения (mobile/desktop — разные контейнеры,
решает JS через `matchMedia`, не двойной рендер с CSS-скрытием — см. обоснование в
ADR-079 §4).

## Последствия

- `ApiClient.getLocale` — теперь единственный правильный способ передавать активный
  язык на бэкенд; любой будущий код, создающий свой `ApiClient` (тестовый двойник и
  т.п.), должен использовать его, а не хардкодить `locale`.
- Мок покрывает только `en`/`ru` реальным переводом — расширение на другие языки
  (когда реальный бэк/внешний конвейер начнёт отдавать больше переводов per contract) не требует
  структурных изменений, только заполнения `versionRenders`.
- `CustomTermsBlock`'s «Перевести (скоро)» — заглушка (disabled), сама функциональность
  автоперевода `custom_terms` — вне скоупа DEV-16b (§9), будущая задача.

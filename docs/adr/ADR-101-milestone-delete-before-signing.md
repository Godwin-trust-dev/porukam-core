# ADR-101. `DELETE /milestones/{id}` — удаление этапа до подписания

Дата: 2026-08-20. Статус: принято.
Ветки: `feat/milestones-delete` (бэкенд, этот ADR), `feat/web-review-aug20` (UI).

## Контекст

Таблица tech-spec.md §8.5 для структуры этапов даёт только
`POST /contracts/{id}/milestones` и `PATCH /milestones/{id}`; удаления не
было, и ADR-088 (Фаза 2) честно прятал крестик у уже созданного этапа в
мастере («DELETE на бэке нет»). Отсмотр 2026-08-20: «если этап добавлен,
его нельзя удалить в этом же окне» — для черновика это тупик: ошибочный
этап остаётся в договоре до отправки.

## Решение

`DELETE /milestones/{id}` → `204`, сервис `apps.milestones.services.
delete_milestone`:

- та же зона редактируемости, что у POST/PATCH структуры
  (`_assert_editable`: `draft`/`under_review`); иначе `409
  contract_immutable` — после заморозки версии изменения только через
  Amendment (`remove_milestone`, уже есть);
- любая сторона договора (как у PATCH), чужой — `403`;
- поддерево (дети, чек-листы, материалы) уходит каскадом по FK —
  удаляемое не юрзначимо: снепшотов `ContractVersion` до подписания нет,
  мягкого удаления не заводим (CLAUDE.md);
- событие `milestone.deleted` в outbox (симметрично `created`/`updated`).

Копирование этапа отдельного эндпоинта не получает: фронт делает
`POST` с теми же полями + `POST checklist-items` (композиция, не новый
инвариант).

## Последствия

- tech-spec.md §8.5: строка `POST /contracts/{id}/milestones · PATCH/DELETE
  /milestones/{id}` — уточнение таблицы этим ADR.
- Тесты: сервис (лист, ветка каскадом, контрагент при `under_review`,
  чужой, после подписания) и API (204 → дерево без этапа; 409 после
  подписания; 403 чужому).

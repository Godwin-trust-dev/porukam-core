# ADR-151. Порядок оплаты этапа (`Contract.payment_order`) — отдельная ось от способа расчёта

**Статус:** принято (фаза 1 — условие договора); фаза 2 (исполнение предоплаты в FSM этапа) —
решена 03.09, вариант A, см. ADR-155
**Контекст:** apps.contracts (модель, PATCH черновика, гейт `send`, snapshot заморозки),
apps.archive (экспорт), фронт `contractNew/*` (мастер, предпросмотр, условия у контрагента)
**Номер:** 151 — следующий после ADR-150 по сканированию `docs/adr/` во всех ворктри;
в индексе README строки 085–150 отсутствуют (индекс вёлся до 084), строка 151 добавлена.

## Контекст

Замечание владельца 02.09 (дословно): «Надо добавить ещё один момент для всех договоров.
Порядок оплаты: Предоплата (до начала этапа, если это услуги). Постоплата (после окончания
этапа). В продажах и аренде тоже будет этот пункт».

У договора уже есть `payment_method` — **рельсы расчёта** (`direct_platform` / `hold` /
`prepayment` / `cash` / `external`, tech-spec §5.2.4). Там `prepayment` означает «предоплата
с двусторонним подтверждением» как СПОСОБ (уровень защиты, гейт `financial_condition_met`),
а не срок. Владелец же просит другое: **когда** лист-этап оплачивается относительно его
исполнения — до начала или после приёмки. Это независимая ось: наличными можно платить и до,
и после; холд — то же самое. Поэтому новое поле, а не новые значения в `PaymentMethod`.

Сегодня платёж по листу возможен только после приёмки: `MILESTONE_FSM` содержит единственный
денежный переход `pay: accepted -> paid` (apps.milestones). Условие «оплата до начала» в
тексте договора появится раньше, чем платформа сможет его исполнить, — это и есть граница
фаз ниже.

## Решение

### 1. Поле и коды значений

`Contract.payment_order` — `CharField(16, null=True)`, миграция `contracts 0010` (только
добавление NULL-колонки, без бэкфилла: договоры, замороженные до раскатки, условия не имеют,
в snapshot у них `payment_order: null`).

Коды — **`before_start`** («Предоплата — до начала этапа») и **`after_acceptance`**
(«Постоплата — после приёмки этапа»), а не `prepayment` / `postpayment`:

- `prepayment` уже занят `PaymentMethod` с другим смыслом. **Уточнение 03.09 (ADR-155):**
  владелец упразднил способ `payment_method=prepayment` целиком («способ оплаты — это каким
  способом перемещаются деньги. предоплата с двусторонним подтверждением — там быть не
  должно»), так что коллизии больше нет — но коды `before_start`/`after_acceptance`
  остаются: они называют СОБЫТИЕ, к которому привязан срок, и переименовывать уже
  замороженные в snapshot значения задним числом нельзя. Аргументы ниже — исторические.
  Одно слово на двух полях одного объекта (`payment_method: "prepayment"`,
  `payment_order: "prepayment"`) путало бы API,
  snapshot, тексты ошибок и переводы (ключ `paymentMethod_prepayment` vs
  `paymentOrder_prepayment`), а протокол разногласий хранит `item_ref` строкой — «правка
  предоплаты» стала бы двусмысленной.
- `before_start` / `after_acceptance` называют **событие**, к которому привязан срок, — ровно
  то, что сказал владелец («до начала этапа», «после окончания этапа»), и то, от чего в фазе
  2 будет считаться дедлайн оплаты. Человекочитаемые подписи («Предоплата — …»,
  «Постоплата — …») остаются в UI и `choices`-лейблах.

### 2. Где живёт условие (фаза 1 — сделано)

- PATCH черновика (`ContractPatchSerializer`, `services.patch_draft`) и POST создания
  (`create_draft`, включая копирование «как в прошлый раз» с `source_contract_id`).
- Обязательность на `send` — по образцу `payment_method`: `PaymentOrderRequiredError` →
  `422 payment_order_required`. Фронт гейтит «Далее» на шаге «Детали», бэк дублирует
  инвариант.
- Canonical snapshot заморозки (`_build_snapshot`) — ключ `payment_order` под
  `integrity_hash`; экспорт архива (`apps.archive.selectors`) отдаёт поле рядом с
  `payment_method`.
- Текст договора / «полные условия» у контрагента — фронт (платформенный шаблон, PreviewStep,
  ContractReviewPage, RealTermsPanel) показывает строку «Порядок оплаты» рядом со «Способом
  оплаты» (ветка `feat/web-payment-order`).

### 3. Применимость по типам

Услуга, продажа, аренда — применимо (владелец: «в продажах и аренде тоже будет этот пункт»):
у продажи этап — передача товара, у аренды — период пользования; «до начала / после приёмки»
определено.

**Займ — неприменимо, явно.** У займа лист-этап — сам денежный транш (выдача, возврат по
графику); «оплата до начала этапа» и «после приёмки этапа» не определены — этап и есть
платёж. Поэтому `services.payment_order_applicable(code)` возвращает `False` для клиентской
опции `loan` (`ContractTypeCatalogItem.client_option`), и:

- попытка задать поле займу (POST/PATCH) — `PaymentOrderNotApplicableError` →
  `400 payment_order_not_applicable`, а не молчаливое сохранение;
- смена типа черновика **на** займ и копирование «как в прошлый раз» с услуги на займ снимают
  ранее выбранный порядок (условие исходника к новому типу не относится);
- гейт `send` для займа не требует поля; snapshot займа содержит `payment_order: null`.

Типы вне клиентского дерева (`client_option` пуст) считаются применимыми: условие безвредно,
запрет удивил бы.

### 4. Протокол разногласий (ADR-123)

`payment_method` в грамматику применяемых `item_ref` (`form.<key>` / `title` / `other`) не
входит — правка по нему «свободная»: хранится в протоколе, попадает в snapshot, к договору
автоматически не применяется. `payment_order` — так же, по аналогии; отдельный адрес не
вводится. Если владелец захочет применяемые правки способа/порядка оплаты — одно расширение
грамматики на оба поля.

### 5. Фаза 2 — исполнение предоплаты в FSM этапа (РЕШЕНО: ADR-155, вариант A)

> **Решено 03.09 (владелец): вариант A.** «Фактически мы переносим оплату до начала этапа
> выполнения работ. Меняется только последовательность. Не надо изобретать велосипед) просто
> условие старта этапа — оплата». Реализация — ADR-155: `financial_condition_met` листа при
> `before_start` = оплата ЭТОГО листа подтверждена обеими сторонами; новых статусов Milestone
> нет; лист закрывается `paid` в момент приёмки, второго платежа не выставляется. Варианты
> B и C ниже сохранены как отклонённые — вместе с разбором последствий, который к ним привёл.

Сейчас `pay` возможен только из `accepted`. Для `before_start` нужен новый порядок
переходов. Варианты:

- **A. Оплата как гейт старта.** `pending -> (оплата листа) -> in_progress`: `pay` разрешить
  из `pending` для листа договора с `before_start`; `start` требует `paid`. Это буквально
  «предоплата до начала этапа» и ложится на уже описанный в domain-model
  `financial_condition_met` (гейт старта по способу расчёта). Минус: статус `paid` перестаёт
  означать «этап закрыт» — `complete_execution` (все листья `paid` → договор `completed`)
  придётся считать по `accepted` для таких листьев; дашборд «к оплате» и уведомления
  `milestone.paid` расходятся по смыслу.
- **B. Отдельный статус/флаг предоплаты.** `Milestone.prepaid_at` (или состояние `prepaid`)
  рядом с существующей цепочкой; `accepted -> paid` остаётся терминалом, но для `before_start`
  переход `pay` вырождается в автоподтверждение. Чище семантически, дороже: новая
  Payment-запись «аванс» в apps.payments, споры (apps.disputes) должны понимать, что деньги
  уже у исполнителя (возврат аванса при `reject` — новый исход спора).
- **C. Только текст.** Оставить как в фазе 1: условие в договоре, исполнение — по
  договорённости сторон вне FSM (для `cash`/`external` так фактически и есть). Не блокирует
  запуск, но платформа не помогает и не фиксирует, что предоплата была.

Последствия для payments/disputes в любом из A/B: дедлайн оплаты (`deadlines`) отсчитывается
от разного якоря (`start` vs `accepted_at`); возврат аванса при расторжении и при исходе
спора «отклонено» — новые денежные правила (этап 7 расширяется). Решение владельца нужно до
того, как «Начать этап» будет зависеть от факта оплаты.

## Последствия

- Snapshot новых заморозок получает ключ `payment_order` → повторная заморозка договора,
  замороженного до раскатки, даст другой `integrity_hash` (новая `ContractVersion`, старая
  остаётся в append-only истории) — штатно, как любая правка условий.
- Существующие черновики без поля при попытке `send` получат `422 payment_order_required` —
  мастер ведёт на шаг «Детали» так же, как для способа оплаты.
- Тесты: PATCH сохраняет; невалидное значение → 400; `send` без поля → 422 (займ — проходит);
  snapshot содержит поле; займ + поле → 400; смена типа на займ снимает поле; копия «как в
  прошлый раз» переносит поле (и снимает при переходе на займ).
- Прод: миграция `contracts 0010` — NULL-колонка, без блокировки; переменных окружения нет.

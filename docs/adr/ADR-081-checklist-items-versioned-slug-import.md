# ADR-081. ChecklistTemplateItem: версионирование по стабильному slug + import_checklists

**Статус:** принято
**Дата:** 2026-08-11
**Контекст этапа:** П-03 (`chore/checklists-seed`, docs/tasks — контент-трек
«Чек-листы приёмки и справочники — все 17 сфер», `docs/content/checklists/
00_индекс.md`)

## Контекст

П-03 подготовил 18 GLOBAL-файлов (`CL-*_GLOBAL.md`, ~1400 пунктов чек-листа
приёмки + ~170 позиций материалов) — контент, не код: полное наполнение
всех 17 сфер + `other`, отревьюенное владельцем (первая партия — `renovation`,
05.08; остальные — по мере ревью). Формат зафиксирован докстрингом
`CL-renovation_GLOBAL.md` §0 «Формат и маппинг на модель данных» и
`00_индекс.md` §2: колонки таблиц уже маппятся на `ChecklistTemplateItem`
(`code`/`text`/`check_method`/`photo_required`/`is_default`), но модель
(миграция 0005/0006, Э4.3) заводилась под ручной минимальный сид без
понятия «стабильный ID пункта» и без версионирования — `update_or_create`
там шёл по (`catalog_item`/`sphere`/`description`), т.е. правка текста
меняла бы СУЩЕСТВУЮЩУЮ строку.

Это не годится для контента, на который может сослаться замороженный
снепшот договора (`ContractVersion`, tech-spec.md — подпись всегда на
`integrity_hash` замороженной версии, CLAUDE.md): если сделка сослалась на
пункт чек-листа (или он вошёл в состав принятого этапа), а контент-ревью
позже уточнил формулировку («перепад ≤ 1 мм» → «≤ 1.5 мм»), правка
пункта задним числом не должна менять то, что стороны реально видели и
приняли. Нужен тот же принцип, что уже применяется к другим
каталожным текстам, зафиксированным в договоре навсегда (замороженная
`ContractVersion` от `integrity_hash`) — но для `ChecklistTemplateItem` его
предстояло завести с нуля: готового версионированного слоя в
`apps.catalog` не было.

Одновременно нужен ПОВТОРЯЕМЫЙ импорт: контент-ревью 18 файлов растянуто
по партиям (`00_индекс.md` §1 — партия 1 принята 05.08, партии 2–6 ждут
ревью владельца), т.е. `import_checklists` будет запускаться многократно по
мере правок одних и тех же файлов, и должен быть безопасен в
деплой-пайплайне (после `manage.py migrate`, как `import_l10n_pack` —
идемпотентный, версионированный, тонкая management-команда над
`services.py`).

## Решение

- **`slug` = `<сфера>.<категория>.<код пункта>`** — не генерируется
  алгоритмом из текста формулировки, а берётся из уже существующего кода
  пункта markdown-таблицы (`00_индекс.md` §2: «Полный код пункта:
  `<сфера>.<категория>.<тип_работ>.<номер>`» — сами файлы уже проектировали
  пункты с человекочитаемым устойчивым кодом). Присваивается ОДИН РАЗ при
  первом импорте строки с этим кодом и дальше не меняется, даже если текст
  правится.
- **`version` + `is_current`** на `ChecklistTemplateItem` (не отдельная
  таблица истории) — импорт при совпадении содержимого (`description`,
  `check_method`, `photo_required`, `is_default`, `category`) для
  существующего `slug` — no-op; при расхождении заводит НОВУЮ строку с тем
  же `slug`, `version + 1`, `is_current=True`, у предыдущей строки
  `is_current` становится `False`. Старая строка НЕ удаляется и НЕ
  редактируется — снепшоты договоров, уже сославшиеся на неё (по `id`, не по
  `slug`), продолжают видеть исходный текст. `selectors.
  recommended_checklist_template_items` (Э4.3, `GET .../checklist-
  recommendations`) дополнительно фильтрует `is_current=True`, чтобы новые
  этапы всегда получали актуальную редакцию.
- **Ровно одна текущая версия на slug** — constraint на уровне БД
  (`UniqueConstraint(fields=["slug"], condition=Q(is_current=True) &
  ~Q(slug=""))`), а не только гарантия сервисным кодом: два параллельных
  запуска `import_checklists` (или ручная правка через shell) не смогут
  создать два «текущих» пункта с одним slug.
- **`measurable_criterion` = `description`** для импортированных пунктов.
  Поле унаследовано от ручного сида Э4.3, где текст и критерий были двумя
  разными строками; в GLOBAL-формате «формулировка» уже несёт единственный
  измеримый критерий одним предложением (`00_индекс.md` §2: «один пункт —
  один критерий») — markdown отдельного текста критерия не содержит,
  заводить его синтетически было бы дублированием без источника, не новой
  информацией.
- **Ручной сид (миграция 0006) не трогается** — `slug=""` у его строк, вне
  контракта версионирования (constraints условны на `~Q(slug="")`,
  `is_current=True` по умолчанию — участвует в выборках как раньше).
  Переименование пересекающегося кода сферы (`tutoring` из старого
  плейсхолдера vs `education` из нового контента — оба остаются в
  справочнике) — отдельная задача, не эта ветка (см. «Последствия»).
- **Материалы (`MaterialCatalogItem`) без версионирования** — `code`
  детерминированный (транслитерация позиции), `update_or_create`-подобный
  upsert без истории: user-ask и домен не требуют историчности каталога
  материалов (в отличие от текста пункта чек-листа, материал не «подписан»
  в договоре напрямую — на него ссылается `ContractMaterial` со своими
  полями, справочник только подсказывает, docstring `MaterialCatalogItem`).
  Привязка «пункт → материал» (`catalog_item` FK) переустанавливается на
  ТЕКУЩУЮ версию пункта при каждом импорте — не версионируется отдельно.
- **`export_checklists_i18n`** — плоский JSON `catalog.checklists.<slug>` →
  текст (RU), только `is_current=True`. Формат ключа согласован с
  namespace `catalog` языковых пакетов `apps.l10n` (ADR-077: `catalog.
  <sub_ns>.<key>`) — вход будущего переводческого конвейера, НЕ сам пакет
  (`apps.l10n.services.import_pack` ожидает вложенное дерево `catalog.
  checklists: {slug: text}`, что тривиально собрать из плоских ключей этой
  команды; интеграция с реальным конвейером — отдельная задача, вне этой
  ветки, как и было с самим импортом волн A/B1/B2, ADR-077 «Последствия»).

## Альтернативы

- **Отдельная таблица истории (`ChecklistTemplateItemVersion`)** вместо
  `version`/`is_current` на самой модели. Отклонено: `selectors.
  recommended_checklist_template_items` и `apps.milestones` уже работают
  с `ChecklistTemplateItem` напрямую (Э4.3) — вынос текущей версии в
  отдельную таблицу потребовал бы менять этот контракт (чужой домен) ради
  History-таблицы, которую можно получить проще — той же моделью с флагом,
  тем же приёмом, что уже есть в репозитории у `ContractVersion` (сама
  таблица версий — не отдельная History-обвязка поверх Contract).
- **Слаг, генерируемый хешем/уникальным ID вместо кода из markdown**.
  Отклонено: коды пунктов (`washer_repair.1`, `inspection.3`) уже
  человекочитаемы и стабильны по построению самих CL-файлов (авторы
  контента их для этого и придумывали, `00_индекс.md` §2) — хеш убрал бы
  единственное практическое преимущество читаемого slug (можно найти
  пункт по коду из документа глазами, не через БД).
- **Semver-подобная версия текста пункта в самом markdown** (правщик
  вручную бампает номер версии в таблице). Отклонено: удваивает источник
  истины (markdown + БД должны были бы синхронно знать номер версии) и
  требует ручной дисциплины на каждую правку опечатки; текущее решение
  выводит версию из факта расхождения содержимого — контент-редактор
  правит только текст, версия — забота импортёра.

## Последствия

- `Sphere.code="tutoring"` (плейсхолдер Э4.3, `apps.contracts.forms.
  SPHERE_CODES`) и `Sphere.code="education"` (новый, из `CL-education_
  GLOBAL.md`) сосуществуют в справочнике после этой ветки — семантически
  один и тот же домен под двумя кодами. Слияние/депрекация плейсхолдера —
  отдельная задача (затрагивает `apps.contracts`, не нижний слой), не
  блокирует П-03: `Sphere` — таблица, не enum, переезд возможен без правки
  релиза (docstring `Sphere`).
- `social.*` (акты передачи архетипа `social`, `CL-other_GLOBAL.md` §2) —
  сознательно ВНЕ этого импорта: не сфера (докстринг файла это явно
  фиксирует), а домен архетипа `social` в `apps.contracts`/будущем
  `apps.milestones`-аналоге для не-услуговых договоров. Если/когда эти акты
  понадобится версионировать так же, как пункты чек-листов сфер — тот же
  slug/version-контракт (`social.<шаблон>.<код>`) переносится прямо,
  инфраструктура для этого уже готова, не изобретается заново.
- `import_checklists` — в `.github/workflows/deploy-staging.yml` сразу
  после `manage.py migrate` (обе БД), до `docker compose up -d` — тем же
  приёмом идемпотентности, что `import_l10n_pack`: повторный прогон того
  же тега (или ре-деплой без изменений в `docs/content/checklists/`) —
  no-op, безопасно перезапускать.

## Дополнение (2026-08-12): `is_jurisdiction_sensitive`, чистка [Л]-маркера, сверка счётчиков П-03

### Контекст дополнения

Две находки в ветке `feat/catalog` при подготовке импорта к ревью:

1. Инлайн-маркер «[Л]» (кириллица; допускался и вариант «[L]», латиницей) —
   авторский конвент `00_индекс.md` §2 «GLOBAL-правила» («страновые
   реалии — пометка [Л]») — жил ТОЛЬКО как подстрока в `description`,
   структурного признака на `ChecklistTemplateItem` не было (план завести
   такой флаг был зафиксирован в `00_индекс.md` §3 п.3 ещё на этапе
   контент-подготовки — `jurisdiction_dependent` + привязка к
   `JurisdictionConfig` — но не реализован).
2. `00_индекс.md` §1 «Итого» заявлял 1393 пункта; `import_checklists`
   реально заводил 1379.

### Решение

- **`is_jurisdiction_sensitive: bool`** на `ChecklistTemplateItem` (миграция
  0016) — не `jurisdiction_dependent`, как называла черновая заметка
  `00_индекс.md` §3 п.3: имя приведено в соответствие остальным булевым
  полям модели (`photo_required`, `is_default`) на этапе реализации.
  Привязка к `JurisdictionConfig` (упомянутая там же) — отдельная задача,
  этой правкой не делается: здесь только сохранение факта «пункт зависит
  от юрисдикции», без логики применения.
- **Маркер вычищается ТОЛЬКО из значения поля, не из markdown**:
  `checklist_markdown.parse_file` регэкспом `\s*\[[ЛL]\]` находит и
  удаляет маркер из `description` перед созданием
  `ParsedChecklistItem`, одновременно выставляя
  `is_jurisdiction_sensitive`. Сами `CL-*_GLOBAL.md` не редактируются —
  маркер остаётся действующим авторским конвентом для контент-ревью и
  будущих правок (`00_индекс.md` §2 меняется не так — только текст,
  сноска, флаг остаётся «[Л]»).
- **Существующие импортированные строки — миграцией 0017 (`RunPython`),
  БЕЗ инкремента `version`.** Это единственное сознательное исключение
  из принципа «правка текста пункта = новая версия» (раздел «Решение»
  выше): маркер — артефакт разметки, продублированное представление
  факта, который отныне хранится структурно; сам смысл формулировки не
  меняется чисткой «[Л]»/«[L]» из конца/середины предложения. Миграция
  правит строки с ЛЮБЫМ `is_current` (в т.ч. уже вытесненные версии, если
  такие появятся к моменту деплоя) — на 12.08.2026 ни одна из 18
  партий `docs/content/checklists/` не прошла итоговое контент-ревью
  (`00_индекс.md` §1: партия 1 принята 05.08 без последующих правок
  текста; партии 2–6 — «⏳ ожидает ревью»), т.е. ни один `ContractVersion`
  физически не мог зафиксировать в подписанном снепшоте текст с
  маркером — прямая правка безопасна. Если бы хоть один пункт уже был
  дозаявлен в подписанном договоре, для него потребовалась бы обычная
  версионированная правка (новая строка через `import_checklists`), не
  прямое редактирование миграцией.
- **Реальных «непопавших» пунктов нет** — расхождение 1393 vs 1379
  полностью объясняется двумя независимыми причинами (сверка
  «пофайлово», `checklist_markdown.parse_file` против таблиц
  `00_индекс.md` §1):
  - `CL-other_GLOBAL.md` содержит 21 пункт (6 сферы `other` + 15 актов
    `social.*`), но `00_индекс.md` §1 «Итого» суммировал ВСЕ 21 в общий
    план импорта, хотя 15 актов `social.*` заведомо вне
    `import_checklists` (раздел «Последствия» этого ADR, ещё до этого
    дополнения) — код не менялся, документ был неточен.
  - `CL-sales_GLOBAL.md`: строка-маркер «пишется сторонами» категории
    `sales.other` была размечена кодом `inspection.3` вместо `other`
    (единственная строка такого рода во всех 18 файлах — сверено
    grep’ом по всем таблицам с пустым «дефолт» (`—`) на месте да/нет:
    больше нигде код не расходится с конвентом). Правило пропуска в
    `checklist_markdown.parse_file` — по КОДУ `other` (`_OTHER_CODE`), не
    по категории, поэтому строка не пропускалась и заводила лишний,
    бессмысленный пункт (`description` без метода/дефолта). Разметка
    файла исправлена (`other | other | ...`); это правка markdown, не
    парсера — конвент «код `other` = маркер» уже во всех остальных 71
    подобных строках репозитория, здесь он просто не был соблюдён при
    авторстве.
  - 1393 (заявлено) − 15 (`social.*`, вне импорта архитектурно) − 1
    (снятый лишний пункт `sales.other`) = 1378 = фактический счётчик
    `import_checklists` после обеих правок. `00_индекс.md` §1
    обновлён (сноски ¹/²) этим же PR, чтобы «Итого» впредь совпадало со
    счётчиком парсера напрямую.

### Проверено

- `docs/content/checklists/CL-*_GLOBAL.md` (все 18) — `import_checklists`
  создаёт 1378 текущих пунктов, второй прогон без изменений в файлах —
  `items_created=0, items_new_version=0` (идемпотентность не нарушена).
- `is_jurisdiction_sensitive=True` — 23 (пункты сфер; 24-й маркер в
  разметке — `sale_vehicle.precheck.1` внутри `social`, вне импорта).
- `l10n/checklists/_source.ru.json` (регенерирован
  `export_checklists_i18n`) — 1378 ключей, ни один текст не содержит
  «[Л]»/«[L]».

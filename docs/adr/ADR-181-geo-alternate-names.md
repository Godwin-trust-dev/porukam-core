# ADR-181. Названия городов/регионов на языке зрителя + поиск на любом из наших языков

**Статус:** принято (план 11.09, часть 2b — продолжение ADR-179: «названия городов и регионов
на языке зрителя + поиск на любом из наших языков»)
**Контекст:** только что влитый справочник `apps.geo` (ADR-179) хранит `name`/`name_latin`
ровно так, как их даёт GeoNames — то есть **латиницей** для России/Казахстана
(`cities15000.txt`: `Moscow`, `Almaty`, не «Москва»/«Алматы»). Человек, набирающий «Москва»
или «Алматы» кириллицей — а это основной рынок продукта — сейчас не находит ничего.
Лечится тем же источником: подушевые файлы GeoNames alternatenames
(`https://download.geonames.org/export/dump/alternatenames/<CC>.zip`).
**Номер:** 181 — сверено по всем ворктри (`ls ~/porukam-worktrees/*/docs/adr ~/porukam/docs/adr
| grep -o 'ADR-[0-9]*' | sort -u | tail -5`, максимум был 180 — занят непришитой веткой
карточки пуша, следующий свободный — 181).

## Решение

### Отдельная таблица имён, а не JSONB-поиск

`City.name_i18n`/`Region.name_i18n` (JSONField, заведены ADR-179 «на будущее», раньше всегда
`{}`) для ПОИСКА непригодны: префиксный поиск по ЗНАЧЕНИЮ внутри JSONB Postgres нормально не
индексируется — GIN на `jsonb_ops` индексирует ключи/пути документа, а не текст значений;
`jsonb_path_ops` тем более не годится под `LIKE`. Единственная рабочая альтернатива в схеме
«значения ищутся» — обычная колонка + функциональный индекс, а обычная колонка не может лежать
внутри одного JSON-поля на несколько языков сразу.

Решение — **две новые таблицы**, `CityName`/`RegionName` (не одна общая полиморфная таблица
на City+Region): `(объект, locale, name, is_preferred, is_historic, geonames_alt_name_id)`.
Одна таблица на тип объекта, а не GenericForeignKey/два nullable FK + CHECK «ровно один не
NULL» — по двум причинам:
- в проекте вообще нет `GenericForeignKey` (`grep -rn GenericForeignKey apps/` — пусто) и
  паттерна «shared name table» для City/Region тоже нет: сам справочник уже устроен как ДВЕ
  отдельные модели (`City`, `Region`), а не общий `Place` с дискриминатором — зеркальные
  `CityName`/`RegionName` продолжают это же архитектурное решение, не вводят новый паттерн
  ради экономии одной таблицы;
- обычный FK (`CityName.city_id -> City`, `RegionName.region_id -> Region`) даёт настоящую
  ссылочную целостность на уровне БД (`ON DELETE CASCADE`) и простые, однозначно читаемые
  индексы — без CHECK-ограничения «ровно один из двух FK заполнен» и без риска реализации
  ссылки на несуществующий тип объекта, который GenericForeignKey не проверяет в БД вовсе.

`geonames_alt_name_id` (натуральный ключ строки источника — `alternateNameId`, глобально
уникален по всей базе GeoNames, в отличие от `geonames_id` City/Region) держит идемпотентность
повторного импорта тем же приёмом, что и остальной `apps.geo` — `bulk_create(...,
update_conflicts=True)`.

### `name_i18n` — предвычисленный кэш «лучшее имя по локали», не удалён

Задание допускало оба варианта — заполнить `name_i18n` для отображения БЕЗ join'а или убрать
поле новой миграцией. Выбрано **заполнить**: `apps.geo.services.refresh_city_name_i18n`/
`refresh_region_name_i18n` пересчитывают `City.name_i18n`/`Region.name_i18n` ПОЛНОСТЬЮ из
текущих `CityName`/`RegionName` при каждом импорте (`DISTINCT ON (city_id) ORDER BY city_id,
-is_preferred, id`, только `is_historic=False`) — то есть выбор «предпочитаемое имя локали,
а если такого нет — любое непустое неисторическое» УЖЕ сделан на этапе импорта и лежит
готовым значением в поле, которое API уже отдавал (`api/serializers.py`, ADR-179). Чтение
(`GET /v1/geo/cities|regions`, батч на всю страницу выдачи) поэтому — простой доступ по ключу
словаря, без единого дополнительного запроса к БД, независимо от того, скольким языкам и
скольким альтернативным именам отвечает конкретный город. Полный пересчёт (не приращение)
корректно отражает изменения источника между прогонами импорта (имя разжаловали из preferred,
поменяли — не только то, что попало именно в этот файл).

Отдать это на откуп READ-запросу (JOIN/подзапрос к `CityName` на каждой странице выдачи) было
бы медленнее без выигрыша: набор языков фиксирован (29 локалей проекта), пересчёт всё равно
детерминирован по тем же правилам preferred/historic — совмещать вычисление с каждым чтением
незачем.

### Сопоставление локали и языка GeoNames — явная таблица

`apps.geo.constants.LOCALE_TO_GEONAMES_LANGS` — наша локаль (код `apps.l10n.Locale`/встроенная
пара `common.i18n.SUPPORTED_LOCALES`, 29 кодов `l10n/packs/*.json`) → код(ы) языка в колонке
`isolanguage` подушевого файла (обычно ISO 639-1). `apps.geo` — нижний слой и НЕ импортирует
`apps.l10n` (даже как соседа по тому же слою, см. `models.py`) — список локалей продублирован
явно в `constants.py`, тем же приёмом, каким `DEFAULT_COUNTRY_CODES` уже дублирует фронтовый
список стран (при появлении нового языкового пакета поправить оба места).

Сопоставление НЕ всегда 1:1 — три случая, проверенные на реальном дампе (`KZ.txt`,
167 140 строк):
- `pt-BR` (Portuguese, Brazil) — GeoNames почти всегда даёт голый `pt` без региона (в `KZ.txt`
  код `pt-BR` встретился ровно 1 раз, `pt` — 54 раза); принимаем оба, `pt` — основной источник;
- `zh-Hans` (упрощённое письмо) — GeoNames в массе даёт голый `zh`, различение Hans/Hant
  встречается только эпизодически (`zh-TW` в том же дампе — традиционное письмо, под нашу
  локаль сознательно НЕ подмешивается: другой алфавит); принимаем `zh` и `zh-Hans`;
- `he`/`id` — исторические коды ISO 639-1 до пересмотра стандарта (`iw` для иврита, `in` для
  индонезийского) местами унаследованы источником; принимаем оба варианта на каждую локаль.

Обратный индекс `GEONAMES_LANG_TO_LOCALE` строится и проверяется на коллизии (один код
источника → максимум одна наша локаль) при загрузке модуля — если правило когда-нибудь
нарушится, упадёт при старте процесса, а не молча перепутает язык в проде.

### `isPreferred`/`isHistoric`

`isPreferred` — предпочитаемое (каноничное) имя ЭТОЙ локали для места; ложится в
`name_i18n` (см. выше). `isHistoric` (пример из источника — geonameid 1526384, «Алма-Ата»,
`isHistoric=1`, «Алматы» с тем же `isPreferred=1`) — участвует в ПОИСКЕ наравне с текущими
именами (`apps.geo.selectors` не фильтрует `is_historic`), но НИКОГДА не в отображении —
`refresh_*_name_i18n` строки с `is_historic=True` не читает вовсе.

### Поиск — полу-соединение, не JOIN

`selectors.list_cities`/`search_regions`: к прежнему условию (`name`/`name_latin`, префикс,
регистронезависимо) добавлено `Q(pk__in=Subquery(CityName_или_RegionName...values("city_id"
или "region_id")))`. `IN`-полу-соединение, а не `JOIN` + `annotate`, — принципиально: у одного
города/региона может быть несколько альтернативных имён, совпавших с одним и тем же запросом
(разные локали, историческое+текущее) — `JOIN` размножил бы строку City/Region по числу
совпадений, `IN` — нет. Сортировка по населению и keyset-пагинация (`selectors.list_cities`)
поэтому не меняются вообще: они видят обычный `QuerySet[City]`, как и раньше.

### Регистронезависимость: `Lower()` в Postgres зависит от КОЛЛАЦИИ, а не от LC_CTYPE — найдено в процессе

ADR-179 (докстринг `apps/geo/models.py`) утверждал: «`lower()`/`upper()` — функции Postgres,
берут регистр символа из `LC_CTYPE` СЕССИИ/БД, а НЕ из коллации колонки» — и поэтому
регистронезависимый поиск под явной коллацией `"C"` (byte-comparison) якобы одинаково хорошо
работает для любого алфавита. Проверка на реальном Postgres 16 этого проекта (при разработке
поиска по `CityName`, первый раз, когда через `Lower()` реально прогнали кириллицу/армянский,
а не только латинские диакритики) это опровергла:

```sql
SELECT lower('АЛМАТЫ' COLLATE "C");        -- 'АЛМАТЫ' — НЕ сворачивается
SELECT lower('АЛМАТЫ' COLLATE "default");  -- 'алматы' — сворачивается верно
```

Под явной коллацией `"C"` (POSIX/ASCII case rules) `lower()`/`upper()` сворачивают ТОЛЬКО
ASCII `A-Z`; кириллица, армянский, латинские диакритики (`Ü`→`ü` тоже не работает под `"C"`)
остаются как есть. Существующий `City.name`/`Region.name` (коллация `"C"`, ADR-179) этой
ошибки не показал только везением — `cities15000.txt`/`admin1CodesASCII.txt` дают `name`
латиницей для стран текущей фикстуры (сам ADR-179 это отмечает как факт источника, не как
доказанную гарантию на 100% стран); реальный дамп вполне может дать `name` кириллицей/греческим
для какой-то страны, и тогда `WHERE lower(name) LIKE 'префикс%'` для неё не сработает уже
сейчас. **Это существующее (до этой ветки) поведение `City`/`Region`, вне рамок этой задачи —
см. «Пределы задачи» ниже, оставлено как есть.**

Для НОВЫХ таблиц (`CityName`/`RegionName`) это не вариант: они хранят НАСТОЯЩИЕ многоязычные
названия, где кириллица/армянский с заглавной буквы — норма, а не редкое исключение. Решение:
`name` БЕЗ явной коллации (дефолт кластера — `en_US.utf8`, Unicode-осведомлённый, `initdb`
по умолчанию), функциональный индекс —
`django.contrib.postgres.indexes.OpClass(Lower("name"), name="text_pattern_ops")` вместо
голого `Lower("name")`: под НЕ-`"C"`-коллацией обычный `LIKE 'x%'` без опкласс-подсказки не
использует btree-индекс (это и есть исходный резон ADR-179 в пользу `"C"`); `text_pattern_ops`
восстанавливает эту поддержку для конкретно этого индекса безотносительно коллации БД —
проверено `EXPLAIN` на реальных данных (`Bitmap Index Scan` вместо `Seq Scan` для
`lower(name) LIKE 'алматы%'` на таблице с несколькими тысячами строк).

Технический нюанс реализации: Django требует `Index(opclasses=...)` только для индексов ПО
ПОЛЮ; для индекса по ВЫРАЖЕНИЮ — явно требует `OpClass` (иначе `ValueError` при
`makemigrations`). `OpClass` при этом распознаётся схема-редактором как «верхний» враппер
выражения (как `OrderBy`/`Collate` — без лишней пары скобок вокруг `Lower(...)`) только если
явно зарегистрирован через `IndexExpression.register_wrappers` — иначе `CREATE INDEX`
получает лишнюю пару скобок и падает синтаксисом (`((LOWER("name") text_pattern_ops))` —
поймано на реальном Postgres при первом прогоне миграции). Регистрацию обычно делает
`django.contrib.postgres.apps.PostgresConfig.ready()`, но `django.contrib.postgres` в
`INSTALLED_APPS` проекта не включён (собственный набор из 25 приложений, CLAUDE.md) — вместо
включения всего contrib-приложения ради одной индексной подсказки, `apps.geo.apps.GeoConfig.
ready()` регистрирует враппер тем же публичным API.

### Пределы задачи

Эта ветка — ТОЛЬКО `apps.geo` (справочник + его API), как и было ограничено планом. Вне неё:
- описанный выше латентный баг `City.name`/`Region.name` под коллацией `"C"` для
  кириллицы/диакритики — существовал ДО этой ветки (ADR-179), здесь только обнаружен и
  задокументирован, не исправлен (потребовал бы редактирования уже смёрженной миграции 0001,
  что запрещено CLAUDE.md; чинить — новая, отдельная задача);
- привязка `apps.profiles.Profile` к `City`/`Region` и сам фильтр `apps.dashboards.get_search`
  по геосправочнику — части 4–5 того же плана, отдельные ветки.

## Импорт

`manage.py import_geo` (без изменений в интерфейсе для существующих флагов):

```
python manage.py import_geo --download --countries=RU,KZ,BY,...
python manage.py import_geo --dir /path/to/geonames-dump
python manage.py import_geo --dir ... --countries=all
python manage.py import_geo --download --skip-names   # прежнее поведение ADR-179, без имён
```

После стран/регионов/городов (не изменилось) команда, если не передан `--skip-names`, тянет
`alternatenames/<CC>.zip` **по тем же странам**, что и основной импорт (при `--countries=all`
— по всем кодам, реально встреченным в `countryInfo.txt` этого прогона, так как заранее список
неизвестен): по одному ZIP-архиву на страну (в отличие от единого `cities15000.zip` на весь
мир) — HTTP-404/сетевая ошибка на ОДНОЙ стране не валит прогон остальных, пропуск логируется.
`apps.geo.services.import_alternate_names` берёт строку, только если её `geonameid` уже есть
у нас (City ИЛИ Region — пространства id не пересекаются, `geonameid` глобально уникален по
всей базе GeoNames) И `isolanguage` — в нашем наборе локалей; следом
`refresh_city_name_i18n`/`refresh_region_name_i18n` пересчитывают `name_i18n` целиком по
затронутому набору стран. Реализация — тот же стиль, что ADR-179: потоково (`ZipFile.open()`),
батчами `bulk_create(update_conflicts=True)`, битые строки — `continue` со счётчиком.

**Реальные цифры** (проверено на факте — один прогон `--countries=KZ`, `--download` для
countryInfo/admin1/cities, файл имён `KZ.zip` скачан отдельно после сетевого сбоя на первой
попытке — см. ниже): страны=1, регионы=21, города=84 (без изменений от ADR-179); имена
городов=944, имена регионов=374 (итого 1318 новых строк), пропущено 165 822 из 167 140 строк
`KZ.txt` — то есть на объект нашего справочника (город/регион) в среднем приходится ≈16 имён
из ~29 возможных языков (не все языки покрыты для каждого места — «любая другая строка» из
формулы задания включает и служебные метки источника вроде `link`/`wkdt`/`iata`/`unlc`/`post`,
которых в `KZ.txt` тысячи, и десятки языков вне нашего набора). На дефолтных 68 странах
(ADR-179 давал «низкие десятки тысяч» городов) это ориентировочно **несколько сотен тысяч**
строк `CityName`+`RegionName`, что для одной Postgres-таблицы с функциональным индексом
некритично.

Скачивание подушевого файла — по одному ZIP-архиву **на страну** (не один файл на весь мир,
как `cities15000.zip`): `KZ.zip` — 1,95 МБ сжатый / 7,7 МБ распакованный на 167 140 строк.
На дефолтных 68 странах это заметно больше сетевого трафика и времени прогона, чем раньше
(десятки отдельных HTTP-запросов вместо трёх) — учитывать при планировании окна деплоя.

**ВАЖНО: после выкатки этой ветки на прод команду `import_geo` НУЖНО ПЕРЕЗАПУСТИТЬ** —
справочник (страны/регионы/города) ещё не выкачен на прод вообще (ADR-179 «Последствия»), но
когда это случится, обычный cron/ручной повторный прогон теперь тянет СУЩЕСТВЕННО больше
данных (имена) при том же наборе стран; если прогон уже случился БЕЗ этой ветки — повторный
запуск с этой веткой доберёт имена и пересчитает `name_i18n`, ничего не задваивая
(идемпотентность на `geonames_alt_name_id`).

## API

`GET /v1/geo/cities`/`GET /v1/geo/regions` — новое поле `display_name` (название НА ЯЗЫКЕ
ЗРИТЕЛЯ, `api/serializers.py::_display_name`): локаль запроса — `common.i18n.
resolve_request_locale` (тот же механизм, что у остальных API проекта — `apps.catalog`,
`apps.dashboards`, …), фолбэк `name_i18n[locale]` → `name` (как дал источник) → `name_latin`.
Существующие поля `name`/`name_latin`/`name_i18n` не убраны (нет ни одного потребителя в
проде, справочник не выкачен — но менять уже описанный ADR-179 контракт без причины незачем).
Вьюхи передают `context={"request": request}` в сериализаторы — без этого `display_name`
всегда фолбэкнулся бы на `DEFAULT_LOCALE`.

## Последствия

- Две новые таблицы (`geo_city_name`, `geo_region_name`), одна новая миграция (`0002`, до
  прод-выкатки основного справочника — историю модели этим не портим).
- `manage.py import_geo` качает и пишет заметно больше данных при том же наборе стран (см.
  «Импорт» выше) — учитывать в окне деплоя/cron.
- Обнаруженный, но НЕ исправленный в этой ветке баг регистронезависимого поиска `City.name`/
  `Region.name` под `"C"`-коллацией для нелатинских исходных названий (см. «Пределы задачи») —
  зафиксировать отдельной задачей на будущее, если/когда в справочник попадёт страна с
  нелатинским `name` в источнике.
- `IndexExpression.register_wrappers` из `apps.geo.apps.GeoConfig.ready()` — глобальный побочный
  эффект (реестр враппера у Django один на процесс): любой другой код проекта, использующий
  `OpClass` на индексе по выражению, тоже получит рабочую регистрацию бесплатно. Побочный эффект
  безопасен (совпадает с тем, что сделал бы `django.contrib.postgres` в `INSTALLED_APPS`) и
  не создаёт обратной зависимости — `apps.geo` по-прежнему ни от кого не зависит.

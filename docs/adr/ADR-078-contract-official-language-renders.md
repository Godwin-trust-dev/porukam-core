# ADR-078. Официальный язык договора и рендеры снепшота при заморозке

**Статус:** принято
**Дата:** 2026-08-10
**Контекст этапа:** Л.1 (`feat/contracts-l10n`, docs/tasks/l10n-wave.md)

## Контекст

Док 32 (§Решение) и уточнение владельца к нему (v1.2, финал, 10.08.2026) требуют:
`ContractVersion.canonical_language` — язык канона текстов блоков; снепшот
при заморозке расширяется рендерами (канон + локализованный текст каждого
подписанта, каждый захеширован, `version_hash` считается ТОЛЬКО от
canonical-структуры — обратная совместимость подписанных договоров
обязательна); экран подписания отдаёт дисклеймер, только если язык
подписанта ≠ языку канона; `SignatureRequest` фиксирует locale реально
показанного текста.

Постановка (`l10n-wave.md`, зафиксирована 08.08) в буквальном виде говорит о
«выборе сторонами при создании договора из языков со статусом ≥ machine» —
т.е. мастер выбора языка в UI на этапе `create_draft`. Уточнение v1.2 это
явно снимает: мастера НЕТ, официальный язык договора вычисляется
автоматически при заморозке, с опциональной точечной правкой через PATCH
черновика, ограниченной quality ≥ reviewed (не ≥ machine — machine-перевод
слишком ненадёжен, чтобы быть тем текстом, ОТ КОТОРОГО считается «перевод
для удобства»). Это решение — расхождение с буквой исходной постановки,
поэтому фиксируется отдельным ADR (CLAUDE.md: «новое архитектурное решение —
файл в docs/adr/ в том же PR»).

## Решение

- **`Contract.language_override`** (новое поле, `apps.contracts.models`) —
  опциональный явный выбор официального языка, выставляется ТОЛЬКО через
  `PATCH /contracts/{id}` (`services.patch_draft`, поле `language` в API),
  только пока договор в статусе `draft`. Валидация —
  `apps.l10n.selectors.is_reviewed_or_better` (quality `canonical`/
  `reviewed`); иначе `LanguageNotEligibleError` → 422
  `language_not_eligible`. Пусто по умолчанию — официальный язык тогда
  решает авторезолв.
- **`services._resolve_official_language`** (вызывается из
  `freeze_contract`) — порядок приоритета:
  1. `contract.language_override`, если выставлен (стороны уже
     договорились явно);
  2. иначе — язык интерфейса, общий для ОБЕИХ сторон
     (`services._shared_party_locale`: `get_user_locale` заказчика ==
     `get_user_locale` исполнителя; `None`, если хоть одна сторона не
     резолвится в пользователя или локали различаются), при условии
     `quality >= reviewed` (тот же `is_reviewed_or_better`) — если стороны
     реально говорят на одном достаточно качественном языке, незачем
     принудительно переводить их же договор на EN/RU;
  3. иначе — прежний фолбэк по jurisdiction Э4.4/Л.1-v1: RU-контур ->
     `"ru"`, GLOBAL-дефолт -> `"en"` (`apps.jurisdictions.selectors.
     resolve_locale(contract.jurisdiction)`).
- **`ContractVersion.canonical_language`/`renders`** — без изменений
  относительно первой итерации Л.1: поля называются по историческому имени
  постановки (`canonical_language`), пересчитываются авторезолвером выше,
  НЕ входят в `snapshot`/`integrity_hash` (подпись остаётся на
  canonical-структуре Э4.4). `renders` — официальный язык + языки текущих
  сторон НА МОМЕНТ заморозки (`_party_locales`, tolerant-резолвер), каждый
  захеширован отдельно от `integrity_hash`.
- **API-тексты не несут слово «canonical»** (продуктовое решение уточнения
  v1.2) — `ContractVersionSerializer` отдаёт наружу `official_language`
  (`source="canonical_language"`), `ContractSerializer` отдаёт
  `language` (`source="language_override"`), дисклеймер `/sign`
  переформулирован: «This is an automatic translation. The official text
  of the contract is {official_language}.» — без «canonical»/«for
  convenience only, not certified».
- **Официальный рендер «по запросу»** (уточнение v1.2, п.4) — отдельного
  эндпоинта не заводили: `Signature`/ответ `/sign` уже несёт
  `version_hash`/`contract_id`, а `ContractVersionDetailView` (существующий
  GET версии) уже отдаёт `renders` целиком, включая официальный —
  инфраструктура уже покрывает требование.
- **`SignatureRequest.locale`** — без изменений: locale ДЕЙСТВИТЕЛЬНО
  показанного рендера, `services.sign` проставляет в момент подписания
  (`selectors.resolve_shown_locale` — честный фолбэк на официальный язык,
  если рендера под текущую locale подписанта в замороженной версии нет).

## Альтернативы

- **Мастер выбора языка в UI при `create_draft`** (буква исходной
  постановки). Отклонено уточнением v1.2 прямым текстом — авторезолв +
  точечный PATCH дешевле для MVP волны и не требует нового шага в форме
  создания договора; выбор всё равно доступен, просто не обязателен и не
  на первом экране.
- **Ограничить `language_override`/авторезолв quality ≥ machine** (буква
  исходной постановки п.1). Отклонено уточнением v1.2: официальный язык —
  то, ОТ ЧЕГО считается дисклеймер «это перевод для удобства» для всех
  остальных языков; `machine`-перевод (beta, непроверенный) не может сам
  быть этим эталоном.
- **Отдельный эндпоинт «выдать официальный рендер»**. Отклонено —
  `ContractVersionDetailView` уже отдаёт `renders` целиком по
  `contract_id`/`version_id`, которые клиент уже получает из ответа
  `/sign`; новый эндпоинт дублировал бы уже читаемые данные.

## Последствия

- `Contract.language_override` можно только выставить, но не «снять»
  обратно на авторезолв через API в этой волне (PATCH трактует
  `language: null` как «не менять», как и остальные поля черновика) —
  если понадобится явный откат на авторезолв, это отдельный маленький
  тикет (доп. сентинел или отдельный DELETE-подобный экшн), не блокирует
  приёмку Л.1.
- Реальная ClauseTemplate-композиция текста по блокам (не просто тег
  `language` поверх той же canonical-структуры) — вне этой волны, как и
  раньше (ADR-075, «предмет будущего контракт-трека»).

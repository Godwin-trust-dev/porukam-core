# ADR-085. SPA-раздача из nginx: сборка `web/` переезжает в multi-stage nginx-образ, собираемый в CI

**Статус:** принято
**Дата:** 2026-08-15
**Контекст этапа:** `docs/tasks/Задача_feat_nginx-serve-spa.md` — на проде
(ADR-069) корень `/` отдавал 404: `location / { proxy_pass http://core:8000; }`
уводил весь трафик в Django, у которого на `/` роута нет; собранный `web/`
в образ nginx не копировался вообще (в конфиге отдача SPA была помечена как
отложенная).

## Контекст

nginx на проде до этого PR **собирался на самой ВМ** (`build:` в
`прод-конфиг`, контекст `конфиг nginx` —
ADR-069 «Альтернативы»: сборка в CI буксом отклонена как ненужная сложность
на тот момент, `docker build` classic builder справлялся). core/celery уже
собирались в CI (`cd-images.yml`, ADR-066) и **тянулись** прод-ВМ готовыми.
Контекст `конфиг nginx` не содержит `web/` — собрать SPA прямо на
проде тем же приёмом, что core/celery, было невозможно без смены контекста.

## Решение

- **SPA собирается ВНУТРИ образа nginx, отдельной стадией `web-builder`**
  (`конфиг nginx`), не отдельным образом и не отдельным
  CI-артефактом. Один физический деплой-юнит (nginx-контейнер) — и
  реверс-прокси, и раздача статики SPA; артефакт сборки (`web/dist`)
  копируется в рантайм-стадию (`nginx:1.27-alpine`) через `COPY
  --from=web-builder`, сам Node в финальном образе не остаётся.
  Альтернатива — собирать `web/dist` отдельным CI-джобом/артефактом и
  монтировать его в nginx volume'ом — отклонена: добавляет отдельный
  промежуточный артефакт (upload/download между джобами) ради того, что
  multi-stage `COPY --from` уже даёт бесплатно и атомарно (SPA и nginx-
  конфиг всегда одной версии, одним тегом).
- **Контекст сборки nginx-образа — КОРЕНЬ РЕПО**, не `конфиг nginx`
  (был) — `web/` и `packages/*` (npm-workspace-зависимости SPA) вне
  прежнего контекста. `.dockerignore` теперь общий для ДВУХ Dockerfile
  (app и nginx) — `web`/`packages` убраны из списка исключений (были
  нужны только там, где контекст-корень использовался единственным
  Dockerfile'ом — приложением, которому фронтенд не нужен). Per-Dockerfile
  BuildKit-игнор-файлы (`<Dockerfile>.dockerignore`) не заводим — два
  разных списка исключений для одного и того же контекста легче
  рассинхронизировать по ошибке, чем держать один общий.
- **Сборка SPA переезжает в CI (`cd-images.yml`), прод-ВМ тянет готовый
  `porukam-nginx` из реестра**, как `core`/`celery` (ADR-066) — тем же
  приёмом: `-f конфиг nginx`, теги `${SHA}`+`latest`,
  build-args `NODE_BASE_IMAGE`/`NGINX_BASE_IMAGE` через собственный
  реестр (тот же `ARG BASE_IMAGE`-приём, что `infra/docker/app/Dockerfile`,
  санкц-риск подмены базового образа на зеркало без правки Dockerfile).
  `build:` в `docker-compose.prod.yml` остаётся (контекст сменён на
  `../../`) — только для локальной проверки; на проде поднимают без
  `--build`, `image:` берёт тег из реестра.
- **`locations.conf`: `location /` инвертирован на раздачу SPA
  (`try_files $uri $uri/ /index.html`), бэкенд-префиксы вынесены в
  СОБСТВЕННЫЕ явные `location`** — `/v1/` (весь API одним префиксом,
  сверено по `backend/config/urls.py`: все urlpatterns под `v1/`, включая
  `v1/health`, `v1/schema/`) и `/admin/` (Django admin). Список собран
  ЧТЕНИЕМ `urls.py`, не «на глаз» — иначе забытый бэкенд-префикс тихо
  начал бы отдавать `index.html` вместо API/админки (тот же класс риска,
  что уже ловился для l10n/checklists-путей в `cd-images.yml`).
- **`/static/`/`/django-static/` НЕ заведены.** `backend/config/settings/*`
  определяют только `STATIC_URL`, без `STATIC_ROOT`/`collectstatic`/
  whitenoise — раздавать сейчас физически нечего (каталога на диске нет),
  location на несуществующий путь ничего бы не решил. Заведётся вместе с
  самой раздачей статики админки — отдельная задача (правка backend-кода/
  Dockerfile приложения, не этого PR, CLAUDE.md «не проектировать под то,
  чего ещё нет»).
- **`/metrics` (django_prometheus, корневой префикс `urls.py`) СОЗНАТЕЛЬНО
  без внешнего `location`.** Прометей в проде скрейпит `core` напрямую
  внутри docker-сети (`прод-конфиг/prometheus.yml`: `targets:
  ["core:8000"]`) — nginx снаружи этот путь не публикует вообще, попадает
  в общий SPA-fallback `location /` (200 `index.html`, не утечка метрик и
  не 404).
- **`deploy-staging.yml`: `nginx` добавлен в `pull`/`up -d` НАРАВНЕ с
  `core`/`celery_worker`/`celery_beat`, в ОБОИХ местах** — основной деплой
  и откат при провале смоука. `porukam-nginx` теперь версионируется тем же
  `${IMAGE_TAG}`, что и остальные образы; без него в откате сломанный
  SPA/конфиг нового тега пережил бы откат ядра приложения. `depends_on`
  (`nginx ← core:healthy`) не тронут — порядок имён в команде `up -d` на
  него не влияет, compose сам упорядочивает по графу зависимостей.

## Альтернативы

- **Собирать SPA отдельно в CI (`actions/upload-artifact`) и класть
  готовый `dist/` в nginx volume'ом на проде, без пересборки образа.**
  Отклонено — держит деплой SPA вне версионирования образа (нужен
  отдельный механизм синхронизации версии SPA с версией остального
  стека, RPO/откат пришлось бы координировать вручную); multi-stage
  `COPY --from=web-builder` даёт то же самое одним артефактом бесплатно.
- **Отдельный образ `porukam-web` (только статика, свой nginx/сервер) —
  раздельные контейнеры для SPA и реверс-прокси.** Отклонено — для лин-T1
  (ADR-069, «максимально дешёвая» инфраструктура, `docs/finmodel-v2.md`
  §2.6) лишняя сущность ради статики, которую и так может отдать тот же
  nginx, что уже проксирует API; `depends_on`/health-цепочку пришлось бы
  дублировать на второй контейнер.
- **`VITE_*_BASE_URL`/build-time конфиг для адреса API.** Не понадобился —
  SPA бьёт в API относительно (`/v1/...`, same-origin через этот же nginx,
  `packages/core/src/api/client.ts`), никакого build-time абсолютного URL
  нет и не требуется.

## Последствия

- Контекст сборки `porukam-nginx` в CI и локально — весь репозиторий
  (крупнее, чем прежний `конфиг nginx`), но `.dockerignore` всё
  равно исключает `node_modules`/`mobile`/`docs`/служебные ВМ-каталоги —
  рост контекста ограничен реальным размером `web/`+`packages/`.
- `cd-images.yml`: триггер-пути расширены `web/**`, `packages/**`,
  `package.json`, `package-lock.json`, `конфиг nginx/**` — без этого
  правки фронта/пакетов/nginx-конфига не пересобирали бы `porukam-nginx`.
- До первого зелёного прогона `cd-images.yml` на этой ветке и
  `docker compose pull nginx && up -d nginx`/прогона `deploy-staging.yml`
  на прод-ВМ — `/` продолжает отдавать 404 (текущее состояние на проде не
  меняется автоматически мержем PR, нужен деплой).

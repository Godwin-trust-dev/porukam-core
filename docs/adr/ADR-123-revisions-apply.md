# ADR-123: Правки v2 — адресуемый `item_ref`, «Было» из договора, применение принятой правки, «Другое»

Дата: 2026-08-25. Статус: принят. Уточняет §8.4 tech-spec (протокол разногласий) и ADR по заморозке
(`_build_snapshot`, integrity_hash).

## Контекст

Отсмотр 2026-08-25: «при создании правки нужно чтобы в поле "Что меняем" был выпадающий список полей
договора, и автоматически в поле "Было" вставлялось текущее значение. Соответственно, если правка
принята, то в это поле должно попадать новое значение. Добавь ещё поле "Другое", чтобы могли добавить
произвольный текст, он тоже выводится в теле договора перед подписанием» + «проверь, что все правки
вносятся в архив сделки».

До этого `RevisionProposal.item_ref` был свободной строкой «на усмотрение вызывающего», `old_value`
не заполнялся, а принятие правки только меняло статус предложения — договор не менялся. Стороны
«договаривались» в протоколе, а затем должны были руками повторить то же в черновике.

## Решения

1. **Грамматика `item_ref`** (`services.REVISION_*`):
   - `form.<key>` — поле схемы формы типа договора (`forms.get_form_schema(contract_type).fields()`);
   - `title` — название договора (`Contract.title`);
   - `other` — новое дополнительное условие, произвольный текст.
   Любая другая строка (`milestones[2].amount` и т.п.) — «свободный» адрес прежнего образца:
   принимается, хранится в протоколе, попадает в snapshot, но к договору НЕ применяется
   (дерево этапов правится своими ручками, Э4.3).
2. **propose / counter** (`propose_revision`, `counter_revision`):
   - `form.<key>` с ключом вне схемы типа (или у типа нет схемы) → `422 revision_item_unknown`
     (`RevisionItemUnknownError`), предложение не создаётся;
   - `old_value` («Было») при отсутствии подставляется из договора: `form.<key>` →
     `form_data[key]` (None, если не заполнено), `title` → `contract.title`; явно переданный
     `old_value` сохраняется как есть;
   - `other`: `old_value` всегда None, `new_value` — непустая строка (иначе `422
     revision_value_invalid`); `title`: `new_value` — непустая строка ≤ 300 символов.
     Проверка значения одна и та же на входе и на применении (`_clean_title_value`/
     `_clean_other_value`) — «принято, но не применилось» невозможно.
3. **accept применяет правку** (`accept_revision`, `accept_all_revisions`,
   `apply_preapproved_alternative`) в той же транзакции, только пока договор на согласовании
   (`_assert_negotiating` — после заморозки/подписания `409 invalid_negotiation_transition`):
   - `form.<key>`: мягкое приведение значения по `field_type` (`"21"` → 21 для integer, `"true"`/«да»
     → True для boolean, число → строка для decimal), затем `forms.validate_form_data` для
     объединённого `form_data` (дефолты, условная видимость, кросс-полевые правила — как у
     `patch_draft`); невалидное значение → `422 revision_value_invalid` с `context.errors`
     формата `FormValidationError`, транзакция откатывается, предложение остаётся `open`;
   - `title` → `Contract.title` (непустая строка ≤ 300);
   - `other` → дописывается в **новый `Contract.additional_terms`** (JSONField `list[str]`,
     default `[]`, миграция `0008_contract_additional_terms`) в порядке принятия;
   - контрпредложение принимается со своим `new_value`;
   - `accept_all` применяет в порядке создания; одно невалидное значение откатывает всё.
   Событие outbox `negotiation.revised` получает `applied: bool` и `field: str | null`
   (`title` / `other` / `<form key>`).
4. **Заранее одобренные альтернативы** (`create_preapproved_alternative`,
   `apply_preapproved_alternative`) применяются по той же грамматике. Значение берётся из
   `payload["value"]`, иначе из «листового» ключа (`payload["title"]` / `payload["text"]` /
   `payload[<key>]`). Для адресуемого `item_ref` адрес и значение проверяются **на создании**
   альтернативы (`422 revision_item_unknown` / `revision_value_invalid`): «одобрить заранее то,
   что не применится», нельзя. Альтернативы, заведённые до ADR-123 и не несущие значения, при
   применении не меняют договор (а не затирают поле) — сентинел `_NO_ALTERNATIVE_VALUE`.
   «Было» применённой альтернативы — значение вытесненного открытого предложения, иначе текущее
   значение договора.
   `payload={"value": null}` для `form.<key>` = «убрать своё значение»: ключ вынимается из
   `form_data`, схема подставляет дефолт (или даёт `required`, если поле обязательно). Через
   `propose_revision` это недостижимо: `RevisionProposal.new_value` — NOT NULL.
5. **Архив сделки = canonical snapshot заморозки.** `_build_snapshot` включает
   `additional_terms` (часть текста договора под `integrity_hash`, выводится в теле договора перед
   подписанием) и `revisions` — протокол разногласий целиком: все предложения всех статусов
   (`id`, `item_ref`, `old_value`, `new_value`, `comment`, `status`, `proposed_by_profile_id`,
   `decided_by_profile_id`, `decided_at`, `created_at`) в порядке создания. Подпись ставится на
   хеш версии, включающей историю согласования, — это и есть ответ на «все правки вносятся в
   архив сделки». Отдельная выгрузка архива (archive-export) остаётся задачей Ф6; отчёт по
   каждому действию по-прежнему пишется в outbox → audit_vault.
6. **API**: `GET /contracts/{id}` отдаёт `additional_terms: string[]`; `POST
   /contracts/{id}/revisions` принимает `item_ref` по грамматике §1 (`old_value` необязателен);
   новые коды ошибок `revision_item_unknown` (422) и `revision_value_invalid` (422,
   `context.errors[]` — список `{field, code, message}`, как у `form_data_invalid`).
   Список допустимых `form.<key>` фронт берёт из уже существующего
   `GET /v1/contract-types/{code}/form-schema` (секции, поля, типы, choices, условная
   видимость) — отдельного эндпоинта «поля для правки» не заводим.
   EN-заголовки новых кодов добавлены в фолбэк-реестр `common/api/error_texts.py`;
   в `l10n/packs/*.json` они не заведены — это потребовало бы 29 переводов и бампа версий
   пакетов (см. `apps.l10n.tests.test_packs_coverage`), выносится в общую волну l10n-backfill.
7. **Фронт (`feat/web-revisions-picker`)**: «Что меняем» — выпадающий список видимых полей схемы
   (подписи как в панели условий) + «Название договора» + «Другое» (последним); «Было» —
   только для чтения, заполняется текущим отформатированным значением; «Стало» — виджет по типу
   поля (choice → select, boolean → Да/Нет, date → дата, иначе текст); для «Другое» — textarea
   «Текст условия» без «Было». Блок «Дополнительные условия» в панели условий и на экране
   подписания.

## Последствия

- Принятая правка сразу меняет черновик — «Стало» становится текущим значением, а следующая
  правка по тому же полю автоматически получает его в «Было».
- Свободные `item_ref` не сломаны (обратная совместимость с существующими предложениями и
  тестами), но и не применяются — расширение грамматики (`milestones[...]`) — отдельный ADR.
- `revisions` в snapshot делает замороженную версию длиннее; это осознанно: договор с историей
  разногласий — юридически ценнее, чем без неё. Существующие замороженные версии не
  пересчитываются: `integrity_hash` считается на момент заморозки, старые версии остаются
  валидными в своём формате.
- Применение правки — единственный путь, которым договор меняется на стадии `under_review`
  (`patch_draft` требует `draft`). Инвариант «подписанный договор неизменяем» не тронут: гейт
  `_assert_negotiating` закрывает и propose, и counter, и accept, и accept-all, и применение
  альтернативы сразу после заморозки.
- `additional_terms` — `list[str]` без идентификаторов: удалить или отредактировать уже принятое
  дополнительное условие можно только новой правкой поверх (или допником после подписания).
  Адресация отдельных пунктов (`other[2]`) — при необходимости отдельным ADR.

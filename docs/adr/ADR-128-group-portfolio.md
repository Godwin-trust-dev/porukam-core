# ADR-128: Портфолио проектов объединения

Дата: 2026-08-25. Статус: принят. Расширение ADR-115/ADR-120 (личное портфолио)
на объединения ADR-117.

## Контекст

Личное портфолио доведено до v2 (ADR-120): проект с обязательной датой
завершения, опциональным городом, просторным описанием и галереей до 5 фото
(первая — основная); проекты редактируются, на карточке репутации работы
кликабельны. Объединения (ADR-117: гильдия/клан/сообщество/витрина компании —
логотип, сфера, география, соцссылки, публичная карточка, участники,
приглашения) такой витрины работ не имеют: гильдия может рассказать, кто она,
но не показать, что сделала.

Нужно: у объединения — свои проекты портфолио; управляют владельцы/админы
объединения; показываются на публичной карточке объединения тем же блоком,
что и у человека.

## Решения

### 1. Отдельная модель в `apps.social`, а не `owner`-обобщение `PortfolioProject`

Рассмотрены оба варианта:

- **(а) обобщить `PortfolioProject` через `owner` (profile | group).** Отклонён.
  `PortfolioProject` живёт в `apps.profiles` и висит на `Portfolio` —
  `OneToOneField` на `Profile`; у объединения `Profile` нет и быть не должно
  (объединение — витрина, НЕ сторона договора и репутацию не носит,
  tech-spec.md §5.2.1b). Обобщение потребовало бы либо `apps.social` →
  `apps.profiles` (запрещено import-linter: «social зависит только от
  accounts»), либо переноса владения группами в `apps.profiles` — то есть
  размывания bounded context: витрина объединения перестала бы жить рядом с
  `AddressableGroup`, её правами и её членством.
- **(б) `GroupPortfolioProject` + `GroupPortfolioPhoto` в `apps.social`,
  переиспользуя байтовый пайплайн.** Принят.

Дублируется ровно то, что и так продублировано между аватаром и логотипом —
несколько полей и порядок фото; НЕ дублируется дорогое: санитария изображений
(`common/images.py`: EXIF в пиксели и прочь, первый кадр, порог
decompression-bomb, WebP) и хранилище (`common/object_store.py`). Это ровно тот
приём, которым логотип объединения переиспользовал пайплайн аватара
(ADR-117 §8), и он уже проверен на проде.

Поля `source` / `is_verified` / `verified_facts` / `counterparty_consent` /
`is_published` в модели объединения НЕТ намеренно:

- сделочных фактов у объединения быть не может — договор подписывает и отвечает
  по нему лидер лично, поэтому `FROM_CONTRACT`-проекту здесь неоткуда взяться, а
  вместе с ним не нужны ни `is_verified`, ни согласие контрагента;
- публикация не нужна: витрина объединения публична целиком, её видимость
  задаёт `AddressableGroup.is_public` (в отличие от человека, который сам решает
  по каждой работе).

### 2. Сфера — код КАТАЛОГА, не enum личного портфолио

`sphere_code` — код активной сферы каталога по значению, проверяется тем же
`settings.GROUP_SPHERE_EXISTS_SELECTOR`, что `AddressableGroup.sphere_code`
(ADR-117 §2); пустое значение при создании = сфера самого объединения (обычный
случай: гильдия показывает работы по своему профилю). Плоский enum
`PortfolioProject.Sphere` (renovation/delivery/…) сюда не тянем: у объединений
сферы каталожные с первого дня, вторая система кодов рядом — рассинхрон.

### 3. Хранилище и пайплайн фото

WebP 1280 (просмотр) и 320 (сетка) БЕЗ кропа — `common.images.process_fit_webp`,
те же размеры, что личное портфолио. Ключ `group-portfolio/<group_id>/<uuid7>`,
варианты `<key>/1280.webp` и `<key>/320.webp`. Бакет и fake-синглтон — общие с
логотипами (`social/storage.py`, `build_group_media_store()`): разводятся
ПРЕФИКСОМ ключа, отдельного тумблера намеренно нет — одна забытая переменная
окружения меньше (мотивация та же, что у `GROUP_LOGO_STORE`, инцидент
2026-08-24 «фото профиля не сохраняется»).

Лимит файла — `GROUP_PORTFOLIO_MAX_UPLOAD_BYTES`, пусто = падаем обратно на
`PROFILE_PORTFOLIO_MAX_UPLOAD_BYTES` (10 МБ). До
`GROUP_PORTFOLIO_MAX_PHOTOS = 5` фото на проект, основное — `order == 0`;
`GroupPortfolioProject.photo_key` — зеркало ключа `photos[0]`, пишет только
сервис (`_sync_group_cover`), порядок пересчитывается без дыр после
удаления/смены основного (приём `_sync_cover`, ADR-120 §1).

### 4. API

Всё скоупится объединением ПРЯМО В URL — чужой `project_id`/`photo_id` даёт
404, а не 403: id не должен работать как оракул принадлежности (приём
`get_contact_or_404`).

| Метод и путь | Права | Ответ |
| --- | --- | --- |
| `GET /v1/groups/{id}/portfolio/projects` | как карточка объединения | `200` список проектов |
| `POST /v1/groups/{id}/portfolio/projects` | leader/admin | `201` проект |
| `GET /v1/groups/{id}/portfolio/projects/{pid}` | как карточка | `200` проект |
| `PATCH /v1/groups/{id}/portfolio/projects/{pid}` | leader/admin | `200` проект |
| `DELETE /v1/groups/{id}/portfolio/projects/{pid}` | leader/admin | `204` |
| `POST .../projects/{pid}/photos` (multipart `file`) | leader/admin | `201` проект |
| `GET .../photos/{photo_id}?size=1280\|320` | как карточка | `200 image/webp` |
| `DELETE .../photos/{photo_id}` | leader/admin | `200` проект |
| `POST .../photos/{photo_id}/primary` | leader/admin | `200` проект |

«Как карточка объединения» = `get_visible_group_or_404`: публичное объединение
видно всем, включая анонима; закрытое анониму — 404 (не 403), авторизованному
видно (приглашённому нужно рассмотреть объединение до вступления). Пишущие
ручки берут объединение БЕЗ фильтра публичности — админ закрытого объединения
обязан управлять витриной; право проверяет сервис (`_assert_can_manage` — тот же
рубеж leader/admin, что у логотипа и настроек).

Коды ошибок совпадают с личным портфолио, чтобы фронт мапил их одним
обработчиком: `permission_denied` (403), `portfolio_dates_invalid` (422),
`invalid_sphere` (422), `portfolio_photos_limit` (409),
`portfolio_photo_too_large` (413), `invalid_portfolio_image` (422).

Форма ответа проекта намеренно совпадает с `PortfolioProjectSerializer` в той
части, которую рисует общий фронт-компонент витрины (`title`, `description`,
даты, `location_label`, `photo_url`, `photos[]` c `{id, url, order, is_primary}`);
отличия — `group` вместо профиля, `sphere_code` вместо `sphere` и отсутствие
сделочных полей.

### 5. Удаление проекта — физическое

`DELETE` проекта удаляет строку и байты всех его фото. Инвариант «мягкого
удаления юрзначимых сущностей нет» здесь не задет с другой стороны: витрина
объединения юрзначимой не является (объединение — не сторона договора), поэтому
удаление честное и без восстановления. Отметим расхождение с личным портфолио:
там `DELETE` проекта нет вовсе (ADR-115/ADR-120 его не заводили) — для человека
это отдельное решение, здесь не принимается.

### 6. Фронт (парный PR `feat/web-group-portfolio`)

Блок портфолио монтируется ВНУТРИ `GroupCard` одним компонентом — значит
появляется сразу на обеих витринах (`/groups/{id}` и гостевая `/@handle`) и
диффом в один импорт плюс одну строку JSX: карточка объединения параллельно
переделывается в `feat/web-actor-context`, мерж должен остаться аддитивным.
Компонент сам решает «читать или управлять» по `group.my_membership`
(leader/admin). Форма создания/редактирования — извлечённая из `PortfolioPage`
`ProjectFormModal`, просмотр — существующий `ProjectViewModal`.

## Последствия

- Новые таблицы `group_portfolio_project` / `group_portfolio_photo`; миграция
  `social/0007_group_portfolio` — только создание, данных не трогает, деплой
  бэка от фронта не зависит (старый фронт новых ручек просто не зовёт).
- Две витрины проектов в кодовой базе (личная и объединения) с общим байтовым
  пайплайном. Если появится третья, стоит вернуться к варианту (а) — но уже как
  к выносу общей модели витрины в нижний слой, а не как к правке `apps.profiles`.
- Объекты удалённых фото удаляются физически; восстановления нет (как аватары и
  логотипы).

# ADR-107. Сессия веб-клиента переживает перезагрузку: refresh в localStorage

Дата: 2026-08-21. Статус: принято.

## Контекст

Отсмотр прода 2026-08-21: «регулярно выбрасывает на авторизацию — смотрела
профиль, опять выбросил». Бэк выдаёт access 15 мин + refresh 30 дней с
ротацией и блэклистом (ADR-061). Клиент уже умеет тихо обновлять пару по 401
(отсмотр 2026-08-19), но `authStore` держал ОБА токена только в памяти
(«на Ф1, в Ф4/Ф6 уедет в хранилище»). Любой F5, ссылка в новой вкладке,
возврат из OAuth-редиректа, перезапуск PWA — и пользователь на /welcome при
живом 30-дневном refresh.

## Решение

1. `authStore` — `zustand/persist` в `localStorage` (`porukam.auth`):
   пара токенов + `loginMethod` (базовый persist влит параллельно PR #160,
   `feat/web-session-persist`; этот ADR фиксирует его и добавляет п. 2).
2. Вкладки делят один refresh, а бэк ротирует его с блэклистом — поэтому:
   - событие `storage` по ключу `porukam.auth` → `rehydrate()` стора
     (соседняя вкладка подхватывает новую пару и logout);
   - `ApiClient.doRefresh`: если refresh отвергнут (4xx), но токен в
     хранилище уже **другой** (другая вкладка успела ротировать) — один
     повтор с новым; только при том же токене — `onAuthExpired` → logout.
3. Logout стирает refresh из хранилища (partialize пишет `null`).

## Отвергнуто

- httpOnly-cookie для refresh — правильнее против XSS, но требует
  CSRF-контура, CORS с credentials и изменения `/auth/token/refresh` на
  бэке; не для горячего фикса. Остаётся целевым вариантом (Ф6).
- Отключить `BLACKLIST_AFTER_ROTATION` на бэке — ослабляет ADR-061 ради
  клиентской гонки, которую клиент может решить сам.

## Последствия

- Риск XSS-кражи refresh из localStorage принят на период до httpOnly-cookie;
  смягчение — ротация + блэклист (украденный токен живёт до первого
  легитимного refresh) и CSP.
- Тесты: `web/tests/authPersistence.test.ts` — persist/rehydrate/storage-событие,
  ротация из другой вкладки, честный отказ.

# ADR-176: Нативный канал пушей в обёртке — RuStore Universal Push (RuStore + FCM + HMS) поверх Web Push

**Статус:** Proposed (принято к исполнению ПОСЛЕ закрытого теста Play и подачи на production, ориентир — после 22.09.2026)
**Дата:** 2026-09-10
**Решение принято:** владелец продукта («на русторе зарегалась, у них пуш-сервис бесплатный… пиши АДР»)
**Связанные:** репо-ADR-110 (Web Push — первый реальный канал), репо-ADR-150 (обёртка TWA в сторах),
репо-ADR-170 (карта якорей «шаблон уведомления → раздел»), репо-ADR-175 (push-разрешение по устройству),
репо-ADR-057 (юрканал — размещение в ЛК), `docs/ops/stores-other.md` §3 (RuStore)
**Область:** уведомления, мобильная обёртка, бэкенд-доставка

---

## Контекст

Единственный канал доставки на телефон сегодня — Web Push (ADR-110): подписку создаёт браузер,
доставка на Android идёт через инфраструктуру Google, показывает уведомление service worker сайта.
Закрытый тест Play (08–10.09) показал границы этого канала:

- на Samsung обёртка открывалась в Samsung Internet; подписка создавалась, доставка до телефона
  не подтверждена, а Chrome держал разрешение сайта «под управлением приложения» и тут же блокировал
  его — пришлось выпускать обёртку v3 (принудительный Chrome) и v4 (делегация уведомлений выключена).
  Итог: пуши намертво привязаны к тому, что на телефоне есть работающий Chrome;
- телефоны без сервисов Google (Huawei, часть китайских прошивок) не получают Web Push ни в одном
  браузере — доставки просто нет;
- следующий магазин — RuStore (приоритет №1 после Play, `stores-other.md`); его пользователи в РФ,
  где Google-инфраструктура нестабильна (замедления Cloudflare/Google у операторов — см. ADR-174 (внутренний ADR, не публикуется)), а
  RuStore с 01.09.2025 предустановлен по закону и даёт бесплатный push-сервис.

Владелец зарегистрировался в RuStore 10.09 и спросил: можно ли их пуш-сервис «сделать и везде
использовать, чтобы уведомления не были привязаны к Хрому».

Ограничение, от которого всё зависит: **RuStore Push доставляет в нативное приложение**, не в
браузер и не в service worker. Значит обёртка должна перестать быть чистой TWA-оболочкой и получить
нативный код. И RuStore Push сам по себе работает только там, где установлено приложение RuStore, —
«везде» одним RuStore не получится.

## Рассмотренные варианты

1. **Оставить Web Push, добавить письмо по умолчанию там, где Web Push не поддерживается.**
   Дёшево (устройство уже сообщает `unsupported`, ADR-175), но не решает Samsung/Huawei-кейсы для
   тех, кто письма не читает, и не снимает зависимость от Chrome.
2. **Только RuStore Push в обёртке.** Покрывает РФ, но вне РФ приложения RuStore нет; для Play-версии
   пришлось бы держать второй канал.
3. **RuStore Universal Push SDK** — один клиентский SDK, который сам выбирает доступный провайдер:
   RuStore Push (телефон с RuStore), Firebase Cloud Messaging (телефон с сервисами Google),
   Huawei Push Kit (Huawei). Уведомление показывает приложение, а не браузер. Web Push остаётся для
   десктопа, iOS (после «На экран Домой») и браузеров без обёртки.
4. **Полностью нативное приложение** (Kotlin/Compose) — снимает все ограничения TWA, но это
   отдельный продукт на месяцы; не сейчас.

## Решение

Вариант 3. Обёртка становится гибридной: TWA для контента + нативный слой для пушей.

### Клиент (обёртка, `~/porukam-twa-alt`, applicationId `porukam.app`; для RuStore — отдельный
applicationId по `stores-other.md` §2.4)

- Подключается RuStore Universal Push SDK с тремя провайдерами (RuStore, FCM, HMS). Порядок выбора —
  по наличию на устройстве; актуальные артефакты и версии SDK сверить при старте работ (документация
  RuStore меняется, здесь не фиксируем).
- Нативный слой получает токен провайдера и **передаёт его в веб через стартовый URL**:
  `/?src=twa&push_provider=<rustore|fcm|hms>&push_token=<token>`. Другого моста у TWA нет
  (страница живёт в браузере, JS-bridge отсутствует). Веб после входа регистрирует токен на бэке;
  до входа — держит в `sessionStorage`. Смена токена (SDK сообщает `onNewToken`) → приложение при
  следующем запуске подставляет новый; старый бэк удалит по ответу провайдера «токен невалиден».
- **Показ уведомления** — нативно, силами SDK/приложения: заголовок и текст из полезной нагрузки, по
  тапу — открытие обёртки на `url` из нагрузки (карта якорей ADR-170 та же, что у ленты, Web Push и
  письма). Иконка и канал уведомлений Android — приложения Porukam, не браузера.
- В режиме обёртки с зарегистрированным нативным токеном веб **не предлагает Web Push** и снимает
  существующую Web Push-подписку этого браузера (иначе один телефон получит два уведомления).
  Признак режима — параметр `push_provider` в стартовом URL; `PushDeviceStatusRow` (ADR-175)
  показывает «уведомления через приложение».

### Бэкенд (`apps.notifications`)

- Новая модель `DeviceToken` рядом с `PushSubscription`: `user`, `provider` (`rustore|fcm|hms`),
  `token` (unique), `app_id` (applicationId сборки), `platform`, `user_agent`, `created_at`,
  `last_seen_at`. Не переиспользуем `accounts.UserDevice.push_token` (модель фейк-эры, ADR-110 п.1) —
  и чтобы не тянуть зависимость notifications → accounts сверх фасада.
- API: `POST /v1/device-tokens` (идемпотентно по `token`; смена аккаунта переписывает владельца —
  токен принадлежит устройству, как endpoint у Web Push), `POST /v1/device-tokens/unregister`
  (204 и для чужого токена). Оба — за `IsAuthenticated`, `Idempotency-Key` не нужен (идемпотентны
  по построению).
- `NativePushProvider` реализует тот же `PushProvider`-протокол (`send(recipient, message)`), что и
  `WebPushProvider`: **сначала нативные токены получателя, затем Web Push-подписки**, но не на одно и
  то же устройство (см. клиентское правило выше). Отправка — по HTTP-API провайдеров: RuStore Push
  API, FCM HTTP v1, Huawei Push Kit; у каждого свой `provider_code` для `common.circuit`
  (`push_rustore`, `push_fcm`, `push_hms`) — отказ одного не гасит остальные.
- **Полезная нагрузка та же, что у Web Push (ADR-110 п.4):** `{title, body, url}` без сумм, имён и
  номеров договоров (`PUSH_PRIVATE_KEYS`). Через серверы RuStore/Google/Huawei проходит только это.
- Мёртвые токены чистятся по месту, как подписки: ответы «unregistered/invalid token» провайдера →
  строка удаляется; `DeliveryAttempt.status` — `sent_<provider>`, `gone_<provider>`,
  `error_<provider>`, чтобы `push-diag.sh` и метрики читались без новых полей.
- Настройки — через env с явным пробросом в compose (правило ADR-069/деплой-хардeнинга: новая
  переменная без строки в `core` и `celery_worker` молча падает в фейк): `RUSTORE_PUSH_PROJECT_ID`,
  `RUSTORE_PUSH_SERVICE_TOKEN`, `FCM_SERVICE_ACCOUNT_JSON_PATH`, `HMS_APP_ID`, `HMS_APP_SECRET`,
  `NOTIFICATIONS_NATIVE_PUSH_PROVIDERS=rustore,fcm,hms` (пустое = канал выключен, дев/тесты без
  ключей).

### Юридическое

Юрканал не меняется: размещение в ЛК (`placed_in_cabinet_at`, ADR-057) остаётся единственным
значимым событием доставки, нативный пуш — напоминание поверх, как Web Push и письмо. ПД через
push-сервисы не проходят (нагрузка без имён и сумм). Токен устройства — идентификатор устройства
пользователя: удаляется при удалении аккаунта тем же `purge_personal_data` (ADR-169), что и
`PushSubscription`.

## Последствия

- Уведомления перестают зависеть от браузера: приходят от приложения Porukam на любом Android с
  RuStore, сервисами Google или HMS. Web Push остаётся для десктопа, iOS и браузеров без обёртки.
- Обёртка — гибрид: собирается по-прежнему gradle напрямую (`docs/ops/play-console.md` 10.09), но с
  нативным кодом и зависимостями SDK; `bubblewrap update` теперь перегенерирует ещё больше — правило
  «после update накладывать правки заново» становится обязательным чек-листом сборки.
- Одна и та же кодовая база обёртки годится для Play и RuStore (политика Play push-SDK других сторов
  не запрещает); различаются applicationId и ключ подписи (`stores-other.md` §2.2, §2.4). Для
  RuStore-сборки в `assetlinks.json` — второй statement-блок с её отпечатком.
- Три внешних интеграции на бэке вместо одной: три набора секретов, три circuit breaker'а, три
  формата ошибок. Тесты: фан-аут по провайдерам, дедуп «нативный токен есть → Web Push не шлём»,
  чистка невалидных токенов, приватность нагрузки — по образцу тестов `WebPushProvider`.
- Оценка: несколько рабочих дней (обёртка 1–2, бэкенд 1–2, регистрация проектов у трёх провайдеров и
  ключи — владелец). Делать после подачи на production: правка обёртки посреди 14-дневного теста
  рискует обнулить счётчик тестировщиков (`play-closed-test-clock`).

## Не делаем

- Не строим свой push-сервер и не держим постоянное соединение из приложения (батарея, Doze).
- Не переносим Web Push на «универсальный» канал для десктопа/iOS — там нативного приложения нет.
- Не отправляем в пуш ничего сверх `{title, body, url}` даже через RuStore: правило ADR-110 п.4
  общее для всех провайдеров.

# ADR-117: Объединения v2 — типы из книги, сфера, география, публичная карточка

Дата: 2026-08-24. Статус: принят.

## Контекст

Отсмотр 2026-08-24 (docs/backlog.md, «Объединения v2»): «надо в объединения добавить
Гильдия, Клан, Сообщество, Витрина компании… обязательно поле выбора сферы деятельности…
логотип… ссылки на соцсети… публичная карточка почти как личная, с перечнем участников…
у человека в профиле — в каких объединениях состоит… география — весь мир или страна и
город… хендл у объединения может быть только 1: создаётся при регистрации, потом меняется
в настройках».

Источник концепции типов — книга (trust_economy/Block IV, глава 14): гильдия — постоянное
профессиональное сообщество с коллективной гарантией качества; клан — проектная команда
3–20 с прямой коллективной ответственностью; сообщество — открытая группа без коллективной
ответственности; витрина компании — публичное лицо компании.

Что есть сейчас (разведка 2026-08-24): `AddressableGroup` (kind: company_storefront |
community | informal), membership/join/leave/заявки/приглашения (отсмотр 2026-08-23),
ровно один активный хендл (claim_handle деактивирует старый), но хендл ставится ОТДЕЛЬНОЙ
кнопкой после создания; публичного (анонимного) просмотра объединений нет вообще;
`GET /handles/{handle}` для группового хендла не отдаёт ни id, ни имени группы — гость по
@хендлу объединения никуда не попадает; у строк участников нет ссылки на их карточки;
блока «состоит в объединениях» нет ни на бэке, ни на фронте.

## Решения

### 1. Типы (`kind`) v2

`guild` Гильдия / `clan` Клан (ДЕФОЛТ) / `community` Сообщество / `company_showcase`
Витрина компании. Миграция данных: `company_storefront → company_showcase`,
`informal → clan`, `community` без изменений. API создания принимает старые коды как
алиасы (маппинг в сериализаторе) — деплой бэка не ломает фронт v1 до его обновления.
Коллективная репутация (агрегат рейтинга из участников, глава 14) — ОТДЕЛЬНАЯ будущая
задача, не здесь; `reputation_mode` остаётся как есть.

### 2. Сфера деятельности — обязательна

`AddressableGroup.sphere_code` — код сферы КАТАЛОГА (`apps.catalog.Sphere.code`),
по значению, НЕ FK: import-linter «social зависит только от accounts» не трогаем — тот же
приём, что `Consent.locale` и `ClauseTemplate.country_code`. Существование кода проверяет
сервис через settings-указатель `GROUP_SPHERE_EXISTS_SELECTOR =
"apps.catalog.selectors.is_active_sphere_code"` + `import_string` (приём
`HANDLE_PUBLIC_PROFILE_SELECTOR`). Обязательна при создании (422 `invalid_sphere` на
неизвестный код); для существующих строк — `""` (легаси, фронт покажет «не указана»,
лидер заполнит в настройках). НЕ enum `PortfolioProject.Sphere` (плоский, 7 значений) —
каталог полнее и локализован; переиспользуем `GET /v1/spheres` на фронте.

### 3. География

`geo_scope` (`world` ДЕФОЛТ | `country` | `city`) + `country_code` (CharField 8, как
`User.country_code`) + `city_name` (CharField 120, как `Profile.city_name`). Инвариант:
`country` требует `country_code`, `city` — оба (422 `invalid_geo`). Деление то же, что
зоны поиска ADR-114; учёт географии объединений в зонах /search — вместе с задачей
«поиск по сферам» (ADR-114 v2), не здесь. География ЛИЧНОГО профиля (выбор «весь мир»)
— фаза 3 (см. ниже), поля city/country у человека уже есть.

### 4. Ссылки (соцсети, портфолио-сайты)

`links` — JSONField, список `{"url": str, "label": str}` (url — http(s), label ≤ 50,
максимум 10). Валидация в сериализаторе. Плоский JSON, не отдельная модель: ссылки —
атрибут витрины, без собственного жизненного цикла (тот же приём, что
`PortfolioProject.media`).

### 5. Хендл — при создании, смена — в настройках

`create_group(handle=…)` — обязательный параметр, клеймится в той же транзакции
(та же `claim_handle`: общая уникальность с пользовательскими, 409 `handle_taken`).
`POST /groups/{id}/handle` остаётся ТОЛЬКО как «смена в настройках» (лидер/админ).
Бэк и раньше держал ровно один активный хендл — «даёт много создавать» лечится UX-ом:
хендл перестаёт быть отдельной необязательной кнопкой. Фронт-форма создания обновляется
в парном web-PR; мержить бэк первым, деплоить после обоих.

### 6. Публичная карточка объединения

- `GET /groups`, `GET /groups/{id}`, `GET /groups/{id}/members` — `AllowAny` через
  `get_permissions()` (приём `ProfileAvatarView`, ADR-103). Аноним видит только
  `is_public=True` (чужое приватное — 404, не 403, как контакты); авторизованный — как
  раньше (приглашённому нужно видеть закрытое объединение).
- `GroupSerializer` +: `sphere_code`, `geo_scope`, `country_code`, `city_name`, `links`,
  `leader_name` (get_full_name — как в контактах). `members_count`/`created_at` уже есть.
- `MembershipRowSerializer` +: `member_handle` (@…), `member_profile_id`
  (через `HANDLE_PUBLIC_PROFILE_SELECTOR`) — участники кликабельны в карточки репутации.
- `GET /handles/{handle}` для группового хендла +: `group_id`, `group_name` — маршрут
  `/@хендл` объединения ведёт на его карточку.

### 7. «Состоит в объединениях» на личной карточке

Блок `groups` в `GET /reputation/profiles/{id}/card`: активные членства владельца в
ПУБЛИЧНЫХ объединениях — `[{id, name, handle, kind}]` (selector
`apps.social.selectors.list_user_public_groups`; reputation→social — прямой импорт,
контрактом не запрещён, вьюха уже так композирует profiles/accounts/social). Показывается
и при `restricted=True`: членство в публичном объединении публично по построению (как
handle). Закрытые объединения на публичную карточку НЕ попадают.

### 8. Логотип — фаза 2

Переиспользовать байтовый пайплайн ADR-103/115 (WebP, варианты, S3/fake). Он весь живёт
в `apps.profiles` (`images.py`, `storage.py`), social импортировать его не может —
вынести generic-части в `common/` (`common/images.py`, `common/object_store.py`),
`apps.profiles` переключить на них тем же PR. Это отдельный PR (рефактор двух приложений
+ новые эндпоинты `POST/GET/DELETE /groups/{id}/logo`), чтобы не смешивать с моделью v2.

## Фазы

1. **Этот PR (`feat/social-groups-v2`)**: модель v2 + миграции, сервисы/селекторы,
   API §§1–7, сид-указатель настроек, тесты.
2. **Логотип** (`feat/social-group-logo` + рефактор common): §8.
3. **Web** (`feat/web-groups-v2`): форма создания (тип с подсказками из книги — l10n 29
   локалей, сфера через `useSpheres`, хендл, география, ссылки), публичная карточка
   объединения ≈ личная, блок «состоит в объединениях» на карточке репутации,
   ActorSwitcher для лидера (отдельное решение), бейдж «сфера не указана» для легаси.

## Последствия

- Старые коды `kind` исчезают из БД (данные мигрируются), API временно принимает алиасы.
- Создание объединения без хендла становится невозможным (фронт v1 сломается на создании
  групп между деплоями бэка и фронта — деплоим после merge обоих PR, флоу build-N).
- Анонимный трафик на публичные карточки объединений — новый (SEO/шаринг), нагрузка
  незначительна.

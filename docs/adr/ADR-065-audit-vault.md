# ADR-065. Audit Vault: отдельный процесс/БД, хеш-цепочка, подписка на все события

**Статус:** принято
**Дата:** 2026-07-31
**Контекст этапа:** ЭФ.3 (`docs/tasks/fundament.md`) — сквозной фундамент, юр-независимая
работа на паузу этапов 4–5.

## Контекст

tech-spec.md §10.3 (ADR-038) требует отдельный сервис + отдельную БД (append-only,
хеш-цепочка, checkpoint у TSA в WORM-хранилище), с односторонним API
(`append`/`verify_chain`/`read`) и подпиской на **все** доменные события (принцип §37a:
«одна запись события порождает (а) ленту объекта, (б) уведомления, (в) запись в Audit
Vault» — три потребителя, один источник). ЭФ.1 уже дал транзакционный outbox +
relay (`common/relay.py`, ADR-064) с реестром подписок `topic -> [handler, ...]`, но
только для точечных тем — универсальной подписки «на всё» механизм не поддерживал.

## Решение

- **Роутер БД, а не отдельный Django-проект.** `services/audit_vault` — Django-приложение
  (`label="audit_vault"`) в том же кодбейзе (dev-setup.md: «периферийные сервисы — отдельные
  процессы поверх общего кодбейза, не отдельные проекты»), но со своим алиасом БД
  `settings.DATABASES["audit"]` (`AUDIT_DATABASE_URL`, порт 5433/`postgres_audit`).
  `common/db_routers.py::AuditVaultRouter` маршрутизирует ЛЮБУЮ модель с
  `app_label == "audit_vault"` исключительно на алиас `"audit"` и запрещает миграцию
  остальных приложений туда (`allow_migrate`) — компрометация основного приложения не даёт
  прямого SQL-доступа к логу (ADR-038), а обычный код физически не может по ошибке записать
  доменные данные в БД Vault или наоборот.
- **Односторонний API — `services/audit_vault/api.py`, три функции.** `append()`,
  `verify_chain()`, `read()` — единственная точка входа; `AuditEntry`/`AuditCheckpoint`
  (models.py) никуда за пределы `services.audit_vault` не импортируются напрямую. Остальная
  система обращается через фасад `apps/audit/client.py` (tech-spec.md §5.2.10: «apps.audit —
  клиент Audit Vault») — это единственный разрешённый импорт из `apps.*` в сторону Vault;
  сам `services.audit_vault` вне графа контрактов import-linter (`root_package = "apps"`),
  поэтому дисциплина «только через apps.audit» держится соглашением/код-ревью, а не
  автоматическим контрактом (можно добавить `forbidden`-контракт `apps.* (кроме audit) ->
  services`, когда появится второй периферийный сервис с той же дисциплемой).
- **Хеш-цепочка: `this_hash = sha256(prev_hash || canonical(entry))`, canonical — детерминированный
  JSON** (`canonical.py`): отсортированные ключи, без пробелов, ASCII, `at` в ISO-8601. В канон
  входят `seq/actor/actor_role/action/target_type/target_id/payload/at/prev_hash` — ровно
  содержимое `audit_entry` из tech-spec.md §5.2.10/§10.3. `source_event_id` (см. ниже) в канон
  НЕ входит — служебное поле реле, не часть юридически значимого содержания записи (тот же
  принцип, что ADR-064 применил к `published_at`/`delivery_attempts` в `OutboxEvent`).
  `verify_chain()` каждый раз пересчитывает ожидаемый `this_hash` заново из `canonical(entry)`
  текущей строки — не доверяет хранимому `prev_hash`, поэтому «испортить любое поле строки
  прямо в БД» детектируется одинаково надёжно (не только подмена самого хеша).
- **`seq` назначается вручную под транзакционным advisory lock, не BigAutoField-последовательностью
  напрямую.** Хеш зависит от `seq`, а `seq` в PostgreSQL известен только ПОСЛЕ вставки
  bigserial-строки — расчёт хеша до вставки требует знать следующий `seq` заранее.
  `append()` берёт `pg_advisory_xact_lock` (снимается автоматически на COMMIT/ROLLBACK),
  читает `seq`/`this_hash` последней строки, вычисляет следующий `seq` и хеш, вставляет с
  явным `seq=`. Так безопасно и на пустой таблице (`select_for_update` на «последнюю строку»
  не спасает от гонки, если строк ещё нет вообще — advisory lock не привязан к наличию строк).
  Последствие: внутренняя PostgreSQL-последовательность `audit_entry_seq_seq` после этого не
  используется и может «отстать» — не проблема, т.к. `append()` — единственный писатель.
- **Подписка на ВСЕ события — новый ключ `"*"` в `settings.OUTBOX_SUBSCRIBERS`, а не отдельный
  механизм.** `common/relay.py::_subscribers_for()` теперь возвращает
  `registry.get("*", []) + registry.get(topic, [])` — минимальное дополнение к контракту
  ADR-064, без нового поля/настройки/таблицы. `settings.OUTBOX_SUBSCRIBERS = {"*":
  ["apps.audit.subscriber.handle_event"]}` — Vault получает буквально любой топик, включая
  ещё не существующие (реестр топиков tech-spec.md §6.4 открытый). Существующие тесты ЭФ.1
  (`override_settings(OUTBOX_SUBSCRIBERS={...})`) не задевает — `override_settings` подменяет
  словарь целиком, без ключа `"*"`, если явно не добавить.
- **Идемпотентность — `source_event_id` (UUID, частичный unique-индекс) на `AuditEntry`, не
  часть `audit_entry` из спеки.** Тот же принцип ADR-064 («идемпотентность подписчиков —
  event_id — ключ дедупликации»): если реле повторно доставит событие (сбой СОСЕДНЕГО
  подписчика той же темы держит событие неопубликованным целиком — гранулярность ADR-064 на
  уровне события, не пары событие/подписчик), `append()` с тем же `source_event_id` возвращает
  уже существующую запись, не трогая цепочку. `apps/audit/subscriber.py::handle_event()`
  передаёt `event.event_id` как `source_event_id`.
- **`actor_role` для событий из outbox — производное значение, не прямое поле конверта.**
  Конверт события (tech-spec.md §6.4) несёт `actor.user_id/profile_id/on_behalf_of_entity`, а
  не готовую роль в смысле `audit_entry.actor_role` (§10.3 — support/compliance/finance/admin,
  роли служебных действий, которых пока нет в кодовой базе). `apps/audit/subscriber.py::_actor_role()`:
  пустой `actor` → `"system"` (фоновые события типа `entity.epoch_changed`), `actor.staff_role`
  (когда появится) → это значение, иначе → `"user"`. Пересмотреть, когда появятся реальные
  служебные действия (apps.backoffice, вне ЭФ.3).
- **`read()` — заглушка авторизации по списку ролей**, не полноценный RBAC: `actor_role not in
  settings.AUDIT_VAULT_READ_ROLES` (`["support","compliance","finance","admin"]`) →
  `VaultReadPermissionError`. `apps.backoffice` — каркас-заглушка (этап позже), полноценная привязка
  к пользователь backoffice — отдельная задача.
- **Checkpoint: `this_hash` последней записи — уже достаточный digest диапазона** (цепочка
  включает всё предыдущее содержание по построению), пересчитывать хеш по всему диапазону
  заново не нужно. `services/audit_vault/checkpoint.py::compute_daily_checkpoint()` идемпотентна:
  `seq_from = last_checkpoint.seq_to + 1` (или 1), no-op если `seq_from > seq_to` (нет новых
  записей с прошлого запуска) — повторный запуск Celery beat в тот же день ничего не
  дублирует (плюс `unique_audit_checkpoint_seq_to` как страховка на БД-уровне).
- **TSA — фейк (`FakeTimestampAuthority`, `providers.py`), хранилище checkpoint — настоящий
  S3/MinIO с Object Lock (`S3CheckpointObjectStore`, `storage.py`), НЕ фейк.** Из
  «Чего НЕ делать в ЭФ» (fundament.md) под фейк попадает только TSA; WORM-выгрузка в
  MinIO — часть самого требования ЭФ.3, не внешняя интеграция «на будущее». Оба провайдера —
  протоколы по образцу `apps.entities/apps.identity.providers` (ядро не знает про boto3/RFC
  3161 конкретно). `boto3` — новая зависимость (`pyproject.toml`), импортируется ЛЕНИВО внутри
  `S3CheckpointObjectStore._client()` — модели/`api.py`/`verify_chain` не требуют её наличия
  (в частности, юнит-тесты checkpoint используют `FakeCheckpointObjectStore`, не трогая boto3
  вовсе). Бакет должен быть создан С Object Lock (`mc mb --with-lock`) ДО первой выгрузки —
  включить Object Lock на существующем бакете нельзя; это dev/infra-операция, не код.
- **Срок хранения checkpoint-объекта — настройка (`AUDIT_VAULT_CHECKPOINT_RETENTION_DAYS`,
  дефолт 3650), не константа в коде** — тот же принцип, что CLAUDE.md формулирует для
  доменных дедлайнов (длительности — из конфигурации, не хардкод); фактический срок — вопрос
  организационной/юридической политики, уточняется отдельно.

## Альтернативы

- **`select_for_update()` на последнюю строку вместо `pg_advisory_xact_lock`.** Не работает на
  пустой таблице (нечего блокировать) — race при самой первой вставке (два конкурентных
  `append()` оба увидели бы «нет строк», оба взяли бы `GENESIS_HASH` как `prev_hash`).
  Advisory lock не зависит от наличия строк — сериализует append() всегда.
- **Отдельная таблица `outbox_delivery` (событие × подписчик) вместо ключа `"*"` в реестре.**
  Точнее (не потребовала бы «доставлять всем заново, включая уже отработавших»), но это уже
  была рассмотренная и отклонённая в ADR-064 альтернатива по той же причине (не требуется
  спекой сейчас); ключ `"*"` — минимальное дополнение к уже принятой модели, не пересмотр.
- **Хранить diff/полный снимок диапазона в checkpoint вместо одного `this_hash`.** Избыточно:
  цепочка уже криптографически включает всё предыдущее; TSA-штамп одного хеша — ровно то
  доказательство «содержание на момент X не менялось», которое требуется §10.3.

## Последствия

- Новая зависимость окружения — вторая PostgreSQL-БД (`AUDIT_DATABASE_URL`) обязательна для
  запуска (как и основная — без дефолта, CLAUDE.md: «настройки через переменные окружения»);
  `make migrate` теперь мигрирует обе БД (`Makefile`).
- `services/__init__.py` добавлен (был отсутствующим namespace-package) — без него mypy путал
  `audit_vault.api` и `services.audit_vault.api` как два разных модуля одного файла.
- `OUTBOX_SUBSCRIBERS["*"]` в проде означает: КАЖДОЕ будущее доменное событие автоматически
  попадёт в Vault без отдельной регистрации по топику — то, ради чего принцип §37a
  формулировался. Уведомления (ЭФ.4) получат отдельный конкретный реестр `topic -> template`
  (не через `"*"`) — это другая ось (какие события порождают уведомления, а не «все»).
- `apps.audit` теперь в `INSTALLED_APPS`; `apps.backoffice` — по-прежнему заглушка, `read()`
  полноценно заработает только когда появится реальная аутентификация/роль backoffice пользователя.

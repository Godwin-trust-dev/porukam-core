# ADR-192. Экран «Поиск»: книга контактов снята, цвета и раскладка выровнены

**Статус:** принято (замечания владельца 18.09, скриншот
`docs/tasks/screenshots_bugs/search.jpg`).
**Номер:** 192 — сверено по репозиторию и всем ворктри
(`ls docs/adr ~/porukam-worktrees/*/docs/adr | grep -o 'ADR-[0-9]*' | sort -u | tail`),
максимум занятый на момент написания — 191.

## Контекст

Отсмотр прода 18.09, дословно: «дизайн не красивый. Сделай цвета и разметку аккуратной. и прячь
поиск по контактам из базы порукам. он бессмысленный. Это будет поиска людей по хендлу или еще
как-то. Было бы здорово со временем сделать поиск по телефону через контакты сохраненные в
телефоне. Как у телеграмм или вотсапп.» И следом: «у нас в комментарии указано, что поиск по
сферам из выполненных договоров. Ищите по … или сфере. Дальше текст убери. И еще поиск по сферам
проверь, нужен поиск не только по выполненным договорам, но и по заявленным. А то получается, что
пока человек сделки не совершил его в поиске нет. так не пойдет».

На скриншоте (телефон, 360 CSS-px) экран `/search` выглядел так: одинокий «?» в пустоте над полем
запроса, обрезанный многоточием плейсхолдер, ТРИ тёмные плашки подряд во всю ширину («Из
контактов», «Весь мир», «Добавить сферу»), под ними бежевый селект «Любой опыт» — четыре разных
цвета подряд там, где стоят однородные контролы одного назначения, — и заглушка каталога, у
которой крупным полужирным кеглем висит целое предложение в три строки плюс ещё одна янтарная
кнопка «Из контактов».

## Решение

### 1. Книги контактов на `/search` нет

Вход в справочник сохранённых контактов убран из ОБОИХ мест: кнопки у поля запроса и CTA стартового
состояния каталога (`ContactPickerSheet` и вся его обвязка из `SearchPage.tsx` удалены, вместе с
ключом `dashboard.searchContactsNoHandleHint` во всех 29 локалях и тестом
`web/tests/SearchContactsPicker.test.tsx`). Это отменяет дополнение ADR-189 от 12.09 вечера —
владелец, увидев его на проде, назвал поиск по собственной книге контактов бессмысленным, и это
верно по сути экрана: на `/search` ищут ЧУЖИХ, а в книге контактов лежат те, с кем уже знакомы и до
кого один клик из других мест.

Справочник контактов остаётся там, где он решает задачу — на шаге «Стороны» мастера договора
(`PartiesStepPage`, `web/tests/ContractNewContactPicker.test.tsx`): там нужно выбрать КОНКРЕТНОГО
контрагента, и «те, с кем уже работали» — самый частый ответ.

Отклонено: «спрятать за кнопку/меню» вместо удаления. Механика (шит, фильтр, поиск по платформе
внутри) продолжала бы жить в коде экрана двумя сотнями строк ради действия, которое владелец
считает бессмысленным; вернуть её при необходимости — один `git revert` этой ветки.

### 2. Цвета: фильтры — контролы, а не действия

Тёмная `secondary` (градиент `--pr-grad-dark` + тень) у гео-кнопки и у «Добавить сферу» заменена на
`outline` (белая заливка + рамка `--pr-line`) — ровно тот же вид, что у поля запроса и у селекта
опыта рядом. Правило, которое из этого следует и которое стоит держать дальше: **фильтр — не
действие экрана**. Тёмная плашка на креме читается как главная кнопка; трёх главных кнопок на
экране не бывает.

Для «Добавить сферу» это новый проп `SphereChipsEditor.addVariant` (по умолчанию `secondary`) — в
формах профиля это действительно действие формы, и там вид не меняется; `outline` передаётся только
из панели фильтров поиска.

### 3. Раскладка

- **Одинокий «?»** (`FieldShell` с `help`, но без `label` — единственный такой случай в проекте)
  прижат к ПРАВОЙ кромке поля и подтянут к нему вплотную (`Field.module.css .labelRowHelpOnly`).
  У левого края он читался как отдельная кнопка экрана неизвестного назначения.
- **Строка фильтров на телефоне** больше не `flex-direction: column`: контролы переносятся по два в
  строку (`flex: 1 1 calc(50% - gap)`). Три полосы во всю ширину подряд выглядели как три главных
  действия и съедали вертикаль до того, как начнётся выдача. Длинное гео-имя внутри кнопки
  переносится второй строкой (`.filterButton`), а не распирает её за край экрана.
- **Сферы вынесены из строки фильтров** отдельным блоком под ней (над видами работ, которые и так
  стоят своей строкой): открытый `SpherePicker` — половина экрана, и центрированная по вертикали
  соседняя гео-кнопка оказывалась посреди него.
- **`<select>` перестал выглядеть выключенным.** Правило ADR-123 «только для чтения» (песочная
  подложка + ПУНКТИРНАЯ рамка) было записано как `.control:read-only:not([type='date'])` — без
  имени тега. По спецификации `:read-only` matches ВСЕ элементы, кроме редактируемых input/textarea,
  то есть каждый `<select>` продукта: бежевый «Любой опыт» рядом с белым полем запроса — это он.
  Селектор сужен до `input.control:read-only…` / `textarea.control:read-only`; поправка общая для
  всего интерфейса, не только для поиска.
- **Стартовое состояние каталога** — заголовок + строка подсказки вместо одного длинного
  предложения крупным кеглем: ключ `dashboard.searchCatalogStartTitle` разрезан по двоеточию,
  вторая половина уехала в новый `dashboard.searchCatalogStartText` (механически, во всех 29
  локалях — из уже переведённых строк, не новый перевод). Кнопки у состояния больше нет: она вела в
  снятую книгу контактов.

### 4. Микрокопия: подсказка «?» больше не обещает поиск только по сделкам

`dashboard.searchHint` во всех 29 локалях обрезан после «Ищите по @хендлу, телефону или сфере.» —
хвост «людей по сфере находим по их завершённым сделкам» был НЕПРАВДОЙ с ADR-122. Там же обрезан
хвост-пример у `dashboard.searchPlaceholder` («— например, «маникюр»»): в поле на телефоне он всё
равно не помещался и обрезался многоточием, а смысл несёт первая половина.

### 5. Поиск по заявленным сферам — уже так работает, проверено

Требование «нужен поиск не только по выполненным договорам, но и по заявленным» в бэкенде выполнено
с ADR-122 и покрыто тестами — код НЕ менялся, менялась только микрокопия, которая утверждала
обратное:

- адресный лукап (`dashboards.selectors.get_search`) складывает кандидатов из ДВУХ источников:
  `reputation.contractor_profile_ids_in_spheres` (факты завершённых сделок, `sphere_match: 'deals'`)
  и `profiles.profile_ids_with_declared_spheres` (заявленные сферы профиля, `'declared'`);
  тест `apps/dashboards/tests/test_search.py::test_declared_profile_spheres_found_and_marked`;
- каталог (`get_search_catalog`) фильтрует по `declared_sphere_q(...) | contractor_sphere_deal_q(...)`;
  тесты `test_catalog_search.py::test_declared_sphere_matches` и
  `::test_sphere_matches_via_completed_deal_as_contractor`.

Человек без единой сделки находится по сфере при условиях каталожной видимости (профиль публичный,
`hide_from_catalog=False`, `discoverable_by_handle=True`) — и обязан САМ заявить сферу в профиле
(`Profile.sphere_codes`): пустой профиль не находится ни по какой сфере, потому что сфера в нём не
названа.

## Пределы задачи

Поиск по телефонной книге УСТРОЙСТВА (как в Telegram/WhatsApp — «было бы здорово со временем»)
этой веткой не делается: это не UI-правка, а отдельная задача с согласием на доступ к контактам,
нормализацией номеров, хешированием и сверкой на бэке против `User.discoverable_by_phone`, плюс
разные API у веба (Contact Picker API, только Android/Chrome по явному жесту) и у обёртки TWA.
Записано в `docs/backlog.md`.

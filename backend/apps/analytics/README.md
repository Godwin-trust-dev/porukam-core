# apps.analytics

Витрины и внутренние метрики продукта. Постановка — `docs/tasks/marketing-metrics.md`
(версия 2.0 от 27.08), решение — `docs/adr/ADR-145-analytics-marts-and-internal-metrics.md`.

## Что это и чем не является

Это **читатель**, а не участник. Приложение не импортирует из `apps.*` ничего — ни моделей,
ни `services`, ни `selectors` (контракт import-linter). Витрины считаются SQL-запросами по
`outbox_event` и доменным таблицам: тому же единственному источнику истины, из которого
строятся хроника объекта, уведомления и журнал аудита. Параллельного трекинга бизнес-событий
нет — расхождение аналитики с тем, что видит пользователь в хронике, невозможно по построению.

Персональных данных здесь нет и не появится: только идентификаторы, коды стран, языки и
агрегаты. Именно это делает аналитический контур совместимым с уничтожением ключа субъекта —
удалять в аналитике нечего, потому что там нечего удалять.

## Витрины (§8.3)

| Витрина | Грань | Что в ней |
|---|---|---|
| `mart_contract_lifecycle` | договор | путь от черновика до закрытия с метками переходов, листья, споры, обе страны, признак кросс-страновой сделки |
| `mart_user_cohorts` | пользователь | неделя регистрации, страна, язык, контур, источник, первый и второй подписанный договор, последняя активность |
| `mart_daily_pulse` | день | 12 строк монитора целиком, включая НЕаддитивные величины (уникальные пары, медиана листьев) |
| `mart_daily_pulse_slice` | день × страна × язык × источник | только пользовательские счётчики: воронка по странам из §4.2 |

Почему две грани, а не одна: у договора две стороны и, в кросс-страновой сделке, две разные
страны — «подписанные договоры по странам» без оговорок складывались бы дважды.

**Страна и язык симметричны.** У них одинаковый набор полей, одинаковая динамика по дням и
одинаковое правило «живой» (есть подписанный договор за окно). §4.3 задаёт два вопроса об
одном и том же договоре — «какую страну поднимать до плагина» и «какой язык вычитывать
носителем следующим», — и разрез, который есть только у одной оси, отвечает на половину.
Рядом с `is_cross_country` живёт `is_cross_language`: первый про юрисдикцию, второй про
понимание.

Пересчёт — раз в час (`CELERY_BEAT_SCHEDULE`, `analytics-refresh-marts`), порядок фиксирован:
дневная витрина считается ПОВЕРХ двух базовых. Вручную:

```bash
python manage.py refresh_analytics_marts            # все, по порядку
python manage.py refresh_analytics_marts --mart mart_user_cohorts
```

Каждый прогон пишется в `MartRefreshRun`, возраст последнего успешного отдаётся в
`/internal/v1/metrics/health`: витрина, которая молча перестала пересчитываться, хуже
отсутствующей — по ней принимают решения, считая её свежей.

## Эндпоинты (§9.1)

Наружу не выведены: статический токен из окружения плюс список адресов — тот же принцип,
что у эндпоинта метрик Prometheus.

```
GET /internal/v1/metrics/pulse?days=30
GET /internal/v1/metrics/geography?window=30
GET /internal/v1/metrics/acquisition?window=90
GET /internal/v1/metrics/funnel?window=90
GET /internal/v1/metrics/languages?window=30
GET /internal/v1/metrics/cohorts?weeks=12
GET /internal/v1/metrics/health?days=7
GET /internal/v1/metrics/search-filters?window=90
```

Переменные окружения: `ANALYTICS_METRICS_TOKEN` (пустой = эндпоинты закрыты полностью),
`ANALYTICS_ALLOWED_IPS` (адреса и подсети; `*` снимает ограничение).

`/health` считается по ЖИВЫМ таблицам, а не по витринам: витрина отстаёт на час, а
недоставленное юрзначимое уведомление нельзя увидеть с часовой задержкой.

## Форма ответа — контракт

Ответы совпадают по форме с SQL-мостом `analytics/` в корне репозитория (§9.3). Это не
вопрос вкуса: перевод клиента на API меняет только `analytics/client.py`, а расхождение
двух источников ловится одной командой:

```bash
python -m analytics.pull --compare
```

Если она показала расхождение — витрина разошлась с базой, и снимку верить нельзя.

## ВВОД первый: шаги конструктора (§8.1)

```
POST /v1/analytics/constructor-step   {"step_code": "stages", "action": "left"}
```

Ровно один узкий слой поведенческих событий во всём продукте. Заведён потому, что брошенный
черновик иначе неизмерим: доменного события «бросил на шаге 3» не существует и не должно
существовать. Условия, на которых слой живёт, — часть решения: только экран конструктора,
без персональных данных (ни пользователя, ни IP, ни значений полей формы), хранение 90 дней
(`analytics-purge-constructor-events`).

Приёмник требует логина: анонимная запись без лимита позволила бы залить витрину выдуманными
шагами, а мастер и так живёт за логином. Личность в событие НЕ попадает — она нужна только
на входе, чтобы отсечь чужих.

Отправка из веба — ветка `feat/web-analytics-steps`: один хук в обёртке мастера
(`ContractNewPage`), у каждого входа есть парный уход, уход из мастера целиком закрывает
последний шаг. Пока эта ветка не влита, поле `abandoned_step` в мониторе честно пусто.

## ВВОД второй: воронка установки приложения (ADR-171)

```
POST /v1/analytics/install-event   {"kind": "pwa_installed", "platform": "android"}
```

Виды: `install_prompt_shown`, `install_click`, `pwa_installed`, `play_click`,
`standalone_open`. Кроме вида — грубая корзина платформы (android/ios/desktop/other; сама
строка User-Agent НЕ хранится), режим показа и источник. `user_id` берётся ИЗ ТОКЕНА, не из
тела, и пуст у гостя.

Приёмник, в отличие от конструктора, открыт АНОНИМНО: приложение ставят с посадочной
страницы, до входа — требование логина отсекло бы ровно тот случай, ради которого счётчик
заведён. Взамен работает лимит по адресу (`ANALYTICS_INSTALL_RATE_LIMIT`, по умолчанию 60 в
час; в ключе кеша — хеш адреса, сам адрес нигде не хранится). Хранение 90 дней
(`analytics-purge-install-events`).

Куда попадает: дневные счётчики в `MartDailyPulse`
(`install_prompt_shown`/`install_clicks`/`pwa_installs`/`play_clicks`/`standalone_opens`),
блок `installs` в `/internal/v1/metrics/acquisition`, строка 14 монитора.

## Активные пользователи: DAU и WAU (ADR-171 §7)

`MartDailyPulse.active_users_day` и `active_users_7d`.

**Активный пользователь дня — человек, совершивший в этот день хотя бы одно действие в живой
сделке.** Вход в аккаунт активностью НЕ считается (§5.4): источник — `outbox_event`
(`actor->>'user_id'`, топики `account.*` исключены) плюс события установки с непустым
`user_id`. Определение дословно совпадает с `mart_user_cohorts.sql` — две метрики активности
с разными определениями были бы двумя правдами.

WAU — скользящее окно 7 дней ВКЛЮЧАЯ текущий, уникальные люди, а НЕ сумма семи DAU. Обе
величины неаддитивны по разрезам, поэтому живут в `MartDailyPulse`, а не в срезе.

Бэкфилл прошлых дней получается сам: `outbox_event` — полная история, пересчёт идёт за окно
`ANALYTICS_PULSE_WINDOW_DAYS`. У установок истории нет — она начинается с выката.

## ВВОД третий: каталожный поиск с фильтром (ADR-186)

В отличие от двух предыдущих, этот ввод НЕ приходит POST-ом от браузера — фронта в этой
задаче нет (часть 6 плана 11.09 её не трогает). Факт распознаёт сам бэкенд: `apps.dashboards`
в момент вычисления ветки `catalog` у `GET /v1/dashboard/search` (ADR-184) обычным вызовом
фасада — `apps.dashboards.services.record_catalog_search_metric` → `services.record_catalog_search`
здесь. Это НЕ нарушение правила «аналитика — читатель, а не участник» (ADR-145, раздел 1
выше): то правило запрещает `apps.analytics` импортировать чужое, а не чужим приложениям
писать в неё через её собственный интерфейс — ровно так, как приложения вообще общаются друг
с другом (CLAUDE.md: через `services.py`-фасады).

Что считается «поиском с фильтром»: любой вызов `GET /dashboard/search`, для которого
вычисляется ветка `catalog` (ADR-184 — запрошены гео/сфера/опыт либо явный `catalog=1`),
ПЕРВОЙ страницей (без `cursor`) — перелистывание уже найденного новой записью не считается.
«С фильтром» — если хотя бы один из трёх видов фильтра применён на деле: гео (глубочайший из
запрошенных уровней страна/регион/город — тот же принцип «глубина побеждает», что и в самом
фильтре), сфера, опыт (в т.ч. `experience_min=0` — валидный порог, а не «фильтра не было»,
ADR-184). Запись — `CatalogSearchEvent`: `geo_level` (`none`/`country`/`region`/`city`),
`has_sphere`, `has_experience`. Ни кодов стран/регионов/городов, ни кодов сфер, ни `user_id`
в записи нет — только коды уровня и булевы флаги.

Дедупликация — короткое окно (`ANALYTICS_CATALOG_SEARCH_DEDUP_SECONDS`, по умолчанию 5с) по
хешу (пользователь + сочетание фильтра) в кеше: защита от случайного двойного вызова (двойной
клик, повторный рендер формы), а не от целенаправленной накрутки — ручка и так за
`IsAuthenticated`. Хранение 90 дней (`analytics-purge-catalog-search-events`).

Куда попадает: `MartDailyPulse.catalog_searches_total`/`catalog_searches_filtered` (день) и
`GET /internal/v1/metrics/search-filters` (полный разрез по видам фильтра и их сочетаниям —
неаддитивно по дням, читается напрямую из `analytics_catalog_search_event`, тот же приём, что
`by_platform`/`by_source` у установок). В снимок `analytics/` (корень репозитория, §9.3) эта
метрика сегодня НЕ добавлена — только через API; добавить SQL-мост, если понадобится сверка
`pull --compare`.

## Чего сегодня измерить нельзя

Эти поля отдаются как `null` с `available: false` и причиной. Ноль читался бы как измеренный
факт, то есть как неправда.

* K-фактор, время жизни приглашения, обратная виральность — сущности приглашения в домене
  нет (`create_draft` требует существующий профиль, телефонная книга не хранит хеши вне
  платформы); контур спроектирован и ждёт решения владельца
  (`docs/tasks/invites-design-proposal-2026-08-28.md`, вариант C). Вместо них измеряется
  воронка согласования ПО СТАТУСАМ договора и `acquisition.arrival` — «пришёл в конкретную
  сделку» как факт двух меток времени;
* разрыв «страна по IP vs выбранная страна» — код страны по IP при регистрации не хранится;
* шаг отвала черновика — нет данных, пока фронт не шлёт события конструктора;
* уникальные УСТРОЙСТВА и установки-на-устройство — нужен отпечаток устройства, которого мы
  не снимаем (ADR-171 §5); `pwa_installs` — это события установки, а не устройства;
* установки из Google Play — их видит только Play Console, обратного вызова на сайт у
  магазина нет (`installs.play_installs.available = false`). С нашей стороны считается
  `play_click` — намерение; как сверять — `docs/ops/play-console.md` §9;
* доступность API — считается по Prometheus, не по БД.

## Тесты

* `apps/analytics/tests/` — только свои модели: доступ, селекторы, пересчёт, слой
  конструктора, воронка установки (`test_install_api.py`), слой каталожного поиска
  (`test_catalog_search_metric.py`).
* `apps/dashboards/tests/test_search_metrics.py` — что именно распознаёт `GET /dashboard/search`
  как «поиск» и «поиск с фильтром» (ADR-186): живёт в `apps.dashboards`, а не здесь, потому что
  само распознавание — код `apps.dashboards`, а не `apps.analytics`.
* `backend/tests/test_analytics_marts.py` — сквозная проверка от реального договора до цифры
  в эндпоинте. Лежит вне `apps/` намеренно: приложение (и его тесты) не импортируют `apps.*`.

# apps.reputation

Read-модель минимальной репутационной карточки (ГВ.4, `docs/tasks/global-wave.md`).
Строится ИСКЛЮЧИТЕЛЬНО из событий outbox — `milestone.accepted`,
`milestone.auto_accepted`, `milestone.rejected`, `dispute.opened`,
`dispute.resolved`, `contract.completed` (payload каждого события
самодостаточен, см. докстринги `apps.milestones.services._event_payload`,
`apps.disputes.services._self_sufficient_payload`,
`apps.contracts.services.complete_execution`). Подписчик идемпотентен по
`event_id` (`ProcessedEvent`, тот же приём, что `services.audit_vault`).

Никаких оценок/звёзд/баллов — только факты («зеркало, а не гарант», док 31
§3): возраст профиля, число сделок, число контрагентов, список завершённых
сделок (тип/сфера/период/исход/контрагент). Удаление отдельной сделки с
карточки — намеренно без API (обнуление только целиком, crypto-shredding,
вне этой задачи).

Портфолио «факт vs заявление» (ADR-045) — на `contract.completed`
создаётся `apps.profiles.PortfolioProject(source=FROM_CONTRACT)` через
`apps.profiles.services.record_from_contract_project` (facade, без прямого
импорта модели чужого приложения бизнес-логикой). Запись создаётся
НЕопубликованной — `publish_project` уже гейтит `FROM_CONTRACT` согласием
контрагента (`counterparty_consent`), и на этом шаге у записи ещё и нет
медиа (реальный evidence-пайплайн — ГВ.3, вне ГВ.4).

Решения, зафиксированные в `docs/adr/ADR-076-reputation-card-read-model.md`:
сфера сделки добавлена в event-payload как additive-поле (`milestone_sphere_code`,
изменение `apps.milestones`/`apps.disputes`, не отдельная ветка — то же
исключение, что уже делали ГВ.1/ГВ.2/ГВ.5, трогая несколько приложений
из одной ветки волны); интерпретация «гостю — стартовая карточка»
(ADR-059): `public` — полная карточка всем, `link_and_deals` — полная
карточка владельцу и подтверждённым контрагентам сделок, остальным
(включая анонимных гостей) — стартовая карточка без списка/счётчиков сделок.

## Дашборд репутации (ADR-163, макет владельца 05.09)

Две системы оценки ПО РОЛИ — слова «в срок» без уточнения в продукте нет:
у исполнителя «сделано в срок» (этап сдан до дедлайна этапа), у заказчика
«оплачено в срок» (платёж по этапу подтверждён плательщиком до срока
оплаты) и «принято без затягивания» (приёмка завершена в окне, НЕ
автоприёмкой по тайм-ауту). Автоприёмка — принятый этап для исполнителя и
«затянуто» для заказчика: один факт, две стороны. Каждая ось складывается
только в блок ТОЙ стороны, чей это срок (`selectors._accumulate_role`).

Доля всегда парой «сделано / всего»; ни процента, ни цветовой зоны сервер
не отдаёт — это арифметика представления (`packages/ui` `zoneOf`), а не
оценка платформы. `total = 0` значит «нечего мерить», не «плохо».

`MilestoneFact` — вторая read-модель, строка на ЭТАП: `DealFact` хранит уже
сложенные счётчики и не может ответить, КАКОЙ этап сдан с опозданием и
почему вернули. Счётчики `DealFact` ПРИСВАИВАЮТСЯ из неё
(`subscriber.recompute_deal_counters`), поэтому редоставка события и
повторный бэкфилл ничего не удваивают.

Объём по валютам (`total_amount`/`total_currency`) и уровень защиты
платежа (`payment_protected`) СЧИТАЮТСЯ, но в публичную карточку не
попадают ни при какой видимости — только `GET /reputation/profiles/{id}/
insights`, приватно владельцу (403 остальным, включая контрагента).
Обжалования репутации нет: каждая цифра — арифметика над фактами, у
которых уже есть свой процессуальный путь.

Прод после раскатки: `migrate` + однократный `reputation_backfill`
(сначала `--dry-run`) — старые события новых полей не несут, пересобрать
их из outbox нельзя. Команда — единственное место в приложении, где чтение
соседних приложений через их selectors-фасады допускается: это разовая
миграция данных, а не рабочий путь чтения.

# apps.contracts

Contract, ContractParty, RevisionProposal, FSM согласования, compute_segment, ContractVersion, Amendment. Не импортирует payments/disputes (import-linter).

Реализация — по docs/tasks/etap-4.md, шесть под-задач = шесть веток:

- **Э4.1 feat/contracts-core (реализовано)** — `Contract`/`ContractParty`, черновик через клиентское дерево каталога v2 (`client_option` → `contract_type_code`, для «Услуги» — автовывод по статусу исполнителя через `apps.catalog.services`), сегментация при создании и PATCH (пересчёт при смене типа/сторон), резолв контрагента по `profile_id`/`@handle`, `source_contract_id` («как в прошлый раз»), `form_data` jsonb под будущую дельту П-16. Никакого fee-кода. `customer_contact`/`contractor_contact` (Representative), `frozen_version` (ContractVersion), `sphere_id` (Sphere в apps.catalog не заведена) — не добавлены, ждут своих веток.
- **Э4.2 feat/contracts-negotiation (реализовано)** — `NEGOTIATION_FSM` (common/fsm.py): `send` (draft→under_review), `revise` (гейт протокола разногласий, под ним — propose/accept/reject/counter/accept-all/apply preapproved), `withdraw`/`reject` (терминалы, только инициатор/только контрагент соответственно — `Contract.created_by`). `RevisionProposal` (open/accepted/rejected/superseded), `PreapprovedAlternative` (apply одним кликом без итерации — сразу `accepted`). `accept-all` при финансово значимых открытых правках (эвристика: `item_ref`/значение похожи на Money) требует `confirm_summary=true`, иначе `422 confirm_summary_required` со списком «было→стало». `GET /timeline` — read-модель прямо из `OutboxEvent` (топики `negotiation.sent|revised|withdrawn|rejected`), без отдельной read-таблицы.
- Э4.3 feat/milestones — дерево этапов, чек-листы, материалы.
- **Э4.4 feat/contracts-signing (реализовано, ADR-073)** — `NEGOTIATION_FSM` дополнена (общий объект с Э4.2, задел под Amendment Э4.5): `freeze` (under_review→pending_signature: нет открытых ревизий, пересчёт `segment`, дерево этапов не пусто, реквизиты для `payment_method` через платформу — `Contract.PROTECTED_PAYMENT_METHODS`), `route_signatory` (выбор подписанта по стороне — person-сторона: только собственный `user`, лимитов нет; business — сеам под `SigningAuthority`, этап 3.5 ещё не смёржен), `sign`/`complete_signing` (вторая подпись — одна транзакция: `signed` + `execution_status=pending_start` + `contract.signed`, без комиссии — финмодель v2), `forward_signature_request`/`expire_signature_request` (→pending_signature), `decline_for_revision` (→under_review, аннулирует активные `SignatureRequest`/`Signature` текущего раунда — `ContractVersion` не удаляется, append-only история). `ContractVersion.integrity_hash` — canonical-сериализация (`common/canonical.py`) + `TimestampProvider` (`common/timestamps.py`, Р1 — серверная метка). Подпись адресуется `version_hash`/`version_id` в теле запроса, не FK — устаревшее значение → `409 version_stale`. Idempotency-Key (`common/api/idempotency.py`, greenfield) на `freeze`/`signature-requests`/`sign`.
- **Э4.5 feat/contracts-amendments (реализовано, ADR-075)** — `Amendment`/`AmendmentChange` (add/modify/remove для этапов и материалов, `custom_terms`) к уже ПОДПИСАННОМУ договору. Тот же `NEGOTIATION_FSM`, что Э4.2/Э4.4(`send`/`freeze`/`route_signatory`/`sign`/`forward`/`decline_for_revision`/`expire` — те же переходы, тот же объект `StateMachine`, на поле `Amendment.negotiation_status`). `SignatureRequest`/`Signature` получили nullable `amendment` (рядом с `contract`, не вместо) + partial-индексы на уникальность подписи по стороне (raw `UniqueConstraint` с NULL не ловит дубли). `/signature-requests/{id}/{sign,forward,decline}` — те же URL/вьюхи для договора и допника (развилка по `amendment_id`, не новые эндпоинты). `amount_delta`/`days_delta` — считаются сервером (`_create_amendment_change`/`compute_amendment_deltas`), не принимаются от клиента. Гейты «нельзя удешевить/убрать принятое» (`accepted_at`) и «нельзя убрать полученный материал» (`received`) — на создании допника, 422. Применение к дереву (`apply_amendment`, `Milestone.created_by_amendment`) — в ТОЙ ЖЕ транзакции, что вторая подпись. `effective_terms(contract)` — плоская склейка снимка + список подписанных допников + живая сумма, не структурный дифф.
- Э4.6 feat/contracts-execution — исполнение, гейты, сдача, приёмка.
- **ADR-138 feat/contracts-idle-autoclose (реализовано)** — автозакрытие сделки без движения (ADR-137 треб. 8). `Contract.last_activity_at` (миграция 0009 с бэкфиллом) двигает подписчик «*» `handlers.handle_contract_activity`: событие семейств договорного контура с `actor.user_id` (системные события без актора движением не считаются), договор — из `subject`/`payload.contract_id`. `record_contract_activity` монотонна/идемпотентна; в `in_progress` заводит/переносит ОДНУ строку `DomainDeadline(kind=contract_idle)` (90 сут., `deadlines_services.reschedule_deadline`) и перепланирует серию предупреждений обеим сторонам (`ReminderPointConfig(contract_idle)` → `contract.idle_warning` за 14 сут., `days_left` в payload). Срабатывание → `auto_close_idle_contract`: не `in_progress` / движение после отсчёта (гонка) → NOOP; этапы `under_acceptance`/`accepted` → отсрочка `contract_idle_retry` (14 сут.) + `contract.idle_blocked`; иначе переход `auto_close_idle` (`in_progress → closed`, минуя `completed`/`warranty`) + `contract.auto_closed` (`reason=idle`, `idle_days`). `contract.closed`/`completed` при этом НЕ публикуются — потребители «договор окончен» (Э6) слушают `contract.auto_closed` отдельно. `complete_execution`/`terminate_by_*` закрывают дедлайн idle досрочно (`close_deadline`, без события). Сериализатор: `last_activity_at`, `idle_deadline_at`.
- **ADR-161 feat/decisions-0905-amendments (реализовано)** — вкладка «Допсоглашения» и жизнь ЧЕРНОВИКА допника до отправки. `PATCH /amendments/{id}` (`update_draft_amendment`) и `DELETE /amendments/{id}` → 204 (`delete_draft_amendment`) — только при `negotiation_status=draft` и только инициатором (`Amendment.created_by`): не инициатор → 403 `not_initiator`, уже отправленный → 409 `amendment_not_draft`. PATCH заменяет `changes` ЦЕЛИКОМ через тот же `_create_amendment_change` (те же гейты 422, те же серверные `amount_delta`/`days_delta`) — второго кодового пути нет; всё в одной транзакции, неудачное изменение не рушит прежний список. Idempotency-Key не нужен (не денежная и не подписная операция). Удаление черновика не нарушает «мягкого удаления юрзначимых нет»: черновик не заморожен, не подписан и второй стороне не показан. Видимость: `list_amendments(contract, viewer=user)` и `is_amendment_visible_to` прячут ЧУЖИЕ черновики (в списке — нет строки, по прямому id — 404 `not_found`, не 403); `apps.archive` зовёт `list_amendments` без `viewer` — там снимок всего. Событий на правку/удаление черновика не публикуется (заготовка — не юрзначимый факт), миграции не требуется.
